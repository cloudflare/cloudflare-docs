# Cloudflare Pages to Workers Migration Guide

## Goal

Migrate a Cloudflare Pages project to Cloudflare Workers with Static Assets.

## Core Migration Concepts

### Understanding the Migration

When migrating from Pages to Workers, you are:

1. Moving from Pages deployment commands (`wrangler pages deploy` / `wrangler pages dev`) to Workers commands (`wrangler deploy` / `wrangler dev`)
2. Converting Pages configuration (`pages_build_output_dir`) to Workers Static Assets configuration (`assets.directory`)
3. Explicitly configuring routing behavior (`not_found_handling`, `run_worker_first`) that Pages previously inferred
4. Updating any Pages-specific framework adapters, `_worker.js`, or `functions/` directory to target Workers
5. Preserving existing bindings, environment variables, secrets, `_headers`, and `_redirects`

### Key Principles

- **Deployment**: Use `wrangler deploy` (never `wrangler pages deploy`)
- **Configuration**: Prefer `wrangler.jsonc` with `"$schema": "./node_modules/wrangler/config-schema.json"`
- **Assets**: Use Workers Static Assets (`"assets": { "directory": "<output-dir>" }`), not the deprecated Workers Sites (`site`)
- **Package Manager**: Use the project's existing package manager (check for `bun.lock`, `bun.lockb`, `pnpm-lock.yaml`, `yarn.lock`, or `package-lock.json`)
- **Verify Official Docs**: Check https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/ for the latest details

## Migration Steps

### 1. Inspect the Project and Prerequisites

- Update Wrangler to the latest v4 release using the project's package manager (for example, `npm install --save-dev wrangler@latest`).
- Check the existing project for:
  - A framework and any Pages-specific adapter (for example, `@cloudflare/next-on-pages`, `@astrojs/cloudflare`, `@sveltejs/adapter-cloudflare`, `@remix-run/cloudflare-pages`, Nitro preset)
  - Existing `wrangler.toml`, `wrangler.json`, or `wrangler.jsonc`
  - A `functions/` directory or `_worker.js` file
  - `_routes.json`, `_headers`, `_redirects`, and `404.html` files in the public/output directory
  - Any runtime bindings (KV, D1, R2, Durable Objects, Queues, AI, Service bindings), environment variables, or secrets configured in Wrangler config or the Cloudflare dashboard

### 2. Switch Framework Adapters (if using a framework)

- If the project uses a supported framework (Next.js, Astro, SvelteKit, Nuxt, React Router, SolidStart, TanStack Start, Angular, Analog, Vite, Vike, Waku), update the framework adapter to target Cloudflare Workers rather than Pages:
  - For Next.js, migrate off `@cloudflare/next-on-pages` to vinext or OpenNext (https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/).
  - For Vite-based apps, consider `@cloudflare/vite-plugin` or run `wrangler setup --dry-run` to inspect automatic configuration (https://developers.cloudflare.com/workers/framework-guides/automatic-configuration/).
  - Remove Pages-only packages once replaced.

### 3. Update Wrangler Configuration

- Convert to `wrangler.jsonc` (or update the existing Wrangler config).
- Replace `pages_build_output_dir` with `"assets": { "directory": "<output-dir>" }`.
- Keep the existing `compatibility_date` if migrating Pages Functions; otherwise set it to today's date (`YYYY-MM-DD`).
- Keep any existing `compatibility_flags` (such as `nodejs_compat`) and placement settings.
- Configure explicit routing behavior under `assets`:
  - **Single-page application (SPA)** (Pages previously served `index.html` when no `404.html` existed): add `"not_found_handling": "single-page-application"`.
  - **Static site with custom `404.html`**: add `"not_found_handling": "404-page"`.
- Only add `"binding": "ASSETS"` when the project has a `"main"` Worker entrypoint; omit `"binding"` for assets-only projects.

### 4. Handle `_worker.js`, `functions/`, and `_routes.json`

- **If a `functions/` directory exists (and no framework replaces it):**
  - Compile the `functions/` directory into a Worker bundle during the build step:
    `wrangler pages functions build --outdir=./dist/worker/`
  - Point `"main"` at the compiled output (for example, `"main": "./dist/worker/index.js"`) and add `"binding": "ASSETS"` under `"assets"`.
  - Consider refactoring simple `functions/` routes into a standard Worker script or Hono app over time.
- **If `_worker.js` is emitted inside the static assets directory:**
  - Either move `_worker.js` outside the static assets directory (recommended) or add `_worker.js` to an `.assetsignore` file in the static assets directory so it is not served publicly.
  - Set `"main"` to the `_worker.js` path and add `"binding": "ASSETS"` under `"assets"`.
- **If `_routes.json` or `functions/_middleware.*` exists:**
  - Unlike Pages (which runs Functions before static assets by default), Workers serves matching static assets first unless `assets.run_worker_first` is configured.
  - Translate `_routes.json` rules into `assets.run_worker_first` (either `true` or an array of patterns such as `["/api/*", "!/api/docs/*"]`) so middleware, auth checks, or dynamic routes run before static assets.

### 5. Preserve Static Asset Behavior (`_headers`, `_redirects`, `.assetsignore`)

- Keep `_headers` and `_redirects` in the `assets.directory` output folder; Workers Static Assets supports both natively.
- Pages automatically ignored files such as `node_modules`, `.DS_Store`, and `.git`. If your asset directory can contain ignored files, add an `.assetsignore` file inside `assets.directory`:

```txt
**/node_modules
**/.DS_Store
**/.git
```

### 6. Preserve Bindings, Environment Variables, and Secrets

- Carry over all bindings (`kv_namespaces`, `d1_databases`, `r2_buckets`, `durable_objects`, `services`, `ai`, `queues`, etc.) and `vars` from the existing Pages Wrangler configuration.
- Ask the user if any bindings, variables, or secrets were configured only in the Cloudflare dashboard for the Pages project, and note that Workers Builds separates build-time variables from runtime variables/secrets.
- Do not commit secret values to `wrangler.jsonc`; configure production secrets with `wrangler secret put` or the Cloudflare dashboard, and local secrets in `.dev.vars`.

### 7. Update `package.json` Scripts and CI/CD

- Replace Pages Wrangler scripts with Workers equivalents:
  - `wrangler pages deploy <dir>` -> `wrangler deploy`
  - `wrangler pages dev <dir>` -> `wrangler dev` (note: default port changes from `8788` to `8787`)
- Keep framework-specific dev/build commands (`astro dev`, `vite build`, etc.) unless the framework's Workers guide specifies otherwise.
- If the project used Pages Git integration, note that the user should connect the repository to Workers Builds (and disable automatic deployments on the Pages project once migrated).

### 8. Validate and Deploy

1. Run the project's build command and confirm the output directory and any Worker entrypoint exist.
2. Run `wrangler deploy --dry-run` to validate the configuration and inspect uploaded bindings/assets.
3. Test locally with `wrangler dev` (or the framework's dev command with `@cloudflare/vite-plugin`).
4. Deploy only with user permission using `wrangler deploy`.

## Common Patterns

### Assets-Only Static Site

```jsonc
{
	"$schema": "./node_modules/wrangler/config-schema.json",
	"name": "my-site",
	"compatibility_date": "<YYYY-MM-DD>",
	"assets": {
		"directory": "./dist",
		"not_found_handling": "404-page",
	},
}
```

### Single-Page Application (SPA) with API Worker

```jsonc
{
	"$schema": "./node_modules/wrangler/config-schema.json",
	"name": "my-app",
	"main": "./src/index.ts",
	"upload_source_maps": true,
	"compatibility_date": "<YYYY-MM-DD>",
	"assets": {
		"directory": "./dist",
		"binding": "ASSETS",
		"not_found_handling": "single-page-application",
		"run_worker_first": ["/api/*"],
	},
}
```

## Migration Summary Format

When complete, summarize:

1. **Project Analysis**: Framework/static setup, Functions or `_worker.js`, routing rules, and bindings found
2. **Migration Steps**: Files added or changed and why
3. **Manual Follow-Ups**: Dashboard secrets/bindings, Workers Builds connection, custom domains, or Pages project cleanup
4. **Validation**: Build, dry-run, and local dev checks performed
