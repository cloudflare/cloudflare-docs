## Restore Super Administrator after group misconfiguration

If you have removed all Super Administrators mistakenly, you can restore access by reapplying a policy with the **Super Administrator - All Privileges** permission group using the Account API token you created for SCIM provisioning.

First, fetch a list of account members and find the member ID for the user you want to restore Super Administrator access to via [list members](/api/resources/accounts/subresources/members/methods/list/).

```curl
curl -X GET "https://api.cloudflare.com/client/v4/accounts/{account_id}/members" \
  -H "Authorization: Bearer YOUR_SCIM_AOT" \
  -H "Content-Type: application/json"
```

Next, fetch the permission group ID for **Super Administrator - All Privileges** from the [Permission Groups API](/api/resources/iam/subresources/permission_groups/).

```curl
curl -X GET "https://api.cloudflare.com/client/v4/accounts/{account_id}/iam/permission_groups" \
  -H "Authorization: Bearer YOUR_SCIM_AOT" \
  -H "Content-Type: application/json"
```

Then restore that member's access via [update member](/api/resources/accounts/subresources/members/methods/update/).

:::note
This request replaces the member's existing policies. If the member should keep any existing policies, include them in the `policies` array.
:::

```curl
curl -X PUT "https://api.cloudflare.com/client/v4/accounts/{account_id}/members/{member_id}" \
  -H "Authorization: Bearer YOUR_SCIM_AOT" \
  -H "Content-Type: application/json" \
  -d '{
    "policies": [
      {
        "access": "allow",
        "permission_groups": [
          {
            "id": "<SUPER_ADMIN_PERMISSION_GROUP_ID>"
          }
        ],
        "resource_groups": [
          {
            "scope": {
              "key": "com.cloudflare.api.account.{account_id}",
              "objects": [
                {
                  "key": "*"
                }
              ]
            }
          }
        ]
      }
    ]
  }'
```

## Update email domains after onboarding

We currently **do not** support updating email domains for users. This means that any SCIM `PATCH`/`PUT` operations that change email domains will be rejected. We recommend not using the email as the matching attribute if email domains are expected to change, and restarting provisioning manually.
