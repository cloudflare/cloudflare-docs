Turnstile Spin is a one-shot setup flow for Cloudflare Turnstile. It creates the widget, deploys a managed siteverify Worker into your Cloudflare account, and validates the integration before you ship. Spin runs two ways:

- **From the Cloudflare dashboard.** Enter your domains, select **Set up**, and Spin creates the widget and Worker server-side. You receive the sitekey, the deployed Worker URL, and a prompt for your AI coding agent to wire the frontend code.
- **From your AI coding agent.** Paste a single prompt into Claude Code, Cursor, Codex, OpenCode, or GitHub Copilot Chat. The agent runs `wrangler` locally and walks you through a nine-step setup.

Both paths produce the same widget and the same Worker. The only difference is where the API calls run.

## Set up from the dashboard

<Steps>

1. Go to the Turnstile dashboard.

	<DashButton url="/?to=/:account/turnstile" />

2. Select **Set up with Spin** in the page header.

3. Enter the domains your Turnstile widget should accept tokens from. The first chip is pre-filled from your account's first active Cloudflare zone. Add more domains, or remove the pre-filled one and type any domain (Turnstile does not require a Cloudflare-managed zone).

4. Select **Set up**. Spin shows a five-step progress indicator while it creates the widget, deploys the managed Worker, binds the secret, and probes the deployed Worker.

5. When setup completes, copy:

	- The **sitekey** (use as `data-sitekey` on your Turnstile widget HTML).
	- The **Worker URL** (your backend posts tokens here for siteverify).
	- The **agent prompt** (paste into your AI coding agent to write the frontend code that mounts the widget and submits the token).

</Steps>

If Spin fails before it finishes, it rolls back any half-created widget or Worker before the dialog returns the error. Select **Try again** to retry from the same dialog. To undo a successful setup, select **Undo** on the result card; Spin deletes the widget and the Worker.

## Set up from the command line

If you do not see the **Set up with Spin** button in your dashboard, or you prefer to drive setup from your editor, paste this prompt into your AI coding agent:

<Steps>

1. **Open your AI coding agent** in your project (Claude Code, Cursor, Codex, OpenCode, GitHub Copilot Chat).

2. **Paste this prompt into your agent:**

	```txt title="Spin prompt"
	Set up Cloudflare Turnstile in this project end to end. Plan insertion points, create the widget, deploy the managed backend Worker, write the frontend code, and validate the integration.

	The full Turnstile Spin skill is at https://developers.cloudflare.com/turnstile/spin/prompt.md. Fetch it now if you do not already have it loaded.

	Domains: <DOMAINS>
	Insertion preference: <every form | only specific form>
	```

	Replace `<DOMAINS>` with your site domains (comma-separated, no spaces; include `localhost,127.0.0.1` for local development). Replace `<insertion preference>` with what you want protected.

3. **Confirm as the agent goes.** The agent checks authentication, proposes widget and Worker names, and asks you to confirm before any irreversible step.

4. **Validate.** When the agent finishes, it runs an automated end-to-end test against your deployed Worker. If that passes, your integration is live.

</Steps>

If you would rather install the skill locally first so the agent has it on disk:

```sh title="One-line install per agent"
# Claude Code
mkdir -p .claude/skills/turnstile-spin && \
  curl -sSL https://developers.cloudflare.com/turnstile/spin/prompt.md \
  -o .claude/skills/turnstile-spin/SKILL.md

# Cursor
mkdir -p .cursor/rules && \
  curl -sSL https://developers.cloudflare.com/turnstile/spin/prompt.md \
  -o .cursor/rules/turnstile-spin.md

# OpenCode
mkdir -p .opencode/skills/turnstile-spin && \
  curl -sSL https://developers.cloudflare.com/turnstile/spin/prompt.md \
  -o .opencode/skills/turnstile-spin/SKILL.md
```

Then prompt your agent: `Use the turnstile-spin skill to add Turnstile to this project.`

### What the agent does

The agent does not run silently. It detects what it can, asks only when it has to, and confirms before every irreversible step. The flow is a nine-step wizard with three confirmation points.

| Step | What happens                                                          | Confirms with you?               |
| ---- | --------------------------------------------------------------------- | -------------------------------- |
| 1    | Acknowledge (agent restates what it is about to do)                   | Yes                              |
| 2    | Wrangler check (installs locally if missing)                          | Yes, if missing                  |
| 3    | Authentication (`wrangler whoami` or API token)                       | If a token is needed             |
| 4    | Account selection (if you have more than one)                         | If more than one                 |
| 5    | Codebase scan (proposes insertion points and domains)                 | Yes                              |
| 6    | Widget creation (calls the Cloudflare API to create the widget)       | No (after step 5 confirms scope) |
| 7    | Worker deploy (uploads the managed Worker template, binds the secret) | No                               |
| 8    | Frontend snippets (edits the files identified in step 5)              | No                               |
| 9    | Validate (health check, dummy siteverify, hostname binding)           | No                               |

If anything fails, the agent reports which step and what it tried. Most failures are recoverable by adjusting one input (token scope, domain list, insertion file) and asking the agent to resume.

## Wire up the frontend

Whichever setup path you use, Spin gives you a sitekey and a deployed Worker URL but does not write your frontend code. The dashboard hands you a prompt for your AI coding agent. The command-line setup edits files directly via the agent.

If you set up from the dashboard and want to wire the frontend by hand, the minimal pattern is:

```html title="Turnstile widget on your form"
<script
	src="https://challenges.cloudflare.com/turnstile/v0/api.js"
	async
	defer
></script>
<form>
	<div
		class="cf-turnstile"
		data-sitekey="YOUR_SITEKEY"
		data-action="turnstile-spin-v2"
	></div>
	<!-- your form fields -->
	<button type="submit">Submit</button>
</form>
```

On submit, post the token to your deployed Worker:

```js title="Gate the submit handler on success"
const form = document.querySelector("form");
form.addEventListener("submit", async (e) => {
	e.preventDefault();
	const token = form.querySelector("[name=cf-turnstile-response]").value;
	const r = await fetch("https://YOUR_WORKER.workers.dev/", {
		method: "POST",
		headers: { "Content-Type": "application/json" },
		body: JSON.stringify({ token }),
	});
	const result = await r.json();
	if (result.success) {
		// existing handler logic runs here, unchanged
	}
});
```

The `data-action="turnstile-spin-v2"` attribute is the telemetry marker for dashboard-deployed widgets. Refer to [Telemetry marker](#telemetry-marker) for the marker convention.

## Recover an existing widget

If you already have a Turnstile widget without a deployed siteverify Worker, recover it from the dashboard. A banner appears above the widgets table when a widget has no matching Worker; select **Fix with Spin** to deploy the managed siteverify Worker against the existing widget and validate end-to-end. No terminal, no `wrangler`.

If you do not see the **Fix with Spin** banner in your dashboard, drive the same recovery from your AI coding agent instead. Paste this prompt:

```txt title="Recovery prompt"
I already have a Turnstile widget. The site key is <SITEKEY>. Use the turnstile-spin skill to recover from step 5 onward: deploy the managed siteverify Worker into my account, write the frontend snippets, and validate.
```

The sitekey does not change. Your existing widget keeps working throughout. The dashboard's `Deployment` column flips from `Manual` to `Spin` once the first request carrying `data-action="turnstile-spin-v1"` or `data-action="turnstile-spin-v2"` lands.

## Migrate from reCAPTCHA or hCaptcha

Use the command-line setup for migrations. The agent detects reCAPTCHA or hCaptcha in your codebase and proposes a substitution. The substitution rules are:

- Replace script tags with `https://challenges.cloudflare.com/turnstile/v0/api.js` (`async defer`).
- Replace `class="g-recaptcha"` or `class="h-captcha"` divs with `class="cf-turnstile"`. Update `data-sitekey` to the new Turnstile site key.
- Remove any manually-added `<input type="hidden" name="g-recaptcha-response">` or `name="h-captcha-response"` elements. Turnstile renders its own hidden input named `cf-turnstile-response` automatically.
- Backend siteverify URL points at the Spin-deployed Worker. Drop `RECAPTCHA_SECRET` or `HCAPTCHA_SECRET` environment variables (the Worker holds the secret).
- The Spin Worker accepts `{ token }`, `{ "cf-turnstile-response": ... }`, or `{ response }` in JSON or form-encoded bodies. Response shape is identical: `success`, `error-codes`.

Two edge cases to flag to the agent. First, reCAPTCHA v3 score thresholds do not translate: Turnstile has no score, so migrated code rejects on `success === false` rather than a numeric threshold. Second, do not auto-migrate reCAPTCHA Enterprise; refer to [the Cloudflare migration guide for reCAPTCHA](/turnstile/migration/recaptcha/) instead.

## Frameworks

The agent ships with frontend snippets for vanilla HTML, Next.js (App Router and Pages Router), Astro, SvelteKit, and Hugo. For other frameworks, the agent falls back to a generic vanilla-HTML pattern and asks you to confirm placement.

For Cloudflare Pages projects, the agent can deploy the managed siteverify Worker, or recommend the [Pages Plugin for Turnstile](/pages/functions/plugins/turnstile/) if you prefer Functions to a separate Worker.

## Reference

### Managed Worker endpoints

The deployed Worker exposes three endpoints.

| Method | Path          | Purpose                                                 |
| ------ | ------------- | ------------------------------------------------------- |
| POST   | `/`           | Siteverify proxy. Accepts JSON or form-encoded body.    |
| POST   | `/siteverify` | Alias of `/`.                                           |
| GET    | `/health`     | Health check. Returns `{"ok": true, "version": "..."}`. |
| GET    | `/`           | Returns the same payload as `/health` for convenience.  |

Request body (JSON):

```json
{
	"token": "TURNSTILE_TOKEN_FROM_WIDGET",
	"remoteip": "1.2.3.4",
	"idempotency_key": "optional-uuid"
}
```

The Worker forwards the token to `https://challenges.cloudflare.com/turnstile/v0/siteverify` with the secret from `TURNSTILE_SECRET_KEY` and returns the upstream response augmented with `_worker` timing metadata.

### Worker configuration

| Variable               | Type   | Default    | Purpose                                                           |
| ---------------------- | ------ | ---------- | ----------------------------------------------------------------- |
| `TURNSTILE_SECRET_KEY` | secret | (required) | The widget's secret. Never on disk.                               |
| `ALLOWED_ORIGIN`       | var    | `*`        | CORS allowed origin. Lock to your customer-facing domain in prod. |
| `EXPECTED_HOSTNAME`    | var    | (unset)    | If set, reject siteverify responses with a mismatched hostname.   |

### Telemetry marker

Spin-deployed widgets emit an account-level marker so Cloudflare can measure activation rates and time-to-first-siteverify for Spin-deployed widgets compared to manual ones. The marker is account-level and aggregate. No PII, no per-user tracking. Refer to the [Turnstile privacy addendum](https://www.cloudflare.com/turnstile-privacy-policy/).

The marker takes one of two values, depending on which setup path created the widget:

| `data-action` value | Set by                                                |
| ------------------- | ----------------------------------------------------- |
| `turnstile-spin-v1` | Command-line setup (AI agent runs `wrangler` locally) |
| `turnstile-spin-v2` | Dashboard setup (**Set up with Spin** button)         |

Each setup path applies its own marker automatically. If you customize the widget snippet by hand, you do not need to add the marker yourself.
