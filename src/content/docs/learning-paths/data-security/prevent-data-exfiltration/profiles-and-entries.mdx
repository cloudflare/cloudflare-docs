DLP profiles and detection entries work together to identify sensitive data. Understanding the relationship between them is key to building effective DLP policies.

## DLP profiles

A DLP profile is a collection of detection entries that define what sensitive data to look for. Profiles are referenced in Gateway HTTP policies to enforce data protection rules.

### Predefined profiles

Cloudflare provides predefined profiles for common data types:

- **Financial Information**: Credit card numbers, bank account numbers, routing numbers
- **Personally Identifiable Information (PII)**: Social Security numbers, driver's license numbers, passport numbers
- **Credentials**: API keys, passwords, authentication tokens, private keys
- **Source Code**: Programming language patterns such as Python, JavaScript, and Java

## Detection entries

Detection entries are the individual rules within a profile that identify specific data patterns.

### Entry types

**Regular expression (regex):**

- Pattern-based matching for structured data
- Example: `\d{3}-\d{2}-\d{4}` for Social Security numbers

**Keyword:**

- Simple text matching
- Example: "CONFIDENTIAL", "INTERNAL ONLY"

**Exact Data Match (EDM):**

- Matches against specific datasets
- Example: List of employee email addresses or customer IDs

**Predefined detectors:**

- Built-in detectors for common data types
- Example: Credit card number detector with Luhn algorithm validation

### How detection entries work

When DLP scans content:

1. Each detection entry in the profile is evaluated
2. If a match is found, it counts toward the match threshold
3. When the threshold is reached, the profile triggers
4. The associated Gateway policy action is taken (Block, Allow, Isolate)

## Profiles vs. detection entries

| Aspect          | Profile                        | Detection Entry                           |
| --------------- | ------------------------------ | ----------------------------------------- |
| **Purpose**     | Groups related detection rules | Defines a specific data pattern to detect |
| **Usage**       | Referenced in Gateway policies | Added to profiles                         |
| **Scope**       | Can contain multiple entries   | Detects one type of data                  |
| **Reusability** | Used across multiple policies  | Can be used in multiple profiles          |

## Profile settings

Each profile has configurable settings that affect how detection works:

### Match count

The number of detection entry matches required to trigger the profile.

- **Low threshold (1-2)**: More sensitive, may have false positives
- **Medium threshold (3-5)**: Balanced approach (recommended)
- **High threshold (6+)**: Less sensitive, fewer false positives

**Example**: A profile with match count of 3 will only trigger if at least 3 detection entries match in the scanned content.

### Confidence level

The minimum confidence score (0-100) required for a match to count.

- **High confidence (80-100)**: Very likely to be real sensitive data
- **Medium confidence (50-79)**: Probably sensitive data
- **Low confidence (0-49)**: Possibly sensitive data

**Example**: Setting confidence level to 80 means only high-confidence matches will count toward the match threshold.

### Context analysis

AI-powered analysis that considers the context around detected data to reduce false positives.

Context analysis helps distinguish:

- Real credit card numbers vs. example numbers in documentation
- Actual SSNs vs. random number sequences that match the pattern
- Sensitive data vs. test data or placeholder values

**Example**: `"Example credit card: 4111-1111-1111-1111"` would not trigger with context analysis enabled, but `"Payment card: 4111-1111-1111-1111"` would.

## Best practices

### Start with predefined profiles

1. Use predefined profiles for common data types
2. Monitor detection rates and false positives
3. Adjust match counts and confidence levels as needed
4. Create custom profiles only when predefined profiles are insufficient

### Organize profiles by use case

Create separate profiles for different scenarios:

- **Compliance profiles**: PCI, HIPAA, GDPR-specific data
- **Intellectual property profiles**: Source code, trade secrets
- **Customer data profiles**: Customer PII, payment information
- **Employee data profiles**: Employee SSNs, salary information

### Layer detection entries

Combine multiple detection entry types in a single profile:

- Regex patterns for structured data
- Keywords for contextual clues
- EDM for specific known values

**Example**: A "Customer Data" profile might include:

- Credit card regex pattern
- Customer ID EDM dataset
- Keywords like "customer", "account number"

### Test before enforcing

1. Create the profile
2. Use it in an Allow policy with logging enabled
3. Review logs for false positives
4. Adjust settings based on results
5. Change policy action to Block when ready
