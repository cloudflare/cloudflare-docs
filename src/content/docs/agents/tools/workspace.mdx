A workspace is a persistent working directory for an agent, provided by [Cloudflare Computer](https://github.com/cloudflare/computer) (`@cloudflare/computer`). Its files live in the SQLite storage of the agent's Durable Object. This page covers the tools the model uses to work in a workspace: `read`, `write`, `edit`, `grep`, and the others, plus an optional `exec` tool that runs code against the same files.

For what a workspace is and how it fits into an agent, refer to [Workspace](/agents/concepts/workspace/). To connect a workspace to a harness, refer to the harness page: [Think](/agents/harnesses/think/) has one built in, and the [Pi harness](/agents/harnesses/pi/) takes the tools through an extension.

Give the model workspace tools when an agent needs to:

- Keep notes, drafts, plans, or generated files across turns and restarts.
- Read, search, and edit text files with tools built for a model.
- Write and run JavaScript against files, without starting a container.
- Provide skills, source files, and other external documents to the agent without filling its context window.

## How it is backed

A `Workspace` is a plain field on a Durable Object, not a Lifecycle capability. It needs only the object's `storage`, and keeps every file there. Files remain after the Durable Object is evicted or restarted, with no external storage to configure.

`workspace.fs` reads, writes, lists, searches, and deletes files. `workspace.runtime` runs code against the same files through an execution backend: a [JavaScript runtime](#run-javascript-in-the-workspace), or an experimental [shell or container](#run-shell-commands). The tools for the model are built on these two objects.

## Install

<PackageManagers pkg="@cloudflare/computer zod" />

Every tool entry point requires `zod`. What else you need depends on how your agent calls tools:

- **[Think](/agents/harnesses/think/)** includes the workspace tools. Install `@cloudflare/computer` alongside it.
- **[AI SDK](https://ai-sdk.dev/)** tools also require `ai`.
- **[Pi](/agents/harnesses/pi/)**, **[OpenCode](/agents/harnesses/opencode/)**, and **[TanStack AI](https://tanstack.com/ai)** tools need nothing beyond `zod`. Your agent brings its own library.

Your Worker needs the `nodejs_compat` [compatibility flag](/workers/configuration/compatibility-flags/).

## Add a workspace to a Durable Object

Create a `Workspace` in your Durable Object class and pass it the `storage` object. The file system is ready to use immediately.

<TypeScriptExample>

```ts
import { Workspace } from "@cloudflare/computer";
import { DurableObject } from "cloudflare:workers";

export class NotesAgent extends DurableObject<Env> {
	workspace = new Workspace({ storage: this.ctx.storage });

	async addTodo(item: string) {
		const path = "/workspace/notes/todo.md";
		await this.workspace.fs.mkdir("/workspace/notes", { recursive: true });

		let todo = "";
		try {
			todo = await this.workspace.fs.readFile(path, "utf8");
		} catch (error) {
			// A missing file means there are no to-do items yet.
			if ((error as { code?: string }).code !== "ENOENT") throw error;
		}

		todo += `- [ ] ${item}\n`;
		await this.workspace.fs.writeFile(path, todo);
		return todo;
	}
}

export default {
	async fetch(request: Request, env: Env) {
		const agent = env.NotesAgent.getByName("user-123");
		return new Response(await agent.addTodo("Ship it"));
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

### Work with files

The `workspace.fs` object provides common methods for working with the file system. It accepts `string` or binary `Uint8Array` content. Use a `ReadableStream` to read or write large files.

<TypeScriptExample>

```ts
const { fs } = this.workspace;

// Write a string, bytes, or a stream.
await fs.writeFile("/workspace/data/blob.bin", new Uint8Array([1, 2, 3]));
await fs.writeFile("/workspace/uploads/report.csv", request.body!);

// Read a file as text, or as a stream when you omit the encoding.
const text = await fs.readFile("/workspace/uploads/report.csv", "utf8");
const stream = await fs.readFile("/workspace/uploads/report.csv");

// List, search, and remove.
for (const entry of await fs.readdir("/workspace/notes")) {
	console.log(entry.isDirectory ? `d ${entry.name}` : `f ${entry.name}`);
}
const matches = await fs.grep("TODO", "/workspace", { ignoreCase: true });
await fs.rm("/workspace/notes", { recursive: true });
```

</TypeScriptExample>

For every file operation, refer to [`workspace.fs`](#workspacefs) in the API reference.

## The tools the model sees

Computer builds one set of file tools for a workspace:

| Tool      | What it does                                                                                 |
| --------- | -------------------------------------------------------------------------------------------- |
| `read`    | Reads a text file by line, or passes an image or PDF to a model that accepts it.             |
| `ls`      | Lists one directory, page by page.                                                           |
| `find`    | Finds paths with `*`, `**`, and `?` globs.                                                   |
| `grep`    | Searches file contents with a regular expression or a fixed string.                          |
| `write`   | Writes a whole file.                                                                         |
| `edit`    | Replaces targeted text in a file and returns a diff.                                         |
| `delete`  | Deletes a file or directory.                                                                 |
| `exec`    | Runs code on an execution backend. Present only when the workspace has one.                  |
| `publish` | Shares a workspace file through a presigned URL. Present only when the workspace has assets. |

Each tool returns bounded output. `read`, `ls`, `find`, and `grep` page through large results, and `edit` returns a diff of what it changed.

## Add the tools to your harness

Computer has one adapter per agent library. Each adapter builds the same tools from the same options:

| Harness or library | Entry point                              | Function                      |
| ------------------ | ---------------------------------------- | ----------------------------- |
| Think              | Built in                                 | None                          |
| Pi                 | `@cloudflare/computer/tools/pi-ai`       | `createPiTools()`             |
| OpenCode           | `@cloudflare/computer/tools/pi-ai`       | `createPiTools()` in a plugin |
| AI SDK             | `@cloudflare/computer/tools/ai-sdk`      | `createAITools()`             |
| TanStack AI        | `@cloudflare/computer/tools/tanstack-ai` | `createTanStackTools()`       |

Each entry point loads only `zod` and its own code, so importing one never pulls in another library.

### Think

Every [Think](/agents/harnesses/think/) agent has a Computer `Workspace` at `this.workspace`, and Think adds the workspace tools to every turn with no configuration. To change the workspace, override `workspace`. A custom tool from `getTools()` with the same name as a workspace tool replaces it.

For more information, refer to [Built-in workspace tools](/agents/harnesses/think/tools/#built-in-workspace-tools).

### Pi

`createPiTools()` returns Pi AI tool declarations and one `execute` function that runs a call by name. [Pi Durable](/agents/harnesses/pi/) runs the agent loop itself and expects each tool to carry its own `execute`, so pair them up as `ToolRegistration` objects:

<TypeScriptExample filename="src/workspace-tools.ts">

```ts
import type { Workspace } from "@cloudflare/computer";
import { createPiTools } from "@cloudflare/computer/tools/pi-ai";
import type { ToolRegistration } from "@earendil-works/pi-durable";

// Running these again after an eviction is harmless.
const REPLAY_SAFE = new Set(["read", "ls", "find", "grep", "write", "delete"]);

export function workspaceTools(workspace: Workspace): ToolRegistration[] {
	const { tools, execute } = createPiTools({ workspace });
	return tools.map((tool): ToolRegistration => ({
		name: tool.name,
		description: tool.description,
		parameters: tool.parameters,
		replay: REPLAY_SAFE.has(tool.name) ? "safe" : "unsafe",
		async execute(args, api, context) {
			const { content, isError } = await execute(
				{ id: api.callId, name: tool.name, arguments: args },
				{ abortSignal: context.abortSignal },
			);
			return { output: content, isError };
		},
	}));
}
```

</TypeScriptExample>

Install the tools in an [extension](/agents/harnesses/pi/extensions/) inside the harness factory, before `Harness.open()`:

<TypeScriptExample>

```ts
this.registry.install({
	name: "workspace",
	tools: workspaceTools(this.workspace),
});
```

</TypeScriptExample>

`execute` validates the arguments against the schema of the tool and reports failures as `isError` results, so the model can retry.

### OpenCode

:::caution[Experimental]
The OpenCode harness is experimental. Its API may change in any release.
:::

[OpenCode](/agents/harnesses/opencode/) receives tools through plugins. The following plugin replaces the OpenCode tools that need a local file system with the workspace tools:

<TypeScriptExample filename="src/workspace-plugin.ts">

```ts
import type { Workspace } from "@cloudflare/computer";
import { createPiTools } from "@cloudflare/computer/tools/pi-ai";
import type { Plugin } from "@opencode/plugin";

// OpenCode tools that need a local file system or process.
const LOCAL_TOOLS = ["read", "write", "edit", "patch", "glob", "grep", "shell"];

export function workspacePlugin(workspace: Workspace): Plugin.Plugin {
	const { tools, execute } = createPiTools({ workspace });
	return {
		id: "workspace",
		async setup(ctx) {
			await ctx.tool.transform((editor) => {
				for (const id of LOCAL_TOOLS) editor.remove(id);
				for (const tool of tools) {
					editor.add({
						name: tool.name,
						description: tool.description,
						input: tool.parameters,
						// Offer each tool by name instead of through OpenCode's code mode.
						options: { codemode: false },
						async execute(input, context) {
							const { content, isError } = await execute(
								{ id: context.id, name: tool.name, arguments: input },
								{ abortSignal: context.signal },
							);
							const text = content
								.map((part) => (part.type === "text" ? part.text : ""))
								.join("\n");
							if (isError) throw new Error(text || `${tool.name} failed`);
							return { content: text };
						},
					});
				}
			});
		},
	};
}
```

</TypeScriptExample>

Add the plugin to the `plugins` array that you pass to `OpenCodeWorkerd.create()` in the harness factory:

<TypeScriptExample>

```ts
OpenCodeWorkerd.create({
	storage,
	plugins: [this.ai.plugin, workspacePlugin(this.workspace)],
});
```

</TypeScriptExample>

### AI SDK

`createAITools()` returns an AI SDK `ToolSet` for a workspace. Pass it to `generateText()` or `streamText()`:

<TypeScriptExample>

```ts
import { Workspace } from "@cloudflare/computer";
import { createAITools } from "@cloudflare/computer/tools/ai-sdk";
import { generateText, stepCountIs } from "ai";
import { DurableObject } from "cloudflare:workers";
import { createAI } from "agents/models/ai-sdk";

export class WriterAgent extends DurableObject<Env> {
	workspace = new Workspace({ storage: this.ctx.storage });

	async write(prompt: string) {
		const { text } = await generateText({
			model: createAI({ binding: this.env.AI })("@cf/moonshotai/kimi-k2.6"),
			system:
				"You are a writing assistant. Keep drafts and notes as files under /workspace.",
			prompt,
			tools: createAITools({
				workspace: this.workspace,
				read: { maxBytes: 32 * 1024, maxLines: 800 },
			}),
			stopWhen: stepCountIs(20),
		});
		return text;
	}
}
```

</TypeScriptExample>

### TanStack AI

`createTanStackTools()` returns a list of [TanStack AI](https://tanstack.com/ai) server tools for `chat()`. Set `approve` to pause tools for approval. `"mutating"` selects every tool that changes the workspace:

<TypeScriptExample>

```ts
import { Workspace } from "@cloudflare/computer";
import { createTanStackTools } from "@cloudflare/computer/tools/tanstack-ai";
import { chat, type ModelMessage } from "@tanstack/ai";
import { DurableObject } from "cloudflare:workers";

export class WriterAgent extends DurableObject<Env> {
	workspace = new Workspace({ storage: this.ctx.storage });

	write(messages: ModelMessage[]) {
		return chat({
			adapter, // Your TanStack AI provider adapter.
			messages,
			tools: createTanStackTools({
				workspace: this.workspace,
				approve: "mutating",
			}),
		});
	}
}
```

</TypeScriptExample>

Pass `format: "object"` to get the tools as an object keyed by name instead of a list.

### Configure the tools

`createAITools()`, `createPiTools()`, and `createTanStackTools()` accept the same options:

| Option      | Default       | Description                                                                         |
| ----------- | ------------- | ----------------------------------------------------------------------------------- |
| `workspace` | Required      | A `Workspace`, or a client from `getWorkspace()`.                                   |
| `readonly`  | `false`       | Offers only `read`, `ls`, `find`, and `grep`.                                       |
| `read`      | Default caps  | Limits for `read`, such as `maxBytes`, `maxLines`, and `includeLineNumbers`.        |
| `write`     | Default caps  | Limits for `write`.                                                                 |
| `edit`      | Default caps  | Limits for `edit`.                                                                  |
| `exec`      | Every backend | A map from backend ID to `{ description }`. Pass `{}` to leave out the `exec` tool. |

To let the model read and search files but not change them, pass `readonly: true`:

<TypeScriptExample>

```ts
createAITools({ workspace: this.workspace, readonly: true });
```

</TypeScriptExample>

## Run JavaScript in the workspace

Add a `WorkerJavaScriptBackend` to let the agent, or the model, run JavaScript against workspace files. Each run is an ECMAScript module that executes in a new [Dynamic Worker](/dynamic-workers/). It is faster and cheaper to run than a container. Network access is configurable but off by default, and the module reaches the workspace through `node:fs/promises`.

<TypeScriptExample>

```ts
import { Workspace } from "@cloudflare/computer";
import { WorkerJavaScriptBackend } from "@cloudflare/computer/backends/worker-javascript";
import { DurableObject } from "cloudflare:workers";

export class NotesAgent extends DurableObject<Env> {
	workspace = new Workspace({
		storage: this.ctx.storage,
		backends: [new WorkerJavaScriptBackend({ loader: this.env.LOADER })],
	});
}
```

</TypeScriptExample>

In a Think agent, set the same `Workspace` as `override workspace`. Once the workspace has a backend, every tool adapter includes `exec`, and the model can run code with it.

The backend needs a [Worker Loader binding](/dynamic-workers/):

<WranglerConfig>

```jsonc
{
	"compatibility_date": "$today",
	"compatibility_flags": ["nodejs_compat"],
	"worker_loaders": [
		{
			"binding": "LOADER"
		}
	]
}
```

</WranglerConfig>

The `exec` tool describes the backend to the model, including the modules that its code can import, so the model can write a module like the following without further instructions:

```js
import fs from "node:fs/promises";

export default async function (input) {
	const names = await fs.readdir("/workspace/notes");
	const counts = {};
	for (const name of names) {
		const text = await fs.readFile(`/workspace/notes/${name}`, "utf8");
		counts[name] = text.split(/\s+/).filter(Boolean).length;
	}
	return counts;
}
```

The module must have a default export. A default-exported function is called with the input of the run, and its return value becomes the result. Put file and module calls inside that function. The Workers runtime does not allow I/O while a module loads, so accessing the file system at the top level of the module fails the run.

### Run code from the agent

Your own code can run a module through `workspace.runtime.exec()`. Pass structured data as `input`, and read the return value from `value`:

<TypeScriptExample>

```ts
using run = await this.workspace.runtime.exec(
	`
	import fs from "node:fs/promises";

	export default async function ({ path }) {
		const text = await fs.readFile(path, "utf8");
		return { lines: text.split("\\n").length };
	}
	`,
	{ input: { path: "/workspace/notes/todo.md" }, encoding: "utf8" },
);

const { exitCode, value, stdout, stderr } = await run.result();
```

</TypeScriptExample>

`console.log()` writes to `stdout`, and `console.error()` writes to `stderr`. The input and the return value must be JSON-compatible plain data. A module can also import other files in the workspace with relative imports, such as `import { summarize } from "./lib/summarize.js"`, which resolve from the `cwd` option of the run.

### Configure the backend

`WorkerJavaScriptBackend` accepts the following common options:

| Option             | Default               | Description                                                                                                                         |
| ------------------ | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `loader`           | Required              | The Worker Loader binding.                                                                                                          |
| `id`               | `"worker-javascript"` | The backend ID that `exec` and `runtime.exec()` use to select this backend.                                                         |
| `root`             | `/workspace`          | The directory that code can access. Paths outside it are rejected.                                                                  |
| `access`           | `"read-write"`        | Set to `"read"` to let code read files but not change them.                                                                         |
| `defaultTimeoutMs` | `60000`               | How long a run can take when the caller does not set a timeout.                                                                     |
| `maxTimeoutMs`     | `180000`              | The longest timeout that a caller can request.                                                                                      |
| `globalOutbound`   | `null`                | A `Fetcher` that receives every outbound request from the code. `null` blocks network access.                                       |
| `modules`          | —                     | Extra modules that code can import, such as bundled libraries or functions that run in the agent.                                   |
| `onInterrupt`      | `"fail"`              | What happens to runs that a restart interrupts. Experimental. Refer to [Resume runs after a restart](#resume-runs-after-a-restart). |
| `onWait`           | —                     | Called when a host module call starts waiting for an answer. Experimental.                                                          |

### Give code access to your own functions

Custom modules can be registered under the `ws:` namespace. Use these modules to give the model access to your application logic or file system tools, or to perform external actions.

<TypeScriptExample>

```ts
// In the `backends` list of the workspace.
new WorkerJavaScriptBackend({
	loader: this.env.LOADER,
	modules: {
		"ws:orders": {
			// Arguments arrive as an array of JSON-compatible values.
			lookup: ([orderId]) => this.lookUpOrder(String(orderId)),
		},
	},
});
```

</TypeScriptExample>

Code imports the module like any other:

```js
import { lookup } from "ws:orders";

export default async function ({ ids }) {
	return Promise.all(ids.map((id) => lookup(id)));
}
```

Always validate input to your module functions, because it comes directly from the model. Computer also includes prebuilt host modules for Git, [Artifacts](/artifacts/), and the agent's own tools. For more information, refer to [Host modules](#host-modules) in the API reference.

## Resume runs after a restart

:::note[Experimental]
Resuming runs and waiting for answers are experimental. Their behavior and stored data may change in any release, and a run interrupted across such an upgrade fails instead of resuming.
:::

A deploy or a crash restarts the Durable Object and ends every JavaScript run in flight. The `onInterrupt` option decides what happens to those runs. Set a default on the backend, and override it for a single run in `exec()`:

<TypeScriptExample>

```ts
new WorkerJavaScriptBackend({ loader: this.env.LOADER, onInterrupt: "replay" });

await this.workspace.runtime.exec(source, { onInterrupt: "fail" });
```

</TypeScriptExample>

| Value              | After a restart                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"fail"` (default) | The run fails.                                                                                                                                          |
| `"restart"`        | The run starts again from the beginning. Calls it already made run again, and its output repeats.                                                       |
| `"replay"`         | The run starts again from the beginning, but calls it already made are answered from a journal, and its output is not repeated. Then it continues live. |

The code being run does not need to change for either policy.

A replayable run writes every file system call, host module call, and `fetch` response to a journal in SQLite before the code sees the result. On replay, the code gets the same responses in the same order. Clocks, timers, `Math.random()`, and `crypto.randomUUID()` also return the same values, so the run takes the same path. Everything saved for a run is deleted when the run finishes.

Interrupted runs resume the next time something calls `workspace.runtime`, such as `exec()` or `getExec()`. Nothing else wakes a Durable Object after a deploy. To resume runs without waiting for traffic, call `workspace.runtime.recover()` from the [alarm](/durable-objects/api/alarms/) of the Durable Object.

### Calls that must not run twice

A call that was still running at the restart never returned, so the replay runs it again. Each host module call gets a `callId` that stays the same across that rerun, which you can pass on as an idempotency key. When a function cannot use one, wrap it in `unsafeToRepeat()`. An interruption during that call then fails the run instead.

<TypeScriptExample>

```ts
import { unsafeToRepeat } from "@cloudflare/computer";

new WorkerJavaScriptBackend({
	loader: this.env.LOADER,
	onInterrupt: "replay",
	modules: {
		"ws:billing": {
			refund: ([order], { callId }) =>
				this.refund(String(order), { idempotencyKey: callId }),
			charge: unsafeToRepeat(([order, cents]) =>
				this.charge(String(order), Number(cents)),
			),
		},
	},
});
```

</TypeScriptExample>

### Wait for an answer

A host module function can pause a replayable run until someone answers, for example to approve an action. The code in the isolate calls the function as usual, and gets its result once the answer arrives.

<TypeScriptExample>

```ts
new WorkerJavaScriptBackend({
	loader: this.env.LOADER,
	onInterrupt: "replay",
	modules: {
		"ws:github": {
			postComment: async ([issue, body], ctx) => {
				const { approved } = await ctx.interrupt<{ approved: boolean }>({
					issue,
					body,
				});
				if (!approved) throw new Error("The comment was rejected.");
				return this.postComment(issue, body, { idempotencyKey: ctx.callId });
			},
		},
	},
});
```

</TypeScriptExample>

`ctx.interrupt(payload)` releases the isolate of the run once its other calls in flight finish. The run stays running, and time spent waiting does not count toward its timeout. A waiting run survives deploys like any interrupted run.

List the waiting calls with `workspace.runtime.pending()`, and answer one with `respond()`:

<TypeScriptExample>

```ts
for (const call of await this.workspace.runtime.pending()) {
	await this.workspace.runtime.respond(call.id, call.callId, {
		approved: true,
	});
}
```

</TypeScriptExample>

Once none of its calls are waiting, the run replays to the call, and the function runs again with the same `callId`. This time, `ctx.interrupt()` returns the answer straight away. To notify someone when a call starts waiting, pass an `onWait` function to the backend. It receives the same fields as `pending()`, at most once per wait. `killExec()` ends a waiting run.

- A call can interrupt once. A second `ctx.interrupt()` in the same call throws.
- Only a run with `onInterrupt: "replay"` can wait. In any other run, `ctx.interrupt()` throws.
- `respond()` throws an `ENOTWAITING` error for a call that is not waiting, such as one already answered.

### Current limitations

These limitations apply to the experimental release and may change in future releases.

- A replay must take the same path as the first attempt. A run fails if it calls or prints something different. Keys from `crypto.subtle.generateKey()`, `node:crypto` randomness, `node:timers`, and `cloudflare:sockets` are not replayed.
- A replayable run buffers `fetch` responses instead of streaming them, and each body must fit in 1 MiB by default. Requests go through the Durable Object, so they are slower than in other runs. A request in flight at the restart is sent again.
- A host module function runs again once its answer arrives, so any work before `ctx.interrupt()` must be safe to repeat. Every answer replays the run from the beginning.
- A run gets three attempts, counted again each time it journals a call. It must finish within its original timeout, counted from when it first started.
- A run resumes only on the same runtime. A new compatibility date or flags, new size limits on the backend, or a package upgrade that changes how runs replay fails the runs it interrupted.
- Interrupted runs restart four at a time, because a Durable Object can run up to ten Dynamic Workers at once.
- Until a run finishes, its journal uses Durable Object storage of roughly the size of every response, plus the code of the run.

## Run shell commands

Two more backends run shell commands instead of JavaScript modules. For a shell backend, `exec` and `workspace.runtime.exec()` take a command line, such as `grep -r TODO /workspace`. Both backends are experimental in `@cloudflare/computer` 0.8.0: their APIs may change in any release, and they are not yet suitable for production use.

| Backend                                        | Import                                            | Runs                                                                | Status       |
| ---------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------- | ------------ |
| [JavaScript](#run-javascript-in-the-workspace) | `@cloudflare/computer/backends/worker-javascript` | ECMAScript modules in a new Dynamic Worker                          | Stable       |
| [Worker shell](#worker-shell)                  | `@cloudflare/computer/backends/worker-shell`      | A bash-like shell with a fixed set of commands, in a Dynamic Worker | Experimental |
| [Container](#container)                        | `@cloudflare/computer/backends/container`         | Real binaries, `npm`, and `node` in a Linux container               | Experimental |

A workspace can have several backends. Give each one an `id`. `exec()` uses the first backend unless the caller names another with the `backend` option, and the model chooses between them from the descriptions in the `exec` tool. To change what the model reads about each backend, pass `exec` to the tool adapter, for example `exec: { shell: { description: "Try this first." } }`.

### Worker shell

:::note[Experimental]
`WorkerShellBackend` and the shell command groups are experimental.
:::

`WorkerShellBackend` runs a [just-bash](https://github.com/vercel-labs/just-bash) shell in a [Dynamic Worker](/dynamic-workers/). It starts fast and needs no container. It has `cat`, `grep`, `sed`, `awk`, `find`, and other text commands, plus a built-in `git` when the workspace has Git. It cannot run `npm`, `node`, or other binaries. Every file operation goes back to the same Durable Object, so there is no second copy of the files.

Install `just-bash` alongside `@cloudflare/computer`. Optional commands come in groups that you import from `@cloudflare/computer/shell/*` and pass to `commands`: `curl`, `html-to-markdown`, `python`, `sqlite`, `js-exec`, `yq`, `file`, `xan`, and `jq`. A group you do not import is left out of your bundle.

The shell reaches the workspace through the Durable Object's binding, so create the workspace with `withWorkspace()`, and export `WorkspaceServiceProxy` from your Worker:

<TypeScriptExample>

```ts
import { withWorkspace, WorkspaceServiceProxy } from "@cloudflare/computer";
import { WorkerShellBackend } from "@cloudflare/computer/backends/worker-shell";
import curl from "@cloudflare/computer/shell/curl";
import jq from "@cloudflare/computer/shell/jq";
import { DurableObject } from "cloudflare:workers";

// The shell reaches the workspace back through this entrypoint.
export { WorkspaceServiceProxy };

export class ShellAgent extends withWorkspace(
	class extends DurableObject<Env> {},
	(self) => {
		const { ctx, env } = self as unknown as {
			ctx: DurableObjectState;
			env: Env;
		};
		return {
			storage: ctx.storage,
			backends: [
				new WorkerShellBackend({
					loader: env.LOADER,
					workspace: { binding: "ShellAgent", id: ctx.id.toString() },
					ctx,
					commands: [curl, jq],
				}),
			],
		};
	},
) {}
```

</TypeScriptExample>

The backend needs a Worker Loader binding and the `experimental` compatibility flag:

<WranglerConfig>

```jsonc
{
	"compatibility_flags": ["nodejs_compat", "experimental"],
	"worker_loaders": [{ "binding": "LOADER" }]
}
```

</WranglerConfig>

From your Worker, reach the workspace with `getWorkspace()` and run a command:

<TypeScriptExample>

```ts
using ws = await getWorkspace(env.ShellAgent.getByName("user-123"));
using run = await ws.runtime.exec("wc -l /workspace/notes/todo.md", {
	encoding: "utf8",
});
const { stdout, exitCode } = await run.result();
```

</TypeScriptExample>

### Container

:::note[Experimental]
`ContainerBackend` and `withWorkspaceContainer()` are experimental.
:::

`ContainerBackend` runs shell commands in a [Cloudflare Container](/containers/) with a full Linux userland, network access, and real binaries such as `npm` and `node`. The container runs Computer's `computerd` daemon, which keeps its own copy of the files and syncs it with the workspace before and after each command. It starts more slowly than the other backends.

The Durable Object schedules the container itself, so its `containers` entry in the Wrangler configuration sets `scheduling_policy: "durable_object"` and an `images` map. Add `withWorkspaceContainer()` to the Durable Object class and pass `ContainerBackend` to the workspace. For a complete project, including the container image, refer to the [container example](https://github.com/cloudflare/computer/tree/main/examples/container).

The container's files are held in memory and reached through FUSE, so heavy I/O, such as a large `npm install`, is slower than on a native disk. Size workspaces for an agent's working files. To run your own container without a workspace, refer to [Sandbox](/agents/tools/sandbox/).

## Git, mounts, and sharing files

A workspace can also work with Git repositories, show read-only content, and share files. Each is a workspace option, so the tools and `exec` see the result as ordinary files.

- **Git.** Pass `git: createGitClient()` from `@cloudflare/computer/git` to turn on `workspace.git`, a Git client that works on the workspace files with no backend. It can clone, add, commit, and push. Set `defaultGitIdentity` for commits. To give model-written code Git, add the `ws:git` [host module](#host-modules).
- **Read-only mounts.** Pass `mounts` to show content at a path without copying it into storage. `R2Bucket(bucket)` mounts an R2 bucket. `WorkerBundle()` mounts files that ship inside your Worker, such as skills or templates, and refreshes them when a deploy changes them. Writes under a mount fail with `EROFS`.
- **Assets.** Pass `assets: createAssets(...)` from `@cloudflare/computer/assets` to upload a workspace file to R2 and share it through a presigned URL. The tool adapters then add the `publish` tool.
- **Artifacts.** Pass an [Artifacts](/artifacts/) binding as `artifacts: { binding }` to work with Artifacts repositories. `createArtifact()` from `@cloudflare/computer/artifacts` wraps the same binding for your own code.

<TypeScriptExample>

```ts
import { Workspace } from "@cloudflare/computer";
import { createGitClient } from "@cloudflare/computer/git";

// A field on the Durable Object class:
workspace = new Workspace({
	storage: this.ctx.storage,
	git: createGitClient(),
	defaultGitIdentity: { name: "Agent", email: "agent@example.com" },
});

// In a method of the same class:
await this.workspace.git.clone({ url: "https://github.com/example/repo.git" });
await this.workspace.fs.writeFile("/workspace/notes.md", "# Notes\n");
await this.workspace.git.add({ paths: ["notes.md"] });
await this.workspace.git.commit({ message: "Add notes" });
```

</TypeScriptExample>

For the full interfaces, refer to the [Computer README](https://github.com/cloudflare/computer/tree/main/packages/computer).

## Upgrade from `@cloudflare/shell`

`@cloudflare/shell` is deprecated. Its `Workspace` is replaced by the Computer `Workspace`. Computer stores files in different tables, so data does not move on its own. To keep an existing workspace, copy its files with the script in [Migrating from `@cloudflare/shell` to `@cloudflare/computer`](https://github.com/cloudflare/agents/blob/main/docs/shell/migrating-to-computer.md). For the changes to Think's built-in tools, refer to [Upgrade from `@cloudflare/shell`](/agents/harnesses/think/tools/#upgrade-from-cloudflareshell).

## Limits

- Each workspace shares the storage of its Durable Object. For storage limits, refer to [Durable Objects limits](/durable-objects/platform/limits/). Size workspaces for an agent's working files, not for full monorepos or large dependency trees.
- The JavaScript backend runs ECMAScript modules, not shell commands or native binaries. When an agent needs a Linux environment, use the experimental [container backend](#container) or a [sandbox](/agents/tools/sandbox/).
- Each JavaScript run is bounded in CPU time, wall-clock time, output size, and the number and size of file operations. Completed runs are kept for 60 minutes by default.

## Security considerations

The model reads everything that the file tools and `exec` return. A file can contain text written to steer the model, such as an instruction to delete other files. Check tool results before the agent acts on them outside the workspace, and require [approval](/agents/harnesses/think/tools/#tool-approval) for tools with side effects.

Code that the JavaScript backend runs cannot read the environment variables, bindings, or storage of the agent. It reaches only the files under `root`, the modules you configure, and the network when you pass a `globalOutbound`. Host modules run with the full access of the agent, so expose only the functions that model-written code needs.

Every user who talks to the same agent instance shares its workspace. Give each user their own agent instance when their files must stay apart.

## API reference

### `Workspace`

`new Workspace(options)` from `@cloudflare/computer` creates a workspace. It accepts the following options:

| Option               | Description                                                                                                    |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| `storage`            | Required. The storage of the Durable Object, `this.ctx.storage`.                                               |
| `backends`           | Execution backends, such as `WorkerJavaScriptBackend`. The first backend is the default.                       |
| `mounts`             | Read-only content mounted at a path, from an R2 bucket (`R2Bucket()`) or the Worker bundle (`WorkerBundle()`). |
| `git`                | A Git client from `createGitClient()` in `@cloudflare/computer/git`, which turns on `workspace.git`.           |
| `defaultGitIdentity` | The `{ name, email }` that Git commits use.                                                                    |
| `artifacts`          | An [Artifacts](/artifacts/) binding, as `{ binding }`.                                                         |
| `assets`             | An assets client from `createAssets()` in `@cloudflare/computer/assets`, which adds the `publish` tool.        |
| `output`             | Where long command output is saved, and how much `result()` keeps.                                             |

### `workspace.fs`

Every path is absolute. Every method returns a promise.

| Method                                | Description                                                                                                                                           |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `readFile(path, encoding?)`           | Reads a file. Returns a string with `"utf8"`, or a `ReadableStream` without an encoding. Accepts `{ byteOffset, byteLength }` to read part of a file. |
| `writeFile(path, content, options?)`  | Writes a string, `Uint8Array`, or `ReadableStream`. Set `options.mode` for permissions.                                                               |
| `mkdir(path, options?)`               | Creates a directory. Set `recursive: true` to create parents.                                                                                         |
| `readdir(path)`                       | Lists a directory as entries with `name`, `parentPath`, `isFile`, and `isDirectory`.                                                                  |
| `stat(path)`                          | Returns `name`, `mode`, `mtime`, `size`, `isFile`, and `isDirectory`, following symbolic links.                                                       |
| `lstat(path)`                         | Like `stat`, but reports a symbolic link itself, with `isSymbolicLink`.                                                                               |
| `rm(path, options?)`                  | Removes a file or directory. Set `recursive: true` for a non-empty directory, and `force: true` to ignore a missing path.                             |
| `rename(oldPath, newPath)`            | Moves a file, directory, or symbolic link in one transaction.                                                                                         |
| `symlink(target, path)`               | Creates a symbolic link at `path` that points to `target`.                                                                                            |
| `readlink(path)`                      | Returns the target of a symbolic link.                                                                                                                |
| `chmod(path, mode)`                   | Changes the permission bits of a path.                                                                                                                |
| `find(directory, pattern?, options?)` | Finds paths that match a glob, relative to `directory`. Accepts `exclude`, `limit`, and `offset`.                                                     |
| `ls(prefix)`                          | Lists every file at or under `prefix`.                                                                                                                |
| `grep(pattern, path, options?)`       | Searches file contents. Accepts `regex`, `ignoreCase`, `context`, `include`, `exclude`, `limit`, and `offset`.                                        |

Failed operations reject with an error whose `code` is a POSIX error code, such as `ENOENT` for a missing path.

### `workspace.runtime`

| Method                                  | Description                                                                                          |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `exec(source, options?)`                | Runs `source` on a backend and returns a handle. Call `result()` on the handle for the final result. |
| `getExec(id, options?)`                 | Reattaches to a run by ID.                                                                           |
| `killExec(id, options?)`                | Stops a run.                                                                                         |
| `disposeExec(id, options?)`             | Discards a completed run.                                                                            |
| `backends()`                            | Lists the backends and the description that each gives to the model.                                 |
| `recover()`                             | Resumes interrupted runs. Call it from an alarm. Experimental.                                       |
| `pending()`                             | Lists the host module calls that are waiting for an answer. Experimental.                            |
| `respond(id, callId, answer, options?)` | Answers a waiting call. Experimental.                                                                |

`exec()` accepts the following options:

| Option        | Description                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `backend`     | The backend ID to run on. Defaults to the first backend.                                            |
| `input`       | JSON-compatible data passed to the default export of a JavaScript module.                           |
| `encoding`    | Set to `"utf8"` to receive `stdout` and `stderr` as strings instead of bytes.                       |
| `cwd`         | The working directory, and the base for relative imports.                                           |
| `env`         | Environment variables for this run, available to JavaScript as `process.env`.                       |
| `stdin`       | Standard input, as a string or `Uint8Array`.                                                        |
| `timeoutMs`   | How long the run can take, up to the backend's `maxTimeoutMs`.                                      |
| `onInterrupt` | What happens to this run if a restart interrupts it. Overrides the backend's default. Experimental. |

The result contains `status` (`"completed"`, `"failed"`, or `"cancelled"`), `exitCode`, `stdout`, `stderr`, and `value`, the return value of a JavaScript module. When output is too long, `truncated` names the workspace file that holds all of it.

Declare handles from `exec()` with `using` so they are disposed when they go out of scope.

### Tool functions

| Function                | Entry point                              | Returns                                                 |
| ----------------------- | ---------------------------------------- | ------------------------------------------------------- |
| `createAITools()`       | `@cloudflare/computer/tools/ai-sdk`      | An AI SDK `ToolSet`.                                    |
| `createPiTools()`       | `@cloudflare/computer/tools/pi-ai`       | Pi AI tool declarations and an `execute` function.      |
| `createTanStackTools()` | `@cloudflare/computer/tools/tanstack-ai` | A list of [TanStack AI](https://tanstack.com/ai) tools. |

### Host modules

Pass these to the `modules` option of `WorkerJavaScriptBackend`:

| Function                  | Entry point                              | Module         | Description                                                                                                                    |
| ------------------------- | ---------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `createGitModule()`       | `@cloudflare/computer/modules/git`       | `ws:git`       | Git operations on the workspace. Requires the `git` workspace option. Pass `{ allowNetwork: true }` to clone, fetch, and push. |
| `createArtifactsModule()` | `@cloudflare/computer/modules/artifacts` | `ws:artifacts` | [Artifacts](/artifacts/) repositories. Requires the `artifacts` workspace option.                                              |
| `createAssetsModule()`    | `@cloudflare/computer/modules/assets`    | `ws:assets`    | Publishes a workspace file through a presigned URL. Requires the `assets` workspace option.                                    |
| `createToolBindings()`    | `@cloudflare/computer/modules/tools`     | `ws:tools`     | The agent's own tools, callable from code. Build the bindings with `forAISDKTools()` or `forPiTools()`.                        |

For the full interfaces, refer to the [Computer design documentation](https://github.com/cloudflare/computer/tree/main/docs).
