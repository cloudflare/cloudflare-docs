A skill is a set of instructions, references, and scripts that an agent loads when a task needs it. Each skill is a directory with a `SKILL.md` file, in the open [Agent Skills](https://agentskills.io/) format. The agent sees a short catalog of skill names and descriptions, and loads a full skill only when a task matches it, so a large library of skills does not fill every prompt.

`agents/skills` reads skills from a source, merges them into a catalog, and builds the tools the model uses to load them. It works with any harness. For background on the format, refer to [Skills concepts](/agents/concepts/skills/).

:::note
Skills are experimental. The API may change in a future release. These pages describe `agents` v0.34.0.
:::

## What a skill looks like

A skill is a directory named after the skill. It holds a `SKILL.md` file and, optionally, other files:

```text
release-notes/
  SKILL.md
  references/style-guide.md
  scripts/format-release-notes.js
  assets/logo.png
```

`SKILL.md` starts with YAML frontmatter, followed by Markdown instructions:

```md
---
name: release-notes
description: Turn a list of changes into release notes. Use when the user asks for release notes or a changelog entry.
metadata:
  author: my-team
---

1. Read `references/style-guide.md`.
2. Group the changes under Features, Fixes, and Other.
```

The files in `scripts/`, `references/`, and `assets/` are the skill's resources. The model reads them when the instructions call for them.

## Load skills into an agent

To give a model skills, you need three pieces:

1. One or more [sources](/agents/skills/sources/) say where the skills live.
2. `loadSkillCatalog()` lists every source and merges the skills into a catalog.
3. `catalog.prompt()` returns the catalog text for the system prompt, and `createSkillTools()` from `agents/skills/tools/ai-sdk` returns the [AI SDK](https://ai-sdk.dev/) tools that load a skill.

This Durable Object stores its conversation in [`Sessions`](/agents/runtime/capabilities/sessions/) and loads skills from an R2 bucket on every turn:

<TypeScriptExample filename="src/index.ts">

```ts
import { DurableObject } from "cloudflare:workers";
import {
	convertToModelMessages,
	stepCountIs,
	streamText,
	type UIMessage,
} from "ai";
import { Lifecycle } from "agents/lifecycle";
import { createAI } from "agents/models/ai-sdk";
import { Sessions } from "agents/sessions";
import { loadSkillCatalog, r2, type SkillCatalog } from "agents/skills";
import { createSkillTools } from "agents/skills/tools/ai-sdk";

export class Assistant extends DurableObject<Env> {
	readonly ai = createAI({ binding: this.env.AI });
	readonly sessions = new Sessions();
	readonly lifecycle = Lifecycle.install(this).use(this.sessions);
	readonly session = this.sessions.session();
	readonly sources = [r2(this.env.SKILLS_BUCKET, { prefix: "skills/" })];
	catalog: SkillCatalog | undefined;

	async onRequest(request: Request): Promise<Response> {
		await this.session.appendMessage(await request.json<UIMessage>(), {
			source: "client",
		});

		// List the sources again each turn, so new and edited skills take effect.
		// `previous` keeps a source's last skills if it fails to list.
		this.catalog = await loadSkillCatalog(this.sources, {
			previous: this.catalog,
		});

		const { messages } = await this.session.getRecentHistory(8 * 1024 * 1024);
		const result = streamText({
			model: this.ai("@cf/moonshotai/kimi-k2.7-code"),
			system: ["You are a helpful assistant.", this.catalog.prompt()]
				.filter(Boolean)
				.join("\n\n"),
			messages: await convertToModelMessages(messages as UIMessage[]),
			tools: createSkillTools(this.catalog),
			stopWhen: stepCountIs(10),
		});

		return result.toUIMessageStreamResponse({
			onFinish: async ({ responseMessage }) => {
				await this.session.appendMessage(responseMessage);
			},
		});
	}
}
```

</TypeScriptExample>

Sources apply in order. The first source to provide a skill name wins, and later duplicates are reported in `catalog.diagnostics`. A source that fails to list, or a skill that cannot be used, becomes a diagnostic too, so one bad source never hides the others.

## Skill tools

`createSkillTools(catalog)` returns these tools when the catalog has at least one skill, and none otherwise:

| Tool                  | Purpose                                                                          |
| --------------------- | -------------------------------------------------------------------------------- |
| `activate_skill`      | Load a skill's instructions, its folder when it has one, and its resource list   |
| `read_skill_resource` | Read a resource by `{ name, path }` or a qualified path such as `name/path`      |
| `run_skill_script`    | Run a bundled script, when you pass a [script runner](/agents/skills/execution/) |

The model can only pass the name of a skill in the catalog. The tools throw on a failure, such as a missing file, and the AI SDK returns the error to the model. For a harness that is not built on the AI SDK, call `catalog.activate()` and `catalog.readResource()` from your own tool handlers. Refer to [Skills tools](/agents/tools/skills/).

## The catalog and the prompt cache

`catalog.prompt()` lists each skill's name and description:

```txt
Available skills. When a task matches a skill, use activate_skill with its name before proceeding.

- release-notes: Turn a list of changes into release notes.
- pirate-voice: Answer in a pirate voice.
```

It returns `null` when there are no skills. The catalog text is part of the system prompt, so adding, editing, or deleting a skill mid-conversation changes the prompt, and the provider's [prompt cache](/agents/concepts/context/#prompt-caching) starts over from that point. `catalog.fingerprint` changes whenever `prompt()` would, so compare it between turns to tell whether the prompt changed. Your harness decides how often to reload the catalog and where in the prompt to put it, and each harness's skills page says what it does.

## Validation

`agents/skills` checks every `SKILL.md` against these rules from the [Agent Skills specification](https://agentskills.io/specification):

- `name` must be 1 to 64 lowercase letters, digits, and hyphens. It cannot start or end with a hyphen or contain `--`. It must match the skill's directory name.
- `description` is required and can be at most 1,024 characters.
- `compatibility`, when present, must be 1 to 500 characters.
- `metadata`, when present, must map string keys to string values.
- `allowed-tools`, when present, must be a space-separated string.

Skills load the way the specification's [guide for agents](https://agentskills.io/client-implementation/adding-skills-support) recommends. Skills written for other agents often break a rule, so a skill that breaks one still loads, with a warning:

| Problem                                                                | What happens                                  |
| ---------------------------------------------------------------------- | --------------------------------------------- |
| `name` breaks the format, is too long, or does not match the directory | Loads, with a warning                         |
| `name` is missing                                                      | Loads with the directory name, with a warning |
| `description` or `compatibility` is too long                           | Loads, with a warning                         |
| `license`, `metadata`, or `allowed-tools` is invalid                   | Loads without that field, with a warning      |
| A value contains an unquoted `: `, so the YAML does not parse          | Loads after quoting the value, with a warning |
| `description` is missing                                               | Skipped, with a diagnostic                    |
| `name` contains `/`, `\`, or control characters, or is `.` or `..`     | Skipped, with a diagnostic                    |
| The frontmatter is missing or still not YAML                           | Skipped, with a diagnostic                    |

Skipped skills are not shown to the model. Frontmatter keys that the specification does not define are kept in `skill.extraFields`. A skill with `disable-model-invocation: true` is not shown to the model.

To check a skill before you write or publish it, parse it with `parseSkill()`. A skill follows the specification when it parses with no warnings:

<TypeScriptExample>

```ts
import { parseSkill } from "agents/skills";

const parsed = parseSkill(markdown, { directory: "release-notes" });
if (!parsed.ok) {
	console.log(parsed.error.message); // the skill cannot be used
} else {
	for (const warning of parsed.warnings) {
		console.log(warning.code, warning.message); // for example, "name-mismatch"
	}
}
```

</TypeScriptExample>

## Skills in a harness

A harness can do all of this for you. [Think](/agents/harnesses/think/) takes sources from `getSkills()`, and [Pi](/agents/harnesses/pi/extensions/#add-skills) takes them through its `skills()` extension. Both use the same sources and the same tools as the example in [Load skills into an agent](#load-skills-into-an-agent).
