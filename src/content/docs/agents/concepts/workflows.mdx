[Cloudflare Workflows](/workflows/) run durable, multi-step processes. Each step is saved when it completes, retries on failure, and never runs twice. A Workflow can also pause for days to wait for an event, such as an approval.

An agent and a Workflow solve different problems, and they work well together.

## Agents and Workflows compared

| Property                | Agent                                      | Workflow                         |
| ----------------------- | ------------------------------------------ | -------------------------------- |
| Execution model         | A long-lived instance that wakes on events | A run that goes to completion    |
| Path                    | Chosen by the model at each turn           | Fixed steps in code              |
| Real-time communication | WebSockets and HTTP streaming              | None                             |
| State                   | Its own SQLite database                    | The saved result of each step    |
| Failure handling        | The harness and the Lifecycle job queue    | Automatic retries per step       |
| Waiting                 | Hibernates until a request or the alarm    | Pauses until an event or a timer |

An agent decides what to do. A Workflow does a known sequence of steps, reliably.

## When to use each

Use an agent on its own for:

- Chat and messaging.
- Tasks where the model picks the next step.
- Real-time features with connected clients.
- Background work that fits in the [job queue](/agents/concepts/durable-agents/), such as a scheduled reminder.

Add a Workflow when the agent starts a process that:

- Has many steps, and each step must not run twice, such as a payment followed by a booking.
- Runs for hours or days, such as a data pipeline or a report.
- Waits for an outside event, such as a person's approval.

Use a Workflow without an agent for background jobs that need no model and no conversation, such as data synchronization.

## How an agent and a Workflow communicate

Any agent can start a Workflow through its [Workflow binding](/workflows/build/trigger-workflows/), and pass its own name in the parameters. The Workflow then reaches the agent back by name, with `getByName()` on the agent's Durable Object binding, and calls its methods over RPC.

A common pattern:

1. A tool call in the agent starts a Workflow, and returns the instance ID to the model.
2. The Workflow runs its steps. After each step, it calls a method on the agent to record progress.
3. The agent pushes the progress to connected clients.
4. When the Workflow finishes, it calls the agent with the result. The agent can start a new turn to tell the user.

Calls from a Workflow back to the agent are not steps, so a retry can repeat them. Make them safe to repeat, for example by keying each update on the step name.

## On the `Agent` class

`AgentWorkflow` from `agents/workflows` exists only for the `Agent` class. It takes the `Agent` that started it as a typed stub, and adds:

- `runWorkflow()` on the agent, which starts a Workflow and tracks it in the agent's database.
- Progress callbacks, such as `onWorkflowProgress()` and `onWorkflowComplete()`.
- Durable steps that update the agent's state, such as `step.mergeAgentState()`.
- Approval helpers: `waitForApproval()` in the Workflow, and `approveWorkflow()` and `rejectWorkflow()` on the agent.

For the full API, refer to [Run Workflows](/agents/agent-class/run-workflows/).
