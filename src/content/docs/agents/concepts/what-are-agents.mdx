An agent is an AI system that completes tasks on its own. It decides which tools to use and in what order. Traditional automation follows a fixed path. An agent adapts its approach to the context and to the results it gets along the way. A co-pilot, such as a chat assistant, helps a person do a task. An agent can do the whole task.

- **Agents**: non-linear and non-deterministic. The path can change from run to run.
- **Workflows**: linear, deterministic execution paths.
- **Co-pilots**: AI assistance that needs a person to decide and act.

## Example: book a vacation

Imagine you are booking a vacation. You need to research flights, find hotels, check restaurant reviews, and keep track of your budget.

### Traditional workflow automation

A traditional automation system follows a predetermined sequence:

- Takes specific inputs (dates, location, budget)
- Calls predefined API endpoints in a fixed order
- Returns results based on hardcoded criteria
- Cannot adapt if unexpected situations arise

![Traditional workflow automation diagram](~/assets/images/agents/workflow-automation.svg)

### AI co-pilot

A co-pilot acts as an assistant that:

- Recommends hotels and itineraries based on your preferences
- Understands and responds to natural language
- Offers guidance and suggestions
- Leaves decisions and actions to you

![A co-pilot diagram](~/assets/images/agents/co-pilot.svg)

### Agent

An agent combines a model's judgment with tools that carry out the task. Its output is non-deterministic, because of:

- Real-time availability and pricing changes
- Dynamic prioritization of constraints
- Recovery from failures
- Decisions based on intermediate results

![An agent diagram](~/assets/images/agents/agent-workflow.svg)

An agent can build an itinerary and book the reservations, as a travel agent would.

## Parts of an agent

An agent runs in a loop:

1. **Observe** the current state or task.
2. **Plan** what to do next, using a model to reason.
3. **Act** by calling tools.
4. **Record** the results in memory, then start the next iteration.

On Cloudflare, each part of that loop maps to a building block:

| Part                      | Building block                                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------------------------------- |
| The loop itself           | A [harness](/agents/concepts/harnesses/), such as the Pi harness                                           |
| Where the agent lives     | The [runtime](/agents/concepts/runtime/): a Durable Object with the Lifecycle and capabilities             |
| Reasoning                 | A [model](/agents/concepts/models/), reached through Workers AI or AI Gateway                              |
| Actions                   | [Tools](/agents/concepts/tools/), including tools from [MCP](/agents/model-context-protocol/) servers      |
| Working files             | A [workspace](/agents/concepts/workspace/), provided by Cloudflare Computer                                |
| What it remembers         | [Memory](/agents/concepts/memory/): conversation history and context                                       |
| How people reach it       | [Channels](/agents/concepts/channels/), such as WebSockets, chat, and email                                |
| Work that must finish     | [Durable agents](/agents/concepts/durable-agents/): a job queue driven by the Durable Object's alarm |

## Build agents on Cloudflare

Each agent instance is a [Durable Object](/durable-objects/). It has a name, its own SQLite database, and an alarm. You can run one agent per user, conversation, or task. An idle agent hibernates and costs close to nothing until a request or an alarm wakes it.

The Agents SDK makes harnesses run well on that runtime. The harness owns the loop. The runtime stores its state and wakes it after an eviction, a deploy, or a crash.
