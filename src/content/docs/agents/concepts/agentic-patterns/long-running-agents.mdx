A long-running agent persists for days, weeks, or months. It does not run all that time. It exists all that time, and runs when something happens.

The short version:

- An agent is a durable identity, not an always-on process.
- Anything stored in SQLite survives hibernation and restarts. Memory, timers, and open requests do not.
- The Lifecycle's job queue wakes the agent for work that must continue.
- The harness recovers a turn that an eviction cut short.
- Hand heavy multi-step processes to Cloudflare Workflows.

## Why Durable Objects fit long-running agents

Agents spend most of their time waiting: for user input, model responses, tool results, approvals, or a scheduled time. On a virtual machine or a container, you pay for all that idle time.

A Durable Object consumes no compute while it hibernates. When something happens, such as a request, a WebSocket message, an alarm, or an email, the platform wakes the object, and it loads its state from SQLite. The agent does its work, then goes back to sleep.

|                                           | Virtual machines or containers     | Durable Objects                  |
| ----------------------------------------- | ---------------------------------- | -------------------------------- |
| Idle cost                                 | Full compute cost, always          | None while hibernated            |
| Scaling                                   | Provision and manage capacity      | Automatic, per agent             |
| State                                     | An external database               | Built-in SQLite                  |
| Recovery                                  | Process managers and health checks | The platform restarts the object |
| Identity and routing                      | Load balancers and sticky sessions | Built in, from name to agent     |
| 10,000 agents, each active 1% of the time | 10,000 always-on instances         | About 100 active at any moment   |

## The life of a long-running agent

```txt
Wake → onStart() → handle events → idle → hibernation
  ▲                                            │
  └────────── alarm or request wakes it ───────┘

Eviction (crash or deploy) can happen at any point.
State persists in SQLite. The agent restarts on the next event.
```

What survives:

- Every table in the object's SQLite database, including the harness transcript and capability tables.
- Jobs in the Lifecycle's job queue, and the alarm that runs them.
- Per-connection WebSocket state.
- Files on the agent's [workspace](/agents/concepts/workspace/).

What does not survive:

- Class fields that are not stored.
- Timers, such as `setTimeout()`.
- In-flight `fetch()` requests and streams.
- Closures and promise chains.

Any work that matters must be stored or recoverable. For the mechanisms, refer to [Durable execution](/agents/concepts/durable-execution/).

## Wake on events

A long-running agent wakes for:

- **A schedule.** The [Scheduler](/agents/runtime/capabilities/scheduler/) wakes it after a delay, at a time, or on a cron expression, such as a daily status report.
- **A request.** A webhook, an HTTP call, or an RPC call from another Worker.
- **A message.** A WebSocket message, a chat message, or an email.
- **Its own work.** A harness or capability that pushed a job to the queue.

## Wait for slow work

Some work outlasts a single activation, such as a CI run that takes 20 minutes. Do not hold the agent in memory while it waits:

- **Webhook callback.** Start the work, store its ID, and let the agent hibernate. The external service calls the agent back when it finishes.
- **Polling.** Schedule a check every few minutes. Each check reads the status, stores it, and schedules the next check until the work finishes.
- **Workflow.** Start a Workflow for the slow work, and let it call the agent back with the result.

## Reconstruct context after a long wait

When the result arrives, the model's original reasoning is gone from memory. Three approaches restore it:

- **Replay the transcript.** The harness stores the conversation. Submit the result as new input, and the harness sends the whole history to the model. In the Pi harness, label the input with your own entry kind, such as `app.ci_result`, so the transcript shows where it came from.
- **Store a continuation note.** Before the wait, store a short note of what the agent was doing, and what to do with the result. On wake, build a focused prompt from the note.
- **Use the plan.** If the agent keeps a structured plan in its database, the plan says where it is: "step 3 of 7, the CI run finished." This is the most robust approach.

## Plan as a durability strategy

A structured plan is both progress for users and a recovery mechanism. Store the plan as rows, one per step, with a status. After any interruption, the agent reads the plan, finds the first unfinished step, and continues. The plan also gives the model a compact context, so it does not need the full history.

## Recovering interrupted LLM streams

A model response streams over a connection. An eviction in the middle of a response cuts the stream, and the user sees the response stop mid-sentence.

The harness recovers the turn:

- The [Pi harness](/agents/harnesses/pi/) stores what Pi committed, and a job wakes the object after an eviction. Pi then resumes the session's work from its stored state.
- [Think](/agents/harnesses/think/recovery/) and `AIChatAgent` store the partial output, then continue or retry the turn when the agent restarts.

The best recovery depends on the model provider. Some providers can continue from the partial text. Others need the partial answer stored, and a new request that asks the model to continue. For a turn that started long ago, store the partial answer, but skip the automatic continuation, so the user is not surprised by an old response.

## Manage data over time

An agent that runs for months accumulates data: transcripts, completed tasks, and logs.

- **Housekeeping.** Schedule a daily job that archives completed work and deletes old rows.
- **Transcript size.** Compact older messages into a summary, so the prompt fits in the model's context window. Keep the original messages in storage for audit.
- **End of life.** When the agent's purpose is complete, cancel its schedules, archive what you need to R2 or D1, and delete its storage. An agent that might be needed again can just stay idle, at no cost.

## When to use Workflows vs agent-internal patterns

|                | Inside the agent                                      | Workflows                            |
| -------------- | ----------------------------------------------------- | ------------------------------------ |
| Best for       | The agent's own rhythm: deadlines, reminders, syncing | Independent multi-step pipelines     |
| Durability     | SQLite and the job queue                              | The Workflows engine                 |
| Retries        | Job retries, and retries in your code                 | Per-step retries with backoff        |
| Human approval | Store the pending action, and wait for an answer      | A step that waits for an event       |
| Complexity     | Lower: everything is in the agent                     | Higher: a separate class and binding |

A pragmatic rule: if the work is the agent managing itself, such as checking deadlines or sending reminders, use schedules and the job queue. If the work is a pipeline that could fail and retry on its own, such as a deployment or a report, use a [Workflow](/agents/concepts/workflows/).

## On the `Agent` class

The `Agent` class has its own APIs for long-running work:

| API                                  | Purpose                                     |
| ------------------------------------ | ------------------------------------------- |
| `setState()` and `this.sql`          | Store state across activations              |
| `schedule()` and `scheduleEvery()`   | Wake the agent at future times              |
| `keepAlive()` and `keepAliveWhile()` | Keep the agent in memory during active work |
| `runFiber()` and `stash()`           | Checkpoint and recover long tasks           |
| `startFiber()`                       | Accept, inspect, and cancel durable jobs    |
| `runWorkflow()`                      | Start a Workflow and track it               |
| `destroy()`                          | Delete the agent and all its data           |

For more information, refer to [Durable execution on the Agent class](/agents/agent-class/durable-execution/), [Schedule tasks](/agents/agent-class/schedule-tasks/), and [Run Workflows](/agents/agent-class/run-workflows/).

For `Agent` class examples of these patterns, refer to [Scheduler](/agents/runtime/capabilities/scheduler/) for polling, recurring work, and housekeeping, [State](/agents/runtime/capabilities/state/) for a plan in state, [Webhooks](/agents/agent-class/communication-channels/webhooks/) for callbacks, [Durable execution on the Agent class](/agents/agent-class/durable-execution/) for continuation notes, and [Run Workflows](/agents/agent-class/run-workflows/) for delegating to a Workflow.
