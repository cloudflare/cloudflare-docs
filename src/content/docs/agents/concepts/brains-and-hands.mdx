An agent has three parts. Where each part runs decides what survives a crash, who can read your credentials, and what you pay for while the agent waits.

| Part        | What it is                                                                                       | Examples                                                 |
| ----------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| The brain   | The model and the [harness](/agents/harnesses/), the loop that calls the model and routes tools. | Pi, Think, OpenCode, Claude Code, Codex                  |
| The hands   | The places where the agent acts: a shell, a file system, a browser, or an API.                   | A [Container](/containers/), a Dynamic Worker, a browser |
| The session | The durable log of everything that happened: prompts, model output, tool calls, and results.     | A transcript in the SQLite database of a Durable Object  |

Anthropic named this split in [Scaling Managed Agents: Decoupling the brain from the hands](https://www.anthropic.com/engineering/managed-agents). This page uses the same terms, and shows how each arrangement maps to Cloudflare.

## Everything in one container

The first way most teams run a coding agent is to put all three parts in one container. Start a Linux container, install Claude Code or Codex, give it an API key, and send it prompts.

This works, and it has real advantages. File edits are system calls. The CLI runs unchanged, with every feature its authors built. There are no service boundaries to design.

The container becomes a pet, though: something you cannot afford to lose.

- **The session dies with the container.** A crash, a deploy, or an idle shutdown loses the transcript and any work in progress.
- **Credentials sit next to generated code.** A prompt injection only has to convince the model to read its own environment.
- **The model waits for the machine.** No inference can start until the container boots, even for a turn that never runs a command.
- **Idle time costs Linux compute.** The container keeps running while the agent waits for the user or the model.

## Take the brain out of the container

The fix is to move the brain and the session out of the container. The harness runs somewhere durable and calls the container like any other tool. Anthropic describes the interface as `execute(name, input) → string`.

The container then becomes disposable. If it dies, the harness reports a failed tool call to the model and starts a new container when one is needed. The session log lives outside both, so a new harness can pick up where the old one stopped. Credentials stay with the harness, or in a proxy outside the sandbox, so code that the model writes cannot reach them.

One brain can also use many hands. A file edit can run in an isolate, a build in a container, and a page load in a browser, all behind the same tool interface.

## Brains and hands on Cloudflare

Cloudflare builds agents this way by default. Each agent is a [Durable Object](/durable-objects/), which holds the brain and the session:

- The harness runs in the isolate of the Durable Object.
- The session lives in the SQLite database of the Durable Object.
- The object hibernates while the agent waits, and the [Lifecycle](/agents/runtime/lifecycle/) wakes it when there is work to finish.

The hands attach to the object on demand:

- A [file system](/agents/tools/filesystem/) from Cloudflare Computer keeps files in the same SQLite database, and runs JavaScript in Dynamic Workers.
- A [sandbox](/agents/tools/sandbox/) attaches a Linux container to the object through `ctx.container`. The object starts it for a command, and it stops again when the agent goes quiet.
- A [browser](/agents/tools/browser/) loads and drives web pages.

Durable Objects scale horizontally, one per agent. The attached container adds vertical scale when one task needs a full Linux userland. For more background, refer to the Cloudflare blog posts [Your agent needs a computer, not a container](https://blog.cloudflare.com/cloudflare-computer/) and [Cloudflare Containers, rebuilt to scale agent sandboxes](https://blog.cloudflare.com/faster-agent-sandboxes/).

The [Pi](/agents/harnesses/pi/), [Think](/agents/harnesses/think/), and [OpenCode](/agents/harnesses/opencode/) harnesses all run this way. The brain is TypeScript in the Durable Object, and every tool is a call out to the hands.

## When the brain is a binary

Some of the best harnesses are not libraries. Claude Code and Codex are command-line programs. They own their loop, their tools, and their session files, and they expect a Linux machine with a shell. You cannot run them in an isolate.

The [Container harness](/agents/harnesses/container/) handles this case. It splits the parts differently:

- The CLI, which is the brain, runs in the container next to the hands.
- The Durable Object keeps the session: the transcript, every queued and running prompt, and the session files the CLI writes.
- The Durable Object keeps the credentials. The CLI only sees a placeholder key, and a Worker outside the container adds the real one to each model request.
- The Durable Object drives the container. It starts the container for a prompt, snapshots it after the agent goes idle, and stops it.

The container is still disposable. When a new container starts, the object restores the CLI's session files into it, and the CLI resumes its own session. You give up a durable brain: a run that is cut short when its container dies does not resume mid-turn. You keep a durable session, credentials outside the sandbox, and an unchanged CLI.

## Choose an arrangement

Each arrangement places the parts differently:

| Arrangement                                 | Brain runs in  | Session lives in | Credentials live in | If the container dies                                         |
| ------------------------------------------- | -------------- | ---------------- | ------------------- | ------------------------------------------------------------- |
| Everything in one container                 | The container  | The container    | The container       | The session and the run are lost.                             |
| Brain in the Durable Object, hands as tools | Durable Object | Durable Object   | Durable Object      | One tool call fails. The run continues.                       |
| Container harness                           | The container  | Durable Object   | Durable Object      | The run ends unanswered. The next prompt resumes the session. |

Use a harness that runs in the Durable Object, such as [Pi](/agents/harnesses/pi/), when you control the agent loop. Add hands as tools. This gives the most durable agent, and the container only runs when a tool needs Linux.

Use the [Container harness](/agents/harnesses/container/) when you want a specific CLI agent, such as Claude Code or Codex, with its own tools, plugins, and settings. The CLI keeps working the way it does on a laptop, and the Durable Object keeps the record.
