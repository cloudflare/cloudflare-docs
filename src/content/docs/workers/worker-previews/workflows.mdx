Worker Previews are one piece of a larger deployment system. This guide helps you choose the right workflow based on **your setup** and **what you are trying to do**.

If you have not set up Worker Previews yet, start with the [get started guide](/workers/worker-previews/).

---

## Understand the pieces

Before choosing a workflow, it helps to know what each piece does and when it gets created. Here is the short version:

| Piece | Created by | What it does |
| --- | --- | --- |
| **Build** | Git push (when connected to [Workers Builds](/workers/ci-cd/builds/)) | Compiles your code. Creates a version on success. |
| **Version** | Successful build, `wrangler deploy`, or `wrangler versions upload` | A snapshot of your code and configuration. Has a unique ID. |
| **Deployment** | `wrangler deploy` or `wrangler versions deploy` | Routes production traffic to one or more versions. |
| **Preview** | `wrangler preview` or git push to non-production branch (with previews enabled) | An isolated environment with its own URL, bindings, and secrets. Separate from production. |

The key distinction:

- **Versions and deployments** are the production pipeline. They share production bindings. You can split traffic between versions and roll back.
- **Previews** are a dedicated testing pipeline. They have isolated bindings. Preview traffic stays entirely separate from production.

When you are done testing in a preview, you ship to production as a separate step. This separation is by design — your preview testing never affects real users.

## Choose your workflow

### Workflow A: Workers Builds — deploy on merge

**Best for:** Teams connected to Git who want automatic builds and deploys.

**Your build settings:**

| Setting | Value |
| --- | --- |
| Deploy command | `npx wrangler deploy` |
| Non-production branch deploy command | `npx wrangler preview` |

**How it works:**

1. Push to a feature branch — Workers Builds runs your build command, then runs `wrangler preview`. A preview is created (or updated) with isolated bindings.
2. Test against the preview URL (`my-feature-my-worker.subdomain.workers.dev`). Preview traffic uses your [Preview Defaults](/workers/worker-previews/concepts/#what-are-preview-defaults) — separate secrets, separate variables, optionally separate storage.
3. Merge to your production branch — Workers Builds runs your build command, then runs `wrangler deploy`. Production is updated immediately at 100%.

![Workflow A: deploy on merge](~/assets/images/workers/worker-previews/workflow-a-deploy-on-merge.svg)

**To set this up:**

1. Navigate to your Worker in the Cloudflare dashboard.
2. Go to **Settings** > **Build**.
3. Set your **Non-production branch deploy command** to `npx wrangler preview`.
4. If you have not already, [configure Preview Defaults](/workers/worker-previews/#5-configure-preview-variables-and-secrets) for your preview bindings and secrets.
5. Push to a feature branch. A preview will be created automatically.

:::note
If your non-production branch deploy command was previously `npx wrangler versions upload`, changing it to `npx wrangler preview` means non-production branches will create isolated previews instead of version preview URLs. [Understand the difference](/workers/worker-previews/concepts/#previews-vs-preview-urls) before switching.
:::

### Workflow B: Workers Builds — with gradual rollouts

**Best for:** Teams connected to Git who want to test in previews AND gradually roll out production deployments.

This workflow combines both capabilities:

- **Previews** for testing branches in isolation (before merge).
- **Gradual deployments** for safely rolling out to production (after merge).

Since the non-production branch deploy command accepts a single command, here are two ways to set this up:

#### Option 1: Preview on branches, gradual rollout after merge (recommended)

| Setting | Value |
| --- | --- |
| Deploy command | `npx wrangler versions upload` |
| Non-production branch deploy command | `npx wrangler preview` |

**How it works:**

1. Push to a feature branch — preview is created automatically.
2. Test against the preview URL.
3. Merge to main — Workers Builds runs `wrangler versions upload`, which creates a version **without deploying it**. No traffic is affected.
4. You manually deploy via Wrangler or the dashboard:

```bash
# See available versions
npx wrangler versions list

# Deploy at 10% (gradual rollout)
npx wrangler versions deploy
# Interactive prompt lets you pick versions and percentages

# Or deploy at 100% when ready
npx wrangler versions deploy --version-id <VERSION_ID> --percentage 100
```

![Workflow B: gradual rollout](~/assets/images/workers/worker-previews/workflow-b-gradual-rollout.svg)

**How this differs from Workflow A:** Merging to main creates a version without deploying it, giving you control over when and how much traffic to send. You choose when to go live.

#### Option 2: Use your CI to run both commands

If you use an external CI system (GitHub Actions, GitLab CI) alongside or instead of Workers Builds, you can run different commands based on context:

```yaml
# Example: GitHub Actions
- name: Deploy
  run: |
    if [ "${{ github.ref }}" = "refs/heads/main" ]; then
      npx wrangler versions upload
    else
      npx wrangler preview
    fi
```

This gives you full control over which command runs when. Refer to [External CI/CD](/workers/ci-cd/external-cicd/) for setup instructions.

### Workflow C: Wrangler from the command line

**Best for:** Teams using Wrangler directly from the command line, with or without a Git connection.

**How it works:**

1. On a feature branch, run `wrangler preview` to create an isolated preview:

```bash
git checkout -b my-feature
npx wrangler preview
```

2. Test against the preview URL.
3. When ready, deploy to production:

```bash
git checkout main
git merge my-feature
npx wrangler deploy
```

That is the simple version — `wrangler deploy` ships to production immediately at 100%.

**If you want gradual rollouts:**

```bash
# Upload a version without deploying it
npx wrangler versions upload

# Gradually deploy
npx wrangler versions deploy
# Interactive prompt: choose versions and traffic percentages

# Monitor, then promote to 100% or roll back
npx wrangler versions deploy
```

Refer to [Gradual deployments](/workers/configuration/versions-and-deployments/gradual-deployments/) for the full walkthrough.

## Understand the two pipelines

Previews and production are **separate pipelines** — each with its own purpose.

| | Preview pipeline | Production pipeline |
| --- | --- | --- |
| **Purpose** | Safe testing in isolation | Serving real users |
| **Created by** | `wrangler preview` | `wrangler deploy` or `wrangler versions upload` + `wrangler versions deploy` |
| **Bindings** | Preview Defaults (isolated resources) | Production bindings |
| **URL** | `branch-worker.subdomain.workers.dev` | `worker.subdomain.workers.dev` or custom domain |
| **Traffic splitting** | Serves latest push at 100% | Yes ([gradual deployments](/workers/configuration/versions-and-deployments/gradual-deployments/)) |
| **Rollback** | Stable URL always points to latest push; per-push URLs remain accessible | Yes ([rollbacks](/workers/configuration/versions-and-deployments/rollbacks/)) |
| **Affects production users** | Never | Yes |

The same code runs in both pipelines, against different bindings. This means you can test destructive operations (clearing a database, writing test data) with full confidence that production data is untouched.

When you are ready to ship, you deploy to production as a separate step — `wrangler deploy` or merge to main with Workers Builds. Production uses production bindings.

:::note
Your preview tests against preview data, and production runs against production data. The code is the same; the environment is different. This keeps production data safe. Keep this in mind when interpreting preview test results — especially if your Worker depends on specific data in its bindings (for example, feature flags in KV or state in Durable Objects).
:::

## Preview URLs vs Worker Previews

There are two types of URLs you can use to test a Worker before it serves production traffic. Each one exists for a specific purpose:

**Worker Previews** (`wrangler preview`) create an isolated environment with its own bindings, secrets, and storage. Use these for feature branch testing. Preview data is completely separate from production data.

**Version preview URLs** (`wrangler versions upload`) let you hit a specific version of your Worker using your production bindings. Use these when you are preparing a [gradual rollout](/workers/configuration/versions-and-deployments/gradual-deployments/) and want to verify the version against real data before sending it traffic.

| | Version preview URLs | Worker Previews |
| --- | --- | --- |
| Created by | `wrangler versions upload` | `wrangler preview` |
| Bindings | **Production** — same KV, R2, DO, secrets as your live Worker | **Isolated** — separate resources configured via Preview Defaults |
| Data | Reads and writes production data | Reads and writes preview data only |
| Gradual rollout | Yes — deploy this version to a percentage of production traffic | Previews serve the latest push at 100% |
| Rollback | Yes — route production back to a previous version | Stable URL always points to latest push; per-push URLs remain accessible |

**For feature branch testing, use Worker Previews.** They give you full isolation so you can test freely.

**For pre-rollout verification, use version preview URLs.** They let you inspect the exact version that will serve production traffic.

## Common scenarios

### "I tested in a preview. How do I ship to production?"

When your testing is done, deploy to production as a separate step:

```bash
# Switch to your production branch
git checkout main
git merge my-feature

# Deploy to production
npx wrangler deploy
```

Or, if using Workers Builds, merge your PR and the build will deploy automatically (depending on your deploy command setting).

### "I want to roll back a production deployment"

Rollbacks apply to production deployments. Your previews remain unaffected.

```bash
# List recent versions
npx wrangler versions list

# Roll back to a specific version at 100%
npx wrangler versions deploy --version-id <PREVIOUS_VERSION_ID> --percentage 100
```

Alternatively, use the Cloudflare dashboard: go to your Worker's **Deployments** tab and click **Rollback** on a previous version.

Refer to [Rollbacks](/workers/configuration/versions-and-deployments/rollbacks/) for the full guide.

### "A preview build failed. Where do I see it?"

If you are connected to Workers Builds:

1. Go to your Worker in the Cloudflare dashboard.
2. Navigate to the **Previews** tab.
3. Click on the preview (branch) that failed.
4. Check the **Deployments** list inside the preview — failed builds will show there.

Alternatively, check your Git provider (GitHub/GitLab) for build status checks on the branch.

### "How do I know my preview is isolated from production?"

After creating a preview, verify that it is using separate resources:

```bash
# Check preview settings
npx wrangler preview settings
```

This shows all bindings and variables that apply to previews. Verify that bindings point to separate resources from production. Refer to the [isolation table](/workers/worker-previews/concepts/#what-is-isolated) for default behavior per binding type.

For Durable Objects specifically, you can verify isolation by comparing instance IDs:

```bash
# Hit a DO endpoint on production
curl https://my-worker.subdomain.workers.dev/do/my-instance

# Hit the same endpoint on the preview
curl https://my-feature-my-worker.subdomain.workers.dev/do/my-instance

# If the instance IDs are different, isolation is working
```

### "I have an existing Worker with bindings. How do I set up previews?"

1. [Enable Worker Previews](/workers/worker-previews/#3-enable-worker-previews-in-the-dashboard) through the setup wizard in the dashboard.
2. Go to **Settings** > **Bindings** and toggle to **Previews**.
3. For each binding, decide whether to keep "Use production value" checked or uncheck it to point at a separate resource.
4. Set preview-specific variables and secrets using the [`previews` block](/workers/worker-previews/#5-configure-preview-variables-and-secrets) in your Wrangler configuration file or `wrangler preview secret put`.
5. Run `wrangler preview` to create your first preview.

:::note
When "Use production value" is checked for a binding, the preview shares that resource with production. For full isolation, uncheck it and select a separate resource — especially for Durable Objects and databases. Refer to the [isolation table](/workers/worker-previews/concepts/#what-is-isolated) for details.
:::
