This page explains the key concepts behind Worker Previews — how they differ from versions and deployments, how binding isolation works, and how preview URLs are structured.

## Previews, versions, and deployments

Workers has several related primitives. They serve different purposes and do not overlap:

| Primitive | Created by | What it is |
| --- | --- | --- |
| **Version** | `wrangler deploy` or `wrangler versions upload` | An immutable snapshot of your Worker's code and config |
| **Deployment** | `wrangler deploy` or `wrangler versions deploy` | Routes production traffic to one or more versions. Supports gradual rollouts and rollbacks |
| **Preview** | `wrangler preview` | An isolated environment tied to a branch, with its own stable URL, bindings, and resources. Each run pushes new code to the preview — the stable URL always points to the latest push |

### Key differences

- **Versions and deployments** are for production. You can split traffic between two versions, gradually roll out, and roll back. All versions share the same Worker identity and bindings.
- **Previews** are for testing. Each preview is completely separate from production. Creating a preview does not create a version on the production Worker.
- You cannot promote a preview to production, split traffic between a preview and production, or roll back to a preview. You test in a preview, then deploy to production separately with `wrangler deploy`.

### When to use which

| I want to... | Use |
| --- | --- |
| Test code changes in isolation before deploying | `wrangler preview` |
| Deploy to production immediately | `wrangler deploy` |
| Upload a version without deploying it, then gradually roll it out | `wrangler versions upload` then `wrangler versions deploy` |
| Roll back to a previous production version | `wrangler versions deploy` (point traffic back to the old version) |

## Preview Defaults

Preview Defaults are Worker-level settings that all previews inherit automatically. They define the base configuration for every preview environment — bindings, variables, secrets, and observability settings.

When a preview is created, Wrangler merges settings from three sources (in order of precedence):

1. **Wrangler configuration file** (`previews` block) — highest precedence
2. **Preview Defaults** (stored on the API, managed via dashboard or `wrangler preview settings update`)
3. **Production settings** — inherited for any binding with "Use production value" checked

You can configure Preview Defaults through:

- The **Cloudflare dashboard**: Settings > Bindings, toggled to Previews
- **Wrangler CLI**: `wrangler preview settings update` (reads from your Wrangler configuration file)
- **Wrangler CLI**: `wrangler preview secret put` (for secrets specifically)

## Binding isolation

Each binding type behaves differently in previews. Some are isolated automatically, others share production resources by default:

| Binding type | Default behavior | How to isolate |
| --- | --- | --- |
| **Environment variables** | Inherited from Preview Defaults or `previews.vars` | Set different values in `previews.vars` in your Wrangler configuration file |
| **Secrets** | Inherited from Preview Defaults | Use `wrangler preview secret put` |
| **KV namespaces** | Uses production namespace unless configured otherwise | Uncheck "Use production value" in dashboard, select a different namespace |
| **R2 buckets** | Uses production bucket | Configure a separate bucket in Preview Defaults |
| **Durable Objects** | Auto-provisioned isolated namespace per preview when using `ctx.exports` | Use [`ctx.exports`](/workers/worker-previews/durable-object-isolation/) (recommended) or configure manually |
| **D1 databases** | Uses production database | Configure a separate database in Preview Defaults |
| **Service bindings** | Uses production target | Configure in Preview Defaults |

:::caution
For any binding where "Use production value" is checked (the default for most binding types), preview traffic reads and writes to your production resources. Always verify your binding configuration before testing with real data.
:::

Durable Objects are a special case because the platform can auto-provision isolated namespaces per preview. Refer to [Durable Object isolation](/workers/worker-previews/durable-object-isolation/) for a detailed guide.

## Preview URLs

Each preview gets a stable URL tied to the preview name, and each deployment within a preview gets its own immutable URL:

| URL type | Format | Changes on redeploy? |
| --- | --- | --- |
| Stable preview URL | `<PREVIEW_NAME>-<WORKER_NAME>.<SUBDOMAIN>.workers.dev` | No — always points to the latest deployment |
| Deployment URL | `<DEPLOYMENT_ID>-<WORKER_NAME>.<SUBDOMAIN>.workers.dev` | N/A — each deployment gets a new one |

### Supported domain types

Worker Previews support three domain types, each with independent production and previews toggles:

| Domain type | Preview URL pattern | Configured via |
| --- | --- | --- |
| `workers.dev` | `<PREVIEW_NAME>-<WORKER_NAME>.<SUBDOMAIN>.workers.dev` | Worker settings |
| Custom domains | `<PREVIEW_NAME>.app.example.com` | Domains API with `previews_enabled: true` |

When `previews_enabled` is set on a custom domain, a wildcard DNS record and wildcard SSL SAN are created automatically. Each preview gets a subdomain of the custom domain.

Custom domain configuration example:

<WranglerConfig>

```jsonc
{
	"routes": [
		{
			"pattern": "app.example.com",
			"custom_domain": true,
			"production_enabled": true,
			"previews_enabled": true
		}
	]
}
```

</WranglerConfig>

## Worker Previews vs Preview URLs

[Preview URLs](/workers/configuration/previews/) are an older feature that generates URLs for each uploaded Worker version. Worker Previews are a newer, more powerful feature with true environment isolation:

| Feature | Preview URLs | Worker Previews |
| --- | --- | --- |
| Isolated bindings | No — shares production bindings | Yes — own bindings per preview |
| Isolated DO storage | No | Yes — auto-provisioned namespaces |
| Own variables and secrets | No | Yes |
| Stable URL per branch | Aliased only | Automatic per branch |
| Gradual deployments | Yes (via versions) | No |
| Rollback | Yes (via versions) | No |
| Custom domain support | No | Yes |

Use Worker Previews when you need isolated testing environments. Continue to use [versions and deployments](/workers/configuration/versions-and-deployments/) for production release workflows like gradual rollouts and rollbacks.
