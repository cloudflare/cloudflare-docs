## Production commands vs preview command

There are two pipelines for your Worker — production and preview. Each has its own commands, and they do not overlap.

![Production vs preview commands](~/assets/images/workers/worker-previews/commands-production-vs-preview.svg)

**Production commands** create versions on your production Worker and use production bindings:

| Command | What it does |
| --- | --- |
| `wrangler deploy` | Creates a version and deploys it to 100% of production traffic immediately |
| `wrangler versions upload` | Creates a version without deploying it. Used for [gradual rollouts](/workers/worker-previews/rollouts-and-rollbacks/) |
| `wrangler versions deploy` | Routes production traffic to specific version(s) at chosen percentages |

**Preview command** creates an isolated environment that is completely separate from production:

| Command | What it does |
| --- | --- |
| `wrangler preview` | Creates or updates a preview with its own URL, bindings, secrets, and data stores. Does not create a production version. |

When you are happy with your changes, you ship to production separately with `wrangler deploy`. Previews and production are independent — previews are for testing, deployments are for shipping.

### The basic flow

```
1. Write code on a branch
2. wrangler preview        → creates an isolated preview with its own URL
3. Test against the preview URL
4. Iterate — each wrangler preview push updates the same preview
5. wrangler deploy          → ships to production (separate step)
```

## What is a preview?

A preview is an isolated copy of your Worker tied to a Git branch. It has:

- **Its own URL** — `my-branch-my-worker.subdomain.workers.dev`. This URL is stable and always points to your latest push.
- **Its own bindings** — KV, R2, Durable Objects, D1 can each point to separate resources so preview traffic never touches production data.
- **Its own secrets and variables** — you can set different API keys, feature flags, or configuration for testing.

A preview persists across code pushes. Every time you run `wrangler preview` on the same branch, it updates the preview with your latest code. The URL stays the same.

## What is isolated?

"Isolated" means your preview can have its own resources that are separate from production. This is the key difference from just hitting your production Worker with test requests — in a preview, you can point at a test database, a separate KV namespace, or an isolated Durable Object namespace.

By default, most bindings share production resources unless you configure them otherwise:

| Resource | Default in a preview | How to isolate |
| --- | --- | --- |
| **Environment variables** | Not inherited from production. Empty unless you set them in Preview Defaults. | Set values in the `previews.vars` block of your Wrangler configuration file or in the dashboard |
| **Secrets** | Not inherited from production. Empty unless you set them in Preview Defaults. | `wrangler preview secret put` or set in the dashboard |
| **Durable Objects** | Auto-provisioned isolated namespace (when using `ctx.exports`) | Use [`ctx.exports`](/workers/worker-previews/durable-object-isolation/) (recommended) or configure manually |
| **KV namespaces** | Shares production | Uncheck "Use production value" in the dashboard, select a different namespace |
| **R2 buckets** | Shares production | Configure a separate bucket in Preview Defaults |
| **D1 databases** | Shares production | Configure a separate database in Preview Defaults |

:::caution
If a binding still points at production, preview traffic will read and write to your production data. Always check your binding configuration before running tests that modify data.
:::

For Durable Objects specifically, refer to [Durable Object isolation](/workers/worker-previews/durable-object-isolation/) for a step-by-step guide.

## What are Preview Defaults?

Preview Defaults are a set of settings stored on your Worker that every new preview inherits automatically. Think of them as the template for what a preview environment looks like — which bindings to use, which variables to set, which observability settings to apply.

You configure Preview Defaults once, and every `wrangler preview` after that picks them up without any extra configuration.

You can set Preview Defaults through:

- **The dashboard:** Settings > Bindings, toggled to Previews
- **Wrangler:** `wrangler preview settings update` (reads the `previews` block from your Wrangler configuration file)
- **Wrangler:** `wrangler preview secret put` (for secrets)

If your Wrangler configuration file has a `previews` block, those values take precedence over what is stored in Preview Defaults. The merge order is:

1. **Wrangler configuration file** (`previews` block) — wins if set
2. **Preview Defaults** (stored on the API) — used if Wrangler config does not override
3. **Production settings** — used for any binding with "Use production value" checked

## How preview URLs work

Each preview gets two kinds of URLs:

| URL | Format | What it points to |
| --- | --- | --- |
| **Stable URL** | `<BRANCH>-<WORKER>.<SUBDOMAIN>.workers.dev` | Always the latest push to this preview |
| **Per-commit URL** | `<DEPLOYMENT_ID>-<WORKER>.<SUBDOMAIN>.workers.dev` | A specific commit (immutable) |

The stable URL is what you share with teammates or use in CI — it always reflects your latest code. The per-commit URL lets you go back and look at a specific version of the preview if needed.

You can also serve previews on your own custom domain. Refer to [Custom domains](/workers/worker-previews/custom-domains/) for setup instructions.

## Preview lifecycle

### Creation

A preview is created the first time you run `wrangler preview` on a branch (or with a `--name`). If a preview already exists for that branch or name, subsequent runs push new code to the existing preview — the stable URL stays the same.

### Updates

Every `wrangler preview` run on the same branch pushes new code to the existing preview. The stable URL always points to the latest code. Previous commits remain accessible via their per-commit URLs.

### Deletion

Previews can be deleted in three ways:

- **Manual CLI:** `wrangler preview delete` removes the preview for the current branch. Use `--name` to delete a named preview.
- **Manual dashboard:** Inside the preview detail page, go to **Settings** > **General** > **Delete**.
- **Auto-deletion (git-connected):** When you enable **Auto-deletion** in the preview's Settings, the preview is automatically deleted when the tracking branch is deleted in the repository. This is enabled by default for previews created by Workers Builds.

For CLI-only previews (not tied to a git connection), auto-deletion does not apply. You are responsible for cleaning up previews you no longer need.

When a preview is deleted, auto-provisioned Durable Object namespaces associated with it are also deleted. KV namespaces, R2 buckets, and D1 databases configured as preview bindings are **not** deleted — they are separate resources you manage independently.

## How Previews compare to other Workers features

### Previews vs `wrangler deploy`

`wrangler deploy` ships code directly to production. There is no isolation — changes are immediately live.

`wrangler preview` creates a separate environment for testing. Production is untouched until you explicitly run `wrangler deploy`.

### Previews vs version URLs

[Version URLs](/workers/configuration/previews/) are generated when you run `wrangler versions upload`. They let you hit a specific version of your Worker at a URL, but the version runs against your **production bindings** — the same KV, R2, Durable Objects, and secrets as production.

Worker Previews (`wrangler preview`) give each branch its own isolated environment with separate resources. The tradeoff is that previews cannot be gradually rolled out or rolled back — those are production-only capabilities.

| | Version URLs | Worker Previews |
| --- | --- | --- |
| **Created by** | `wrangler versions upload` | `wrangler preview` |
| **Bindings** | Production bindings | Isolated — own bindings, secrets, storage |
| **Gradual rollout** | Yes — the version can be deployed to a % of traffic | No — previews are for testing only |
| **Rollback** | Yes | No |
| **Custom domains** | No | Yes |
| **Observability** | No logs, traces, or logpush | Per-preview logs and traces |
| **Durable Objects** | Not generated for Workers with DOs | Isolated DO namespace per preview |
| **Stable URL per branch** | Aliased URLs supported but versioned URL changes on every upload | Yes — tied to the branch name by default |

**For branch testing, use Worker Previews.** They give you full isolation so you can test freely without risking production data.

Version URLs are not the recommended path for testing. They were designed for inspecting a version before a [gradual rollout](/workers/worker-previews/rollouts-and-rollbacks/), not as a general-purpose preview environment. They have [limitations](/workers/configuration/previews/#limitations) including no isolation, no Durable Object support, no logs, and no stable URL per branch.

### Availability of version URLs

**New Workers:** `wrangler versions upload` no longer generates a version URL. This cannot be enabled. Use `wrangler preview` to get a preview URL with [isolated resources](/workers/worker-previews/concepts/#previews-vs-version-urls).

**Existing Workers** that already have version URLs enabled can continue to use them. However, we recommend disabling them to avoid confusion between production resources (used by version URLs) and isolated preview resources (used by Worker Previews). You can disable version URLs in **Settings** > **Domains & Routes** or by setting `preview_urls: false` in your Wrangler configuration file. Refer to [Preview URLs](/workers/configuration/previews/) for details.

### Previews vs gradual rollouts

[Gradual rollouts](/workers/worker-previews/rollouts-and-rollbacks/) let you send a percentage of production traffic to a new version (for example, 10% to the new code, 90% to the old code). This is a production deployment strategy — both versions share the same bindings and serve real users.

Previews are not a deployment strategy. They are a separate testing environment. You cannot split traffic between a preview and production, and you cannot promote a preview to production. When you are done testing in a preview, you ship to production with `wrangler deploy` as a separate step.

## Reference: what each command does

| Command | What happens | Touches production? |
| --- | --- | --- |
| `wrangler deploy` | Ships code to production immediately | Yes |
| `wrangler versions upload` | Creates a version you can inspect or gradually roll out later | No (until you deploy it) |
| `wrangler versions deploy` | Routes production traffic to specific version(s) | Yes |
| `wrangler preview` | Creates or updates an isolated preview environment | No |
| `wrangler preview secret put` | Adds a secret to Preview Defaults | No |
| `wrangler preview settings update` | Updates Preview Defaults from your Wrangler configuration file | No |
| `wrangler preview delete` | Deletes a preview and its resources | No |

## Limits

Previews count against a separate account-level preview limit, not the Worker limit. If you reach the limit, the least-recently-deployed preview is deleted to make room for new ones.
