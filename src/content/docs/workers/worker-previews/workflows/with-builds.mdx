Your Worker is connected to a Git repository via [Workers Builds](/workers/ci-cd/builds/). Builds runs the right command based on the branch — feature branches create previews, the production branch deploys to production.

![With Workers Builds](~/assets/images/workers/worker-previews/lifecycle-with-builds.svg)

---

## Deploy on merge

The simplest setup. Feature branches get previews. Merging to main deploys to production at 100%.

**Your build settings:**

| Setting | Value |
| --- | --- |
| Deploy command | `npx wrangler deploy` |
| Preview command | `npx wrangler preview` |

**How it works:**

1. Push to a feature branch — Builds runs `wrangler preview`. A preview is created with isolated bindings.
2. Test against the preview URL (`my-feature-my-worker.subdomain.workers.dev`).
3. Merge to main — Builds runs `wrangler deploy`. Production is updated at 100%.

**To set this up:**

1. Navigate to your Worker in the Cloudflare dashboard.
2. Go to **Settings** > **Build**.
3. Set the **Preview command** (previously called "Non-production branch deploy command" in the dashboard) to `npx wrangler preview`.
4. If you have not already, [configure preview bindings and settings](/workers/worker-previews/#1-configure-preview-bindings-and-settings).
5. Push to a feature branch. A preview will be created automatically.

:::note[What if you change the preview command back to `wrangler versions upload`?]
If you switch the preview command from `npx wrangler preview` to `npx wrangler versions upload`:

- **Existing Workers** (created before Worker Previews): `wrangler versions upload` will still generate a version URL and Builds will write it back to your Git provider. These URLs use [production bindings](/workers/worker-previews/concepts/#previews-vs-version-urls).
- **New Workers** (created after Worker Previews): `wrangler versions upload` will **not** generate a URL. Version URLs are disabled for new Workers and cannot be enabled. Use `wrangler preview` for preview URLs.
:::

## Deploy on merge with gradual rollouts

There are two ways to set this up. The tradeoff is whether every merge automatically creates a version you have to manually roll out, or whether you keep automatic deploys and only use gradual rollouts when you choose to.

### Option 1: Every merge creates a version (you always control rollout)

| Setting | Value |
| --- | --- |
| Deploy command | `npx wrangler versions upload` |
| Preview command | `npx wrangler preview` |

**How it works:**

1. Push to a feature branch — Builds runs `wrangler preview`. Preview is created with isolated bindings.
2. Test against the preview URL.
3. Merge to main — Builds runs `wrangler versions upload`. A version is created. **No traffic changes.**
4. You control the rollout via Wrangler, the dashboard, or the [API](/api/resources/workers/subresources/scripts/subresources/deployments/methods/create/):

```bash
# Interactive — prompts you to pick versions and percentages
npx wrangler versions deploy

# Non-interactive — specify directly
npx wrangler versions deploy <VERSION_ID>@<PERCENTAGE> <OLD_VERSION_ID>@<PERCENTAGE> -y
```

**The tradeoff:** Every merge to main creates a version that sits at 0% traffic until you roll it out. If you merge frequently, versions will pile up and each one requires a manual `versions deploy` step.

### Why you cannot mix `wrangler deploy` with gradual rollouts in Builds

You might want to keep your deploy command as `npx wrangler deploy` (auto-deploy to 100% on merge) and only use gradual rollouts occasionally. This does not work with Builds because:

![Why you cannot mix wrangler deploy with gradual rollouts in Builds](~/assets/images/workers/worker-previews/cannot-mix-deploy-gradual.svg)

1. **You cannot `wrangler versions upload` from a feature branch** — it would create a production version using preview resources, not production bindings.
2. **Merging a PR triggers Builds** — Builds runs your deploy command (`wrangler deploy`), which deploys to 100% immediately. There is no way to intercept this and do a gradual rollout instead.
3. **Merging locally and running `wrangler versions upload` before pushing** creates a race condition — when you push the merge, Builds will still run `wrangler deploy` on top of your gradual rollout.

If you need gradual rollouts with Builds, use [Option 1](#option-1-every-merge-creates-a-version-you-always-control-rollout) — set your deploy command to `npx wrangler versions upload` so every merge creates a version without deploying it. You then control the rollout manually.

If you only need gradual rollouts occasionally and are not using Builds, see [Without Workers Builds — gradual rollouts](/workers/worker-previews/workflows/without-builds/#with-gradual-rollouts).

For the full gradual rollout and rollback guide, see [Gradual rollouts and rollbacks](/workers/worker-previews/rollouts-and-rollbacks/).

## Common scenarios

### "I tested in a preview. How do I ship to production?"

Merge your PR. Builds runs your deploy command on main — either `wrangler deploy` (deploys to 100%) or `wrangler versions upload` (creates a version for gradual rollout), depending on your build settings.

The code is the same as what you tested. The difference is it now runs with production bindings instead of preview bindings.

### "A preview build failed. Where do I see it?"

1. Go to your Worker in the Cloudflare dashboard.
2. Navigate to the **Previews** tab.
3. Click on the preview (branch) that failed.
4. Check the **Deployments** list inside the preview — failed builds will show there.

Alternatively, check your Git provider (GitHub/GitLab) for build status checks on the branch.

### "My preview command was `wrangler versions upload`. What changes?"

Changing from `wrangler versions upload` to `wrangler preview` means non-production branches will create isolated previews instead of production versions. Your deploy command is unchanged. See [Switching from `wrangler versions upload`](/workers/worker-previews/workflows/#switching-from-wrangler-versions-upload) for the full walkthrough.
