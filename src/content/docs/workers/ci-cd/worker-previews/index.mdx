Worker Previews let you create fully isolated preview environments for your Worker. Each preview gets its own URL, bindings, variables, secrets, and — for [Durable Objects](/durable-objects/) — its own isolated storage namespace.

Unlike [Preview URLs](/workers/configuration/previews/), which share the same bindings and resources as your production Worker, Worker Previews provide true environment isolation. When configured correctly, preview traffic never touches your production data.

:::note
Worker Previews is currently in private beta. You need a pre-release version of Wrangler to use this feature.
:::

## How Worker Previews work

A **preview** is an isolated environment tied to a Git branch (or a custom name). Each preview has:

- A **stable URL** that always points to the latest deployment: `<PREVIEW_NAME>-<WORKER_NAME>.<SUBDOMAIN>.workers.dev`
- Its own **bindings, variables, and secrets** — inherited from Preview Defaults or your Wrangler configuration file
- For Durable Objects, an **auto-provisioned isolated namespace** per preview

A **preview deployment** is an immutable snapshot within a preview. Each time you run `wrangler preview` on the same branch, a new deployment is added. Each deployment also gets its own immutable URL: `<DEPLOYMENT_ID>-<WORKER_NAME>.<SUBDOMAIN>.workers.dev`.

Previews are completely separate from your production Worker. Creating a preview does not create a [version](/workers/configuration/versions-and-deployments/#versions) on the parent Worker, and you cannot promote a preview to production or split traffic between them. You test in a preview, then deploy to production separately with `wrangler deploy`.

## Concepts

### Previews vs deployments vs versions

Workers has several related but distinct concepts. Understanding their differences helps clarify where Worker Previews fit in:

| Concept | Created by | What it is | Supports traffic splitting |
| --- | --- | --- | --- |
| **Version** | `wrangler deploy` or `wrangler versions upload` | A code + config snapshot on the production Worker | Yes (via gradual deployments) |
| **Deployment** | `wrangler deploy` or `wrangler versions deploy` | Traffic routing to one or more versions | Yes |
| **Preview** | `wrangler preview` | An isolated branch environment with its own URL and resources | No |
| **Preview deployment** | `wrangler preview` (each run) | An immutable snapshot within a preview | No |

Use [versions and deployments](/workers/configuration/versions-and-deployments/) for production release workflows like gradual rollouts and rollbacks. Use Worker Previews for testing changes in isolation before deploying.

### Preview Defaults

Preview Defaults are Worker-level settings that all previews inherit automatically. They define the base configuration for every preview environment — bindings, variables, secrets, observability settings, and more.

You can configure Preview Defaults through:

- The **Cloudflare dashboard**: Settings > Bindings, toggled to Previews
- **Wrangler CLI**: `wrangler preview settings update` (reads from your Wrangler configuration file)
- **Wrangler CLI**: `wrangler preview secret put` (for secrets)

When a preview is created, it merges Preview Defaults with any `previews` block in your Wrangler configuration file. Values from the Wrangler configuration file take precedence.

### Binding isolation

Each binding type has different isolation behavior in previews:

| Binding type | Default behavior | How to isolate |
| --- | --- | --- |
| **Environment variables** | Inherited from Preview Defaults or `previews.vars` | Set different values in `previews.vars` |
| **Secrets** | Inherited from Preview Defaults | Use `wrangler preview secret put` |
| **KV namespaces** | Uses production namespace (or preview-specific if configured) | Uncheck "Use production value" in dashboard, select a different namespace |
| **R2 buckets** | Uses production bucket | Configure a separate bucket in Preview Defaults |
| **Durable Objects** | Auto-provisioned isolated namespace per preview (with `ctx.exports`) | Use [`ctx.exports`](/workers/ci-cd/worker-previews/durable-object-isolation/) (recommended) or configure manually |
| **D1 databases** | Uses production database | Configure a separate database in Preview Defaults |
| **Service bindings** | Uses production target | Configure in Preview Defaults |

For most bindings, you control isolation through Preview Defaults — either in the dashboard or via the `previews` block in your Wrangler configuration file. Durable Objects are special because the platform can auto-provision isolated namespaces. Refer to [Durable Object isolation](/workers/ci-cd/worker-previews/durable-object-isolation/) for details.

## URLs

Worker Previews support three domain types, each with independent production and previews toggles:

| Domain type | Preview URL pattern | Configured via |
| --- | --- | --- |
| `workers.dev` | `<PREVIEW_NAME>-<WORKER_NAME>.<SUBDOMAIN>.workers.dev` | Worker settings |
| `cloudflare.app` | `<PREVIEW_NAME>-<WORKER_NAME>.cloudflare.app` | Worker settings |
| Custom domains | `<PREVIEW_NAME>.app.example.com` | Domains API (`previews_enabled: true`) |

When `previews_enabled` is set on a custom domain, a wildcard DNS record and wildcard SSL SAN are created automatically. Each preview gets a subdomain of the custom domain.

## Worker Previews vs Preview URLs

| Feature | Preview URLs | Worker Previews |
| --- | --- | --- |
| Isolated bindings | No — shares production bindings | Yes — own bindings per preview |
| Isolated DO storage | No | Yes — auto-provisioned namespaces |
| Own variables and secrets | No | Yes |
| Stable URL per branch | Aliased only | Automatic per branch |
| Gradual deployments | Yes (via versions) | No |
| Rollback | Yes (via versions) | No |
| Custom domain support | No | Yes |

If you need gradual deployments or rollback capabilities, continue to use [versions and deployments](/workers/configuration/versions-and-deployments/). Worker Previews are designed for testing changes in isolation before deploying to production.
