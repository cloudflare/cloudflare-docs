Modern applications require multiple types of storage to handle different data patterns and user needs. This guide helps you choose the right Cloudflare storage products based on your application architecture and requirements.

Start with your use case, get a clear recommendation, and understand why it's the best choice.

## Storage for common architectures

Real applications combine multiple storage products. Here are proven patterns for common application types:

### SaaS application
**Stack**: D1 + Workers KV + R2

- **D1** - Customer data, user profiles, subscription plans, billing history
- **Workers KV** - Feature flags, session data, configuration settings  
- **R2** - Customer uploads, backups, exported reports

**Why this works**: D1 handles transactional customer data with strong consistency. KV provides fast global access to frequently-read config data. R2 stores large files cost-effectively.

### E-commerce platform
**Stack**: Hyperdrive + Workers KV + R2

- **Hyperdrive** - Product catalog, inventory, orders, customer data (connects to existing Postgres/MySQL)
- **Workers KV** - Product recommendations, A/B test configurations, cached pricing
- **R2** - Product images, user-generated content, order documents

**Why this works**: Hyperdrive accelerates your existing e-commerce database globally. KV caches frequently-accessed data near users. R2 delivers media assets without egress fees.

### Real-time collaboration tool
**Stack**: Durable Objects + D1 + R2

- **Durable Objects** - Live document state, WebSocket connections, real-time coordination
- **D1** - User accounts, document metadata, access permissions
- **R2** - Document versions, exported files, user avatars

**Why this works**: Durable Objects provide the coordination and consistency needed for real-time features. D1 handles user management. R2 stores large document assets.

### Content management system
**Stack**: D1 + R2 + Workers KV

- **D1** - Articles, comments, user accounts, publishing workflow
- **R2** - Images, videos, document attachments  
- **Workers KV** - Published content cache, site configuration, CDN cache keys

**Why this works**: D1 manages structured content with full SQL capabilities. R2 handles media storage and delivery. KV caches published content globally for fast page loads.

## Common architectural requirements

Most applications need to solve these core storage challenges. Use these opinionated recommendations:

### User and customer data
**Use D1 for new applications** or **Hyperdrive for existing databases**

D1 when:
- Building a new application
- Customer data under 10GB per database
- Need global read replicas
- Want serverless simplicity

Hyperdrive when:
- Have existing Postgres or MySQL database
- Database size exceeds 10GB
- Using existing database tools and ORMs  
- Need maximum compatibility

### Configuration and feature flags
**Use Workers KV**

Perfect for:
- Application settings read on every request
- Feature flags and A/B test configurations
- API keys and external service credentials
- Cached data that changes infrequently

**Why**: KV's global edge cache means config data is available in microseconds, and you stay within the 1 write/second per key limit.

### File and media storage
**Use R2**

Essential for:
- User uploads (images, documents, videos)
- Generated reports and exports
- Backup storage
- Static assets for your application

**Why**: R2 provides S3-compatible storage without egress fees, making it cost-effective for high-traffic applications.

### Background job processing
**Use Queues**

Critical for:
- Email sending and notifications
- Data processing and transformations  
- Third-party API calls that can be deferred
- Batch operations and cleanup tasks

**Why**: Queues handle retries and failures automatically, letting you build resilient async workflows.

## Choose your storage pattern

Use this decision framework to select the right product for your specific need:

### For structured, relational data

**Start here**: Do you have an existing database?

**Yes** → Use **Hyperdrive**
- Connects to existing Postgres or MySQL
- Reduces connection overhead and latency globally
- Works with your existing tools and queries

**No** → Use **D1**
- Serverless SQL database  
- Automatic scaling and read replicas
- No connection management required

### For key-value data

**How often is this data read vs. written?**

**Read-heavy (100:1 or higher)** → Use **Workers KV**  
- Global edge caching
- Microsecond read latency
- Limited to 1 write/second per key

**Write-heavy or need consistency** → Use **Durable Objects**
- Strong consistency guarantees  
- No write rate limits
- Single-threaded per object for coordination

### For large files and media

**Use R2** - This is the clear choice
- S3-compatible APIs
- No egress charges  
- Global CDN integration

### For real-time coordination

**Use Durable Objects** - The only option for this use case
- WebSocket support with hibernation
- Global ordering of operations
- Strong consistency guarantees

## When to use each product

### Workers KV - Configuration and caching
**Best for**: Data read thousands of times but written rarely

Use Workers KV when you need:
- **Sub-10ms global reads** - Config data, feature flags, A/B test settings
- **High read-to-write ratios** - Works within 1 write/second per key
- **Edge caching** - Frequently accessed data cached globally
- **Simple key-value operations** - No complex queries needed

**Start here**: [Create your first KV namespace](/kv/get-started/)

### R2 - File and media storage  
**Best for**: Any files larger than a few kilobytes

Use R2 when you need:
- **Cost-effective storage** - No egress fees unlike other cloud providers
- **Large file handling** - Images, videos, documents, backups
- **S3 compatibility** - Works with existing S3 tools and SDKs
- **Global content delivery** - Integrates with Cloudflare's CDN

**Start here**: [Upload your first object to R2](/r2/get-started/)

### D1 - Serverless SQL database
**Best for**: New applications with relational data under 10GB

Use D1 when you need:
- **Zero-maintenance SQL** - No connection pooling or server management  
- **Global read replicas** - Fast reads for users worldwide
- **Read-heavy workloads** - Typical web application patterns
- **Full SQL support** - Joins, transactions, indexes

**Start here**: [Create your first D1 database](/d1/get-started/)

### Hyperdrive - Accelerate existing databases
**Best for**: Existing Postgres or MySQL databases over 10GB

Use Hyperdrive when you need:
- **Existing database compatibility** - Keep using your current database
- **Global acceleration** - Connection pooling and query caching worldwide
- **Large datasets** - No 10GB limit like D1
- **Database tool support** - Works with ORMs, admin tools, migrations

**Start here**: [Connect Hyperdrive to your database](/hyperdrive/get-started/)

### Durable Objects - Stateful coordination
**Best for**: Real-time features requiring strong consistency  

Use Durable Objects when you need:
- **Real-time coordination** - Chat, collaboration, multiplayer games
- **WebSocket support** - Long-lived connections with hibernation
- **Strong consistency** - Guaranteed ordering of operations globally
- **Per-entity state** - Isolated storage per user, room, or session

**Start here**: [Build your first Durable Object](/durable-objects/get-started/)

### Queues - Background job processing
**Best for**: Work that can be done asynchronously

Use Queues when you need:
- **Reliable message delivery** - At-least-once guarantees with retries
- **Background processing** - Email sending, data transforms, cleanup
- **Worker-to-worker communication** - Decouple services
- **Batch processing** - Process multiple messages together

**Start here**: [Create your first queue](/queues/get-started/)

### Specialized products

**Vectorize** - Store and query AI embeddings for semantic search and RAG applications. [Get started →](/vectorize/get-started/intro/)

**Analytics Engine** - Write high-cardinality time-series data for custom analytics and metrics. [Get started →](/analytics/analytics-engine/get-started/)

**Pipelines** - Ingest streaming data at high throughput directly to R2 for analytics. [Get started →](/pipelines/getting-started/)
