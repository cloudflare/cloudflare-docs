An OpenID Connect (OIDC) token binding issues short-lived JSON Web Tokens (JWTs) that identify your Worker. A service that supports OIDC federation verifies these tokens with Cloudflare's public keys. Exchange a token for short-lived cloud credentials, or send it to an API as a bearer token. Your Worker does not need to store a long-lived credential as a [secret](/workers/configuration/secrets/).

:::note
OIDC token bindings are in open beta.
:::

## Configure the binding

To create an OIDC token binding, add an `oidc_tokens` array to your Wrangler configuration file. Each binding issues tokens for one audience:

<WranglerConfig>

```jsonc
{
	"oidc_tokens": [
		{
			"binding": "API_TOKEN",
			"audience": "https://api.example.com",
		},
		{
			"binding": "EXCHANGE_TOKEN",
			"audience": "api://token-exchange",
			"alg": "RS256",
		},
	],
}
```

</WranglerConfig>

- `binding` <Type text="string" /> <MetaInfo text="required" />
  - The name of the binding on the `env` object.
- `audience` <Type text="string" /> <MetaInfo text="required" />
  - The `aud` claim of every token from this binding. Use the value your verifier expects. It must be 1 to 2,048 printable ASCII characters, with no whitespace.
- `alg` <Type text="string" /> <MetaInfo text="optional" />
  - The signing algorithm: `ES256` (the default) or `RS256`. Set `RS256` for verifiers that do not accept ES256.

To get tokens for more than one verifier, add one binding for each audience.

## Get a token

The binding has one method, `getToken()`. It returns a newly signed JWT for the binding's audience. This example sends the token to an API as a bearer token:

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request, env): Promise<Response> {
		const token = await env.API_TOKEN.getToken();
		return fetch("https://api.example.com/v1/orders", {
			headers: { Authorization: `Bearer ${token}` },
		});
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

Many verifiers exchange the token for their own short-lived credentials. This example uses an OAuth 2.0 token exchange ([RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)). For the exact request, refer to your verifier's documentation.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request, env): Promise<Response> {
		const response = await fetch("https://sts.example.com/token", {
			method: "POST",
			body: new URLSearchParams({
				grant_type: "urn:ietf:params:oauth:grant-type:token-exchange",
				subject_token: await env.EXCHANGE_TOKEN.getToken(),
				subject_token_type: "urn:ietf:params:oauth:token-type:jwt",
			}),
		});
		const { access_token } = await response.json<{ access_token: string }>();

		return fetch("https://api.example.com/v1/orders", {
			headers: { Authorization: `Bearer ${access_token}` },
		});
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

Each token is valid for five minutes and has a new `jti` claim. Some verifiers accept each `jti` only once. Call `getToken()` each time you need a token, and do not store tokens across requests.

`wrangler types` generates the `OidcTokenBinding` type for each binding:

```ts
interface OidcTokenBinding {
	getToken(): Promise<string>;
}
```

## Token claims

Each token carries the following claims:

| Claim        | Value                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| `iss`        | `https://oidc.cloudflare.com/accounts/<ACCOUNT_ID>`                                                    |
| `sub`        | `worker:<WORKER_ID>` for a deployed Worker, or `worker:<WORKER_ID>:preview:<PREVIEW_ID>` for a Preview |
| `aud`        | The binding's `audience`                                                                               |
| `iat`        | The time the token was issued                                                                          |
| `nbf`        | The time the token was issued                                                                          |
| `exp`        | Five minutes after `iat`                                                                               |
| `jti`        | A unique ID for the token                                                                              |
| `execution`  | `deployed` for a deployed Worker, or `preview` for a [Preview](/workers/previews/)                     |
| `worker_id`  | The Worker's ID                                                                                        |
| `preview_id` | The Preview's ID, only in tokens from a Preview                                                        |
| `version_id` | The ID of the [Worker version](/workers/versions-and-deployments/) that requested the token            |

The token header has `alg`, `kid`, and `typ`. The `kid` identifies the key that signed the token.

Each account has its own issuer. A trust policy for one account does not accept tokens from another account.

## Configure the verifier

The issuer publishes a discovery document and its public keys:

- Discovery document: `https://oidc.cloudflare.com/accounts/<ACCOUNT_ID>/.well-known/openid-configuration`
- JSON Web Key Set (JWKS): `https://oidc.cloudflare.com/accounts/<ACCOUNT_ID>/.well-known/jwks.json`

To trust tokens from your Worker:

<Steps>

1. Deploy your Worker with its OIDC token binding. A new Worker gets its ID on its first deploy.
2. In your verifier, add the issuer `https://oidc.cloudflare.com/accounts/<ACCOUNT_ID>` as an OIDC identity provider.
3. Set the audience to the binding's `audience`.
4. Allow the subject `worker:<WORKER_ID>`.

</Steps>

Until the verifier trusts the subject, it rejects the Worker's tokens.

:::caution
Match `iss`, `aud`, and `sub` exactly. Do not match `sub` by prefix or wildcard. A pattern such as `worker:<WORKER_ID>*` also matches every Preview of the Worker.
:::

### Find the subject

After a deploy, Wrangler prints the issuer and subject of a Worker that has an OIDC token binding:

<PackageManagers type="exec" pkg="wrangler" args="deploy" />

```txt output
OIDC tokens for this Worker:
  Issuer:  https://oidc.cloudflare.com/accounts/<ACCOUNT_ID>
  Subject: worker:<WORKER_ID>
```

You can also get the Worker ID from the [Workers API](/api/resources/workers/subresources/beta/subresources/workers/methods/list/). It is the `id` of the Worker:

```sh
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/workers" \
	--header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" |
	jq --raw-output '.result[] | select(.name == "my-worker") | .id'
```

The Worker ID does not change when you rename the Worker.

### Signing keys

Cloudflare rotates the signing keys regularly. The JWKS lists every key that can verify a current token. Verifiers that fetch keys from the JWKS pick up new keys automatically. Do not copy a key into your verifier's configuration.

## Verify tokens in your own API

To accept tokens in your own service, verify them with an OIDC or JWT library. This example uses [`jose`](https://github.com/panva/jose) in a Worker:

<TypeScriptExample filename="src/index.ts">

```ts
import { createRemoteJWKSet, jwtVerify } from "jose";

const ISSUER = "https://oidc.cloudflare.com/accounts/<ACCOUNT_ID>";
const JWKS = createRemoteJWKSet(new URL(`${ISSUER}/.well-known/jwks.json`));

export default {
	async fetch(request): Promise<Response> {
		const token = request.headers.get("Authorization")?.replace(/^Bearer /, "");
		if (!token) {
			return new Response("Unauthorized", { status: 401 });
		}
		try {
			await jwtVerify(token, JWKS, {
				issuer: ISSUER,
				audience: "https://api.example.com",
				subject: "worker:<WORKER_ID>",
				algorithms: ["ES256", "RS256"],
			});
		} catch {
			return new Response("Unauthorized", { status: 401 });
		}
		return new Response("OK");
	},
} satisfies ExportedHandler;
```

</TypeScriptExample>

## Previews and versions

[Previews](/workers/previews/) can use OIDC token bindings. Add `oidc_tokens` to the [`previews` block](/workers/previews/configuration/) of your Wrangler configuration file. A Preview's tokens have the subject `worker:<WORKER_ID>:preview:<PREVIEW_ID>`, so a trust policy for the deployed Worker does not accept them. To let a Preview reach a test resource, allow the Preview's subject in a separate trust policy.

Workers with an OIDC token binding do not get [version preview URLs](/workers/versions-and-deployments/version-urls/). A version preview URL would run code that is not deployed with the Worker's identity.

## Local development

OIDC token bindings are not available in local development. `wrangler dev` lists them as not supported, and they do not connect to remote resources. To test with a real verifier, use a [Preview](/workers/previews/).

## Security

- A token is a bearer credential. Anyone who has the token can use it until it expires. Do not log tokens, or send them to services other than the verifier.
- Each binding issues tokens for its own audience only. A Worker cannot request a token for a different audience at runtime.
- [Workers for Platforms](/cloudflare-for-platforms/workers-for-platforms/) does not support OIDC token bindings.
