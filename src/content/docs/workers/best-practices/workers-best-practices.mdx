Every Worker runs in a lightweight V8 isolate with its own memory, CPU limits, and request lifecycle. These best practices help you write Workers that are fast, reliable, observable, and secure. Each recommendation includes code showing the correct pattern.

## Configuration

### Keep your compatibility date current

The `compatibility_date` in your Wrangler configuration controls which runtime features and bug fixes are available to your Worker. Setting it to today's date on new projects ensures you get the latest behavior. Periodically updating it on existing projects gives you access to new APIs and fixes without changing your code.

If you omit `compatibility_date` when uploading via the API, it defaults to `2021-11-02` — missing years of improvements.

<WranglerConfig>

```toml
name = "my-worker"
main = "src/index.ts"
# ✅ Good: use $today for new projects, update periodically for existing ones
compatibility_date = "$today"
```

</WranglerConfig>

For more information, refer to [Compatibility dates](/workers/configuration/compatibility-dates/).

### Enable nodejs_compat

The `nodejs_compat` compatibility flag gives your Worker access to Node.js built-in modules like `node:crypto`, `node:buffer`, `node:stream`, and others. Many libraries depend on these modules, and enabling this flag avoids cryptic import errors at runtime.

Requires `compatibility_date` of `2024-09-23` or later for the full v2 behavior with polyfills and globals.

<WranglerConfig>

```toml
name = "my-worker"
main = "src/index.ts"
compatibility_date = "$today"
# ✅ Good: enable Node.js compatibility
compatibility_flags = ["nodejs_compat"]
```

</WranglerConfig>

For more information, refer to [Node.js compatibility](/workers/runtime-apis/nodejs/).

### Generate binding types with wrangler types

Do not hand-write your `Env` interface. Run `wrangler types` to generate a type definition file that matches your actual Wrangler configuration. This catches mismatches between your config and code at compile time instead of at deploy time.

Re-run `wrangler types` whenever you add or rename a binding.

```bash
wrangler types
```

<TypeScriptExample filename="src/index.ts">

```ts
// ✅ Good: Env is generated by wrangler types and always matches your config
// Do not manually define Env — it drifts from your actual bindings

export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		// env.MY_KV, env.MY_BUCKET, etc. are all correctly typed
		const value = await env.MY_KV.get("key");
		return new Response(value);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

For more information, refer to [wrangler types](/workers/wrangler/commands/#types).

### Store secrets with wrangler secret, not in source

Secrets (API keys, tokens, database credentials) must never appear in your Wrangler configuration or source code. Use `wrangler secret put` to store them securely, and access them through `env` at runtime. Use a `.dev.vars` file for local development — it is automatically excluded from version control.

<WranglerConfig>

```toml
name = "my-worker"
main = "src/index.ts"
compatibility_date = "$today"

# ✅ Good: non-secret configuration lives in version control
[vars]
API_BASE_URL = "https://api.example.com"

# 🔴 Bad: never put secrets here
# API_KEY = "sk-live-abc123..."
```

</WranglerConfig>

```bash
# Store secrets securely
wrangler secret put API_KEY

# For local development, use .dev.vars (gitignored)
# API_KEY=sk-test-abc123
```

For more information, refer to [Secrets](/workers/configuration/secrets/).

### Use wrangler.jsonc for non-secret configuration

Keep environment variables, bindings, routes, and other non-secret configuration in your `wrangler.jsonc` (or `wrangler.toml`) file and commit it to version control. This makes deployments reproducible and auditable. Only use `wrangler secret` for actual secret values.

<WranglerConfig>

```toml
name = "my-worker"
main = "src/index.ts"
compatibility_date = "$today"
compatibility_flags = ["nodejs_compat"]

[vars]
ENVIRONMENT = "production"
LOG_LEVEL = "info"

[[kv_namespaces]]
binding = "CACHE"
id = "abc123"

[[r2_buckets]]
binding = "UPLOADS"
bucket_name = "user-uploads"
```

</WranglerConfig>

## Request and response handling

### Stream request and response bodies

Workers have a [128 MB memory limit](/workers/platform/limits/). Buffering an entire request or response body with `await response.text()` or `await request.arrayBuffer()` will exceed that limit on large payloads, causing your Worker to crash.

Stream data through your Worker instead. Use `TransformStream` to pipe data from a source to a destination without holding it all in memory.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		// 🔴 Bad: buffers the entire response body in memory
		// const response = await fetch("https://api.example.com/large-dataset");
		// const text = await response.text();
		// return new Response(text);

		// ✅ Good: stream the response body through without buffering
		const response = await fetch("https://api.example.com/large-dataset");
		return new Response(response.body, response);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

When you need to transform data as it passes through, use a `TransformStream`:

<TypeScriptExample filename="src/transform.ts">

```ts
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const response = await fetch("https://api.example.com/data");

		// ✅ Good: transform data as a stream without buffering the whole body
		const { readable, writable } = new TransformStream({
			transform(chunk, controller) {
				// Process each chunk as it arrives
				controller.enqueue(chunk);
			},
		});

		// pipeTo() runs concurrently — not awaited so the response streams immediately.
		// Errors on the pipe will close the readable side, surfacing to the client.
		response.body?.pipeTo(writable);
		return new Response(readable, response);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

For more information, refer to [Streams](/workers/runtime-apis/streams/).

### Use waitUntil for work after the response

`ctx.waitUntil()` lets you perform work after the response is sent to the client — analytics, cache writes, non-critical logging, or webhook notifications. This keeps your response fast while still completing background tasks.

There are two common pitfalls: destructuring `ctx` (which loses the `this` binding and throws "Illegal invocation"), and exceeding the 30-second time limit after the response is sent.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(
		request: Request,
		env: Env,
		ctx: ExecutionContext,
	): Promise<Response> {
		const data = await processRequest(request);

		// ✅ Good: send the response immediately, do background work after
		ctx.waitUntil(logToAnalytics(env, data));
		ctx.waitUntil(updateCache(env, data));

		return Response.json(data);
	},
} satisfies ExportedHandler<Env>;

// 🔴 Bad: destructuring ctx loses the `this` binding
// async fetch(request, env, ctx) {
//   const { waitUntil } = ctx; // "Illegal invocation" at runtime
//   waitUntil(somePromise);
// }

async function logToAnalytics(env: Env, data: unknown): Promise<void> {
	await fetch("https://analytics.example.com/events", {
		method: "POST",
		body: JSON.stringify(data),
	});
}

async function updateCache(env: Env, data: unknown): Promise<void> {
	await env.CACHE.put("latest", JSON.stringify(data));
}
```

</TypeScriptExample>

For more information, refer to [Context](/workers/runtime-apis/context/).

### Set cache headers explicitly

Workers responses served through Cloudflare can be cached by default depending on the content type and response headers. If your Worker returns dynamic or sensitive data, set `Cache-Control` headers explicitly to prevent accidental caching.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const user = await getAuthenticatedUser(request, env);

		// ✅ Good: explicitly prevent caching of user-specific data
		return Response.json(user, {
			headers: {
				"Cache-Control": "no-store",
			},
		});
	},
} satisfies ExportedHandler<Env>;

// For static or rarely-changing public data, cache aggressively:
// headers: { "Cache-Control": "public, max-age=3600" }

async function getAuthenticatedUser(
	request: Request,
	env: Env,
): Promise<object> {
	return { id: "user-123", name: "Example User" };
}
```

</TypeScriptExample>

For more information, refer to [How the cache works](/workers/reference/how-the-cache-works/).

## Architecture

### Use bindings for Cloudflare services, not REST APIs

Cloudflare services like R2, KV, D1, Queues, and Workflows are available as [bindings](/workers/runtime-apis/bindings/) — direct, in-process references that require no network hop, no authentication, and no extra latency. Using the REST API from within a Worker wastes time and adds unnecessary complexity.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		// 🔴 Bad: calling the REST API from a Worker
		// const response = await fetch(
		//   "https://api.cloudflare.com/client/v4/accounts/.../r2/buckets/.../objects/my-file",
		//   { headers: { Authorization: `Bearer ${env.CF_API_TOKEN}` } }
		// );

		// ✅ Good: use the binding directly — no network hop, no auth needed
		const object = await env.MY_BUCKET.get("my-file");

		if (!object) {
			return new Response("Not found", { status: 404 });
		}

		return new Response(object.body, {
			headers: {
				"Content-Type":
					object.httpMetadata?.contentType ?? "application/octet-stream",
			},
		});
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

### Use Queues and Workflows for async and background work

Long-running, retriable, or non-urgent tasks should not block a request. Use [Queues](/queues/) to decouple producers from consumers with guaranteed delivery and automatic retries. Use [Workflows](/workflows/) for multi-step, durable processes that survive failures.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const order = await request.json<{ id: string }>();

		// ✅ Good: accept the request immediately, process asynchronously
		await env.ORDER_QUEUE.send({
			orderId: order.id,
			action: "process-payment",
		});

		// ✅ Good: kick off a durable, multi-step workflow for complex processing
		const instance = await env.FULFILLMENT_WORKFLOW.create({
			params: { orderId: order.id },
		});

		return Response.json(
			{
				status: "accepted",
				workflowId: instance.id,
			},
			{ status: 202 },
		);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

### Use service bindings for Worker-to-Worker communication

When one Worker needs to call another, use [service bindings](/workers/runtime-apis/bindings/service-bindings/) instead of making an HTTP request to a public URL. Service bindings are zero-cost, bypass the public internet, and support type-safe RPC.

<TypeScriptExample filename="src/index.ts">

```ts
import { WorkerEntrypoint } from "cloudflare:workers";

// The "auth" Worker exposes RPC methods
export class AuthService extends WorkerEntrypoint {
	async verifyToken(
		token: string,
	): Promise<{ userId: string; valid: boolean }> {
		// Token verification logic
		return { userId: "user-123", valid: true };
	}
}

// The "api" Worker calls the auth Worker via a service binding
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const token = request.headers.get("Authorization")?.replace("Bearer ", "");

		if (!token) {
			return new Response("Unauthorized", { status: 401 });
		}

		// ✅ Good: call another Worker via service binding RPC — no network hop
		const auth = await env.AUTH_SERVICE.verifyToken(token);

		if (!auth.valid) {
			return new Response("Invalid token", { status: 403 });
		}

		return Response.json({ userId: auth.userId });
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

## Observability

### Enable Workers Logs and Traces

Logs and traces make your Worker observable in production. Enable them in your Wrangler configuration and use `head_sampling_rate` to control volume and manage costs. A sampling rate of `1` captures everything; lower it for high-traffic Workers.

Use structured JSON logging with `console.log` — log objects, not strings — so logs are searchable and filterable.

<WranglerConfig>

```toml
name = "my-worker"
main = "src/index.ts"
compatibility_date = "$today"

[observability]
enabled = true

[observability.logs]
# Capture 100% of logs — lower this for high-traffic Workers
head_sampling_rate = 1

[observability.traces]
head_sampling_rate = 0.01  # Sample 1% of traces
```

</WranglerConfig>

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const url = new URL(request.url);

		// ✅ Good: structured JSON logs are searchable and filterable
		console.log(
			JSON.stringify({
				message: "incoming request",
				method: request.method,
				path: url.pathname,
				cf: {
					country: request.cf?.country,
					colo: request.cf?.colo,
				},
			}),
		);

		// 🔴 Bad: unstructured string logs are hard to query
		// console.log("Got a request to " + url.pathname);

		return new Response("OK");
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

For more information, refer to [Workers Logs](/workers/observability/logs/workers-logs/) and [Traces](/workers/observability/traces/).

### Use Tail Workers for durable logging

`console.log` is best-effort — if a Worker crashes or is evicted, in-flight logs can be lost. For logs that must not be dropped (audit trails, billing events, compliance), use a [Tail Worker](/workers/observability/logs/tail-workers/). Tail Workers receive log events asynchronously and can forward them to any destination.

<WranglerConfig>

```toml
# Main Worker configuration
name = "my-worker"
main = "src/index.ts"
compatibility_date = "$today"

# ✅ Good: attach a Tail Worker for durable log delivery
[[tail_consumers]]
service = "my-log-consumer"
```

</WranglerConfig>

<TypeScriptExample filename="src/log-consumer.ts">

```ts
// Tail Worker: receives log events from the main Worker
export default {
	async tail(events: TraceItem[]): Promise<void> {
		for (const event of events) {
			// Forward to your logging service, R2 bucket, or Queue
			await fetch("https://logs.example.com/ingest", {
				method: "POST",
				headers: { "Content-Type": "application/json" },
				body: JSON.stringify({
					scriptName: event.scriptName,
					outcome: event.outcome,
					logs: event.logs,
					exceptions: event.exceptions,
					timestamp: event.eventTimestamp,
				}),
			});
		}
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

## Code patterns

### Do not store request-scoped state in global scope

Workers reuse isolates across requests. A variable set during one request is still present during the next. This causes cross-request data leaks, stale state, and "Cannot perform I/O on behalf of a different request" errors.

Pass state through function arguments or store it on `env` bindings — never in module-level variables.

<TypeScriptExample filename="src/index.ts">

```ts
// 🔴 Bad: global mutable state leaks between requests
// let currentUser: string | null = null;
// let requestHeaders: Headers | null = null;

export default {
	async fetch(
		request: Request,
		env: Env,
		ctx: ExecutionContext,
	): Promise<Response> {
		// 🔴 Bad: storing request-scoped data globally
		// currentUser = request.headers.get("X-User-Id");

		// ✅ Good: pass request-scoped data through function arguments
		const userId = request.headers.get("X-User-Id");
		const result = await handleRequest(userId, env);

		return Response.json(result);
	},
} satisfies ExportedHandler<Env>;

async function handleRequest(userId: string | null, env: Env): Promise<object> {
	return { userId };
}
```

</TypeScriptExample>

For more information, refer to [Workers errors](/workers/observability/errors/#cannot-perform-io-on-behalf-of-a-different-request).

### Keep startup fast

Top-level code in your Worker runs on every cold start and counts against [CPU time limits](/workers/platform/limits/). Avoid heavy computation, large synchronous operations, or eager initialization of resources in module scope. Defer expensive setup to the first request using lazy initialization.

<TypeScriptExample filename="src/index.ts">

```ts
// 🔴 Bad: expensive work at the top level runs on every cold start
// const config = JSON.parse(readFileSync("large-config.json"));
// const decoder = new TextDecoder();
// const precomputed = buildLargeIndex();

// ✅ Good: lazy initialization — runs once on first use, not on cold start
let _client: ApiClient | null = null;

function getClient(env: Env): ApiClient {
	if (!_client) {
		_client = new ApiClient(env.API_BASE_URL);
	}
	return _client;
}

export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const client = getClient(env);
		const result = await client.getData();
		return Response.json(result);
	},
} satisfies ExportedHandler<Env>;

class ApiClient {
	private baseUrl: string;

	constructor(baseUrl: string) {
		this.baseUrl = baseUrl;
	}

	async getData(): Promise<object> {
		const response = await fetch(`${this.baseUrl}/data`);
		return response.json<object>();
	}
}
```

</TypeScriptExample>

### Always await or waitUntil your Promises

A `Promise` that is not `await`ed, `return`ed, or passed to `ctx.waitUntil()` is a floating promise. Floating promises cause silent bugs: dropped results, swallowed errors, and unfinished work. The Workers runtime may terminate your isolate before a floating promise completes.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(
		request: Request,
		env: Env,
		ctx: ExecutionContext,
	): Promise<Response> {
		const data = await request.json();

		// 🔴 Bad: floating promise — result is dropped, errors are swallowed
		// fetch("https://api.example.com/webhook", { method: "POST", body: JSON.stringify(data) });

		// ✅ Good: await if you need the result before responding
		const response = await fetch("https://api.example.com/process", {
			method: "POST",
			body: JSON.stringify(data),
		});

		// ✅ Good: waitUntil if you do not need the result before responding
		ctx.waitUntil(
			fetch("https://api.example.com/webhook", {
				method: "POST",
				body: JSON.stringify(data),
			}),
		);

		return new Response("OK");
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

### Handle nullable binding returns

KV `.get()`, R2 `.get()`, and D1 `.first()` all return `null` when the key or row does not exist. Always check for `null` before using the result. Do not use non-null assertions (`!`) to silence TypeScript — handle the missing case explicitly.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const url = new URL(request.url);
		const key = url.searchParams.get("key") ?? "";

		// 🔴 Bad: assuming the value exists
		// const value = (await env.MY_KV.get(key))!;

		// ✅ Good: handle null explicitly
		const value = await env.MY_KV.get(key);

		if (value === null) {
			return new Response("Not found", { status: 404 });
		}

		return new Response(value);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

### Prefer Workers-compatible libraries

Many Node.js libraries rely on APIs not available in Workers: persistent TCP connections, file system access, or global mutable state. These fail at runtime even if they compile fine. When choosing libraries, prefer ones built for edge runtimes or that use standard `fetch()`.

Common patterns to avoid:

- SDKs that maintain persistent connection pools (most traditional database drivers)
- Libraries that rely on `fs`, `net`, or `child_process`
- HTTP clients that store cookies or state globally across requests

Use Cloudflare-specific adapters when they exist (for example, Prisma with D1, Drizzle with D1, or `pg` with Hyperdrive).

## Security

### Use Web Crypto for secure token generation

The Workers runtime provides the [Web Crypto API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API) for cryptographic operations. Use `crypto.randomUUID()` for unique identifiers and `crypto.getRandomValues()` for random bytes. Never use `Math.random()` for anything security-sensitive — it is not cryptographically secure.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		// 🔴 Bad: Math.random() is predictable and not suitable for security
		// const token = Math.random().toString(36).substring(2);

		// ✅ Good: cryptographically secure random UUID
		const sessionId = crypto.randomUUID();

		// ✅ Good: cryptographically secure random bytes for tokens
		const tokenBytes = new Uint8Array(32);
		crypto.getRandomValues(tokenBytes);
		const token = Array.from(tokenBytes)
			.map((b) => b.toString(16).padStart(2, "0"))
			.join("");

		return Response.json({ sessionId, token });
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

When comparing secret values (API keys, tokens, HMAC signatures), use `crypto.subtle.timingSafeEqual()` to prevent timing side-channel attacks. Do not short-circuit on length mismatch — encode both values to a fixed-size hash first.

<TypeScriptExample filename="src/verify.ts">

```ts
async function verifyToken(
	provided: string,
	expected: string,
): Promise<boolean> {
	const encoder = new TextEncoder();

	// ✅ Good: hash both values to a fixed size, then compare in constant time
	// This avoids leaking the length of the expected value
	const [providedHash, expectedHash] = await Promise.all([
		crypto.subtle.digest("SHA-256", encoder.encode(provided)),
		crypto.subtle.digest("SHA-256", encoder.encode(expected)),
	]);

	return crypto.subtle.timingSafeEqual(providedHash, expectedHash);

	// 🔴 Bad: direct string comparison leaks timing information
	// return provided === expected;
}
```

</TypeScriptExample>

### Do not use passThroughOnException as error handling

`passThroughOnException()` is a fail-open mechanism that sends requests to your origin when your Worker throws an unhandled exception. While it can be useful during migration from an origin server, it hides bugs and makes debugging difficult. Use explicit try/catch blocks with structured error responses instead.

<TypeScriptExample filename="src/index.ts">

```ts
export default {
	async fetch(
		request: Request,
		env: Env,
		ctx: ExecutionContext,
	): Promise<Response> {
		// 🔴 Bad: hides errors by falling through to origin
		// ctx.passThroughOnException();

		// ✅ Good: explicit error handling with structured responses
		try {
			const result = await handleRequest(request, env);
			return Response.json(result);
		} catch (error) {
			const message = error instanceof Error ? error.message : "Unknown error";

			console.error(
				JSON.stringify({
					message: "unhandled error",
					error: message,
					path: new URL(request.url).pathname,
				}),
			);

			return Response.json({ error: "Internal server error" }, { status: 500 });
		}
	},
} satisfies ExportedHandler<Env>;

async function handleRequest(request: Request, env: Env): Promise<object> {
	return { status: "ok" };
}
```

</TypeScriptExample>

## Development and testing

### Test with @cloudflare/vitest-pool-workers

The [`@cloudflare/vitest-pool-workers`](/workers/testing/vitest-integration/) package runs your tests inside the Workers runtime, giving you access to real bindings (KV, R2, D1, Durable Objects) during tests. This catches issues that Node.js-based tests miss — like unsupported APIs or missing compatibility flags.

One known pitfall: the Vitest pool automatically injects `nodejs_compat`, so tests pass even if your Wrangler configuration does not have the flag. Always confirm your `wrangler.jsonc` includes `nodejs_compat` if your code depends on Node.js built-in modules.

<TypeScriptExample filename="test/index.test.ts">

```ts
import { describe, it, expect } from "vitest";
import { env } from "cloudflare:test";

describe("KV operations", () => {
	it("should store and retrieve a value", async () => {
		await env.MY_KV.put("key", "value");
		const result = await env.MY_KV.get("key");
		expect(result).toBe("value");
	});

	it("should return null for missing keys", async () => {
		const result = await env.MY_KV.get("nonexistent");
		// ✅ Good: test the null case explicitly
		expect(result).toBeNull();
	});
});
```

</TypeScriptExample>

For more information, refer to [Testing with Vitest](/workers/testing/vitest-integration/).
