Review how the Workers Vitest integration runs your tests, isolates storage **per test file** (not per individual test), and imports modules.

## Run tests

When you run your tests with the Workers Vitest integration, Vitest will:

1. Read and evaluate your configuration file using Node.js.
2. Run any [`globalSetup`](https://vitest.dev/config/globalsetup) files using Node.js.
3. Collect and sequence test files.
4. For each Vitest project, depending on its configured isolation and concurrency, start one or more [`workerd`](https://github.com/cloudflare/workerd) processes, each running one or more Workers.
5. Run [`setupFiles`](https://vitest.dev/config/setupfiles) and test files in `workerd` using the appropriate Workers.
6. Watch for changes and re-run test files using the same Workers if the configuration has not changed.

## Isolation model

Storage isolation in Vitest 4 and later is **per test file**, not per individual test. Each test file (`*.test.ts` or `*.spec.ts`) receives its own isolated storage environment, so writes to KV, R2, D1, Durable Objects, or the Cache API in one test file are not visible to other test files.

:::caution[Storage is shared across tests in the same file]

Storage is **not** automatically reset between individual `test()` or `it()` blocks within the same test file. Any data written in one test remains visible to subsequent tests in that file until you reset or namespace it explicitly.

In earlier Vitest 3 versions of `@cloudflare/vitest-pool-workers` (v0.12.x and earlier), the `isolatedStorage` option rolled back storage after each individual test. In Vitest 4 and later (`@cloudflare/vitest-pool-workers` v0.13.0+ and `@cloudflare/vitest-plugin`), the `isolatedStorage` and `singleWorker` options were removed to match standard Vitest per-file isolation, and setting `isolatedStorage: true` has no effect.

:::

The Workers Vitest integration reuses Workers and their module caches between test runs where possible. A copy of all auxiliary `workers` exists in each `workerd` process.

By default, test files run concurrently. To make test files share the same storage (for example, for integration tests that depend on shared state), use the Vitest flags `--max-workers=1 --no-isolate`.

### Clean up state between tests in the same file

Because tests in the same file share storage bindings, use one of the following patterns to prevent state from leaking between `test()` or `it()` blocks:

- **Reset storage in `beforeEach()` or `afterEach()`**: Delete rows from D1 tables, remove KV keys or R2 objects created by the test, or call [`reset()`](/workers/testing/vitest-integration/test-apis/#durable-objects) from `cloudflare:test` to delete all data across attached bindings.
- **Use unique IDs or key prefixes per test**: Generate a unique identifier with `crypto.randomUUID()` for Durable Object names (`idFromName()`) or KV and R2 key prefixes so tests do not collide within the shared storage environment.
- **Split tests into separate files**: Move tests that require a completely clean storage environment (for example, testing initial migrations or listing all keys in a namespace) into separate `*.test.ts` files so each file receives its own isolated storage.

The following example combines `afterEach()` cleanup for D1 tables with unique per-test IDs for Durable Objects, KV keys, and R2 objects:

<TypeScriptExample filename="test/storage.test.ts">
```ts
import { env } from "cloudflare:workers";
import { afterEach, describe, expect, it } from "vitest";

describe("isolated state within a test file", () => {
	// Reset shared D1 tables between tests in the same file
	afterEach(async () => {
		await env.DB.exec("DELETE FROM items");
	});

	it("writes to D1 without leaking rows to the next test", async () => {
		await env.DB.prepare("INSERT INTO items (id, name) VALUES (?, ?)")
			.bind("1", "first")
			.run();

		const { results } = await env.DB.prepare("SELECT * FROM items").all();
		expect(results).toHaveLength(1);
	});

	it("uses unique IDs for Durable Objects, KV keys, and R2 objects", async () => {
		const testId = crypto.randomUUID();

		// Each test addresses its own Durable Object instance
		const stub = env.COUNTER.get(env.COUNTER.idFromName(testId));
		const response = await stub.fetch("https://example.com/increment");
		expect(await response.text()).toBe("1");

		// Prefix KV and R2 keys with the per-test ID to avoid collisions
		const kvKey = `${testId}:status`;
		await env.KV.put(kvKey, "ready");
		expect(await env.KV.get(kvKey)).toBe("ready");

		const r2Key = `${testId}/report.txt`;
		await env.BUCKET.put(r2Key, "ok");
		const object = await env.BUCKET.get(r2Key);
		expect(await object?.text()).toBe("ok");
	});
});
```
</TypeScriptExample>

To wipe all data across every attached storage binding between tests in a file, call `reset()` from `cloudflare:test` inside `afterEach()`:

<TypeScriptExample filename="test/reset.test.ts">
```ts
import { reset } from "cloudflare:test";
import { afterEach } from "vitest";

afterEach(async () => {
	await reset();
});
```
</TypeScriptExample>

## Modules

Each Worker has its own module cache. As Workers are reused between test runs, their module caches are also reused. Vitest invalidates parts of the module cache at the start of each test run based on changed files.

The Workers Vitest plugin runs code inside a Cloudflare Worker that Vitest would usually run inside a [Node.js Worker thread](https://nodejs.org/api/worker_threads.html). To make this possible, the plugin **automatically injects** the [`nodejs_compat`](/workers/configuration/compatibility-flags/#nodejs-compatibility-flag), [`no_nodejs_compat_v2`] and [`export_commonjs_default`](/workers/configuration/compatibility-flags/#commonjs-modules-do-not-export-a-module-namespace) compatibility flags. This is the minimal compatibility setup that still allows Vitest to run correctly, but without pulling in polyfills and globals that are not required. If you already have a Node.js compatibility flag defined in your configuration, the Vitest plugin does not add those flags.

:::caution

Using the Workers Vitest plugin may cause your Worker to behave differently when deployed because the `nodejs_compat` flag is enabled by default. This means that Node.js-specific APIs and modules are available when running your tests. However, Cloudflare Workers do not support these Node.js APIs in the production environment unless you specify this flag in your Worker configuration.

If you do not have a `nodejs_compat` or `nodejs_compat_v2` flag in your configuration and you import a Node.js module in your Worker code, your tests may pass, but you will find that you will not be able to deploy this Worker, as the upload call (either via the REST API or via Wrangler) will throw an error.

However, if you use Node.js globals that are not supported by the runtime, your Worker upload will be successful, but you may see errors in production code. Let's create a contrived example to illustrate the issue.

The Wrangler configuration file does not specify either `nodejs_compat` or `nodejs_compat_v2`:

<WranglerConfig>
```jsonc
{ "name": "test",
	"main": "src/index.ts",
	"upload_source_maps": true,
	"compatibility_date": "$today"
	# no nodejs_compat flags here
}
```
</WranglerConfig>

In our `src/index.ts` file, we use the `process` object, which is a Node.js global, unavailable in the Workerd runtime:

```typescript
export default {
	async fetch(request, env, ctx): Promise<Response> {
		process.env.TEST = "test";
		return new Response(process.env.TEST);
	},
} satisfies ExportedHandler<Env>;
```

The test is a simple assertion that the Worker managed to use `process`.

```typescript
it('responds with "test"', async () => {
	const response = await exports.default.fetch("https://example.com/");
	expect(await response.text()).toMatchInlineSnapshot(`"test"`);
});
```

Now, if we run `npm run test`, we see that the tests will _pass_:

```
 ✓ test/index.spec.ts (1)
   ✓ responds with "test"

 Test Files  1 passed (1)
      Tests  1 passed (1)
```

And we can run `wrangler dev` and `wrangler deploy` without issues. It _looks like_ our code is fine. However, this code will fail in production as `process` is not available in the Workerd runtime.

To fix the issue, we either need to avoid using Node.js APIs, or add the `nodejs_compat` flag to our Wrangler configuration.

:::
