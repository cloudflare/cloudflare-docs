`createTestServer()` from `@cloudflare/test-server` works like Wrangler's `createTestHarness()`, but it runs each Worker from its project's Build Output, which [`cf build`](/cf/projects/#build) writes. Your tests then exercise the build that you deploy.

## Install the package

<PackageManagers pkg="@cloudflare/test-server" dev />

Import `createTestServer()` from the new package in place of Wrangler's `createTestHarness()`. The `TestHarness` and `TestHarnessOptions` types become `TestServer` and `TestServerOptions`:

```diff
- import { createTestHarness } from "wrangler";
+ import { createTestServer } from "@cloudflare/test-server";
```

## Run each project's Build Output

Build each project with `cf build`. Then replace `configPath` with `projectDir`, the directory that contains the project's Build Output:

```diff
- const server = createTestHarness({
+ const server = createTestServer({
	workers: [
-		{ configPath: "./workers/web/wrangler.jsonc" },
-		{ configPath: "./workers/api/wrangler.jsonc" },
+		{ projectDir: "./workers/web" },
+		{ projectDir: "./workers/api" },
	],
});
```

List every Worker that the tests use, including other Workers from the same build, which you select with `name`.

Build once and test the production build. The `env` and `prebuiltWorkerDir` options are gone. To test a [mode](/cf/projects/#modes), build the project in that mode.

## Replace test values with `envOverrides`

`vars`, `secrets`, and `bindingOverrides` become one `envOverrides` option, written as in `cloudflare.config.ts`:

```diff
+ import { bindings } from "cf/config";

{
-	configPath: "./workers/web/wrangler.jsonc",
-	vars: { API_HOST: "http://localhost:8787" },
-	secrets: { API_TOKEN: "test-token" },
-	bindingOverrides: { BROWSER: "mock-browser" },
+	projectDir: "./workers/web",
+	envOverrides: {
+		API_HOST: bindings.text("http://localhost:8787"),
+		API_TOKEN: bindings.text("test-token"),
+		BROWSER: bindings.worker({ worker: "mock-browser" }),
+	},
}
```

`envOverrides` can only replace bindings that the Worker declares. Adding a binding, which Wrangler's `vars` and `secrets` allowed, is an error, and a binding cannot be removed. A replacement must be able to stand in for the binding: a variable or secret takes `bindings.text()` or `bindings.json()`, a Durable Object takes another Durable Object, and any other binding takes one of its own type, such as a local KV namespace for a remote one, or `bindings.worker()` to mock it.

## Other changes

- **Secrets:** Only secrets that `cloudflare.config.ts` declares with `bindings.secret()` read `.dev.vars` and `.env`. Other keys in those files are ignored and no longer override variables, unlike Wrangler, which binds every key unless `secrets.required` is set. Declare the secret, or set its value with `envOverrides`.
- **Credentials:** Remote bindings use the same credentials as `cf`. If you have only logged in with Wrangler, run `cf auth login`.
- **Errors:** An uncaught Worker error is a `500` response from `fetch()`, as in production, instead of a rejected promise.
- **D1 migrations:** `applyD1Migrations()` takes `dir`, `pattern`, and `table` options, as in `cf d1 migrations apply`, instead of reading the Wrangler configuration. It does not migrate a remote D1 database, so replace one with a local database in `envOverrides`.
- **Durable Objects and Workflows:** `listDurableObjectIds()`, `evictDurableObject()`, `getDurableObjectStorage()`, `introspectWorkflow()`, and `introspectWorkflowInstance()` take the export name, not a binding name. A Workflow no longer needs a binding to be introspected.
- **Inline Workers:** An inline Worker takes Miniflare's Worker configuration as `miniflareConfig`, which Miniflare runs as given, instead of an inline Wrangler configuration. Each module's code goes in `manifest`, and each binding takes the value to use, such as `{ type: "text", value }` rather than a secret. Inline Workers do not read `.dev.vars` or `.env`.
- **Updates:** `update()` can change the number of Workers.
- **Types:** `getWorker<typeof import("./cloudflare.config")>()` infers a Worker's types from its configuration. Wrangler's `getWorker<Env, Module>()` becomes `getEnv<Env>()` and `getExport<Export>()`, where `Export` can be the export's methods, such as `getExport<{ getMessage(): string }>()`.
- **Runtime:** The package is ESM-only, and Bun is not supported.
