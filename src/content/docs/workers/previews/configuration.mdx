When you create a branch, Git gives you a copy of your code. Previews work the same way — when you run `npx wrangler preview`, you get a running deployment with your branch's code and a copy of your [Base configuration](#setting-your-previews-base-configuration).

Each Preview owns its copy, so you can add, remove, or update any setting — variables, secrets, bindings, observability, and runtime — without affecting other Previews.

This page covers where Preview configuration lives. For how data and state behave after you bind a Preview to KV, D1, R2, Durable Objects, Containers, or other resources, refer to [Resources and isolation](/workers/previews/resources/).

## Setting your Previews Base configuration

You can set your Base configuration in the dashboard or your Wrangler configuration file — whichever you use for production, use for Previews. For a step-by-step setup walkthrough, refer to [Get started](/workers/previews/get-started/#step-1-configure-previews-base-settings).

## Wrangler configuration file

Your Wrangler file has production settings and a `previews` block. Production settings stay outside the block. Anything your Preview needs goes inside the `previews` block, pointed at a staging or test resource.

If `wrangler preview` creates a Preview URL but warns that bindings are missing, the URL is live but the runtime configuration is incomplete. Copy the missing bindings into the `previews` block below, using Preview-safe values and test resources. For resource sharing behavior, refer to [Resources and isolation](/workers/previews/resources/).

<WranglerConfig>

```jsonc
{
  "vars": {
    "ENVIRONMENT": "production"
  },
  "r2_buckets": [
    {
      "binding": "UPLOADS",
      "bucket_name": "prod-uploads"
    }
  ],
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    },
    "r2_buckets": [
      {
        "binding": "UPLOADS",
        "bucket_name": "r2-staging"
      }
    ]
  }
}
```

</WranglerConfig>

Set your `previews` block on your production branch (or wherever you branch from), so when you create a new branch it carries that configuration over. When you run `wrangler preview`, the `previews` block on that branch is always the source of truth.

Your Wrangler configuration does not sync to the Previews Base section in the dashboard — if you see it empty there, that is expected. You will still see each individual Preview's settings in the dashboard once it has been deployed.

### What goes in `previews`

If your production Worker already has settings in your Wrangler file, use this table to decide what needs a copy in the `previews` block.

| If your production config has...                                   | Put this in `previews`                                                                                                                                                      |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vars`                                                             | Add `previews.vars` with Preview values.                                                                                                                                    |
| Secrets                                                            | Add Preview secrets in the dashboard or with [`wrangler preview secret put`](/workers/wrangler/commands/workers/#preview-secret-put). Do not put secret values in Wrangler. |
| [Storage and data bindings](/workers/previews/resources/#resource-bindings) | Add the same binding name under `previews`, pointed at a Preview-safe resource. Examples: KV, D1, R2, Hyperdrive, Vectorize, Analytics Engine, Pipelines, Secrets Store.    |
| [Workflows](/workers/previews/resources/#resource-bindings)         | Add a Workflow binding under `previews`. Use a different Workflow name if the Preview needs isolated instances.                                                             |
| Queue producers                                                    | Add `previews.queues.producers`, pointed at a Preview-safe queue.                                                                                                            |
| [Service bindings](/workers/previews/resources/#service-bindings)   | Add the binding only if the Preview needs it. It currently points at the bound Worker's production deployment.                                                               |
| [Durable Objects](/workers/previews/resources/#durable-objects)     | Keep classes and migrations at the top level. Add `previews.durable_objects.bindings` only if your code reads the binding from `env`.                                        |
| [Containers](/workers/previews/resources/#containers)               | Keep `containers` and migrations at the top level. Add the Durable Object binding under `previews` only if your code reads the container binding from `env`.                 |
| [Cloudflare API bindings](#cloudflare-api-bindings)                | Add under `previews` if your code reads it from `env`. No staging resource to create.                                                                                        |
| `observability`, `tail_consumers`, `logpush`, `limits`, `define`   | Add these to `previews` only if you want Preview-specific values.                                                                                                            |
| `assets`                                                           | Leave at the top level, even if you use an `ASSETS` binding. `wrangler preview` uploads assets from the branch you are previewing.                                           |
| `compatibility_date`, `compatibility_flags`, `placement`           | Leave them at the top level.                                                                                                                                                |
| Queue consumers, Cron Triggers, production routes                  | Do not add to `previews`. These do not target Previews today. For Preview hostnames, refer to [Custom domains](/workers/previews/custom-domains/).                            |

For sharing and isolation behavior after a binding exists, refer to [Resources and isolation](/workers/previews/resources/). For unsupported invocation types, refer to [Limitations](/workers/previews/limitations/).

### Cloudflare API bindings

Bindings like `ai`, `browser`, `images`, `stream`, `media`, `worker_loaders`, and `version_metadata` give Preview code access to Cloudflare APIs. Unlike resource bindings, there is no staging resource to create — add the binding to the `previews` block if your code reads it from `env`.

<WranglerConfig>

```jsonc
{
  "assets": {
    "directory": "./dist",
    "binding": "ASSETS"
  },
  "previews": {
    "ai": {
      "binding": "AI"
    },
    "browser": {
      "binding": "BROWSER"
    },
    "images": {
      "binding": "IMAGES"
    }
  }
}
```

</WranglerConfig>

### Secrets

Secrets cannot be stored in Wrangler configuration files. Use these commands to manage them:

| I want to                                  | Command                                                                                                                          |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Add a secret to the **Base configuration** | [`npx wrangler preview base-config secret put SECRET_NAME`](/workers/wrangler/commands/workers/#preview-base-config-secret-put)  |
| Add a secret to **one Preview**            | [`npx wrangler preview secret put SECRET_NAME --name <preview>`](/workers/wrangler/commands/workers/#preview-secret-put)         |
| List secrets for **one Preview**           | [`npx wrangler preview secret list --name <preview>`](/workers/wrangler/commands/workers/#preview-secret-list)                  |
| Remove a secret                            | Replace `put` with [`delete`](/workers/wrangler/commands/workers/#preview-secret-delete) in the commands above                  |
| Bulk upload secrets                        | [`npx wrangler preview secret bulk secrets.json --name <preview>`](/workers/wrangler/commands/workers/#preview-secret-bulk)     |

The `--name` flag defaults to the current git branch if omitted. For `bulk`, setting a key to `null` deletes that secret.

If your team uses [Wrangler environments](/workers/wrangler/environments/), refer to [Compare workflows](/workers/previews/compare-workflows/#wrangler-environments) for guidance on creating Previews under each environment.
