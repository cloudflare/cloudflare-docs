A Preview can have its own variables, secrets, bindings, observability, and runtime configuration. These are separate from production, and can be configured in the [Wrangler configuration file](/workers/wrangler/configuration/), the [dashboard](#dashboard), or through the API.

## Set a base configuration

Previews can be configured one at a time. If you want new Previews to start with the same variables, secrets, and bindings, you can set a base configuration.

In the same way a Git branch starts from a base branch, a new Preview starts with a copy of the base configuration when you use one. After a Preview is created, it owns its copy. You can add, remove, or update settings on that Preview without affecting other Previews.

<PreviewsConfigDiagram />

Adding, removing, or updating values in a base configuration applies to new Previews by default. If you want existing Previews to receive the change on their next deployment, choose to apply the change to existing Previews.

| Change this            | When to use it                    | What is affected                                                                                    |
| ---------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------- |
| Base configuration     | Set what new Previews start from  | New Previews by default; existing Previews on their next deployment if you apply the change to them |
| One Preview's settings | Change one branch or pull request | Only that Preview                                                                                   |

## Wrangler configuration file

### Variables and bindings

Add a `previews` block to your Wrangler file for Preview-specific variables and bindings. Keep production configuration at the top level, and put Preview configuration inside `previews`.

<WranglerConfig>

```jsonc
{
  "vars": {
    "ENVIRONMENT": "production"
  },
  "r2_buckets": [
    {
      "binding": "UPLOADS",
      "bucket_name": "prod-uploads"
    }
  ],
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    },
    "r2_buckets": [
      {
        "binding": "UPLOADS",
        "bucket_name": "preview-uploads"
      }
    ]
  }
}
```

</WranglerConfig>

### Secrets

Secrets cannot be stored in Wrangler configuration files. Use Wrangler commands to add or remove secrets in the base configuration or for one Preview. Each per-Preview secret change patches the latest deployment and creates a new deployment that goes live immediately.

| I want to                                            | Command                                                           |
| ---------------------------------------------------- | ----------------------------------------------------------------- |
| Add or update a secret in the **base configuration** | `npx wrangler preview base-config secret put SECRET_NAME`         |
| Remove a secret from the **base configuration**      | `npx wrangler preview base-config secret delete SECRET_NAME`      |
| Add or update a secret for **one Preview**           | `npx wrangler preview secret put SECRET_NAME --name <preview>`    |
| Remove a secret for **one Preview**                  | `npx wrangler preview secret delete SECRET_NAME --name <preview>` |
| List secrets for **one Preview**                     | `npx wrangler preview secret list --name <preview>`               |
| Bulk upload secrets for **one Preview**              | `npx wrangler preview secret bulk secrets.json --name <preview>`  |

The `--name` flag defaults to the current git branch if omitted. For `bulk`, setting a key to `null` in JSON format deletes that secret.

### How Wrangler applies Preview settings

When you run `wrangler preview`, Wrangler reads the `previews` block from your current branch and applies those settings to that Preview. Those settings are pushed to the API and appear in the dashboard under that individual Preview. The Preview name decides which Preview receives the settings. For details, refer to [Preview names](/workers/previews/#preview-names).

Running `wrangler deploy` updates production with your top-level Wrangler configuration. It does not update the Preview base configuration in the dashboard. If you check the dashboard and do not see your Preview settings reflected in the base configuration, that is intentional — your Wrangler configuration file is the single source of truth for Preview settings. There is no separate command to push to the base configuration, and nothing outside your Wrangler file is part of your Preview configuration. Everything your Preview needs lives in your Wrangler file and is version-controlled alongside your code.

## Dashboard

In the dashboard, select **Production** from the breadcrumb at the top of your Worker, then go to **Settings**. When you add or edit a variable, secret, or binding, use the **Environments** dropdown to choose where it applies — **Production**, **Preview**, or both.

Selecting **Preview** updates the base configuration. For example, to rotate a secret for Previews, add the secret with **Preview** selected. Every future Preview starts with the new value.

### Individual Preview

Select a Preview from the breadcrumb, then go to **Settings**. Changes here apply to that Preview only. Nothing else is affected.

Use this when one branch needs different configuration. For example, a branch that tests a billing provider can use a different `BILLING_API_KEY` without changing other Previews.
