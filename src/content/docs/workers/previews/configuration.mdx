When you create a branch, Git gives you a copy of your code. Previews work the same way — each Preview gets its own copy of your code **and** its configuration (variables, secrets, bindings). Production is never affected.

Your production settings do not carry over to Previews. If your code reads a binding from `env`, you need to declare it for Previews too — otherwise it will not exist at runtime.

![Diagram showing main branch with code and production config branching into two feature Previews, each with their own copy of code and preview config](~/assets/images/workers/previews/preview-branching.svg)

## Base configuration

Every new Preview needs variables, secrets, and bindings. Instead of setting these up from scratch each time, you can define a base configuration that new Previews start from. After a Preview is created, it owns its copy — you can change one Preview without affecting others.

<PreviewsConfigDiagram />

How you set the base configuration depends on your workflow:

| How you create Previews  | Source of truth                     | How to update it                                  |
| ------------------------ | ----------------------------------- | ------------------------------------------------- |
| `wrangler preview` or CI | The `previews` block in your branch | Edit the Wrangler file and run `wrangler preview` |
| Dashboard                | The dashboard base configuration    | Edit Preview settings in the dashboard            |
| API                      | The API base configuration          | Use the Preview API                               |

The dashboard base configuration and the Wrangler `previews` block are independent — they do not sync with each other. Pick one.

## Wrangler configuration file

Your Wrangler file has production settings and a `previews` block. Production settings stay outside the block. Anything your Preview needs goes inside the `previews` block, pointed at a staging or test resource.

<WranglerConfig>

```jsonc
{
  "vars": {
    "ENVIRONMENT": "production"
  },
  "r2_buckets": [
    {
      "binding": "UPLOADS",
      "bucket_name": "prod-uploads"
    }
  ],
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    },
    "r2_buckets": [
      {
        "binding": "UPLOADS",
        "bucket_name": "preview-uploads"
      }
    ]
  }
}
```

</WranglerConfig>

The `previews` block in your branch is the source of truth for that Preview. When you run `wrangler preview`, Wrangler reads this block and applies it. There is no command to push it to the dashboard — to set defaults for future branches, update the `previews` block on your main branch and let Git carry it forward.

### What you need to restate and what is shared

Most settings need to be restated in the `previews` block. A few are shared automatically.

| Configuration                                                      | Shared with production? | What to do                                                                                          |
| ------------------------------------------------------------------ | ----------------------- | --------------------------------------------------------------------------------------------------- |
| `vars`                                                             | No                      | Add to `previews.vars`                                                                              |
| Secrets                                                            | No                      | Use `wrangler preview secret put`                                                                   |
| KV, D1, R2, Hyperdrive, Vectorize, Queues, service bindings        | No                      | Restate each binding in `previews`, pointed at a staging resource                                   |
| Durable Object `env` bindings                                      | No                      | Restate in `previews.durable_objects.bindings`. Missing bindings cause 1101 errors                  |
| Durable Object classes and migrations                              | Yes                     | Keep with your production config                                                                    |
| Containers                                                         | Yes                     | Keep with your production config. Add the DO binding in `previews` if your code reads it from `env` |
| `compatibility_date`, `compatibility_flags`, `assets`, `placement` | Yes                     | Keep with your production config                                                                    |
| `limits`, `observability`, `logpush`, `tail_consumers`, `define`   | No                      | Add to `previews` if you want Preview-specific values                                               |
| Cron Triggers, routes, queue consumers                             | Not applicable          | These do not target Previews yet                                                                    |

### Secrets

Secrets cannot be stored in Wrangler configuration files. Use these commands to manage them:

| I want to                                  | Command                                                          |
| ------------------------------------------ | ---------------------------------------------------------------- |
| Add a secret to the **base configuration** | `npx wrangler preview base-config secret put SECRET_NAME`        |
| Add a secret to **one Preview**            | `npx wrangler preview secret put SECRET_NAME --name <preview>`   |
| List secrets for **one Preview**           | `npx wrangler preview secret list --name <preview>`              |
| Remove a secret                            | Replace `put` with `delete` in the commands above                |
| Bulk upload secrets                        | `npx wrangler preview secret bulk secrets.json --name <preview>` |

The `--name` flag defaults to the current git branch if omitted. For `bulk`, setting a key to `null` deletes that secret.

### Wrangler environments

You can keep long-lived Wrangler environments like `production` and `staging` and still use Previews for pull requests.

| Command                              | Result                                               |
| ------------------------------------ | ---------------------------------------------------- |
| `npx wrangler preview`               | Creates a Preview for the main Worker                |
| `npx wrangler preview --env staging` | Creates a Preview for the staging environment Worker |

Environment blocks and Preview settings are separate. If the Preview needs a binding, declare it in the `previews` block. For a comparison, refer to [Previews, Version URLs, and Wrangler environments](/workers/configuration/compare-preview-workflows/).

## Dashboard

In the dashboard, go to your Worker's **Settings**. When you add or edit a variable, secret, or binding, use the **Environments** dropdown to choose where it applies — **Production**, **Preview**, or both.

<span className="font-semibold text-red-600">
	&lt;input screenshot of Worker Settings with the environment picker showing
	Production and Preview options&gt;
</span>

Selecting **Preview** updates the base configuration. Every future Preview starts with the new value.

### One Preview

To change settings for a single branch, select that Preview from the breadcrumb at the top of your Worker, then go to **Settings**. Changes here apply to that Preview only.
