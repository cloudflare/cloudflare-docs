## Shared Preview Settings

Think about Preview settings like branches in a repository.

Shared Preview Settings are the starting config for new Preview branches. When Cloudflare creates a Preview, it copies the shared settings into that Preview. From then on, that Preview has its own settings and can change without changing the shared settings or other Previews.

Use Shared Preview Settings for common settings across Preview branches. Use one Preview's settings for exceptions. When you add or change a setting, choose where it should apply:

| I want this setting to apply to...   | Choose this target                                    |
| ------------------------------------ | ----------------------------------------------------- |
| Future Preview branches              | Shared Preview Settings                               |
| One branch or pull request Preview   | This Preview                                          |
| Some existing Preview branches       | Selected Preview branches                             |
| All existing Preview branches        | All existing Preview branches                         |
| Existing and future Preview branches | Shared Preview Settings and existing Preview branches |

Changing Shared Preview Settings changes the starting config copied into future Preview branches. It does not rewrite Preview branches that already exist.

For example:

- Add `API_HOST` to Shared Preview Settings when every future Preview should call the same test API.
- Add `API_HOST` to one Preview when only `feature/login` should call a different API.
- Add a test D1 binding to one Preview when only that branch needs temporary data.

Workers Builds, Wrangler, external CI, and the API all use the same Preview settings. You do not need a different settings model for each way you create a Preview.

## Secrets

Secrets are never stored in Wrangler config files.

Use one-Preview secrets when only a branch needs access to a test credential. Use Shared Preview Settings when every new Preview branch should receive the same secret. Existing Preview branches keep their own secrets.

## Dashboard, Wrangler, and API

You can manage Preview settings from the dashboard, Wrangler, or the API. They all change the same Preview settings.

API users should follow the same model: update Shared Preview Settings for future Preview branches, update one Preview branch when only that branch should change, or apply a change to existing Preview branches when current Previews need the same update. Changing Shared Preview Settings does not change existing Preview branches unless the request also targets existing Preview branches.

| What you want to change              | API target                                            |
| ------------------------------------ | ----------------------------------------------------- |
| Future Preview branches              | Shared Preview Settings                               |
| One Preview branch                   | One Preview branch                                    |
| Selected existing Preview branches   | Selected Preview branches                             |
| All existing Preview branches        | All existing Preview branches                         |
| Existing and future Preview branches | Shared Preview Settings and existing Preview branches |

### Conflict warnings

If the dashboard, Wrangler, or API changed the same setting, Cloudflare warns before applying a change. Treat that warning as a signal to choose which value should win before continuing.

In CI, do not ignore Preview settings warnings. Review command output and configure your workflow to stop when Wrangler exits with an error.

For fewer surprises:

- Choose one place to manage each category of settings.
- Keep non-secret shared settings in Wrangler config if your team reviews configuration through Git.
- Keep secrets in the dashboard, API, or Wrangler secret commands.
- Review diffs and warnings before applying changes from another place.

## Preview URL routing

The top-level `preview_urls` setting controls routing to `workers.dev` Preview URLs and Deployment URLs.

When `preview_urls` is not set, Preview URL routing follows your `workers_dev` setting:

- If `workers_dev` is enabled, Preview URLs are enabled.
- If `workers_dev` is disabled, Preview URLs are disabled.
- Set `preview_urls` explicitly when you want Preview URL routing to differ from `workers_dev`.

Disabling Preview URLs disables routing to `workers.dev` Preview URLs and Deployment URLs. Custom domain Preview URLs use separate custom domain settings. For details, refer to [Custom domains](/workers/previews/custom-domains/).

### Dashboard

To enable or disable Preview URLs:

1. In the Cloudflare dashboard, go to **Workers & Pages**.
2. Select your Worker.
3. Go to **Settings** > **Domains & Routes**.
4. Find **Preview URLs**.
5. Select **Enable** or **Disable**.

### Wrangler

To enable Preview URLs, add `preview_urls` to your Wrangler config:

<WranglerConfig>

```jsonc
{
  "preview_urls": true
}
```

</WranglerConfig>

To disable Preview URLs:

<WranglerConfig>

```jsonc
{
  "preview_urls": false
}
```

</WranglerConfig>

## Wrangler config

Use the `previews` block when you want non-secret Preview settings reviewed and versioned with your code.

Wrangler sends the `previews` block when it creates or updates a Preview.

Everything outside the `previews` block is production configuration. Everything inside the `previews` block is Preview configuration.

<WranglerConfig>

```jsonc
{
  "vars": {
    "ENVIRONMENT": "production"
  },
  "kv_namespaces": [
    {
      "binding": "CACHE",
      "id": "prod-kv-id"
    }
  ],
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    },
    "kv_namespaces": [
      {
        "binding": "CACHE",
        "id": "preview-kv-id"
      }
    ]
  }
}
```

</WranglerConfig>

Your Worker code stays the same. `env.CACHE` works in production and Previews. Each environment points that binding at a different resource.

:::note
Production bindings are not automatically copied into Previews. Configure each binding that should be available to Preview branches.
:::

## Per-branch overrides

Wrangler reads the config from the branch being deployed. To test a setting on one branch, edit the `previews` block on that branch and run `wrangler preview`.

Other Previews are not modified.

When the branch lands, the change either becomes part of the shared config on your main branch or disappears with the branch.

## Update Shared Preview Settings from Wrangler config

Use `wrangler preview-defaults push` to update Shared Preview Settings from the `previews` block in your Wrangler config.

This updates Shared Preview Settings for future Preview branches. Existing Preview branches keep their own settings unless you also apply the change to existing Preview branches.

Secrets are not stored in Wrangler config files and are not pushed from the `previews` block.

## Auto-provisioning

For KV, D1, and R2, you can omit the resource identifier in your `previews` block and Wrangler can create a new resource the first time you run `wrangler preview`.

| Binding         | Omit this field | Wrangler creates    |
| --------------- | --------------- | ------------------- |
| `kv_namespaces` | `id`            | A new KV namespace. |
| `d1_databases`  | `database_name` | A new D1 database.  |
| `r2_buckets`    | `bucket_name`   | A new R2 bucket.    |

Other resource types must be created manually before referencing them in the `previews` block.

## Wrangler environments

If you use [Wrangler environments](/workers/wrangler/environments/), you can define `env.<name>.previews` to give one environment different Preview settings.

<WranglerConfig>

```jsonc
{
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    }
  },
  "env": {
    "staging": {
      "previews": {
        "vars": {
          "ENVIRONMENT": "staging-preview"
        }
      }
    }
  }
}
```

</WranglerConfig>

Use Wrangler environments for persistent staging or production-style Workers. Use Previews for branch and pull request copies.

You do not need to create a Wrangler environment to use Previews. Use both only when you need a persistent environment, such as `staging`, and branch Previews for that environment.
