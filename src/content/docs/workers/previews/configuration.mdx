When you create a branch, Git gives you a copy of your code. Previews work the same way — when you run `npx wrangler preview`, you get a running deployment with your branch's code and a copy of your [Base configuration](#setting-your-previews-base-configuration).

Each Preview owns its copy, so you can add, remove, or update any setting — variables, secrets, bindings, observability, and runtime — without affecting other Previews.

![Diagram showing main branch with code and production config branching into two feature Previews, each with their own copy of code and preview config](~/assets/images/workers/previews/preview-branching.svg)

## Setting your Previews Base configuration

You can set your Base configuration in the dashboard or your Wrangler configuration file — whichever you use for production, use for Previews. For a step-by-step setup walkthrough, refer to [Get started](/workers/previews/get-started/#step-1-configure-previews-base-settings).

## Wrangler configuration file

Your Wrangler file has production settings and a `previews` block. Production settings stay outside the block. Anything your Preview needs goes inside the `previews` block, pointed at a staging or test resource.

<WranglerConfig>

```jsonc
{
  "vars": {
    "ENVIRONMENT": "production"
  },
  "r2_buckets": [
    {
      "binding": "UPLOADS",
      "bucket_name": "prod-uploads"
    }
  ],
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    },
    "r2_buckets": [
      {
        "binding": "UPLOADS",
        "bucket_name": "preview-uploads"
      }
    ]
  }
}
```

</WranglerConfig>

Set your `previews` block on your production branch (or wherever you branch from), so when you create a new branch it carries that configuration over. When you run `wrangler preview`, the `previews` block on that branch is always the source of truth.

Your Wrangler configuration does not sync to the Previews Base section in the dashboard — if you see it empty there, that is expected. You will still see each individual Preview's settings in the dashboard once it has been deployed.

### What goes in the `previews` block

Most settings need to be redefined in the `previews` block. A few are shared automatically.

| Configuration                                                      | Shared with production? | What to do                                                                                          |
| ------------------------------------------------------------------ | ----------------------- | --------------------------------------------------------------------------------------------------- |
| `vars`                                                             | No                      | Add to `previews.vars`                                                                              |
| Secrets                                                            | No                      | Use `wrangler preview secret put`                                                                   |
| KV, D1, R2, Hyperdrive, Vectorize, Queues, service bindings        | No                      | Restate each binding in `previews`, pointed at a staging resource                                   |
| Durable Objects and Containers                                     | Partial                 | Classes and migrations are shared. Bindings must be restated. Refer to [Resources — Durable Objects and Containers](/workers/previews/resources/#durable-objects-and-containers) for setup. |
| `compatibility_date`, `compatibility_flags`, `assets`, `placement` | Yes                     | Keep with your production config                                                                    |
| `limits`, `observability`, `logpush`, `tail_consumers`, `define`   | No                      | Add to `previews` if you want Preview-specific values                                               |
| Cron Triggers, routes, queue consumers                             | Not applicable          | These do not target Previews yet                                                                    |

### Secrets

Secrets cannot be stored in Wrangler configuration files. Use these commands to manage them:

| I want to                                  | Command                                                          |
| ------------------------------------------ | ---------------------------------------------------------------- |
| Add a secret to the **Base configuration** | `npx wrangler preview base-config secret put SECRET_NAME`        |
| Add a secret to **one Preview**            | `npx wrangler preview secret put SECRET_NAME --name <preview>`   |
| List secrets for **one Preview**           | `npx wrangler preview secret list --name <preview>`              |
| Remove a secret                            | Replace `put` with `delete` in the commands above                |
| Bulk upload secrets                        | `npx wrangler preview secret bulk secrets.json --name <preview>` |

The `--name` flag defaults to the current git branch if omitted. For `bulk`, setting a key to `null` deletes that secret.

### Wrangler environments

If your team already models separate environments (like staging and production) as [Wrangler environments](/workers/wrangler/environments/), you can create Previews under each one. Each environment Worker gets its own Previews with its own configuration.

| Command                              | Result                                               |
| ------------------------------------ | ---------------------------------------------------- |
| `npx wrangler preview`               | Creates a Preview for the main Worker                |
| `npx wrangler preview --env staging` | Creates a Preview for the staging environment Worker |

Each environment's `previews` block configures that environment's Previews independently — different variables, bindings, and secrets per environment.

:::caution
Without `--env`, all `wrangler preview` commands target your production Worker — including `wrangler preview delete`. Always pass `--env` when working with environment-scoped Previews to make sure you are targeting the right Worker.
:::

<WranglerConfig>

```jsonc
{
  "name": "my-worker",
  "vars": {
    "ENVIRONMENT": "production"
  },
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    }
  },
  "env": {
    "staging": {
      "name": "my-worker-staging",
      "vars": {
        "ENVIRONMENT": "staging"
      },
      "previews": {
        "vars": {
          "ENVIRONMENT": "staging-preview"
        }
      }
    }
  }
}
```

</WranglerConfig>

For a working example, refer to the [Previews with Wrangler environments demo](https://github.com/yomna-shousha/workers-previews-envs-demo). For a comparison of Previews, Version URLs, and Wrangler environments, refer to [Compare preview workflows](/workers/previews/compare-preview-workflows/).
