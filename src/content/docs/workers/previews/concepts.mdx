Understanding these concepts will help you configure Previews correctly and reason about what happens when you run `wrangler preview`.

## Preview vs. Preview deployment

A **Preview** is an isolated copy of your Worker that runs at its own URL. A Preview is typically tied to something like a feature branch, a pull request, or a teammate's local work, and stays up until you delete it.

A **Preview deployment** is an immutable snapshot of your Worker code and configuration pushed to a Preview — similar in spirit to a Git commit. Each time you run `wrangler preview` or push a commit that triggers a Preview build, Cloudflare creates a new deployment under the existing Preview.

One Preview can have many deployments over its lifetime. The latest deployment is what serves traffic on your Preview URL.

## How Preview configuration works

Previews share a set of settings called **Preview defaults**. You configure them once — in the dashboard or via the API — and every new Preview starts from them. This includes bindings, environment variables, and secrets. Previews never inherit from production.

If you only use the dashboard or Workers Builds, every Preview gets the same configuration. There is nothing per-Preview to configure, which is why the dashboard uses a toggle (production / previews) rather than a settings page per Preview.

### Wrangler

Wrangler introduces an additional layer. Your main branch has a Wrangler configuration file with a `previews` block that typically matches your defaults. When you run `wrangler preview`, Wrangler sends the values from that block along with the deployment.

For example, if you are working on a feature that requires a new KV binding, you create a branch and add the binding to the `previews` block in your Wrangler config. When you run `wrangler preview`, your Preview receives the new binding — but the shared defaults on the platform are not modified. Other Previews are unaffected. You can continue iterating on the configuration without any changes leaking to other branches or the platform.

When the branch is ready, you open a pull request. Your teammates review the configuration changes in the diff. After the PR merges and `wrangler deploy` runs from main, the updated `previews` block is now on main. From this point on, every new Preview — whether created from the dashboard, Builds, or any branch — picks up the new binding.

### What this means

Per-Preview settings do not exist on the platform. The shared defaults are the settings. Wrangler also shares defaults across all Previews — because every branch inherits the same `previews` block from main.

The only time a Preview gets something different is when you change the `previews` block on a feature branch. What Wrangler sends from that branch rides along with the deployment. It is temporary, scoped to that one deployment, and goes away when the branch merges and everyone gets the updated config.

### How the two sources combine

When you run `wrangler preview`, the platform combines your Preview defaults (from the dashboard) with whatever your `previews` block sends (from your branch). Here is exactly what happens:

**Your branch adds something new** — say you add `FEATURE_FLAG = "on"` to your `previews` block but it is not in the dashboard defaults. Your Preview gets it. Other Previews do not.

**Your branch changes something** — say the defaults have `DB_NAME = "staging-db"` and your branch changes it to `DB_NAME = "my-test-db"`. Your Preview gets `"my-test-db"`. The defaults stay as `"staging-db"`. Other Previews still get the default.

**Your branch removes something** — say the defaults have `CACHE_TTL = "60"` and your branch omits it from the `previews` block entirely. Your Preview **still gets it**. You cannot remove a default by omitting it from your branch. The only way to remove something from the defaults is in the dashboard.

**Something exists only in the defaults** — say someone added `API_KEY` in the dashboard but it is not in your `previews` block. Your Preview gets it from the defaults.

Neither source is modified. The defaults stay the same, your local config is unchanged.

:::note
**Dashboard and Builds users** do not have a second source. Their Previews get exactly the defaults and nothing else. The merge behavior above only applies when Wrangler is creating the Preview.
:::

## Preview URLs

Every Preview has two kinds of URLs on the `workers.dev` subdomain.

The **Preview URL** is the stable URL for a Preview. Think of it as your branch URL — it always points at the latest deployment.

`<preview-name>-<worker-name>.<subdomain>.workers.dev`

The **Deployment URL** is the URL for a specific deployment. Think of it as your commit URL — it is immutable and, once created, always points at that exact deployment.

`<deployment-short-id>-<worker-name>.<subdomain>.workers.dev`

You can also serve Previews from your own **custom domain**. When Previews are enabled on a Worker custom domain, Cloudflare provisions a wildcard DNS record (`*.app.example.com`) and a wildcard certificate to cover all Preview subdomains:

- **Preview URL**: `<preview-name>.app.example.com`
- **Deployment URL**: `<deployment-short-id>-<preview-name>.app.example.com`

Previews can only be reached through these auto-generated URLs and custom domain wildcard URLs. User-managed triggers like [Worker routes](/workers/configuration/routing/routes/), [cron triggers](/workers/configuration/cron-triggers/), and [Queue](/queues/) consumers do not apply to Previews.

For configuration details, refer to [Custom domains](/workers/previews/guides/custom-domains/).

Preview URLs can be secured with [Cloudflare Access](/cloudflare-one/access-controls/policies/) to restrict who can reach them.

## What's shared and what's isolated

Previews are designed so that testing changes does not risk your production data. The isolation model differs by binding type.

### Isolated per Preview automatically

When your Worker defines the class itself, these binding types give each Preview its own isolated namespace, instances, and storage — separate from production and from every other Preview:

- [**Durable Objects**](/durable-objects/)
- [**Workflows**](/workflows/)
- [**Containers**](/containers/) (hosted on Durable Objects)

Concretely, this means:
- A Durable Object you reach via `env.MY_DO.getByName("some-id")` in a Preview returns a different instance — with different storage — than the same call in production, and different from the same call in another Preview.
- Writes to `ctx.storage` inside a Preview's Durable Object never affect production data or other Previews.
- State persists across deployments within the same Preview. Pushing a new deployment to the Preview keeps its Durable Object storage intact.
- When you delete a Preview, its Durable Objects, Workflows, and Container instances are deleted along with it.

This isolation applies only when the class is defined in the same Worker. If you set `script_name` on a Durable Object or Workflow binding, the binding points at another Worker's production instance and this isolation does not apply.

For Durable Objects and Workflows defined in the same Worker, you can access them via [`ctx.exports`](/workers/runtime-apis/context/#exports) without configuring a binding at all. Refer to [Durable Object isolation](/workers/previews/guides/durable-object-isolation/) for a full walkthrough.

### Shared across Previews

These binding types reference resources that exist at the account level. All Previews pointing at the same resource ID share it with each other and with production (unless you override the ID in `previews`):

- [KV](/kv/)
- [D1](/d1/)
- [R2](/r2/)
- [Queues](/queues/) (producers only — Previews cannot consume from Queues)
- [Vectorize](/vectorize/)
- [Hyperdrive](/hyperdrive/)
- [Analytics Engine](/analytics/analytics-engine/)
- [Pipelines](/pipelines/)
- [Secrets Store](/secrets-store/)
- [mTLS certificates](/workers/runtime-apis/bindings/mTLS/)
- [Dispatch namespaces](/cloudflare-for-platforms/workers-for-platforms/)

To keep Preview writes separate from production, create a dedicated resource for Previews and reference it under `previews`, or use [auto-provisioning](/workers/previews/configuring-previews/#auto-provisioning) for KV, D1, and R2.

### Always target production

- [**Service bindings**](/workers/runtime-apis/bindings/service-bindings/) from a Preview always resolve to the bound Worker's production deployment. You cannot point a service binding at another Preview.

### Scoped to the Preview

- **Secrets** set via `wrangler preview secret put` apply only to Preview deployments.
- **Environment variables** set in `previews.vars` apply only to Preview deployments.

## External state

Preview isolation covers only resources that Cloudflare manages on your behalf. If your Durable Object writes to an external API, publishes to a Queue that your production Worker consumes, or mutates a shared D1 database, the Preview can still affect production through those channels. Audit for shared side effects and override them in `previews` where it matters.

## Limits

Previews have account-level limits:

| | Free | Paid |
| --- | --- | --- |
| Previews per Worker | 10 | 100 |
| Deployments per Preview | 100 | 100 |

When you reach the Preview limit for a Worker and create a new Preview, the oldest Preview is automatically deleted to make room. When you reach the deployment limit within a Preview, the oldest deployment is automatically deleted.

:::caution
Automatic deletion of the oldest Preview may be surprising if you are not expecting it. Monitor your Preview count if you have many active branches.
:::
