This page covers every binding type you can use in the `previews` block. For each one, you get the behavior, a config snippet, and what to watch out for.

Previews do **not** inherit bindings from your top-level Wrangler configuration. Any binding you want available inside a Preview must be declared in the `previews` block. If you omit a binding, your Preview will not have access to it at runtime.

## Variables and secrets

| `previews` field | How it behaves |
| --- | --- |
| `vars` | Plain-text and JSON string environment variables. Production vars stay separate from Preview vars. Preview base/default vars apply to new Previews. One Preview can override vars without affecting production or another Preview. Never put secrets in `vars`. |
| Preview secrets | Secrets are not stored in Wrangler config. Use `wrangler preview secret put` to add a secret to one Preview, or `wrangler preview base secret put` to add it to the base configuration. Secret values are write-only — API GET responses redact them. |

<WranglerConfig>

```jsonc
{
	"vars": {
		"ENVIRONMENT": "production"
	},
	"previews": {
		"vars": {
			"ENVIRONMENT": "preview",
			"FEATURE_FLAGS": { "checkoutV2": true }
		}
	}
}
```

</WranglerConfig>

## Resource-ID bindings

These bindings point at account-level resources by ID or name. Two Previews bound to the same resource share data. Create a separate resource to isolate.

For KV, D1, and R2, you can omit the resource identifier (`id`, `database_name`, or `bucket_name`) and Wrangler will create a new resource the first time you run `wrangler preview`, then write the identifier back to your configuration file.

| `previews` field | How it behaves | To isolate one Preview |
| --- | --- | --- |
| `kv_namespaces` | Binds to a KV namespace by `id`. Two Previews sharing the same `id` share namespace data. | Bind to a different KV namespace. |
| `d1_databases` | Binds to a D1 database by `database_id`. Two Previews sharing the same `database_id` share rows. | Bind to a different D1 database. |
| `r2_buckets` | Binds to an R2 bucket by `bucket_name`. Two Previews sharing the same `bucket_name` share objects. | Bind to a different R2 bucket. |
| `queues.producers` | Binds a Queue producer to a queue by name. Two Previews sharing the same queue name send to the same queue. `delivery_delay` is preserved when set. | Bind to a different queue. |
| `vectorize` | Binds to a Vectorize index by `index_name`. Must be created manually before deploying. | Bind to a different index. |
| `hyperdrive` | Binds to a Hyperdrive configuration by `id`. Must be created manually. True data isolation requires a separate config pointing at a separate database or schema. | Bind to a different Hyperdrive config. |
| `analytics_engine_datasets` | Writes to the `dataset` name you specify. Datasets are created implicitly by writes. Two Previews writing to the same dataset share rows. | Bind to a different dataset name. |
| `pipelines` | Binds to a Pipeline stream by `pipeline` ID. Two Previews sharing the same stream send events to the same destination. | Bind to a different stream. |
| `secrets_store_secrets` | Binds to a Secrets Store secret by `store_id` and `secret_name`. | Bind to a different store or secret name. |
| `dispatch_namespaces` | Binds to a Workers for Platforms dispatch namespace by `namespace`. `outbound.service`, `outbound.environment`, and `outbound.parameters` are preserved when set. | Bind to a different namespace. |
| `mtls_certificates` | Binds to an mTLS client certificate by `certificate_id`. The Preview API validates the ID — synthetic or missing IDs are rejected. | Bind to a different certificate. |
| `vpc_services` | Binds to a VPC service by `service_id`. The Preview API validates the ID. | Bind to a different service. |
| `ratelimits` | Creates a Rate Limiting binding. `namespace_id` and `simple` (limit/period) are preserved. **The runtime binding name comes from `name`, not `binding`.** | Use a different `namespace_id`. |

<WranglerConfig>

```jsonc
{
	"previews": {
		"kv_namespaces": [
			{ "binding": "MY_KV", "id": "preview-kv-id" }
		],
		"d1_databases": [
			{ "binding": "DB", "database_name": "preview-db", "database_id": "preview-db-id" }
		],
		"r2_buckets": [
			{ "binding": "BUCKET", "bucket_name": "preview-bucket" }
		],
		"vectorize": [
			{ "binding": "VECTOR_INDEX", "index_name": "preview-index" }
		],
		"hyperdrive": [
			{ "binding": "HYPERDRIVE", "id": "preview-hyperdrive-id" }
		],
		"analytics_engine_datasets": [
			{ "binding": "ANALYTICS", "dataset": "preview_events" }
		],
		"pipelines": [
			{ "binding": "EVENT_STREAM", "pipeline": "preview-stream-id" }
		],
		"ratelimits": [
			{ "name": "API_LIMITER", "namespace_id": "1001", "simple": { "limit": 100, "period": 60 } }
		]
	}
}
```

</WranglerConfig>

:::note[Queue consumers are not Preview bindings]
`queues.consumers` settings target production. Queue delivery goes to the configured consumer Worker, not to a Preview of that Worker. To test queue-consuming logic in a Preview, configure the queue to deliver to a staging consumer Worker, or expose a guarded HTTP endpoint in your Preview that calls the same handler logic.
:::

## Workflows

:::caution
Workflows do **not** isolate like Durable Objects. Do not assume they work the same way.
:::

A Workflow binding points to a named Workflow resource. If production and multiple Previews bind to the same Workflow name, they share the same Workflow resource and instance namespace. Workflow code invoked from a Preview may still run with production environment values.

| `previews` field | How it behaves | To isolate one Preview |
| --- | --- | --- |
| `workflows` | Binds to a Workflow resource by `name` and `class_name`. Two Previews sharing the same Workflow `name` share the instance namespace. | Bind to a different Workflow name. |

<WranglerConfig>

```jsonc
{
	"workflows": [
		{
			"binding": "MY_WORKFLOW",
			"name": "my-workflow",
			"class_name": "MyWorkflow"
		}
	],
	"previews": {
		"workflows": [
			{
				"binding": "MY_WORKFLOW",
				"name": "preview-workflow",
				"class_name": "MyWorkflow"
			}
		]
	}
}
```

</WranglerConfig>

**Recommended setup:**

| Goal | Approach |
| --- | --- |
| All Previews share staging Workflow instances | Put a staging Workflow name in the base configuration. |
| One Preview needs isolated instances | Bind that Preview to its own Workflow resource. |
| Keep production safe | Never bind Previews to the production Workflow name. |

Verify the Workflow execution environment before relying on Preview-specific variables, bindings, or code inside the Workflow body.

## Automatically isolated bindings

These are covered in detail on [Durable Objects and Containers](/workers/previews/resources/durable-objects/).

| `previews` field | How it behaves |
| --- | --- |
| `durable_objects.bindings` | When the class is defined in the same Worker (no `script_name`), each Preview gets its own isolated namespace and instances. If `script_name` points at another Worker, the binding targets that Worker's production Durable Object. For same-Worker classes, prefer [`ctx.exports`](/workers/runtime-apis/context/#exports) — no binding declaration needed. |
| Containers | Containers run on Durable Objects. Same-Worker container classes get automatic per-Preview isolation of both DO state and container instances. Container support in Previews is partial — verify container process startup in your deployment path. |

## Account-level bindings

These bindings attach an account-level capability to your Preview. There is no resource ID and no shared data between Previews. Isolation means whether the binding is present, not whether data is separate.

Deleting the binding from one Preview does not affect another. Product operation success for some of these (Images, Stream) additionally depends on account-level product enablement, independent of binding presence.

| `previews` field | How it behaves |
| --- | --- |
| `ai` | Creates a Workers AI binding. |
| `browser` | Creates a Browser Rendering binding. |
| `images` | Creates an Images binding. Account must have Images enabled for operations to succeed. |
| `stream` | Creates a Stream binding. Account must have Stream enabled for operations to succeed. |
| `media` | Creates a Media binding. |
| `worker_loaders` | Creates a dynamic Worker loader binding. Code is supplied inline at runtime — no external resources are created. |
| `version_metadata` | Creates a version metadata binding. Returns per-deployment metadata (version ID, timestamp). The stable Preview URL returns the latest Preview deployment's metadata; immutable deployment URLs return that specific deployment's metadata. |

<WranglerConfig>

```jsonc
{
	"previews": {
		"ai": { "binding": "AI" },
		"browser": { "binding": "MY_BROWSER" },
		"images": { "binding": "IMAGES" },
		"stream": { "binding": "STREAM" },
		"media": { "binding": "MEDIA" },
		"worker_loaders": [{ "binding": "LOADER" }],
		"version_metadata": { "binding": "CF_VERSION_METADATA" }
	}
}
```

</WranglerConfig>

## Service bindings

Service bindings from a Preview always resolve to the bound Worker's production deployment. You cannot point a service binding at another Worker's Preview.

| `previews` field | How it behaves |
| --- | --- |
| `services` | Binds to a Worker `service` and optional `entrypoint`. Always targets production. |

For same-Worker calls, use [`ctx.exports`](/workers/runtime-apis/context/#exports) instead of a service binding to self — `ctx.exports` stays inside the Preview's own code, variables, and bindings.

<WranglerConfig>

```jsonc
{
	"previews": {
		"services": [
			{ "binding": "AUTH_SERVICE", "service": "auth-service" }
		]
	}
}
```

</WranglerConfig>

## Other bindings

| `previews` field | How it behaves |
| --- | --- |
| `send_email` | Creates a Send Email binding. `destination_address`, `allowed_destination_addresses`, and `allowed_sender_addresses` are preserved when set. **The runtime binding name comes from `name`, not `binding`** — access it as `env.MAILER`, not `env.send_email`. Successful delivery requires valid Email Routing setup. |

<WranglerConfig>

```jsonc
{
	"previews": {
		"send_email": [
			{
				"name": "MAILER",
				"destination_address": "preview@example.com"
			}
		]
	}
}
```

</WranglerConfig>

## Non-binding Preview settings

Some `previews` fields change how Previews behave but are not runtime bindings.

| `previews` field | How it behaves |
| --- | --- |
| `tail_consumers` | Sends Preview logs to the Tail Workers you list. Each entry is identified by its `service` name. These are Preview-level settings, not deployment `env` bindings. Two Previews can share the same Tail Worker, or one Preview can use a different one. Removing `tail_consumers` from a Preview stops delivery without causing runtime failures. |
| `observability` | Sets default observability settings (enabled, head_sampling_rate) for new Previews. |
| `logpush` | Turns default Logpush on or off for new Previews. |
| `limits` | Sets default deployment limits (cpu_ms, subrequests) for new Preview deployments. |
| `define` | Changes compile-time replacements for the Preview build. Does not create a runtime binding. |

Some settings come from the **top level** of your Wrangler config, not from `previews`:

- [`compatibility_date`](/workers/configuration/compatibility-dates/)
- [`compatibility_flags`](/workers/configuration/compatibility-flags/)
- [`placement`](/workers/configuration/smart-placement/)
- [`assets`](/workers/static-assets/)
- [`migrations`](/durable-objects/reference/durable-objects-migrations/)
- [`containers`](/containers/)
