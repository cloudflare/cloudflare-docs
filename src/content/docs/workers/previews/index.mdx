A Worker serves live traffic from a production branch with a URL, variables, secrets, and bindings configured for production.

**Previews** give every other branch the same setup — a separate URL, variables, secrets, and bindings — so you can review and test without touching production.

Select a branch below to see how the command, URL, and settings change between production and a Preview.

<WorkerPreviewsDiagram />

Previews are the recommended approach for testing non-production changes. Coming from Version URLs or Wrangler environments? Refer to [Previews, Version URLs, and Wrangler environments](/workers/configuration/compare-preview-workflows/) to compare and migrate.

## How it works

Running `npx wrangler preview` creates or updates a Preview from your current branch. As you use `npx wrangler deploy` for production, use `npx wrangler preview` to test a branch before merging.

| Branch          | Command                | What happens                                        |
| --------------- | ---------------------- | --------------------------------------------------- |
| `main`          | `npx wrangler deploy`  | Deploys to production with production settings.     |
| `feature/login` | `npx wrangler preview` | Creates or updates a Preview with its own settings. |

### URLs

Each Preview gets two URLs. The **Preview URL** always serves the latest deployment. The **Deployment URL** is immutable and points to one specific deploy.

Choose to serve these URLs on `workers.dev` or a [custom domain](/workers/previews/custom-domains/):

| Host type     | Preview URL                                            | Deployment URL                                          |
| ------------- | ------------------------------------------------------ | ------------------------------------------------------- |
| `workers.dev` | `<preview-name>-<worker-name>.<subdomain>.workers.dev` | `<deployment-id>-<worker-name>.<subdomain>.workers.dev` |
| Custom domain | `<preview-name>.app.example.com`                       | `<deployment-id>-<preview-name>.app.example.com`        |

### Preview names

A Preview name identifies the branch Preview. By default, the name comes from your git branch. Deploying again with the same name updates the same Preview and keeps the Preview URL stable.

You can also set the name explicitly with `npx wrangler preview --name <preview-name>`.

### Settings and isolation

Every Preview gets its own variables, secrets, and bindings. Configure each Preview independently, or set a [base configuration](/workers/previews/configuration/#set-a-base-configuration) so every new Preview starts from the same settings.

Bindings connect a Preview to resources. Previews that bind to the same KV namespace, D1 database, R2 bucket, or external system share that data. For details, refer to [Resources and isolation](/workers/previews/resources/).

### Access control

Preview URLs are public by default. Use [Cloudflare Workers Access](/workers/configuration/cloudflare-access/) to require visitors to sign in before they can reach a Preview.

You can protect all Previews on an account or only one Worker's Previews. Access applies to `workers.dev` Preview URLs, Deployment URLs, and custom domain Preview URLs.

### Limits and automatic cleanup

| Limit | Free plan | Paid plans |
| --- | --- | --- |
| Active Previews per Worker | 10 | 100 |
| Deployments per Preview | 100 | 100 |

When a limit is reached, Cloudflare automatically cleans up older Previews or deployments:

- When a Worker reaches the active Preview limit, Cloudflare deletes the least recently deployed Preview.
- When a Preview reaches the deployment limit, Cloudflare deletes the oldest deployments first.
