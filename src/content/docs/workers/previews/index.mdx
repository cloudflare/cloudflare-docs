Worker Previews give each branch or pull request its own URL before you merge code or send live traffic to a change.

In Git workflows, each Preview usually represents one branch or pull request. It can use its own variables, secrets, bindings, resources, and custom domains, including test resources such as a test D1 database or R2 bucket. This lets reviewers test the branch in an app-like environment without changing production Worker settings or routing live traffic.

Coming from Version URLs or Wrangler environments? Refer to [Previews, Version URLs, and Wrangler environments](/workers/configuration/compare-preview-workflows/) to compare the workflows.

## How it works

Production and Preview changes use different commands. Use `wrangler deploy` for the Worker that serves live traffic. Use `wrangler preview` for branch and pull request testing.

| Branch          | Command            | What happens                                                                                                                    |
| --------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `main`          | `wrangler deploy`  | Deploys your Worker to production with its production variables, secrets, bindings, resources, and custom domains.              |
| `feature/login` | `wrangler preview` | Creates or updates a Preview for that branch with Preview-specific variables, secrets, bindings, resources, and custom domains. |

Each Preview name maps to one stable Preview URL. In Git workflows, use one Preview name per branch or pull request. When you push more changes and run `wrangler preview` with the same name, the same Preview URL serves the latest deployment for that Preview.

Each new Preview branches from [Shared Preview Settings](/workers/previews/configuration/#shared-preview-settings). After it exists, you can change that Preview's settings without changing production, the shared settings, or other Previews.

## URL formats

Previews can be served on `workers.dev` or on a [custom domain](/workers/previews/custom-domains/). Each Preview has two URL types:

| Host type     | Preview URL                                            | Deployment URL                                          |
| ------------- | ------------------------------------------------------ | ------------------------------------------------------- |
| `workers.dev` | `<preview-name>-<worker-name>.<subdomain>.workers.dev` | `<deployment-id>-<worker-name>.<subdomain>.workers.dev` |
| Custom domain | `<preview-name>.app.example.com`                       | `<deployment-id>-<preview-name>.app.example.com`        |

The **Preview URL** stays the same and serves the latest changes for the branch.

The **Deployment URL** points to one specific deploy for version history, comparisons, or debugging.

## Resource isolation

Previews can use their own test resources, such as a test D1 database or R2 bucket.

Set this up in Preview settings. Use Shared Preview Settings for future Preview branches, or this Preview's settings for one branch.

Cloudflare creates separate Preview resources automatically for Durable Objects, Workflows, and Containers. For account-level resources such as KV, D1, R2, Queues, Vectorize, and Hyperdrive, point the Preview at the test resource you want it to use.

For details, refer to [Resources and isolation](/workers/previews/resources/).

## Access control

Preview URLs are public when routing is enabled unless you add an access control layer. You can use [Cloudflare Access](/cloudflare-one/access-controls/policies/) to require authentication for Preview URLs and Deployment URLs.

Production and Preview access can be controlled independently.

To turn Preview URL routing on or off, refer to [Configuration](/workers/previews/configuration/#preview-url-routing).

For custom domain Preview URLs, refer to [Custom domains](/workers/previews/custom-domains/).

## Limits

Each Worker can have up to 100 active Previews. Each Preview can have up to 100 deployments.

When a Worker reaches the Preview limit, Cloudflare automatically deletes the least recently deployed Preview to make room for a new one. When a Preview reaches the deployment limit, Cloudflare deletes the oldest deployments first.
