Use CI/CD to create or update a Preview every time a pull request changes.

Before adding CI, check [Resources and isolation](/workers/previews/resources/) so you know which resources are isolated and which resources are shared.

## Workers Builds

Use [Workers Builds](/workers/ci-cd/builds/) when you want Cloudflare to build your Worker, create the Preview, and comment the Preview URL on your pull request.

1. [Connect your Worker to a GitHub or GitLab repository](/workers/ci-cd/builds/#get-started).
2. Enable [Preview Builds](/workers/ci-cd/builds/build-branches/#configure-preview-builds).
3. Confirm the [Preview command](/workers/ci-cd/builds/configuration/#preview-command) is `npx wrangler preview`.

Workers Builds is the simplest path when your repository is already connected to Cloudflare.

## GitHub Actions

Use GitHub Actions when you want to keep builds in GitHub, use an existing workflow, or customize how Preview URLs are posted to pull requests.

### Add repository secrets

Use the GitHub CLI to add the secrets used by the workflow:

```sh
gh secret set CLOUDFLARE_API_TOKEN
gh secret set CLOUDFLARE_ACCOUNT_ID
```

Create an API token with permissions to edit Workers Scripts and the resources your Preview uses.

### Minimal wrangler-action workflow

This workflow creates or updates a Preview for every pull request. The Preview name is stable for the PR, so the Preview URL stays stable across commits.

```yaml title=".github/workflows/preview.yml"
name: Preview

on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: cloudflare/wrangler-action@v4
        with:
          command: preview --name pr-${{ github.event.pull_request.number }}
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
```

For all supported options, refer to [`cloudflare/wrangler-action`](https://github.com/cloudflare/wrangler-action).

### Post the Preview URL to the pull request

Use `wrangler preview --json` when you need the Preview URL in another workflow step.

```yaml title=".github/workflows/preview.yml"
name: Preview

on:
  pull_request:
    types: [opened, synchronize, reopened, closed]

jobs:
  preview:
    if: github.event.action != 'closed'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - id: preview
        run: |
          OUTPUT=$(npx wrangler preview --name "pr-${{ github.event.pull_request.number }}" --json)
          echo "url=$(echo "$OUTPUT" | jq -r '.preview_url')" >> "$GITHUB_OUTPUT"
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
      - uses: marocchino/sticky-pull-request-comment@v2
        with:
          message: |
            ### Preview
            ${{ steps.preview.outputs.url }}

  cleanup:
    if: github.event.action == 'closed'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx wrangler preview delete --name "pr-${{ github.event.pull_request.number }}"
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
```

## Persistent staging Preview

Use `--name` for a stable non-branch Preview, such as `staging`, `qa`, or `demo`:

```sh
npx wrangler preview --name staging
```

The staging Preview keeps the same URL across deployments:

```txt
staging-<worker-name>.<subdomain>.workers.dev
```

Use named Previews when you want a stable URL without creating a separate Worker. Use Wrangler environments instead when you need separate routes, Cron Triggers, queue consumers, or service-binding targets.

## Monorepo with multiple Workers

Preview names are scoped to a Worker. In a monorepo, each Worker can have a Preview with the same pull request name:

```sh
cd workers/api && npx wrangler preview --name "pr-123"
cd ../web && npx wrangler preview --name "pr-123"
```

Service bindings between these Previews currently resolve to the bound Worker's production deployment rather than to another Worker's matching Preview. For end-to-end multi-Worker testing, use staging Workers or another environment strategy while Preview coverage continues to expand.

## Other CI providers

In any CI provider, run `npx wrangler preview` instead of `npx wrangler deploy` for pull request or branch previews:

```sh
npx wrangler preview --name "$BRANCH_NAME" --json
```

Use the JSON output to post the Preview URL wherever your team reviews changes.
