## PR preview per branch

Every pull request gets its own preview URL. The preview is created when the PR opens and deleted when it closes.

### Set up the Wrangler config

Add preview-specific variables so your Worker knows it is running in a preview context:

<WranglerConfig>

```jsonc
{
	"name": "my-app",
	"main": "src/index.ts",
	"compatibility_date": "$today",
	"vars": {
		"APP_ENV": "production"
	},
	"previews": {
		"vars": {
			"APP_ENV": "preview"
		}
	}
}
```

</WranglerConfig>

### Deploy production first

```sh
wrangler deploy
```

### Add a GitHub Actions workflow

Create `.github/workflows/preview.yml`:

```yaml
name: Preview
on:
  pull_request:
    types: [opened, synchronize, reopened, closed]

jobs:
  preview:
    if: github.event.action != 'closed'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - id: preview
        run: |
          OUTPUT=$(npx wrangler preview --name "pr-${{ github.event.pull_request.number }}" --json)
          echo "url=$(echo "$OUTPUT" | jq -r '.preview_url')" >> "$GITHUB_OUTPUT"
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
      - uses: marocchino/sticky-pull-request-comment@v2
        with:
          message: |
            ### Preview
            ${{ steps.preview.outputs.url }}

  cleanup:
    if: github.event.action == 'closed'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx wrangler preview delete "pr-${{ github.event.pull_request.number }}"
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
```

### Steps

1. Set `CLOUDFLARE_API_TOKEN` as a GitHub repository secret.
2. Commit the workflow file to your default branch.
3. Open a pull request. The preview URL appears as a PR comment.
4. Push more commits to the same PR. The preview updates at the same URL.
5. Close or merge the PR. The cleanup job deletes the preview.

:::note
If you use [Workers Builds](/workers/ci-cd/builds/) instead, connect your repo and enable preview builds in the dashboard. No workflow file is needed.
:::

## Persistent staging URL

A stable staging preview that persists across deploys. Always at the same URL, always named `staging`.

### Set up the Wrangler config

Override variables and bindings for staging in the `previews` block:

<WranglerConfig>

```jsonc
{
	"name": "my-app",
	"main": "src/index.ts",
	"compatibility_date": "$today",
	"vars": {
		"APP_ENV": "production",
		"API_URL": "https://api.example.com"
	},
	"previews": {
		"vars": {
			"APP_ENV": "staging",
			"API_URL": "https://api.staging.example.com"
		}
	}
}
```

</WranglerConfig>

### Steps

1. Deploy production:

   ```sh
   wrangler deploy
   ```

2. Create the staging preview:

   ```sh
   wrangler preview --name staging
   ```

3. The staging URL is `staging-my-app.<subdomain>.workers.dev`. This URL stays the same across updates.

4. Update staging from any branch — run `wrangler preview --name staging` again. Same name means same preview and same URL.

5. When staging looks good, deploy production with a version tag:

   ```sh
   wrangler deploy --tag $(git rev-parse --short HEAD)
   ```

6. Roll back production if needed:

   ```sh
   wrangler versions deploy <version-id>@100%
   ```

The `--name` flag decouples the preview identity from the git branch. Use it for any persistent environment: staging, QA, demo.

## Isolate data per branch

Point previews at test KV namespaces, D1 databases, or R2 buckets so preview branches do not read or write production data.

### Set up the Wrangler config

Separate resource IDs in the `previews` block:

<WranglerConfig>

```jsonc
{
	"name": "my-app",
	"main": "src/index.ts",
	"compatibility_date": "$today",
	"kv_namespaces": [
		{ "binding": "CACHE", "id": "prod-kv-id" }
	],
	"previews": {
		"kv_namespaces": [
			{ "binding": "CACHE", "id": "preview-kv-id" }
		]
	}
}
```

</WranglerConfig>

### Steps

1. Create a test KV namespace:

   ```sh
   wrangler kv namespace create PREVIEW_CACHE
   ```

2. Copy the namespace ID from the output and add it to `previews.kv_namespaces` in your Wrangler config.

3. Create a preview:

   ```sh
   wrangler preview --name my-branch
   ```

   The preview reads from and writes to the test namespace. Production is unaffected.

4. Repeat for D1, R2, Queues, Vectorize, or Hyperdrive by adding the test resource ID to the corresponding `previews` block.

KV, D1, R2, Queues, Vectorize, Hyperdrive, and Workflows are shared with production or other Previews unless you point them at different resources. Durable Objects and Containers are isolated automatically when they are defined in the same Worker. Separate Workflow resources separate Workflow instances, but are not equivalent to Durable Object Preview isolation.

For the full isolation matrix, refer to [Resources and isolation](/workers/previews/resources/).

## Monorepo, multiple Workers

A monorepo with multiple Workers where each deploys independently and gets its own preview lifecycle.

### Project structure

```
workers/
  api/
    src/index.ts
    wrangler.jsonc    # name: "api"
  web/
    src/index.ts
    wrangler.jsonc    # name: "web"
```

Each Worker has its own Wrangler config with its own `name`.

### Steps

1. Deploy each Worker from its own directory:

   ```sh
   cd workers/api && wrangler preview --name feature/login
   cd workers/web && wrangler preview --name feature/login
   ```

   Preview names are scoped to the Worker. Both Workers can have a preview named `feature/login` without conflict.

2. In CI, use path filtering to detect which Workers changed. For example, with GitHub Actions:

   ```yaml
   - uses: dorny/paths-filter@v3
     id: changes
     with:
       filters: |
         api:
           - 'workers/api/**'
         web:
           - 'workers/web/**'
   ```

3. Only deploy previews for changed Workers:

   ```yaml
   - if: steps.changes.outputs.api == 'true'
     run: cd workers/api && npx wrangler preview --name "pr-${{ github.event.pull_request.number }}" --json
     env:
       CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}

   - if: steps.changes.outputs.web == 'true'
     run: cd workers/web && npx wrangler preview --name "pr-${{ github.event.pull_request.number }}" --json
     env:
       CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
   ```

4. If a shared package changes, trigger all dependent Workers.

## Migrate from Wrangler environments

Replace `wrangler deploy --env staging` and `wrangler deploy --env production` with one Worker and previews.

### Before and after

| Before (environments) | After (previews) |
| --- | --- |
| `wrangler deploy --env staging` | `wrangler preview --name staging` |
| `wrangler deploy --env production` | `wrangler deploy` |
| Two Workers: `my-app-staging`, `my-app` | One Worker: `my-app` |
| Secrets per env: `wrangler secret put X --env staging` | Preview secrets: `wrangler preview secret put X --name staging` |
| Bindings duplicated in both envs | Production top-level, preview overrides in `previews {}` |

### Update your config

Replace environment blocks with the `previews` block:

<WranglerConfig>

```jsonc
// Before (environments):
// [vars]
// APP_ENV = "production"
// [env.staging.vars]
// APP_ENV = "staging"

// After (previews):
{
	"name": "my-app",
	"main": "src/index.ts",
	"compatibility_date": "$today",
	"vars": {
		"APP_ENV": "production"
	},
	"previews": {
		"vars": {
			"APP_ENV": "staging"
		}
	}
}
```

</WranglerConfig>

### Steps

1. Add a `previews` block to your Wrangler config with the staging-specific overrides.
2. Deploy production: `wrangler deploy`.
3. Create the staging preview: `wrangler preview --name staging`.
4. Update CI scripts to use `wrangler preview --name staging` instead of `wrangler deploy --env staging`.
5. Delete the old staging Worker when the migration is complete.

No more environment duplication. One config file, one Worker, one set of bindings.

## API-managed previews

Manage previews entirely through the REST API. Create, patch variables and secrets, remove bindings, and delete — without Wrangler.

### Key endpoints

```
GET    /accounts/{account_id}/workers/workers/{worker_name}/previews
GET    /accounts/{account_id}/workers/workers/{worker_name}/previews/{preview_name}
PATCH  /accounts/{account_id}/workers/workers/{worker_name}/previews/{preview_name}/deployments/latest
DELETE /accounts/{account_id}/workers/workers/{worker_name}/previews/{preview_name}
```

### Steps

1. Deploy the Worker first (Wrangler or API):

   ```sh
   wrangler deploy
   ```

2. Create a preview:

   ```sh
   wrangler preview --name my-preview
   ```

3. Patch a variable via API:

   ```sh
   curl -X PATCH \
     "https://api.cloudflare.com/client/v4/accounts/{account_id}/workers/workers/{worker_name}/previews/my-preview/deployments/latest" \
     -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "env": {
         "DEBUG": { "text": "true", "type": "plain_text" }
       }
     }'
   ```

4. Remove a binding by setting it to `null`:

   ```sh
   curl -X PATCH \
     "https://api.cloudflare.com/client/v4/accounts/{account_id}/workers/workers/{worker_name}/previews/my-preview/deployments/latest" \
     -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{ "env": { "DEBUG": null } }'
   ```

5. Rotate a secret:

   ```sh
   curl -X PATCH \
     "https://api.cloudflare.com/client/v4/accounts/{account_id}/workers/workers/{worker_name}/previews/my-preview/deployments/latest" \
     -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "env": {
         "API_KEY": { "text": "new-value", "type": "secret_text" }
       }
     }'
   ```

6. Delete the preview:

   ```sh
   curl -X DELETE \
     "https://api.cloudflare.com/client/v4/accounts/{account_id}/workers/workers/{worker_name}/previews/my-preview" \
     -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN"
   ```

Key concepts:

- Each PATCH creates a new immutable deployment.
- Omitted fields inherit from the latest deployment.
- `null` removes a binding.
- `secret_text` values are write-only — GET responses redact them.
- Use `/workers/workers/` in API paths, not `/workers/scripts/`.
