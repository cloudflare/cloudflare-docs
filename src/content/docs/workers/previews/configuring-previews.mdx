A Worker can have many Previews, such as one Preview per feature branch. Before you can create Previews, you need to first define the **Preview settings** that all Previews will start with.

### What are Preview settings?

Your **Preview settings** are the default [bindings](/workers/configuration/bindings/), [environment variables](/workers/configuration/environment-variables/), and other values that every new Preview starts with. You can define Preview settings in the Cloudflare dashboard or in your Wrangler configuration file. Previews never inherit values from your production settings.

When a specific Preview needs different values, you can override them for that single Preview deployment — without affecting other running Previews. You can learn more about Overrides in this section.

## Configure Preview settings

### Cloudflare dashboard

To configure Preview settings in the Cloudflare dashboard:

1. Go to **Compute** > **Workers & Pages** > Select your Worker >**Settings**. There, you can add values to be used for all Previews, or import values from your Production settings.
2. You can also do the same for your bindings in your Worker's **Bindings** tab.

### Wrangler configuration file

Preview settings are stored on the Cloudflare platform's API, meaning that you can configure your Preview settings in the Cloudflare dashboard, and don't need to also define them in Wrangler configuration.

If you do want to always have Preview settings in your **Wrangler configuration file** (for exaple, when using coding agents or when you want to keep all settings checked into version control), you can define them in a `previews` block. Wrangler treats your top-level configuration as your Production settings.

Any Preview settings defined in Wrangler configuration will always override settings in the Cloudflare dashboard. Learn more about Overrides in this section.

<WranglerConfig>

```toml
vars = { ENVIRONMENT = "production" }

[[kv_namespaces]]
binding = "MY_KV"
id = "prod-kv-id"

[previews]
vars = { ENVIRONMENT = "preview" }

[[previews.kv_namespaces]]
binding = "MY_KV"
id = "preview-kv-id"
```

</WranglerConfig>

In this example:

- Your **Production settings** use `ENVIRONMENT = "production"` and the KV namespace `prod-kv-id`
- Your Preview settings use `ENVIRONMENT = "preview"` and the KV namespace `preview-kv-id`
- The binding name stays the same, so your Worker code can keep using `env.MY_KV`, and only the values themselves change.

Cloudflare does not automatically create `preview-kv-id` for you, unless you use Wrangler's auto-provisioning feature. Otherwise, you must create that KV namespace first, then reference it in the `previews`block.

## Overrides

Any values in the `previews` block will always override settings defined in the Cloudflare dashboard for that specific Preview deployment. This makes it possible to override a value (for example, using a different environment variable) without also changing that value for all the running Previews your teammates might be using.

Let's say you check out a branch and want to use a different D1 database for your testing, without other Previews now using that database. You can simply change the `database_name` to point to a different database in the `previews` block, and then run `wrangler preview`. You'll notice that the Preview deployment now uses the new database, but your shared Preview settings remain unchanged. You can view the values that your Preview deployments run with in the dashboard under **Previews** > Preview name > **Deployments**. If you don't want to merge that new `database_name` into `main`, simply revert the change.

If you want to update all your Preview settings with the values defined in your `previews` block, you can run `wrangler preview settings update` to push those values to the Cloudflare platform. This is purely for hygeine purposes, and so that you can see the consistency between the values in your configuration file and the Preview settings in the Cloudflare dashboard.

## Binding behavior in `previews` block

Previews do **not** inherit bindings from your top-level Wrangler configuration. Any binding you want available inside a Preview must be declared in the `previews` block. If you omit a binding here, your Preview will not have access to it at runtime.

For most binding types — such as KV, D1, R2, Queues, Vectorize, and Hyperdrive — all of your Previews share the same underlying resource that you specify in `previews`. These are account-level resources referenced by ID or name, so pointing two Previews at the same `kv_namespaces.id` means they read and write the same data. If you need a Preview's writes to stay separate from production, create a dedicated resource for Previews (or omit the id/name to let Wrangler auto-provision one for KV, D1, and R2).

The exceptions are **Durable Objects**, **Workflows**, and **Containers**. When your Worker defines the class itself (no `script_name` on the binding), each Preview automatically gets its own isolated instances, separate from production and from other Previews. State persists across deployments within the same Preview and is deleted when the Preview is deleted. If you set `script_name` to point at another Worker, the binding targets that Worker's production instance and this isolation does not apply — prefer [`ctx.exports`](/workers/runtime-apis/context/#exports) for Durable Objects and Workflows defined in the same Worker.

[Service bindings](/workers/runtime-apis/bindings/service-bindings/) behave differently from both: they always resolve to the bound Worker's production deployment, and cannot be pointed at another Worker's Preview.

## Other Preview settings

Some `previews` fields are not runtime bindings, but they still change how new Previews behave.
| `previews` field | How it behaves |
| --- | --- |
| `observability` | Sets default observability settings for new Previews. |
| `logpush` | Turns default Logpush on or off for new Previews. |
| `tail_consumers` | Sends Preview logs to the Tail Workers you list. Each entry is specified by its `service` name. These are not deployment bindings. |
| `limits` | Sets default deployment limits for new Preview deployments. |
| `define` | Changes compile-time replacements for the Preview build. It does not create a runtime binding. |
Some Preview-related settings still come from the top level of your Wrangler config, not from `previews`:

- `compatibility_date`
- `compatibility_flags`
- `placement`
- `assets`
- `migrations`

### Use environment-specific Preview defaults

If you use Wrangler environments, you can define `env.<name>.previews` to give one environment a different set of Preview defaults.

When `env.<name>.previews` exists, Wrangler uses the values from that block for the fields you define there. If a field is not defined there, Wrangler falls back to the top-level `previews` block.

Example:

- top-level `previews.kv_namespaces` can point all new Previews at a shared staging KV namespace
- `env.dev.previews.kv_namespaces` can instead point development Previews at a different KV namespace
