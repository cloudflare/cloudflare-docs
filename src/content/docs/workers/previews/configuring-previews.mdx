A Worker can have many Previews — for example, one per feature branch. Before you create Previews, you define the **Preview settings** that all Previews start with.

Learn more about how Previews work in [Previews concepts](/workers/previews/concepts/).

## What are Preview settings?

Your **Preview settings** are the default [bindings](/workers/runtime-apis/bindings/), [environment variables](/workers/configuration/environment-variables/), and other values that every new Preview starts with. You can define Preview settings in the Cloudflare dashboard or in your Wrangler configuration file. Previews never inherit values from your production settings.

When a specific Preview needs different values, you can send them with that single Preview deployment without changing the shared settings. See [Per-deployment overrides](#per-deployment-overrides) below for more information.

## Configure Preview settings

### Cloudflare dashboard

To configure Preview settings in the Cloudflare dashboard:

1. Go to **Compute** > **Workers & Pages** > select your Worker > **Settings**. You can add values used for all Previews, or import values from your Production settings.
2. Do the same for bindings in your Worker's **Bindings** tab.

### Wrangler configuration file

Preview settings are stored on the Cloudflare platform, so you can configure them in the Cloudflare dashboard without also defining them in Wrangler.

If you want your Preview settings checked into version control (for example, when working with coding agents or collaborating across a team), define them in a `previews` block. Wrangler treats your top-level configuration as your Production settings.

Any Preview settings defined in Wrangler configuration override the corresponding values in the Cloudflare dashboard for that deployment. See [Per-deployment overrides](#per-deployment-overrides) for more information.

<WranglerConfig>
```toml
vars = { ENVIRONMENT = "production" }
[[kv_namespaces]]
binding = "MY_KV"
id = "prod-kv-id"
[previews]
vars = { ENVIRONMENT = "preview" }
[[previews.kv_namespaces]]
binding = "MY_KV"
id = "preview-kv-id"
```
</WranglerConfig>
In this example:
- Your **Production settings** use `ENVIRONMENT = "production"` and the KV namespace `prod-kv-id`.
- Your **Preview settings** use `ENVIRONMENT = "preview"` and the KV namespace `preview-kv-id`.
- The binding name stays the same, so your Worker code can keep using `env.MY_KV` and only the underlying values change.
Cloudflare does not automatically create `preview-kv-id` for you unless you use Wrangler's [auto-provisioning feature](#auto-provisioning). Otherwise, you must create the KV namespace first, then reference it in the `previews` block.

	"containers": [

		// Never put secrets here — use `wrangler preview secret put` instead.
		"vars": {

			"FEATURE_FLAGS": { "checkoutV2": true },

		"browser": { "binding": "MY_BROWSER" },
		"ai": { "binding": "AI" },

## Binding behavior in the `previews` block

Previews do **not** inherit bindings from your top-level Wrangler configuration. Any binding you want available inside a Preview must be declared in the `previews` block. If you omit a binding here, your Preview will not have access to it at runtime.

:::note
If your production Worker has bindings and you run `wrangler preview` without those bindings in your `previews` block or in the platform-side Preview defaults, Wrangler will raise an error telling you the Preview is missing a binding that is present in your top-level configuration.
:::

For most binding types — such as [KV](/kv/), [D1](/d1/), [R2](/r2/), [Queues](/queues/), [Vectorize](/vectorize/), and [Hyperdrive](/hyperdrive/) — all of your Previews share the same underlying resource that you specify in `previews`. These are account-level resources referenced by ID or name, so pointing two Previews at the same `kv_namespaces.id` means they read and write the same data.

If you need a Preview's writes to stay separate from production, create a dedicated resource for Previews, or use [auto-provisioning](#auto-provisioning) for KV, D1, and R2.

The exceptions are [**Durable Objects**](/durable-objects/), [**Workflows**](/workflows/), and [**Containers**](/containers/). When your Worker defines the class itself (no `script_name` on the binding), each Preview automatically gets its own isolated namespace and instances, separate from production and from other Previews. State persists across deployments within the same Preview and is deleted when the Preview is deleted. If you set `script_name` to point at another Worker, the binding targets that Worker's production instance and this isolation does not apply — prefer [`ctx.exports`](/workers/runtime-apis/context/#exports) for Durable Objects and Workflows defined in the same Worker. Refer to [Durable Object isolation](/workers/previews/guides/durable-object-isolation/) for details.

[Service bindings](/workers/runtime-apis/bindings/service-bindings/) behave differently from both: they always resolve to the bound Worker's production deployment, and cannot be pointed at another Worker's Preview.
| `previews` field | How it behaves |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vars` | For defining plain-text and JSON string environment variables. Never define secrets in `vars` — instead, use the `wrangler preview secret` command. |
| `kv_namespaces` | For connecting your KV namespace binding to a Preview KV namespace `id`. You need to manually create a separate KV namespace for Previews, or leave the `id` field empty and Wrangler will auto-provision you a new KV namespace and write the `id` back to your configuration file. |
| `d1_databases` | For connecting your D1 database binding to a Preview D1 database `database_id`. You need to manually create the D1 database for Previews to use, or leave the `database_name` field empty and Wrangler will auto-provision you a new D1 database and write the `database_name` back to your configuration file. |
| `r2_buckets` | For connecting your R2 bucket binding to a Preview R2 bucket `bucket_name`. You need to manually create the R2 bucket for Previews to use, or leave the `bucket_name` field empty and Wrangler will auto-provision you a new R2 bucket and write the `bucket_name` back to your configuration file. |
| `services` | For connecting a Service binding to a Worker `service` and optional `entrypoint`. Service bindings from a Preview always target the production instance of the bound Worker — they cannot be pointed at another Preview. |
| `durable_objects.bindings` | For connecting a Durable Object binding to the `class_name` (and optional `script_name`) you specify. When the class is defined in the same Worker, each Preview gets its own isolated Durable Object namespace and instances, separate from production. If `script_name` points at another Worker, the binding targets that Worker's production Durable Object. For Durable Objects defined in the same Worker, you can access them via `ctx.exports` without configuring a binding. |
| `workflows` | For connecting a Workflow binding to the `class_name`, Workflow `name`, and optional `script_name` you specify. When the class is defined in the same Worker, each Preview gets its own isolated Workflow instances, separate from production. If `script_name` points at another Worker, the binding targets that Worker's production Workflow. For Workflows defined in the same Worker, you can access them via `ctx.exports` without configuring a binding. |
| `send_email` | For creating a Send Email binding. The runtime binding name comes from `name`, not `binding`. `destination_address`, `allowed_destination_addresses`, and `allowed_sender_addresses` are preserved when set. |
| `queues.producers` | For connecting a Queue producer binding to the `queue` name you specify. `delivery_delay` is preserved when set. Queue consumer settings (`queues.consumers`) are not Preview bindings — Previews cannot consume from Queues. |
| `vectorize` | For connecting a Vectorize binding to the `index_name` you specify. You need to manually create the Vectorize index for Previews to use. |
| `hyperdrive` | For connecting a Hyperdrive binding to the configuration `id` you specify. You need to manually create the Hyperdrive configuration for Previews to use. |
| `analytics_engine_datasets` | For creating an Analytics Engine binding that writes to the `dataset` you specify. |
| `dispatch_namespaces` | For connecting a Dispatch Namespace binding to the `namespace` you specify. `outbound.service`, `outbound.environment`, and `outbound.parameters` are preserved when set. |
| `mtls_certificates` | For connecting an mTLS certificate binding to the `certificate_id` you specify. |
| `pipelines` | For connecting a Pipelines binding to the `pipeline` you specify. |
| `secrets_store_secrets` | For connecting a Secrets Store binding to the `store_id` and `secret_name` you specify. |
| `ratelimits` | For creating a Rate Limiting binding. The runtime binding name comes from `name`, not `binding`. `namespace_id` and `simple` are preserved when set. |
| `vpc_services` | For connecting a VPC Services binding to the `service_id` you specify. |
| `worker_loaders` | For creating a dynamic Worker loader binding using the `binding` name you specify. |
| `browser` | For creating a Browser Rendering binding using the `binding` name you specify. |
| `ai` | For creating a Workers AI binding using the `binding` name you specify. |
| `images` | For creating an Images binding using the `binding` name you specify. |
| `stream` | For creating a Stream binding using the `binding` name you specify. |
| `media` | For creating a Media binding using the `binding` name you specify. |
| `version_metadata` | For creating a version metadata binding using the `binding` name you specify. |

## What your Preview deployment actually gets

When you run `wrangler preview`, the platform combines your Preview defaults (configured in the dashboard) with whatever your `previews` block sends:

- Defaults have it, Wrangler did not send it → included.
- Wrangler sent it, defaults do not have it → included.
- Both have the same binding → Wrangler wins.

Neither source is modified. The defaults stay the same, your local config is unchanged. Refer to [How Preview configuration works](/workers/previews/concepts/#how-preview-configuration-works) for the full explanation.

:::note
If you only use the dashboard or Workers Builds to create Previews, there is no second source. Your Previews get exactly the Preview defaults.
:::

## Auto-provisioning

For KV, D1, and R2, you can omit the resource identifier and Wrangler will create a new resource the first time you run `wrangler preview`, then write the identifier back to your configuration file.
| Binding | Omit this field | Wrangler creates |
| --------------- | --------------- | ------------------ |
| `kv_namespaces` | `id` | A new KV namespace |
| `d1_databases` | `database_name` | A new D1 database |
| `r2_buckets` | `bucket_name` | A new R2 bucket |
Other resource types (Vectorize, Hyperdrive, Pipelines, mTLS certificates, and so on) must be created manually before you reference them in the `previews` block.

## Other Preview settings

Some `previews` fields are not runtime bindings, but they still change how new Previews behave.
| `previews` field | How it behaves |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `observability` | Sets default observability settings for new Previews. |
| `logpush` | Turns default Logpush on or off for new Previews. |
| `tail_consumers` | Sends Preview logs to the Tail Workers you list. Each entry is specified by its `service` name. These are not deployment bindings. |
| `limits` | Sets default deployment limits for new Preview deployments. |
| `define` | Changes compile-time replacements for the Preview build. It does not create a runtime binding. |
Some Preview-related settings come from the top level of your Wrangler config, not from `previews`:

- [`compatibility_date`](/workers/configuration/compatibility-dates/)
- [`compatibility_flags`](/workers/configuration/compatibility-flags/)
- [`placement`](/workers/configuration/smart-placement/)
- [`assets`](/workers/static-assets/)
- [`migrations`](/durable-objects/reference/durable-objects-migrations/)
- [`containers`](/containers/)

## Use environment-specific Preview defaults

If you use [Wrangler environments](/workers/wrangler/environments/), you can define `env.<name>.previews` to give one environment a different set of Preview defaults.
When `env.<name>.previews` exists, Wrangler uses values from that block for the fields you define there. If a field is not defined there, Wrangler falls back to the top-level `previews` block.
For example:

- Top-level `previews.kv_namespaces` can point all new Previews at a shared staging KV namespace.
- `env.dev.previews.kv_namespaces` can point development Previews at a different KV namespace.

## Advanced: syncing to the platform

The `wrangler preview settings update` command pushes your local `previews` block to the platform as the new Preview defaults. After running it, the dashboard will reflect whatever is in your Wrangler configuration, and new Previews created from the dashboard, Builds, or the API will use those values.

This command is for teams that manage settings in both the dashboard and the CLI and want them in sync. If you only use Wrangler and commit your `previews` block to your main branch, you do not need this command — the shared layer is your Git repository.

```sh
wrangler preview settings update
```

A few things to know:

- This command is **additive**. It can add and modify settings in the Preview defaults. It cannot remove them. If you need to remove a binding from the Preview defaults, use the dashboard.
- **Existing Previews are not affected.** Only Previews created after the update pick up the new defaults.
- It shows a diff of what will change before applying, and asks for confirmation.
