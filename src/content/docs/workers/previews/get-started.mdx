Previews give each branch its own isolated environment with a live URL. Production stays untouched.

Setup has two parts: **configure** your Preview settings, then **deploy** a Preview.

<WorkerPreviewsAgentPrompt />

## Step 1: Configure Preview settings

Previews do not use your production variables, secrets, or bindings. You need to define what each Preview starts with.

Pick where you want to manage that configuration:

<Tabs syncKey="workerPreviewsSetup">
<TabItem label="Dashboard">

<Steps>
1. In the Cloudflare dashboard, go to **Workers & Pages**.

   <DashButton url="/?to=/:account/workers-and-pages" />

2. Select your Worker.
3. Go to **Settings** and switch from **Production** to **Previews**.
4. Add variables, secrets, and bindings for Previews. You can import names from Production.
</Steps>

</TabItem>
<TabItem label="Wrangler">

Add a `previews` block to your Wrangler configuration file. Top-level settings are production. The `previews` block overrides them for Previews.

```txt title="wrangler.jsonc"
{
  "vars": {
    "ENVIRONMENT": "production"
  },
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    }
  }
}
```

</TabItem>
</Tabs>

For the full list of what inherits from production and what you need to restate, refer to [Configuration](/workers/previews/configuration/).

## Step 2: Deploy a Preview

All three options use `npx wrangler preview` under the hood. Pick the one that fits your workflow:

<Tabs syncKey="workerPreviewsDeploy">
<TabItem label="Workers Builds (Git push)">

Best when your Worker is connected to GitHub or GitLab and you want automatic Previews on every push.

<Steps>
1. [Connect your repo to Workers Builds](/workers/ci-cd/builds/#get-started).
2. Enable [Preview Builds](/workers/ci-cd/builds/build-branches/#configure-preview-builds).
3. Push a branch or open a pull request.
</Steps>

Workers Builds runs `npx wrangler preview`, deploys the Preview, and [comments the Preview URL](/workers/ci-cd/builds/git-integration/github-integration/#pull-request-comment) on your PR.

</TabItem>
<TabItem label="External CI">

Best when you already use GitHub Actions, GitLab CI, Buildkite, or another provider.

Add `wrangler preview` to your CI workflow. You do not need Workers Builds.

```yaml title=".github/workflows/preview.yml"
name: Preview
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: cloudflare/wrangler-action@v4
        with:
          command: preview
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
```

The Preview URL stays stable across commits to the same PR.

For more CI examples, refer to [GitHub Actions and CI](/workers/previews/ci-cd/).

</TabItem>
<TabItem label="Local (Wrangler CLI)">

Best for testing a branch on your machine before pushing.

```sh
npx wrangler preview
```

The Preview name defaults to your current git branch. Set it explicitly with `--name`:

```sh
npx wrangler preview --name staging
```

</TabItem>
</Tabs>

## What to know about resources

Durable Objects and Containers get separate state per Preview automatically. For KV, D1, R2, and other resources, isolation depends on what you bind the Preview to — point it at a staging resource to keep data separate.

Full details in [Resources and isolation](/workers/previews/resources/).
