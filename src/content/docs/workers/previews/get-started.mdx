To avoid any risk of accidentally using production resources, Previews are fully isolated from production and do not inherit any production configuration.

Configure your Previews [Base configuration](/workers/previews/configuration/#setting-your-previews-base-configuration) first to deploy a running Preview from any branch.

## Step 1: Configure Previews Base settings

You can configure Previews in the dashboard or your Wrangler configuration file, just as you would for production.

To understand how resources work with your [Base configuration](/workers/previews/configuration/#setting-your-previews-base-configuration) — including how to configure [separate namespaces for Durable Objects and Containers](/workers/previews/resources/#durable-objects-and-containers) — refer to [Resources and isolation](/workers/previews/resources/).

<Tabs syncKey="workerPreviewsSetup">
<TabItem label="Dashboard">

<Steps>
1. In the Cloudflare dashboard, go to **Workers & Pages**.

   <DashButton url="/?to=/:account/workers-and-pages" />

2. Select your Worker.
3. Go to **Settings**. The **Variables and secrets**, **Bindings**, **Observability**, and **Runtime** sections each have inline toggles for **Production** and **[Previews Base](/workers/previews/configuration/#setting-your-previews-base-configuration)**.

   ![Settings tab showing Production and Previews Base toggles for variables, secrets, and bindings](~/assets/images/workers/previews/settings-base-configuration.png)

4. Select **[Previews Base](/workers/previews/configuration/#setting-your-previews-base-configuration)** in each section to configure your Preview settings. To get started quicker, you can import names and values from production and then edit them — but secrets must be manually re-entered.

   ![Import dialog showing variables and secrets imported from production to Previews](~/assets/images/workers/previews/import_from_prod.png)
</Steps>

</TabItem>
<TabItem label="Wrangler">

Add a `previews` block to your Wrangler configuration file. Top-level settings are production. The `previews` block contains the configuration for the Preview you deploy to.

```txt title="wrangler.jsonc"
{
  "vars": {
    "ENVIRONMENT": "production"
  },
  "previews": {
    "vars": {
      "ENVIRONMENT": "preview"
    }
  }
}
```

For details on what to include in your `previews` block based on your production settings, refer to [Wrangler configuration file](/workers/previews/configuration/#wrangler-configuration-file).

</TabItem>
</Tabs>

## Step 2: Deploy a Preview

Deploy a Preview by running `npx wrangler preview`. The Preview name defaults to your current Git branch, or you can set it explicitly with `--name`.

<Tabs syncKey="workerPreviewsDeploy">
<TabItem label="Workers Builds">

Best when your Worker is connected to GitHub or GitLab and you want automatic Previews on every push.

<Steps>
1. [Connect your repo to Workers Builds](/workers/ci-cd/builds/#get-started).
2. Enable [Preview Builds](/workers/ci-cd/builds/build-branches/#configure-preview-builds), if not already enabled. If your Worker is already connected to Builds, you need to update your preview command. Select **Enable Worker Previews** in the dashboard to switch from your old version command to `npx wrangler preview`.

   **TODO: input screenshot of command change dialog**

3. Push a branch or open a pull request.
</Steps>

Workers Builds runs `npx wrangler preview`, deploys the Preview, and [comments the Preview URL](/workers/ci-cd/builds/git-integration/github-integration/#pull-request-comment) on your PR.

</TabItem>
<TabItem label="External CI">

Best when you already use GitHub Actions, GitLab CI, Buildkite, or another provider.

Add `wrangler preview` to your CI workflow. You do not need Workers Builds.

```yaml title=".github/workflows/preview.yml"
name: Preview
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: cloudflare/wrangler-action@v4
        with:
          command: preview
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
```

The Preview URL stays stable across commits to the same PR.

For more CI examples, refer to [GitHub Actions and CI](/workers/previews/ci-cd/).

</TabItem>
</Tabs>

## Override settings for a specific Preview

Once a Preview is deployed, you can access it through the breadcrumb dropdown in the dashboard, which lets you switch between Production and any of your Previews.

![Breadcrumb dropdown showing Production and individual Previews](~/assets/images/workers/previews/breadcrumb.png)

Each Preview has its own Metrics, Deployments, Observability, and Settings tabs. If you go to **Settings**, you can override any value copied over from [Previews Base](/workers/previews/configuration/#setting-your-previews-base-configuration) — meaning each Preview effectively has its own independent settings.

![Per-Preview settings page with its own variables and bindings](~/assets/images/workers/previews/scoped_settings.png)
