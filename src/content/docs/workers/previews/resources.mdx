Use Preview resource settings to control what data and services a branch can access before it lands in production.

Previews are isolated from production Worker deployments, but not every resource is copied automatically. Some resources are isolated per Preview. Other account-level resources are shared unless you configure different resources for Previews.

After you choose how to create a Preview, configure the resources each Preview branch should use. For settings ownership, refer to [Configuration](/workers/previews/configuration/).

Before sharing a Preview URL, check every account-level binding. If a Preview points at a production resource ID, the Preview can read or write production data.

## Resource behavior

| Resource type    | Preview behavior                                                  |
| ---------------- | ----------------------------------------------------------------- |
| Durable Objects  | Isolated automatically per Preview.                               |
| Workflows        | Isolated automatically per Preview.                               |
| Containers       | Isolated automatically per Preview.                               |
| KV               | Shared unless you configure a Preview namespace.                  |
| D1               | Shared unless you configure a Preview database.                   |
| R2               | Shared unless you configure a Preview bucket.                     |
| Queues           | Shared unless you configure Preview queues.                       |
| Vectorize        | Shared unless you configure a Preview index.                      |
| Hyperdrive       | Shared unless you configure a Preview Hyperdrive config.          |
| Service bindings | Call the Worker named in the binding unless configured otherwise. |

Use [Preview settings](/workers/previews/configuration/) to decide where a resource setting goes: future Preview branches, this Preview branch, or existing Preview branches.

Changing a resource in Shared Preview Settings affects future Preview branches. To change a resource for a Preview branch that already exists, edit that Preview's settings directly.

## Automatically isolated resources

Durable Objects, Workflows, and Containers are provisioned separately for each Preview.

For Durable Objects, each Preview gets its own namespace and storage for the same Durable Object class. Production, Preview A, and Preview B do not share Durable Object storage.

You do not need to create separate Durable Object namespaces for each Preview.

## Shared account-level resources

Resources such as KV, D1, R2, Queues, Vectorize, Hyperdrive, Analytics Engine, Secrets Store, mTLS, and Dispatch namespaces are account-level resources. If a Preview points at the same resource ID as production, the Preview can read or write the same resource as production.

To isolate a branch, point its Preview binding at a test resource.

<WranglerConfig>

```jsonc
{
	"kv_namespaces": [
		{
			"binding": "CACHE",
			"id": "prod-kv-id",
		},
	],
	"previews": {
		"kv_namespaces": [
			{
				"binding": "CACHE",
				"id": "preview-kv-id",
			},
		],
	},
}
```

</WranglerConfig>

Your Worker code still uses `env.CACHE`. The Preview receives a different namespace.

## Auto-provisioned resources

Use auto-provisioning when you want Wrangler to create a test resource for your branch instead of manually creating one first.

Wrangler can create Preview resources for KV, D1, and R2 when you omit the resource identifier in the `previews` block.

| Binding         | Omit this field | Created resource |
| --------------- | --------------- | ---------------- |
| `kv_namespaces` | `id`            | KV namespace.    |
| `d1_databases`  | `database_name` | D1 database.     |
| `r2_buckets`    | `bucket_name`   | R2 bucket.       |

After creating the resource, Wrangler writes the identifier back to your config file.

## Service bindings

A Preview does not automatically call matching Previews of other Workers. A service binding calls the Worker configured in the binding.

For example, if `frontend` has a service binding to `api`, a Preview of `frontend` calls the configured `api` Worker. If the `frontend` Preview should call a test API, configure the Preview binding to point at that test Worker.

### Same-Worker entrypoints

If the call stays inside the same Worker, avoid binding the Worker to itself. A self-service binding can still call the Worker named in the binding, which may be production.

Use [`ctx.exports`](/workers/runtime-apis/context/#exports) for [named entrypoints](/workers/runtime-apis/bindings/service-bindings/rpc/#named-entrypoints) in the same Worker. This keeps the call inside the same Preview, so it uses the Preview's code, variables, secrets, and bindings.

`ctx.exports` requires the [`enable_ctx_exports` compatibility flag](/workers/configuration/compatibility-flags/#enable-ctxexports).

## User-managed triggers

Routes, cron triggers, and queue consumers target production Workers. They do not target Previews.

Use a Preview URL or custom domain Preview URL when you want to send HTTP traffic to a Preview.

## External state

Previews can still affect external systems if you configure them with production credentials, URLs, or resource IDs. Before sharing a Preview, verify that its settings point at safe test resources.
