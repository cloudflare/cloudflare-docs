This guide shows you how to move an application from Vercel to Cloudflare Workers. Workers runs your framework's server code and serves its static assets from a single Worker.

## Choose your framework

Each framework guide includes a prompt for your coding agent and the equivalent manual steps. Every guide was tested end to end by migrating a real Vercel-hosted application.

| Framework                      | Guide                                                                                                           | What changes                                                    |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Astro                          | [Migrate Astro from Vercel](/workers/static-assets/migration-guides/vercel-to-workers/astro/)                   | `@astrojs/vercel` is replaced by `@astrojs/cloudflare`          |
| Next.js                        | [Migrate Next.js from Vercel](/workers/static-assets/migration-guides/vercel-to-workers/nextjs/)                | vinext runs your Next.js app on Vite and Workers                |
| Nuxt                           | [Migrate Nuxt from Vercel](/workers/static-assets/migration-guides/vercel-to-workers/nuxt/)                     | The Nitro `vercel` preset is replaced by `cloudflare_module`    |
| Remix and React Router         | [Migrate React Router from Vercel](/workers/static-assets/migration-guides/vercel-to-workers/react-router/)     | `@vercel/remix` is replaced by the Cloudflare Vite plugin       |
| SvelteKit                      | [Migrate SvelteKit from Vercel](/workers/static-assets/migration-guides/vercel-to-workers/sveltekit/)           | `adapter-vercel` is replaced by `adapter-cloudflare`            |

## Before you begin

These steps apply to every framework:

- Install dependencies before you run any migration tool. [Automatic project configuration](/workers/framework-guides/automatic-configuration/) cannot detect your framework without `node_modules`.
- If you use pnpm 10 or later, allow the `esbuild` and `workerd` build scripts. Otherwise, installs fail with `ERR_PNPM_IGNORED_BUILDS`. Run `pnpm approve-builds --all`, or add the packages to `allowBuilds` in `pnpm-workspace.yaml`.
- Set the Worker `name` explicitly. Migration tools default to the `name` field in `package.json`, which is often a template name.
- Use a compatibility date of `2026-08-04` or later, for example today. [Node.js compatibility](/workers/runtime-apis/nodejs/) is on by default for these dates, so new configurations do not need the `nodejs_compat` flag. Existing configurations can keep it. For more information, refer to [Node.js compatibility flag](/workers/configuration/compatibility-flags/#nodejs-compatibility-flag).
- Add `.wrangler/` and `.dev.vars*` to `.gitignore`.
- If your account has access to more than one Cloudflare account, set the `CLOUDFLARE_ACCOUNT_ID` environment variable before you deploy.

## Migrate a static site or single-page application

Use these steps if your project does not render pages on the server.

<Steps>

1. In the Vercel dashboard, go to your project's **Settings** > **Build & Development settings**. Note the **Build Command** and **Output Directory** values.

   ![Finding the Build Command and Output Directory fields](~/assets/images/workers/migrations/vercel-deploy-1.png)

2. In the root of your project, create a Wrangler configuration file. Replace `<your-project-name>` with your project name, and `<your-build-directory>` with the output directory, for example `./dist`.

   For a static site:

   <WranglerConfig>

   ```jsonc
   {
   	"name": "<your-project-name>",
   	"compatibility_date": "$today",
   	"assets": {
   		"directory": "<your-build-directory>",
   	},
   }
   ```

   </WranglerConfig>

   For a single-page application, add `not_found_handling`:

   <WranglerConfig>

   ```jsonc
   {
   	"name": "<your-project-name>",
   	"compatibility_date": "$today",
   	"assets": {
   		"directory": "<your-build-directory>",
   		"not_found_handling": "single-page-application",
   	},
   }
   ```

   </WranglerConfig>

3. Build your project, then deploy it:

   <PackageManagers type="exec" pkg="wrangler" args="deploy" />

4. To deploy on every push, [connect your repository to Workers Builds](/workers/ci-cd/builds/#connect-a-new-worker). Use the same build command as on Vercel, and use `npx wrangler deploy` as the deploy command.

</Steps>

## Map Vercel features to Cloudflare

Each Vercel feature has a Cloudflare equivalent:

| Vercel feature                        | Cloudflare equivalent                                                                                                                             |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Analytics and Speed Insights          | [Web Analytics](/web-analytics/)                                                                                                                  |
| Blob                                  | [R2](/r2/)                                                                                                                                        |
| Cron Jobs                             | [Cron Triggers](/workers/configuration/cron-triggers/) with a `scheduled()` handler                                                               |
| Edge Config                           | [Workers KV](/kv/)                                                                                                                                |
| Environment variables                 | [Environment variables](/workers/configuration/environment-variables/) and [secrets](/workers/configuration/secrets/)                             |
| Functions, Edge Functions, Middleware | One Worker, built by your framework adapter                                                                                                       |
| Git integration and preview URLs      | [Workers Builds](/workers/ci-cd/builds/) and [preview URLs](/workers/previews/)                                                                   |
| Image Optimization                    | [Images binding](/images/optimization/binding/) or [image transformations](/images/optimization/transformations/)                                 |
| ISR and `s-maxage` caching            | Prerendering, or your framework's Cloudflare cache integration. Refer to [Replace ISR and edge caching](#replace-isr-and-edge-caching).           |
| KV and Upstash Redis                  | [Workers KV](/kv/), or keep Upstash and connect over HTTP                                                                                         |
| Postgres                              | Keep your database and connect with [Hyperdrive](/hyperdrive/), or use [D1](/d1/)                                                                 |
| Queues                                | [Queues](/queues/)                                                                                                                                |
| `vercel.json` headers and redirects   | Framework configuration, or [`_headers`](/workers/static-assets/headers/) and [`_redirects`](/workers/static-assets/redirects/) for static assets |

Vercel-specific URLs, such as `/_vercel/image` and `/_vercel/insights`, return `404` after you migrate. Update any references to them.

## Move environment variables and secrets

To copy production environment variables from Vercel to your Worker:

<Steps>

1. Pull the production environment variables with the Vercel CLI:

   ```sh
   vercel env pull .env.production.local --environment=production
   ```

   Vercel does not return the values of sensitive environment variables. Add those values to the file manually.

2. Upload the variables as Worker secrets:

   <PackageManagers type="exec" pkg="wrangler" args="secret bulk .env.production.local" />

3. Delete `.env.production.local` after the upload.

</Steps>

Store non-secret values in `vars` in your Wrangler configuration file. Store local development secrets in a `.dev.vars` file. Public build-time variables, such as `NEXT_PUBLIC_*`, `VITE_*`, and `PUBLIC_*`, must exist when your project builds. If you use Workers Builds, add them as [build variables](/workers/ci-cd/builds/configuration/).

## Restore caching for hashed assets

Vercel serves hashed build assets with a one-year immutable cache. Workers serves static assets with `max-age=0, must-revalidate` by default. To restore long-lived caching, add a `_headers` file to your static directory. Adjust the path to match your framework's asset directory:

```txt title="public/_headers"
/assets/*
  Cache-Control: public, max-age=31536000, immutable
```

SvelteKit and Nuxt generate a `_headers` file for you. Cloudflare applies every `_headers` rule that matches a path. To replace a header value from a less specific rule, add `! Header-Name` before the new value. For more information, refer to [Headers](/workers/static-assets/headers/).

## Replace ISR and edge caching

On Vercel, a `Cache-Control: s-maxage` header caches server-rendered responses at the edge. On Workers, turn on [Workers Cache](/workers/cache/) to cache your Worker's responses based on the `Cache-Control` headers they return. Workers Cache requires Wrangler 4.69.0 or later.

<WranglerConfig>

```jsonc
{
	"cache": {
		"enabled": true,
	},
}
```

</WranglerConfig>

Workers Cache does not serve stale responses that include `s-maxage`, even if they also set `stale-while-revalidate`. For more information, refer to [Cache-Control semantics](/workers/cache/configuration/#cache-control-semantics).

When caching is on, all requests to your Worker are billed at the standard request rate, including static asset requests. For more information, refer to [Workers Cache pricing](/workers/cache/#pricing).

You can also prerender pages that do not change between deploys, use your framework's Cloudflare cache integration, such as Astro route caching or a vinext cache adapter, or use the [Cache API](/workers/runtime-apis/cache/) from your server code.

## Add a custom domain

Workers Custom Domains only supports domains that are configured as zones on your account. A zone is a domain, such as `example.com`, that Cloudflare manages for you, including its DNS and traffic.

To move a domain without downtime:

<Steps>

1. Deploy your Worker and test it on its `workers.dev` URL. Keep Vercel serving production.
2. Lower the time to live (TTL) of your DNS records.
3. Add your domain to Cloudflare as a zone. Confirm that the imported DNS records match your Vercel records, then update the nameservers at your registrar.
4. [Add a custom domain to your Worker](/workers/configuration/routing/custom-domains/#add-a-custom-domain). The custom domain replaces the existing Vercel DNS record for that hostname and issues a certificate.
5. Confirm that traffic reaches your Worker, then remove the domain from your Vercel project.

</Steps>

## Delete your Vercel app

After your custom domain sends requests to Cloudflare Workers, you can delete your Vercel application.

## Troubleshooting

- Review the [Workers limits](/workers/platform/limits/). SSR applications usually need the Workers Paid plan, because the Free plan allows 10 ms of CPU time per request.
- Native Node.js modules, such as `sharp` and `canvas`, do not run on Workers. Runtime writes to the file system also fail.
- On a `workers.dev` URL, Cloudflare serves a managed `robots.txt` file if your application does not provide one.
- For more migration steps, refer to the [Cloudflare Pages to Workers migration guide](/workers/static-assets/migration-guides/migrate-from-pages/).
