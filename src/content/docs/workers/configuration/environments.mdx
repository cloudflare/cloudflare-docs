An **environment** is a collection of settings that determines how your Worker runs. These settings include which resources it connects to, what [environment variables](/workers/configuration/environment-variables/) and [secrets](/workers/configuration/secrets/) it uses, and what domains it's available on.

Every Worker has two **environments**:

- **[Production](#production)**: For serving your live application to real users.

- **[Preview](#preview)**: For reviewing, testing, and sharing changes before they go live. When you create a preview deployment (by pushing to a pull request or running `wrangler deploy --preview`), the deployment uses your Preview environment settings.

You can also easily set up your **[local development environment](#local-development)** by pulling down your **Preview** settings with `wrangler env pull` to develop and test changes on your local machine.

## Configuration

When you write a Worker, you need to tell Cloudflare two things:

1. **What your Worker is** - Its name, which code file to run, and how it should behave
2. **What your Worker connects to** - Which databases, API keys, and resources to use

The second part is different for **Production** (your live site) and **Preview** (testing changes). You configure these separately so your tests don't accidentally mess with real user data.

Here's what a configuration file looks like:

<WranglerConfig>
```jsonc title="wrangler.jsonc"
{
  "name": "my-worker",
  "compatibility_date": "$today",
  "main": "src/index.ts",
  "production": {
    "domains": ["app.example.com"],
    "env": {
      "DB": {
        "type": "d1",
        "database_id": "prod-db-123"
      }
    }
  },
  "preview": {
    "env": {
      "DB": {
        "type": "d1",
        "database_id": "preview-db-456"
      }
    }
  }
}
```
</WranglerConfig>

Notice how `production` and `preview` have different values for `database_id`? Your Worker code always uses `env.DB` - it never references a specific database ID. The configuration file tells Cloudflare what `env.DB` actually points to.

**What can differ between environments:**

You can configure environment variables, secrets, resource connections, and observability settings differently between **Production** and **Preview**. Everything else stays the same - like your Worker's name, which code file to run, and build settings.

**How it works in practice:**

When you're developing a new feature, you push your code to a feature branch and open a pull request. Cloudflare automatically creates a preview deployment at a unique URL where you can test your changes. This preview deployment runs your new code and uses your **Preview** environment settings - so `env.DB` connects to your test database, `env.API_SECRET` uses your test API key, and so on. You and your team can click the URL and try out the feature without affecting your live site.

If someone else on your team is working on a different feature in a separate pull request, they get their own preview deployment with their own unique URL. Each preview deployment runs different code (your feature vs their feature), but they all share the same **Preview** environment settings - they all connect to the same test database, use the same test API keys, and so on. This way multiple people can test their changes at the same time without their code clashing.

When you're ready to go live, you merge your pull request. Cloudflare deploys your code to **Production**, and now the exact same code that you just tested runs with your **Production** environment settings instead - `env.DB` now connects to your real database with actual user data, `env.API_SECRET` uses your live API key, and your Worker serves traffic to your users.

### Configuring the env object

An environment variable can have one of the following types:

- **Plain text** (`type: "text"`) - String values
- [**Secrets**](/workers/configuration/secrets/) - Sensitive data like API keys (managed via [`wrangler secret put`](/workers/configuration/secrets/), not in the configuration file)
- **Resource bindings** (`type: "kv_namespace"`, `type: "d1"`, `type: "r2_bucket"`, etc.) - Live objects that let you interact with Cloudflare resources

<WranglerConfig>
```jsonc title="wrangler.jsonc"
{
  "name": "my-worker",
  "compatibility_date": "$today",
  "production": {
    "domains": ["app.example.com"],
    "env": {
      // Plain text
      "API_BASE": {
        "type": "text",
        "value": "https://api.cloudflare.com/client/v4"
      },
      // KV namespace
      "MY_KV": {
        "type": "kv_namespace",
        "id": "abc123prod"
      },
      // D1 database
      "DB": {
        "type": "d1",
        "database_id": "prod-db-id-123"
      }
    }
  },
  "preview": {
    "env": {
      "API_BASE": {
        "type": "text",
        "value": "https://api.cloudflare.com/client/v4"
      },
      "MY_KV": {
        "type": "kv_namespace",
        "id": "def456preview"
      },
      "DB": {
        "type": "d1",
        "database_id": "preview-db-id-456"
      }
    }
  }
}
```
</WranglerConfig>

### Accessing environment variables in your Worker

All environment variables you configure are accessible in your Worker code via the `env` object. Access them using `env.<VARIABLE_NAME>`:

<TypeScriptExample>
```ts
export default {
  async fetch(request, env, ctx) {
    // Access plain text environment variable
    const apiBase = env.API_BASE;

    // Access KV namespace binding
    await env.MY_KV.put("key", "value");

    // Access D1 database binding
    const results = await env.DB.prepare("SELECT * FROM users").all();

    return new Response("Hello!");
  }
}
```
</TypeScriptExample>

The `env` parameter is automatically passed to your Worker's `fetch` handler and contains all the environment variables specific to the environment (Production or Preview) your Worker is running in.

### Secrets

[Secrets](/workers/configuration/secrets/) contain sensitive data like API keys, passwords, and tokens. You cannot define secrets in your [Wrangler configuration file](/workers/wrangler/configuration/) - you must set them using the CLI or dashboard.

Secrets are **not shared** between environments. You must set them separately for each environment ([Production](#production), [Preview](#preview)) to keep them secure.

#### Set secrets for your Production environment

**CLI**

<PackageManagers type="exec" pkg="wrangler" args="secret put API_SECRET" />

**Dashboard**

Go to **Settings** > **Environments** > **Production** > **Secrets**

#### Set secrets for your Preview environment

**CLI**

<PackageManagers type="exec" pkg="wrangler" args="secret put API_SECRET --preview" />

**Dashboard**

Go to **Settings** > **Environments** > **Preview** > **Secrets**

## Production

Your **Production** environment defines the configuration your Worker uses to serve live traffic. This includes what [environment variables](/workers/configuration/environment-variables/) it has access to and which resources it connects to.

Your Worker uses **Production** settings when you:

- Run [`wrangler deploy`](/workers/wrangler/commands/#deploy) using the Wrangler CLI
- Merge a change into your **Production** branch (which defaults to `main`) with [automated builds](/workers/ci-cd/builds/)

### Configuration

You define your **Production** environment using the `production` section in your configuration file.

<WranglerConfig>
```jsonc title="wrangler.jsonc"
{
  "name": "my-worker",
  "compatibility_date": "$today",
  "production": {
    "domains": ["app.example.com"],
    "env": {
      "ENVIRONMENT": {
        "type": "text",
        "value": "production"
      },
      "MY_KV": {
        "type": "kv_namespace",
        "id": "xyz789production"
      },
      "DB": {
        "type": "d1",
        "database_id": "prod-db-id-123"
      }
    }
  }
}
```
</WranglerConfig>

### Domains

You can configure which domains your Worker is available on by setting the `domains` field. If you don't include a `domains` field, your existing domain configuration stays unchanged.

<WranglerConfig>
```jsonc title="wrangler.jsonc"
// Use the free workers.dev subdomain
{
  "name": "my-worker",
  "production": {
    "domains": ["my-worker.workers.dev"]
  }
}

// Use your own custom domain
{
  "name": "my-worker",
  "production": {
    "domains": ["app.example.com"]
  }
}

// Use both workers.dev and a custom domain
{
  "name": "my-worker",
  "production": {
    "domains": [
      "my-worker.workers.dev",
      "app.example.com"
    ]
  }
}
```
</WranglerConfig>

For advanced routing patterns (like running your Worker only on specific URL paths), use the `routes` field:

<WranglerConfig>
```jsonc title="wrangler.jsonc"
{
  "name": "my-worker",
  "production": {
    "domains": ["app.example.com"],
    "routes": [
      { "pattern": "www.example.com/api/*", "zone_id": "your-zone-id" }
    ]
  }
}
```
</WranglerConfig>

## Preview

Your **Preview** environment is a collection of settings that keep your **Production** data safe while you develop and review changes. For example, you can configure **Preview** to use a separate database instead of your production database.

### Configuration

Define your **Preview** environment using the `preview` section:

<WranglerConfig>
```jsonc title="wrangler.jsonc"
{
  "name": "my-worker",
  "compatibility_date": "$today",
  "production": {
    "domains": ["app.example.com"],
    "env": {
      "DB": {
        "type": "d1",
        "database_id": "prod-db-id-123"
      }
    }
  },
  "preview": {
    "env": {
      "DB": {
        "type": "d1",
        "database_id": "preview-db-id-456"  // Use separate database
      }
    }
  }
}
```
</WranglerConfig>

**Preview deployments** will use the separate database (`preview-db-id-456`).

### Using Preview deployments

Cloudflare automatically creates a **Preview deployment** with its own unique URL when you:

- Push a commit to a pull request (when you've connected your [Git repository](/workers/ci-cd/builds/git-integration/)). Cloudflare posts a comment on your PR with a link.
- Run [`wrangler deploy --preview`](/workers/wrangler/commands/#deploy) using the CLI.

Each deployment you create can run different code but uses the same **Preview** environment settings - so you and your team can review multiple changes at the same time without affecting your live site.

### Override settings for a specific Preview deployment

If a specific PR needs to use different resources, [environment variables](/workers/configuration/environment-variables/), or [secrets](/workers/configuration/secrets/) than what's configured for the **Preview** environment, you can override them for that specific **Preview deployment**.

For example, one PR might be debugging a complex issue and needs `DEBUG_MODE=true` with verbose logging enabled, while other PRs use normal logging levels.

**To set overrides for a specific Preview deployment:**

1. Go to **Workers & Pages** > select your Worker
2. Go to **Deployments** > find your **Preview deployment**
3. Click **Settings** > **Variables & secrets** > toggle the **Override** button
4. Add or modify the values you want to override for this specific PR
5. Click **Save** - this redeploys the **Preview deployment** with your overrides

All future commits to that branch will automatically use these overrides. When the branch is deleted, the overrides are automatically cleaned up.

## Local Development

**Local Development** is where you develop and test changes on your local machine. Unlike **[Production](#production)** and **[Preview](#preview)** which run on Cloudflare's network, local development uses [Miniflare](https://miniflare.dev/) to simulate the Workers runtime on your computer.

Local development is not a separate stored environment. Instead, you pull environment variables from Preview or Production.

You can set up your local development environment by pulling down environment settings from **Preview** (default) or **Production**.

By default, `wrangler env pull` pulls from your **Preview** environment:

<PackageManagers type="exec" pkg="wrangler" args="env pull" />

This creates a `.env.local` file in your project root that contains:

```ini title=".env.local"
# Environment variables from Preview environment
API_KEY=your-preview-api-key
ENVIRONMENT=preview

# Bindings (commented out by default - simulated locally)
# Uncomment to connect to the remote resource
# MY_KV=@kv_namespace:abc123preview
# DB=@d1:preview-db-id-456
# MY_BUCKET=@r2_bucket:preview-bucket
```

You can also pull from **Production**:

<PackageManagers type="exec" pkg="wrangler" args="env pull --prod" />

### Local vs Remote bindings

By default, all bindings in your `.env.local` file are commented out. This means [Miniflare](https://miniflare.dev/) will create local simulations of your resources (like [KV namespaces](/kv/) or [D1 databases](/d1/)). This lets you develop offline without costs or needing to connect to deployed resources.

To connect a binding to its remote resource in **Preview** or **Production**, uncomment the line in your `.env.local` file:

```ini title=".env.local"
# Environment variables
API_KEY=your-preview-api-key
ENVIRONMENT=preview

# Simulated locally (commented out)
# MY_KV=@kv_namespace:abc123preview

# Connected to remote Preview resource (uncommented)
DB=@d1:preview-db-id-456
MY_BUCKET=@r2_bucket:preview-bucket
```

The syntax is: `BINDING_NAME=@resource_type:resource_id`

- `BINDING_NAME` - The name of your binding
- `@` - Directive that indicates this is a binding, not a plain text value
- `resource_type` - The type of resource (`kv_namespace`, `d1`, `r2_bucket`, etc.)
- `resource_id` - The ID of the specific resource to connect to

When you run [`wrangler dev`](/workers/wrangler/commands/#dev) or `vite dev`, Wrangler will:
- Simulate `MY_KV` locally (commented out)
- Connect `DB` and `MY_BUCKET` to their remote **Preview** resources (uncommented)
- Use the environment variables from **Preview** (`API_KEY`, `ENVIRONMENT`)

<TabItem label="API">

This guide walks you through deploying to both **Production** and **Preview** environments using the Cloudflare API. We'll break it down step by step.

#### Create your Worker

Before you can deploy anything, you need to create a Worker. Think of this as creating your **Production** Worker - the main container that will hold all your production code and settings. Later, we'll create preview Workers as sub-resources of this main Worker.

```bash
# Set your credentials
ACCOUNT_ID="your_account_id"
API_TOKEN="your_api_token"
WORKER_NAME="my-worker"

# Create the Worker (this is your Production Worker)
WORKER_ID=$(curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/workers" \
  -X POST \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "'$WORKER_NAME'"
  }' \
  | jq -r '.result.id')

echo "Worker ID: $WORKER_ID"
```

This gives you back a Worker ID that you'll use in the next steps. Keep this ID handy!

#### Configure Preview settings

```bash
# Set up preview_settings on your Worker
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/workers/$WORKER_ID" \
```

#### Deploy to Production

Now let's deploy your code to **Production**. A [version](/workers/configuration/versions-and-deployments/) is a snapshot of your Worker's code and settings at a specific point in time. A [deployment](/workers/configuration/versions-and-deployments/#deployments) controls which version(s) receive traffic and how much. This is a two-step process:

1. **Create a version** - Upload your code and specify your **Production** environment variables
2. **Create a deployment** - Tell Cloudflare to send traffic to this version

```bash
# First, prepare your script by encoding it to base64
SCRIPT_BASE64=$(cat ./dist/index.js | base64)

# Step 1: Create a version with your Production environment variables
VERSION_ID=$(curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/workers/$WORKER_ID/versions" \
  -X POST \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "compatibility_date": "$today",
    "main_module": "index.js",
    "modules": [
      {
        "name": "index.js",
        "content_type": "application/javascript+module",
        "content_base64": "'$SCRIPT_BASE64'"
      }
    ],
    "bindings": [
      {
        "type": "plain_text",
        "name": "ENVIRONMENT",
        "text": "production"
      },
      {
        "type": "kv_namespace",
        "name": "MY_KV",
        "namespace_id": "xyz789production"
      },
      {
        "type": "secret_text",
        "name": "API_SECRET",
        "text": "your-production-secret"
      }
    ]
  }' \
  | jq -r '.result.id')

echo "Version ID: $VERSION_ID"

# Step 2: Create a deployment that sends 100% of traffic to this version
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/scripts/$WORKER_NAME/deployments" \
  -X POST \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "strategy": "percentage",
    "versions": [
      {
        "percentage": 100,
        "version_id": "'$VERSION_ID'"
      }
    ]
  }'
```

Your Worker is now live in **Production**! Notice how we included all the environment variables in the `bindings` array - the `ENVIRONMENT` variable set to "production", the production KV namespace (`xyz789production`), and the production secret (`API_SECRET`).

#### Deploy a Preview

**Preview deployments** are temporary, fully-featured Workers that are automatically cleaned up when your pull request is merged or closed. They're created as sub-resources nested under your main Production Worker (notice the `/workers/$WORKER_ID/previews` endpoint).
```bash
BRANCH_NAME="feature-xyz-123"
PREVIEW_SCRIPT_BASE64=$(cat ./dist/index.js | base64)

  -X POST \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "annotations": {
      "workers/branch": "'$BRANCH_NAME'"
    }
  }' \
  | jq -r '.result.id')

echo "Preview Worker ID: $PREVIEW_ID"

# Create a version for the preview and deploy it immediately
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/workers/$WORKER_ID/previews/$PREVIEW_ID/versions?deploy=true" \

        "content_type": "application/javascript+module",

```

The preview automatically uses the environment variables from your `preview_settings` - `ENVIRONMENT` is set to "preview", it connects to the preview KV namespace (`abc123preview`), and includes the preview secret (`API_SECRET`). This keeps your test data and secrets separate from production!

Notice the `?deploy=true` parameter - this creates the version and deploys it in one step.

#### Deploy a Preview

**Preview deployments** are temporary, fully-featured Workers that are automatically cleaned up when your pull request is merged or closed. They're created as sub-resources nested under your main Production Worker. When you create a preview, it automatically uses the `preview_settings` you configured earlier. Here's how you create one:

```typescript
async function deployPreview(workerId: string, branchName: string) {
	// Step 1: Create a preview Worker (nested under your Production Worker)
	const preview = await client.workers.beta.workers.previews.create(workerId, {
		account_id: ACCOUNT_ID,
		annotations: {
			"workers/branch": branchName,
		},
	});

	console.log(`Preview Worker created with ID: ${preview.id}`);

	// Step 2: Read and encode your script
	const scriptContent = fs.readFileSync("./dist/index.js", "utf8");
	const scriptBase64 = Buffer.from(scriptContent).toString("base64");

	// Step 3: Create a version for the preview and deploy it immediately
	// Notice: We only pass the script code, NOT the bindings!
	// The bindings come from preview_settings we configured earlier.
	await client.workers.beta.workers.versions.create(
		preview.id,
		{
			account_id: ACCOUNT_ID,
			compatibility_date: new Date().toISOString().split("T")[0],
			main_module: "index.js",
			modules: [
				{
					name: "index.js",
					content_type: "application/javascript+module",
					content_base64: scriptBase64,
				},
			],
		},
		{
			params: { deploy: true },
		}
	);

	console.log("Preview deployed successfully!");
	return preview;
}

// Example usage
await deployPreview(workerId, "feature-xyz-123");
```

Notice a few important things here:

1. **We don't pass bindings** when creating the preview version - they automatically come from the `preview_settings` template we configured earlier. The API applies those settings (`ENVIRONMENT`, `MY_KV`) without us specifying them again.

2. **`{ params: { deploy: true } }`** - This creates the version and deploys it in one step, like adding `?deploy=true` to the API URL.

This keeps your test data separate from production while making it easy to deploy previews - you set up the template once, then every preview automatically uses those settings! Secrets are managed separately using the Wrangler CLI as shown in the [Set secrets](#set-secrets-1) section above.

```hcl
variable "account_id" {
```

```hcl
  versions {
    percentage = 100
    version_id = cloudflare_worker_version.my_worker_production.id
  }
}
```

### Using with Wrangler Environments

If you're using [Wrangler Environments](/workers/wrangler/environments/), each environment creates a separate Worker with the name `<worker-name>-<environment-name>`. You can add a `preview` block within each Wrangler environment to give each Worker its own **Production** and **Preview** configurations with separate **Preview deployments**. For example:

- `env.staging` creates `my-worker-staging` with its own Preview deployments
- `env.production` creates `my-worker-production` with its own Preview deployments

Here's an example configuration:

<WranglerConfig>
