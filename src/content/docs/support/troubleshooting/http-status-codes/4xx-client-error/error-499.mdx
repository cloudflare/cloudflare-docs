## 499 Client Close Request

The `HTTP 499` response code is an nginx-specific status code logged when a client closes the connection before the server finishes processing the request. Because Cloudflare is built on nginx, 499 appears in [Cloudflare Logs](/logs/) and analytics whenever this happens. A 499 is never sent in an HTTP response — it only appears in logs.

:::note
A low rate of 499 errors is expected. Clients routinely cancel requests due to page navigation, app backgrounding, or browser tab closure. Investigate when 499 errors spike noticeably above your zone's normal baseline, persist at a specific Cloudflare data center, or affect a latency-sensitive endpoint.
:::

### Common causes

499 errors typically have one of three causes, but diagnosing which requires comparing multiple log fields, time windows, and request populations — no single field is conclusive:

| Cause | Signals to look for | What to do |
|---|---|---|
| **Client timeout or cancellation** | Rate near baseline; `OriginIP` present; no TTFB spike; pattern consistent across data centers | Expected behavior. Review client timeout settings if the rate is unexpectedly elevated. |
| **Origin too slow — client aborts** | Rate spike correlated with elevated origin response time for the same endpoint and window; `OriginIP` present; same-window completed requests show elevated `OriginResponseDurationMs` | Investigate origin performance. Compare 499 requests against completed requests for the same endpoint during the same window. |
| **Possible Cloudflare-side issue** | Rate spike; `OriginIP` absent; `CfCacheStatus` is MISS, BYPASS, or DYNAMIC; errors concentrated in one data center with a rate notably higher than other data centers in the same window; no origin-side or cache explanation | Collect evidence and contact Cloudflare Support. |

### How to investigate

Use [Instant Logs](/logs/instant-logs/) or [Logpush](/logs/logpush/) to inspect 499 requests. Diagnose by comparing 499 entries against completed requests for the same endpoint and time window — not from any single field in isolation:

- **`OriginIP`** — indicates whether an origin IP was recorded for the request. An absent value does not by itself indicate a Cloudflare fault: cache-served responses (HIT or STALE) do not require an origin fetch and will not have an origin IP; an aborted or partially logged request may also lack one.
- **`CfCacheStatus`** — cross-check with `OriginIP`. If `OriginIP` is absent and `CfCacheStatus` is HIT or STALE, the request was served from cache and the missing origin IP is expected. If `OriginIP` is absent and `CfCacheStatus` is MISS, BYPASS, or DYNAMIC, Cloudflare should have contacted the origin but may not have — this combination warrants investigation.
- **`OriginResponseDurationMs`** — measures the elapsed time from the start of the origin request to the last byte of the response, including Argo Smart Routing and Tiered Cache time in addition to origin connection and response time. An elevated value suggests a delay somewhere in the origin-connect-respond path, not necessarily at the origin server itself.
- **`EdgeColoCode`** — if 499 errors concentrate in one data center, compare the 499 rate in that data center against the same-window rate in other data centers serving the same zone. A significantly higher rate in one location is worth investigating further; the location alone is not evidence of an infrastructure fault.
- **UTC time window and volume trend** — compare 499 counts against completed requests in the same window. A spike that affects only 499s while successful requests continue normally suggests a timeout or stall condition.

To investigate a 499 spike:

1. Compare `OriginResponseDurationMs` for 499 requests against completed (non-499) requests for the same endpoint and time window. If the 499 requests have notably higher values, origin-path latency is a likely contributor — check origin server logs and upstream service timing to isolate where the delay occurs.
2. Filter Cloudflare Logs to `EdgeResponseStatus = 499` and check `OriginIP` and `CfCacheStatus` for those entries.
3. Group the 499 entries by `EdgeColoCode` and compare the rate in the highest-volume data center against other data centers serving the zone in the same window. If one data center is significantly elevated with no origin-side explanation, contact Cloudflare Support with the data center name, the 499 rate comparison, and the affected time window.

### TCP connection timing

When Cloudflare cannot complete a TCP handshake with your origin, it makes at most two attempts: an initial SYN with a 19-second timeout, followed by one retry with a 15-second timeout. If a client disconnects during this period, Cloudflare logs a 499.

This is one scenario in which a 499 can occur. Clients can also disconnect during the HTTP request phase, while the response headers are being sent, or while the response body is being delivered. The timing of the client disconnect determines which phase is affected, and the 19-second plus 15-second origin-connect window applies specifically to the TCP handshake phase.

### Streaming and media clients

Media players such as HLS players, DASH clients, and Android ExoPlayer often use short default connection and read timeouts. Default values vary by player and SDK version; some are configurable by the application developer and some are not.

A 499 on a streaming request can occur when first-byte delivery exceeds the player's deadline, but it can also be logged while a response body is being delivered — for example, if a segment transfer stalls mid-download. Before selecting a remedy, compare both first-byte timing and body-delivery timing for the 499 requests against completed requests for the same paths.

To investigate 499 errors in a streaming context:

1. Confirm the effective timeout in use — check the player SDK documentation and, if possible, confirm with your development team whether the timeout is configurable.
2. In Cloudflare Logs, check `EdgeTimeToFirstByteMs` and compare it against `EdgeResponseBodyBytes` and total response duration for the 499 requests versus completed requests on the same paths. This identifies whether the disconnect occurred at first byte or during body delivery.
3. Check whether the cache hit rate dropped for the affected paths. A lower hit rate forces origin fetches that can delay both first-byte and body delivery.
4. Group the 499 entries by `EdgeColoCode`. If errors concentrate in a specific data center with a rate notably higher than other data centers, contact Cloudflare Support.
5. If the cache hit rate is normal but 499 errors persist, review your [Tiered Cache](/cache/how-to/enable-tiered-cache/) settings to reduce origin latency for cache misses.

### Transaction-sensitive requests

When a 499 occurs on a request that modifies server state — for example, a payment submission or an order creation — the connection closed before a response was received. The outcome is ambiguous: your origin may or may not have processed the operation before the connection was lost.

To handle ambiguous outcomes:

- Check your origin server logs for the affected requests to determine whether the operation was recorded before the connection closed.
- Implement idempotency keys for transaction-sensitive endpoints. An idempotency key allows you to safely resubmit an ambiguous request and have your origin return the original result if the operation was already processed.

:::note
`DELETE` is defined as idempotent by [HTTP method semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) — repeating a well-formed `DELETE` request is safe. The ambiguity concern applies primarily to non-idempotent operations such as payment submissions, order creation, and other state-changing `POST` or `PATCH` requests.
:::

### When to contact Cloudflare Support

Contact support when:

- 499 errors spike clearly above your zone's normal baseline and the spike is not explained by a corresponding change in origin response time for the same endpoints and window.
- `OriginIP` is absent and `CfCacheStatus` is MISS, BYPASS, or DYNAMIC for the affected requests — ruling out cache-served responses as the explanation.
- 499 errors are significantly elevated in one data center compared to other data centers serving the same zone in the same window, with no origin-side or cache explanation.

When you contact support, include:

- The affected hostname and zone ID
- The UTC time window (start and end)
- 10–20 Ray IDs from the 499 responses
- The `OriginIP` and `CfCacheStatus` values for those Ray IDs
- The `EdgeColoCode` distribution for the 499 entries and the same-window rate in other data centers
- Whether other zones or hostnames experienced the same spike simultaneously
- For Enterprise customers: a [Logpush](/logs/logpush/) export filtered to `EdgeResponseStatus = 499` for the time window
