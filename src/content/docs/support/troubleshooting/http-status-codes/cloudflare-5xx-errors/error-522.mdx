## Error 522: connection timed out

Error `522` means Cloudflare reported a connection timeout while trying to reach the website's origin server.

### Connection setup and reuse

For a new TCP-based HTTPS connection, setup includes the TCP handshake followed by SSL/TLS negotiation. TCP can already be established while HTTPS setup remains unfinished. A timeout during that unfinished setup can be reported as `522`. A `522` therefore does not necessarily mean the TCP handshake failed.

Requests can also reuse established connections. A new TCP/TLS handshake is not required for every request.

One documented `522` condition is a timeout waiting for TCP acknowledgment of a request on an established connection. A TCP acknowledgment is distinct from an HTTP response. This means `522` is not limited to initial connection setup.

`522` reports a connection timeout. [525](/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-525/) reports an SSL/TLS handshake failure. These codes do not simply separate TCP errors from TLS errors. A timeout while TLS is pending can be reported as `522` rather than `525`. The error code alone does not identify the exact timed operation or what caused this request's failure.

### Documented TCP timeout conditions

The [Connection limits reference](/fundamentals/reference/connection-limits/) documents these TCP timeout conditions. They are not an exhaustive list of every operation that can produce `522`:

- **Before TCP establishment:** Cloudflare does not receive a SYN+ACK within 19 seconds after sending a SYN. The documented SYN retry backoff intervals are 1, 1, 1, 1, 1, 2, 4, and 8 seconds.
- **After TCP establishment:** Cloudflare does not receive a TCP acknowledgment of its resource request within 90 seconds.

These values apply to the named TCP conditions. Do not interpret either number as a universal TCP-plus-TLS setup budget or as the measured duration of this request's failure.

### Resolution

If you own the website, use these general checks:

- Verify the configured origin address and port. Confirm the service is running and accepting connections. Review its capacity and logs for overload or connection limits, and review its [HTTP keep-alive settings](/fundamentals/reference/connection-limits/#keep-alives).
- Review firewall, security, rate-limiting, and network settings for your connection path. For standard proxied origin connections, check [Cloudflare's published IP ranges](https://www.cloudflare.com/ips/). For [Dedicated CDN Egress IPs](/smart-shield/configuration/dedicated-egress-ips/), check the addresses assigned to your setup.
- If geographic restrictions are configured, review the origin's permitted connection sources separately from [visitor-country WAF rules](/waf/custom-rules/use-cases/block-by-geographical-location/). Visitor filtering and origin reachability are different checks.
- Review origin and network logs for the reported time. If the origin connection uses HTTPS, include SSL/TLS negotiation in the investigation.
- If you use Cloudflare Tunnel, review the connector and local service logs using the [Tunnel troubleshooting guide](/tunnel/troubleshooting/).
- Ask your hosting provider or network administrator to investigate the connection timeout and relevant connection-path settings. Share the [error details](/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/#required-error-details-for-hosting-provider).
- If the problem persists, contact Cloudflare Support with the Ray ID, affected URL, timestamp and time zone, and relevant findings.

### Product-specific checks

- If you are using [Cloudflare Pages](/pages/), verify that you have a custom domain set up and that your CNAME record is pointed to your [custom Pages domain](/pages/configuration/custom-domains/#add-a-custom-domain).

- If you are using [Workers with a Custom Domain](/workers/configuration/routing/custom-domains/), performing a `fetch` to its own hostname will cause a `522` error. Consider using a [Route](/workers/configuration/routing/), targeting another hostname, or enabling the [`global_fetch_strictly_public` compatibility flag](/workers/configuration/compatibility-flags/#global-fetch-strictly-public) instead.

- If you are using [Origin Rules](/rules/origin-rules/), make sure the resulting hostname can be resolved. For example, if your Origin Rule point to a Worker route, a `522` error will be returned if the hostname for this route is an A record pointing to a reserved address such as `100::` or `192.0.2.0`. 

### Information for Cloudflare Support

Request the following information from your hosting provider or site administrator before [contacting Cloudflare Support](/support/contacting-cloudflare-support/):

- An [MTR or traceroute](/support/troubleshooting/general-troubleshooting/gathering-information-for-troubleshooting-sites/#perform-a-traceroute) from your origin web server to a [Cloudflare IP address](https://www.cloudflare.com/ips/) that connected to your origin web server before the issue occurred. Identify the connecting address in origin logs. This probes the route from the origin to that address. It does not, by itself, establish the forward route used for the failed request.
- Details from the hosting provider's investigation, such as pertinent logs or conversations with the hosting provider.

### Diagnose with Origin Analytics

Use [Origin Analytics](/speed/origin-analytics/) to check for TCP connection failures to your origin. If the **Top endpoints** table shows a high TCP failure rate for specific paths, the issue may be path-specific rather than a general origin problem. Origin Analytics can also help confirm whether your origin is reachable from Cloudflare's edge.
