Origin Rules allow you to change the origin server that Cloudflare sends a request to, or modify how the request reaches that server. This is useful when you need to route specific requests to a different backend, such as a third-party service or a server on a non-standard port. You can perform the following overrides:

- [Host header](/rules/origin-rules/features/#host-header): Overrides the `Host` header of incoming requests.
- [Server Name Indication (SNI)](/rules/origin-rules/features/#server-name-indication-sni): Overrides the Server Name Indication (SNI) value of incoming requests.
- [DNS record](/rules/origin-rules/features/#dns-record): Overrides the resolved hostname of incoming requests, sending the request to a different origin server.
- [Destination port](/rules/origin-rules/features/#destination-port): Overrides the resolved destination port of incoming requests.

Each origin rule includes a [filter expression](/ruleset-engine/rules-language/expressions/) that defines which requests the overrides apply to (for example, matching on hostname, path, or other request properties).

## Important remarks

If you override the hostname with an origin rule (via `Host` header override or DNS record override) and add a header override to your load balancer configuration, the origin rule will take precedence over the load balancer configuration.

Like [Page Rules](/rules/page-rules/), an origin rule performing a `Host` header override will update the SNI value of the original request to the same value of the `Host` header. To set an SNI value different from the `Host` header override, add an SNI override in the same origin rule or create a separate origin rule for this purpose.

## Route a path on an O2O hostname

If your hostname uses [Orange-to-Orange (O2O)](/cloudflare-for-platforms/cloudflare-for-saas/saas-customers/how-it-works/), use a [DNS record override](/rules/origin-rules/features/#dns-record) on your Enterprise customer zone to send matching requests to a directly reachable origin. These requests bypass the original SaaS provider zone and its settings. Requests that do not match the rule continue using the existing O2O route.

For example, to serve `/microsite` and its subpaths from another origin:

1. Keep the proxied `CNAME` record for `platform.example.com` pointing to your SaaS provider.
2. Create a DNS record, such as `microsite-origin.example.com`, that points to the alternate origin.
3. [Create an origin rule](/rules/origin-rules/create-dashboard/) on `example.com` with this expression:

   ```txt
   http.host eq "platform.example.com" and (http.request.uri.path eq "/microsite" or starts_with(http.request.uri.path, "/microsite/"))
   ```

4. Set the DNS record override to `microsite-origin.example.com`. If the alternate origin expects a different `Host` header, also set a [`Host` header override](/rules/origin-rules/features/#host-header).

Like [Resolve Override in Page Rules](/rules/page-rules/reference/settings/), this changes the origin for matching requests without redirecting visitors. It does not onboard the hostname with another SaaS provider or add a provider zone to the existing O2O route.
