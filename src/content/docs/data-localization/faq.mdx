## Are DLP and data residency the same?

No. DLP stands for [Data Loss Prevention](/cloudflare-one/data-loss-prevention/), and it is part of Cloudflare's Zero Trust offering. It requires Gateway, Cloudflare's secure web gateway for filtering outbound internet traffic. DLP scans web traffic and SaaS applications for sensitive data such as secret keys, financial information, and other keywords.

[Data residency](/data-localization/) controls where your data is processed and stored, so you can meet data residency requirements. It is sold as the Data Localization Suite (DLS).

## Are Cloudflare's services GDPR compliant?

Yes. Even without data residency settings, Cloudflare services are designed to satisfy the requirements of the GDPR (General Data Protection Regulation). Cloudflare services are also verified compliant with the EU Cloud Code of Conduct (EU Cloud CoC), Verification-ID: 2023LVL02SCOPE4316. For further information, visit the EU Cloud CoC [public register](https://eucoc.cloud/en/public-register).

## How do I get started?

Data residency is an Enterprise add-on. Once you have purchased it, your account team enables it on your account, and you can configure every setting through the dashboard or the API. Refer to the [Configuration guides](/data-localization/how-to/).

## Does a processing region work with HTTP/3 and QUIC?

Not yet. HTTP/3 uses the QUIC transport protocol, which is not currently compatible with a processing region.

## Can I apply a processing region to only part of my traffic?

Yes. A [processing region](/data-localization/processing-region/) is not all-or-nothing. You choose which hostnames or zones are regionalized by assigning a region to each one, and all other traffic continues to be served from Cloudflare's global network. For example, you can regionalize `eu.example.com` to the European Union while `www.example.com` keeps using the global network. Different hostnames can use different regions.

This also lets you keep latency-sensitive, non-sensitive content global. For instance, you can serve static CDN content that does not normally contain PII, such as product images on a global `assets.example.com` hostname, from Cloudflare's global network for best performance, while regionalizing only the hostnames that handle personal data.

The granularity depends on which [option](/data-localization/processing-region/#ways-to-set-a-processing-region) you use. With Regional Hostnames, you assign a region per hostname. With Regionalized Spectrum Applications, the region is assigned per zone and applies to all Spectrum HTTP/S applications in that zone.

## How is traffic from users outside the configured region handled?

Cloudflare accepts connections at any data center worldwide. When a request arrives outside your processing region, Cloudflare forwards it, still encrypted, to a data center inside the region, where TLS termination and all Layer 7 processing take place. Requests from users far from the region therefore carry extra latency, corresponding to the round trip to the in-region data center.

If you want users inside a region to benefit from local processing while still serving a global audience, use a regionalized hostname for in-region users, for example `eu.example.com`, alongside a non-regionalized hostname for everyone else, for example `www.example.com`.

## Which option works with Static IPs or BYOIP?

- [Spectrum Static IPs](/spectrum/about/static-ip/) are supported only by Regionalized Spectrum Applications.
- [BYOIP](/byoip/) is supported by both Regionalized Spectrum Applications and [Regionalized IP Bindings](/data-localization/processing-region/ip-bindings/).
- Regional Hostnames use Cloudflare's shared anycast IP addresses and do not support Static IPs.

For an overview of each option, refer to [Ways to set a processing region](/data-localization/processing-region/#ways-to-set-a-processing-region).

## What is the difference between managed and custom regions?

**Managed regions** are predefined regions that Cloudflare maintains, available to all accounts. **Custom regions** are tailored to your account for when the managed regions do not meet your compliance requirements. For full details, and which options support them, refer to [Region types](/data-localization/regions-by-setting/#region-types).

## Are there other options if I prefer not to have Cloudflare handle TLS termination?

Yes:

- [Spectrum TCP/UDP Apps](/spectrum/) without TLS termination
- [Magic Transit](/magic-transit/)
- [Cloudflare OHTTP Relay (formerly Privacy Gateway)](/ohttp-relay/)

These options only offer L3/L4 DDoS protection, at the network and transport layers. Using them means no application-layer (L7) security or performance services can be applied, because Cloudflare does not decrypt the traffic.

## Why do I get a data availability error in the dashboard when my log region is the EU and I am in Europe?

The full error reads `Data not available due to your account's Customer Metadata Boundary configuration`.

This is typically caused by dynamic network routing. Based on Internet conditions that vary over time, your dashboard connection may be routed to a data center physically outside your log region. Enabling [out-of-region access](/data-localization/log-region/out-of-region-access/) allows requests arriving in the United States to read logs from the European Union, and the reverse.

Your logs are still stored only in your configured log region. Only the read path changes.
