## Overview

Hyperdrive with Dynamic Workers lets [Dynamic Workers](/dynamic-workers/) use [Hyperdrive](/hyperdrive/) to query existing databases. Use it when each Dynamic Worker needs to connect to a separate tenant database.

A tenant is an isolated customer, user, or workspace in your platform. With Hyperdrive using Dynamic Workers, each tenant connects to its own database.

When a Dynamic Worker connects to a database, Cloudflare creates a Hyperdrive configuration for that database at runtime. Hyperdrive reuses that per-database configuration for connection pooling and query caching across Dynamic Worker requests that connect to and query the same database.

In this model, the [loader Worker](/dynamic-workers/getting-started/#configure-worker-loader) creates each Dynamic Worker. Each Dynamic Worker connects to its own tenant database through Hyperdrive.

![A loader Worker creates each Dynamic Worker, and each Dynamic Worker connects to its own tenant database through its own Hyperdrive configuration.](~/assets/images/hyperdrive/configuration/hyperdrive-dynamic-workers.svg)

:::note

Hyperdrive with Dynamic Workers is in private preview. You configure the Hyperdrive binding through the `unsafe.bindings` array, and the API may change.

:::

## How it works

Hyperdrive with Dynamic Workers uses the Dynamic Workers [egress control model](/dynamic-workers/usage/egress-control/#intercept-outbound-requests). Your loader Worker decides how a Dynamic Worker opens outbound connections.

This example shows the loader Worker and Dynamic Worker code together. Your loader Worker defines a `WorkerEntrypoint` (`OutboundInterceptor`) that intercepts outbound `connect()` calls from a Dynamic Worker and uses the Hyperdrive binding (`CUSTOMER_HYPERDRIVE`) to connect to a specific tenant database.

<TypeScriptExample filename="loader-worker.ts">

```ts
import { WorkerEntrypoint } from "cloudflare:workers";

export class OutboundInterceptor extends WorkerEntrypoint {
	async connect(host) {
		// The interceptor only sees the host and port, so compare against the
		// host parsed from the tenant's placeholder connection string.
		if (
			host === new URL(this.ctx.props.tenant.placeholderConnectionString).host
		) {
			const hyperdrive = this.env.CUSTOMER_HYPERDRIVE.get({
				connectionString: this.ctx.props.tenant.connectionString,
				targetRegion: this.ctx.props.tenant.databaseRegion,
			});

			// Do not pass host into connect(). Hyperdrive connects using the
			// real connection string from the binding above.
			return hyperdrive.connect();
		}

		throw new Error("Outbound TCP connections are not allowed.");
	}
}

export default {
	async fetch(request, env, ctx): Promise<Response> {
		// Look up per-tenant database context in a system like Workers KV.
		const tenant = await env.KV.get<Tenant>("<TENANT_ID>", { type: "json" });

		if (tenant === null) {
			return new Response("Tenant not found", { status: 404 });
		}

		const worker = env.LOADER.load({
			compatibilityDate: "$today",
			compatibilityFlags: ["nodejs_compat"],
			mainModule: "src/index.js",
			modules: {
				"src/index.js": `
					import { Client } from "pg";

					export default {
						async fetch(request, env) {
							const client = new Client({
								connectionString: env.CONNECTION_STRING,
							});

							await client.connect();
							const result = await client.query("SELECT * FROM pg_tables");

							return Response.json({ success: true, result: result.rows });
						},
					};
				`,
			},
			env: {
				// This tenant-specific placeholder does not contain the real
				// database credentials. The loader Worker passes the real
				// database configuration to OutboundInterceptor through props.
				CONNECTION_STRING: tenant.placeholderConnectionString,
			},
			globalOutbound: ctx.exports.OutboundInterceptor({
				props: { tenant },
			}),
		});

		return worker.getEntrypoint().fetch(request);
	},
};

type Tenant = {
	placeholderConnectionString: string;
	connectionString: string;
	databaseRegion: string;
};
```

</TypeScriptExample>

:::note[Abbreviated example]

This snippet inlines the Dynamic Worker as a single module string for readability. In practice, Dynamic Workers require their npm dependencies (such as `pg`) to be fully bundled before you pass them to `load()`. Bundle your Dynamic Worker code and its dependencies, then pass the built modules to `load()`.

:::

Breaking it down:

1. Your loader Worker has two bindings. The Worker Loader binding (`LOADER`) lets the loader Worker create Dynamic Workers. The Hyperdrive binding (`CUSTOMER_HYPERDRIVE`) creates Hyperdrive configurations at runtime.

   Because Hyperdrive with Dynamic Workers is in private preview, configure the Hyperdrive binding through the `unsafe.bindings` array instead of the standard `hyperdrive` binding.

<WranglerConfig>

```jsonc
{
	"worker_loaders": [{ "binding": "LOADER" }],
	"unsafe": {
		"bindings": [
			{
				"name": "CUSTOMER_HYPERDRIVE",
				"type": "hyperdrive"
			}
		]
	}
}
```

</WranglerConfig>

2. Your loader Worker defines an `OutboundInterceptor` class and passes it as [`globalOutbound`](/dynamic-workers/api-reference/#globaloutbound) when it creates the Dynamic Worker. This routes outbound `connect()` calls from the Dynamic Worker through your interceptor. The loader Worker uses `props` to pass the tenant database configuration to the interceptor.

<TypeScriptExample filename="loader-worker.ts">

```ts
const worker = env.LOADER.load({
	compatibilityDate: "$today",
	compatibilityFlags: ["nodejs_compat"],
	mainModule: "src/index.js",
	modules: { "src/index.js": code },
	env: {
		CONNECTION_STRING: tenant.placeholderConnectionString,
	},
	globalOutbound: ctx.exports.OutboundInterceptor({
		props: { tenant },
	}),
});
```

</TypeScriptExample>

3. The interceptor only receives the host and port of the outbound connection. It compares that host against the host in the tenant's placeholder connection string. When they match, it calls `CUSTOMER_HYPERDRIVE.get()` to connect to that tenant database through Hyperdrive at runtime.

   With a regular Hyperdrive configuration, Hyperdrive probes Cloudflare locations to decide where to run your database connection pool for low-latency queries. With Hyperdrive using Dynamic Workers, Hyperdrive creates and reuses configurations at runtime, so you specify the database region with `targetRegion` for the best performance. `targetRegion` uses the same [cloud region hints as Tiered Cache](/cache/how-to/tiered-cache/#set-a-cloud-region-hint), for example `aws:us-east-1`.

<TypeScriptExample filename="outbound-interceptor.ts">

```ts
import { WorkerEntrypoint } from "cloudflare:workers";

export class OutboundInterceptor extends WorkerEntrypoint {
	async connect(host) {
		if (
			host === new URL(this.ctx.props.tenant.placeholderConnectionString).host
		) {
			const hyperdrive = this.env.CUSTOMER_HYPERDRIVE.get({
				connectionString: this.ctx.props.tenant.connectionString,
				targetRegion: this.ctx.props.tenant.databaseRegion,
			});

			// Do not pass host into connect().
			return hyperdrive.connect();
		}

		throw new Error("Outbound TCP connections are not allowed.");
	}
}
```

</TypeScriptExample>

4. Your loader Worker creates Dynamic Workers with `env.LOADER.load` and looks up tenant context in a system like Workers KV to identify which tenant database a user's Dynamic Worker should use.

   Dynamic Workers use your preferred database client, such as [`pg`](https://www.npmjs.com/package/pg), with a tenant-specific placeholder connection string. The `OutboundInterceptor` receives the actual database credentials through `props` and uses them to connect with `CUSTOMER_HYPERDRIVE.get()`.

## Placeholder connection string requirements

The placeholder connection string does not contain real database credentials, but it must still be a valid connection string that your database driver can parse. The driver parses and uses the placeholder's username, password, database name, host, port, and TLS settings.

Use a unique, randomized placeholder host and port for each tenant. The outbound interceptor compares the intercepted host against `new URL(tenant.placeholderConnectionString).host` to decide which connections to route through Hyperdrive.

:::caution

Do not point the placeholder at a real database host. If the placeholder is malformed, the database driver can crash. If it points at a real host, the driver can connect directly and leak real credentials.

:::

For PostgreSQL drivers, the placeholder must be a valid PostgreSQL connection string. Follow this structure:

```txt
postgresql://<PLACEHOLDER_USER>:<PLACEHOLDER_PASSWORD>@<PLACEHOLDER_HOST>:<PORT>/<DATABASE_NAME>?sslmode=require
```

For example:

```txt
postgresql://placeholder_user:placeholder_password@placeholder.example:5432/database?sslmode=require
```

The hostname and port let the outbound interceptor decide whether to route the TCP connection through Hyperdrive. The remaining fields must be acceptable to your database driver and compatible with the Hyperdrive connection behavior.
