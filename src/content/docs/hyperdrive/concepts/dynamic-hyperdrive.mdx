## Overview

Hyperdrive lets you connect to external databases from [Dynamic Workers](/dynamic-workers/). 

In this model, a [loader Worker](/dynamic-workers/getting-started/#configure-worker-loader) creates each Dynamic Worker and controls its outbound network access by providing the database connection details for that Dynamic Worker. Each Dynamic Worker can then connect to the provided database through Hyperdrive.

When a Dynamic Worker connects to a database, Cloudflare creates a Hyperdrive configuration for that database at runtime using the database connection details. Hyperdrive reuses that per-database configuration for connection pooling and query caching across Dynamic Worker requests that connect to the same database.

This means you do not need to pre-provision a separate Hyperdrive configuration for every database that your Dynamic Workers use. Instead, Dynamic Workers can connect to specific databases provided by the loader Worker, while Hyperdrive manages the configuration at runtime, pooling, and caching for each database.

## How it works

Hyperdrive with Dynamic Workers uses the Dynamic Workers [egress control model](/dynamic-workers/usage/egress-control/#intercept-outbound-requests). The `globalOutbound` option lets the loader Worker define a `WorkerEntrypoint` (`OutboundInterceptor`) to intercept outbound `connect()` calls from Dynamic Workers and route them through Hyperdrive.

Dynamic Workers do not use a pre-provisioned Hyperdrive configuration. Instead, Hyperdrive generates a connection string at runtime. This connection string contains a generated user, password, and dynamic Hyperdrive ID, and points at the reserved `hyperdrive-dynamic.local` hostname. This hostname is not a real address. It is a marker that the `OutboundInterceptor` uses to identify connections that Hyperdrive should handle.

The security model uses temporary, Hyperdrive-generated credentials rather than hiding the real database credentials from the Dynamic Worker. The generated connection string authenticates the Dynamic Worker to Hyperdrive, while the real database credentials stay with the `OutboundInterceptor` and are applied when Hyperdrive opens the origin connection.

At request time:

1. The Dynamic Worker's code calls `DYNAMIC_HYPERDRIVE.getHyperdriveConnectionString()` with the real database connection string. Hyperdrive returns a generated connection string that points at `hyperdrive-dynamic.local`.
2. The Dynamic Worker passes the generated connection string to its database client and calls `connect()`. `globalOutbound` routes the outbound TCP connection to `OutboundInterceptor.connect()`.
3. `OutboundInterceptor` detects the `hyperdrive-dynamic.local` hostname on the intercepted connection. It then calls `DYNAMIC_HYPERDRIVE.get()` with the Hyperdrive configuration arguments, which include the real database connection string.
4. Hyperdrive opens or reuses a pooled connection to the database. `OutboundInterceptor` bridges bytes between the Dynamic Worker's socket and the Hyperdrive connection for the duration of the database session.

### Bridge sockets with a byte pump

`OutboundInterceptor.connect()` must return `Promise<void>`. You cannot return the Hyperdrive socket and let the runtime relay traffic. Returning early cuts the connection short.

Instead, you bridge the two sockets manually. A database session stays open for the length of the request, often several minutes, so you pipe bytes in both directions until either side disconnects. This continuous relay is the `pump` function. It keeps `connect()` pending until the session ends, then resolves so the request can complete.

### Generated connection string

`getHyperdriveConnectionString()` returns a real, syntactically valid connection string. The Dynamic Worker's database client parses it and uses its generated user, password, and dynamic Hyperdrive ID to pass Hyperdrive authentication at runtime.

Every generated connection string uses the `hyperdrive-dynamic.local` hostname. Because the hostname is consistent, `OutboundInterceptor` can detect it with a simple check before routing the connection through Hyperdrive.

## Getting started

The following steps show how a Dynamic Worker connects to a database through Hyperdrive at runtime. You do not create a Hyperdrive configuration in advance.

### 1. Store your database connection string as a secret

Store the real database connection string as a [secret](/workers/configuration/secrets/) so it is not exposed in plaintext:

```sh
npx wrangler secret put PG_CONNECTION_STRING
```

### 2. Add the binding

Add the Dynamic Hyperdrive binding to your Wrangler configuration file as an `unsafe` binding:

<WranglerConfig>

```jsonc
{
	"worker_loaders": [{ "binding": "LOADER" }],
	"unsafe": {
		"bindings": [
			{
				"type": "hyperdrive_dynamic",
				"name": "DYNAMIC_HYPERDRIVE",
			},
		],
	},
}
```

</WranglerConfig>

:::note
Dynamic Hyperdrive is currently exposed through an `unsafe` Wrangler binding. The public release shape may change, likely toward a first-class `hyperdrive` binding. Do not use `hyperdrive: [{ id: "" }]` yet, because current deploy validation rejects it. Standard Hyperdrive bindings require an `id`.
:::

### 3. Ensure Dynamic Hyperdrive types are present

For TypeScript projects, use the `worker-configuration.d.ts` included with this example. It contains the temporary Dynamic Hyperdrive types needed while the binding is still under `unsafe`.

Do not regenerate this file with `npx wrangler types` yet, because current Wrangler may replace it with types that do not include the Dynamic Hyperdrive API.

If you are using JavaScript, this step is not required.

### 4. Get a generated Hyperdrive connection string

Call `getHyperdriveConnectionString()` with the real database connection string. Do this first, because the Dynamic Worker needs the generated connection string to pass Hyperdrive authentication at runtime.

<TypeScriptExample filename="dynamic-worker.ts">

```ts
// The generated connection string contains a generated user, password, and
// dynamic Hyperdrive ID, and points at the hyperdrive-dynamic.local hostname.
const hyperdriveDynamicConnectionString =
	await env.DYNAMIC_HYPERDRIVE.getHyperdriveConnectionString(
		env.PG_CONNECTION_STRING,
	);
```

</TypeScriptExample>

### 5. Build the Hyperdrive arguments

Build `HyperdriveDynamicArgs` to pass to the `OutboundInterceptor`. `cachingEnabled` and `maxConnections` are optional:

<TypeScriptExample filename="dynamic-worker.ts">

```ts
const hyperdriveDynamicArgs = {
	// Generated connection string from getHyperdriveConnectionString()
	dynamicHyperdriveConnectionString: hyperdriveDynamicConnectionString,
	// Required. The real database connection string.
	connectionString: env.PG_CONNECTION_STRING,
	// Required. Places the connection pool near the database.
	targetRegion: "aws:us-east-1",
	// Optional. Defaults to false.
	cachingEnabled: true,
	// Optional. Defaults to 60.
	maxConnections: 60,
};
```

</TypeScriptExample>

For the full list of target regions, refer to [supported regions](/api/resources/cache/subresources/origin_cloud_regions/methods/supported_regions/).

### 6. Create the outbound interceptor

Define an `OutboundInterceptor` class and pass it as [`globalOutbound`](/dynamic-workers/api-reference/#globaloutbound) when you load the Dynamic Worker. This intercepts every outbound `connect()` call the Dynamic Worker makes. Pass the Hyperdrive arguments to the interceptor through `props`:

<TypeScriptExample filename="loader-worker.ts">

```ts
const worker = env.LOADER.load({
	compatibilityDate: "$today",
	compatibilityFlags: ["nodejs_compat"],
	mainModule: "src/index.js",
	modules: { "src/index.js": code },
	env: {
		HD_CONNECTION_STRING: hyperdriveDynamicConnectionString,
	},
	globalOutbound: ctx.exports.OutboundInterceptor({
		props: { hyperdrive: hyperdriveDynamicArgs },
	}),
});
```

</TypeScriptExample>

Because the interceptor sees every outbound `connect()` call, check the connection before routing it through Hyperdrive. Each generated connection string uses the `hyperdrive-dynamic.local` hostname, so a single check confirms which connections Hyperdrive should handle. Route all other connections to normal TCP egress, or deny them to keep `globalOutbound` restrictive.

<TypeScriptExample filename="outbound-interceptor.ts">

```ts
import { WorkerEntrypoint } from "cloudflare:workers";
import { connect, type Socket } from "cloudflare:sockets";

export class OutboundInterceptor extends WorkerEntrypoint {
	async connect(socket: Socket): Promise<void> {
		const { localAddress } = await socket.opened;

		if (localAddress === undefined) {
			throw new Error("connect: no address on incoming socket");
		}

		const args = this.ctx.props?.hyperdrive;

		if (localAddress.includes("hyperdrive-dynamic.local")) {
			// Detected the generated Hyperdrive hostname. Open a Hyperdrive
			// connection using the real database credentials in the arguments.
			const db = await this.env.DYNAMIC_HYPERDRIVE.get(args);
			const upstream = await db.connect();
			await this.pump(socket, upstream);
		} else {
			// Normal TCP egress for any other outbound connection.
			const passthrough = connect(localAddress);
			await this.pump(socket, passthrough);
		}
	}
}
```

</TypeScriptExample>

### 7. Bridge the connection with a pump

`connect()` must return `Promise<void>`, so you cannot return the socket and expect the runtime to relay traffic. Bridge the two sockets by piping bytes in both directions. `pump` resolves only when either side disconnects, which keeps the connection open for the full database session:

<TypeScriptExample filename="outbound-interceptor.ts">

```ts
import { WorkerEntrypoint } from "cloudflare:workers";
import { type Socket } from "cloudflare:sockets";

export class OutboundInterceptor extends WorkerEntrypoint {
	private async pump(downstream: Socket, upstream: Socket): Promise<void> {
		await Promise.all([
			// Dynamic Worker client to database
			downstream.readable.pipeTo(upstream.writable),
			// Database to Dynamic Worker client
			upstream.readable.pipeTo(downstream.writable),
		]);
	}
}
```

</TypeScriptExample>

## Pricing

Hyperdrive with Dynamic Workers adds a separate usage charge for active Hyperdrive configurations. This charge applies only to Hyperdrive configurations created at runtime with `DYNAMIC_HYPERDRIVE.get()`.

This pricing does not change standard [Hyperdrive pricing](/hyperdrive/platform/pricing/). Hyperdrive connection pooling and query caching remain included in Workers Paid.

| Billable unit                   | Rate                                |
| ------------------------------- | ----------------------------------- |
| Active Hyperdrive configuration | $0.002 per configuration per day    |

[Dynamic Workers pricing](/dynamic-workers/pricing/) still applies separately. Dynamic Workers created daily, requests, and CPU time remain part of Dynamic Workers billing.

### Active configurations

A Hyperdrive configuration is active for a UTC day if either action occurs during that day:

- It serves at least one customer-originated database query through Hyperdrive. This includes cached and uncached queries.
- It opens or maintains at least one origin database connection.

Each active configuration counts once per UTC day. Query volume does not increase the Hyperdrive with Dynamic Workers charge for the same configuration and day.

### Billing example

If 1,000 Hyperdrive configurations are active every day for a 30-day billing period, the charge is 1,000 × 30 × $0.002, or $60.00.
