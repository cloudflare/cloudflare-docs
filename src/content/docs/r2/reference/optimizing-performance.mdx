Your applications can achieve thousands of requests per second when reading and writing from R2, with multiple options to scale further.

## Performance and scaling

R2 provides multiple ways to scale your application's throughput. When accessing R2 directly via the S3 API or Workers API, each bucket supports approximately 20,000 read requests per second (GET, HEAD) and 4,000 write requests per second (PUT, POST, COPY, DELETE). Note that writing to the same key concurrently is limited to 1 request per second. R2's performance will continue to improve as we iterate on the underlying infrastructure.

You can scale beyond these rates by distributing requests across multiple buckets or enabling caching for read-heavy workloads.

## Distributing requests across buckets

Each bucket has independent throughput limits, so spreading requests across buckets increases your aggregate capacity.

For example, with 10 buckets, on aggregate your application can achieve about 200,000 read requests per second (10 buckets × 20,000 requests per second), and 40,000 write requests per second (10 buckets × 4,000 requests per second).

## Caching with custom domains

For read-heavy workloads serving frequently accessed objects, using a custom domain with Cloudflare's cache enabled can significantly increase read throughput. Cached requests are served from Cloudflare's edge network, distributing load across the network instead of requests going directly to your bucket.

Note that custom domains only support read operations, and you cannot write to R2 through a custom domain. Enabling a custom domain makes your bucket publicly accessible via that domain. You can add access controls to restrict access.

## Rate limiting on r2.dev

The r2.dev subdomain is rate limited and intended for development and testing purposes only. Production workloads should use the S3 API, Workers API, or a custom domain. Refer to [Limits](/r2/platform/limits/) for more details.
