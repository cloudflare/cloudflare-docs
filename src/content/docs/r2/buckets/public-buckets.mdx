Public Bucket is a feature that allows users to expose the contents of their R2 buckets directly to the Internet. By default, buckets are never publicly accessible and will always require explicit user permission to enable.

Public buckets can be set up in either of two ways:

- Expose your bucket as a custom domain under your control.
- Expose your bucket using a Cloudflare-managed `https://r2.dev` subdomain for non-production use cases.

These options can be used independently. Enabling custom domains does not require enabling `r2.dev` access.

To use features like [WAF custom rules](/waf/custom-rules/), caching, access controls, or [Bot Management](/bots/get-started/bot-management/), you must configure your bucket behind a custom domain. These capabilities are not available when using the `r2.dev` development url.

:::note

Currently, public buckets do not let you list the bucket contents at the root of your (sub) domain.

:::

To test public object access on your machine, use the [local public bucket endpoint](/r2/local-development/#serve-objects-publicly). It does not require enabling public access on a deployed bucket.

## Custom domains

### Caching

Domain access through a custom domain allows you to use [Cloudflare Cache](/cache/) to accelerate access to your R2 bucket.

Configure your cache to use [Smart Tiered Cache](/cache/how-to/tiered-cache/#smart-tiered-cache) to have a single upper-tier data center next to your R2 bucket.

:::note

By default, only certain file types are cached. To cache all files in your bucket, you must set a Cache Everything page rule.

For more information on default Cache behavior and how to customize it, refer to [Default Cache Behavior](/cache/concepts/default-cache-behavior/#default-cached-file-extensions)

:::

### Access control

To restrict access to your custom domain's bucket, use Cloudflare's existing security products.

- [Cloudflare Zero Trust Access](/cloudflare-one/access-controls/): Protects buckets that should only be accessible by your teammates. Refer to [Protect an R2 Bucket with Cloudflare Access](/r2/tutorials/cloudflare-access/) tutorial for more information.
- [Cloudflare WAF Token Authentication](/waf/custom-rules/use-cases/configure-token-authentication/): Restricts access to documents, files, and media to selected users by providing them with an access token.

:::caution

Disable public access to your [`r2.dev` subdomain](#disable-public-development-url) when using products like WAF or Cloudflare Access. If you do not disable public access, your bucket will remain publicly available through your `r2.dev` subdomain.

:::

### Minimum TLS Version & Cipher Suites

To customise the minimum TLS version or cipher suites of a custom hostname of an R2 bucket, you can issue an API call to edit [R2 custom domain settings](/api/resources/r2/subresources/buckets/subresources/domains/subresources/custom/methods/update/). You will need to add the optional `minTLS` and `ciphers` parameters to the request body. For a list of the cipher suites you can specify, refer to [Supported cipher suites](/ssl/edge-certificates/additional-options/cipher-suites/supported-cipher-suites/).

## Custom domain CDN cache versus Worker binding reads

Requests through a [Workers R2 binding](/r2/api/workers/workers-api-usage/) (`env.BUCKET.get()`) read directly from R2 and bypass Cloudflare's CDN cache. Requests through a public bucket Custom Domain pass through [Cloudflare Cache](/cache/) before reaching R2.

The following table compares direct Worker binding reads and Custom Domain CDN caching across caching, consistency, HTTP features, access control, and billing:

| Behavior | Direct Worker binding (`env.BUCKET.get()`) | Public bucket with a Custom Domain |
| --- | --- | --- |
| **CDN caching** | A binding call bypasses the CDN cache. Enable [Workers Cache](/workers/cache/) to serve cached HTTP responses without running the Worker handler. | Passes through [Cloudflare Cache](/cache/). Cloudflare serves cacheable `GET` and `HEAD` responses from edge cache (with optional [Smart Tiered Cache](/cache/how-to/tiered-cache/#smart-tiered-cache)). Non-default file extensions require a [Cache Rule](/cache/how-to/cache-rules/) set to **Eligible for cache**. |
| **Read consistency** | [Strongly consistent](/r2/reference/consistency/) globally on every read after a write, metadata update, or delete. | Eventually consistent for cached responses. Overwriting or deleting an object in R2 can serve stale cached bytes until the cache TTL expires, the entry is evicted, or you [purge the cache](/cache/how-to/purge-cache/). |
| **`404` and negative responses** | Returns `null` directly from R2 with no edge `404` caching. Newly uploaded keys are readable immediately. | Cloudflare Cache can cache `404 Not Found` responses depending on default [Edge TTLs](/cache/how-to/configure-cache-status-code/#edge-ttl) (three minutes by default without `Cache-Control` or `Expires`) and Cache Rules. Uploading to that key may return `404` until the TTL expires or you purge the cache. Override with [Cache TTL by status code](/cache/how-to/configure-cache-status-code/). |
| **Cache status headers** | Does not pass through the zone CDN cache, so responses do not receive a zone CDN `CF-Cache-Status` hit. | Returns [`CF-Cache-Status`](/cache/concepts/cache-responses/) (`HIT`, `MISS`, `EXPIRED`, `REVALIDATED`, `BYPASS`, or `DYNAMIC`). Non-default extensions without a Cache Rule report `DYNAMIC` and reach R2 on every request. |
| **Range requests** | Accepts `range` (`R2Range` or `Headers`) in [`R2GetOptions`](/r2/api/workers/workers-api-reference/#r2getoptions) directly against R2. Your Worker constructs the `206 Partial Content` status and `Content-Range` header. | Handled natively by Cloudflare Cache and R2. HTTP `Range` headers return `206 Partial Content` (or `416 Range Not Satisfiable`) from cached or origin bytes per [Range request behavior](/cache/reference/range-requests/). |
| **Conditional requests** | Accepts `onlyIf` (`R2Conditional` or `Headers`, excluding `If-Range`) in [`R2GetOptions`](/r2/api/workers/workers-api-reference/#r2getoptions) directly against R2. On precondition failure, `get()` returns an `R2Object` without a `body` for your Worker to translate to `304` or `412`. | Handled natively over HTTP. `If-None-Match` and `If-Modified-Since` return `304 Not Modified`, and `If-Range` is evaluated against the cached or origin validator. |
| **Access control and origin** | Keeps the bucket private with full custom authorization logic in Worker code. Serves objects on your application's own origin without bucket CORS rules. | Exposes the bucket on a separate hostname. Enforce access with [Cloudflare Access](/r2/tutorials/cloudflare-access/), [WAF custom rules](/waf/custom-rules/), or [WAF Token Authentication](/waf/custom-rules/use-cases/configure-token-authentication/). Cross-origin browser reads require a [CORS policy](/r2/buckets/cors/). |
| **R2 Class B operations** | Every `get()` or `head()` incurs a billed R2 [Class B operation](/r2/pricing/#class-b-operations) and a Worker invocation. | Edge cache `HIT` responses do not incur R2 Class B operations or Worker invocations. Cache `MISS`, `DYNAMIC`, `BYPASS`, and origin revalidations count as Class B operations. |

### Choose or combine approaches

- **Use a direct Worker binding** when you require strong read-after-write consistency, private buckets with custom per-request authorization, dynamic response headers, or same-origin URLs without CORS configuration.
- **Use a Custom Domain** when you serve read-heavy objects and want edge caching to reduce latency and R2 Class B operations. Add a [Cache Rule](/cache/how-to/cache-rules/) for extensions outside the [default cached file extensions](/cache/concepts/default-cache-behavior/#default-cached-file-extensions) list, check `CF-Cache-Status` on repeated `GET` requests, and keep files within Cloudflare's [cacheable size limits](/cache/concepts/default-cache-behavior/#cacheable-size-limits).
- **Combine immutable or versioned keys with a Custom Domain** by embedding a content hash or version in each object key (for example, `assets/v2/file-<HASH>.bin`) and setting a long `Cache-Control` `max-age` in object metadata. Because each update writes to a new key, you get high CDN hit rates without stale-read surprises on overwrite or manual cache purges.
- **Use [Workers Cache](/workers/cache/) with a Worker binding** when your Worker serves objects from a private bucket and can reuse its HTTP responses. Enable caching and set `Cache-Control` on responses you want to cache. A hit skips the cached handler and the R2 read, but standard [Workers request charges](/workers/cache/#pricing) still apply. If you need to authorize every request, [authorize in an uncached entrypoint before calling the cached handler](/workers/cache/examples/#cache-authenticated-responses).

## Add your domain to Cloudflare

The domain being used must have been added as a [zone](/fundamentals/concepts/accounts-and-zones/#zones) in the same account as the R2 bucket.

- If your domain is already managed by Cloudflare, you can proceed to [Connect a bucket to a custom domain](/r2/buckets/public-buckets/#connect-a-bucket-to-a-custom-domain).
- If your domain is not managed by Cloudflare, you need to set it up using a [partial (CNAME) setup](/dns/zone-setups/partial-setup/) to add it to your account.

Once the domain exists in your Cloudflare account (regardless of setup type), you can link it to your bucket.

## Disable domain access

Disabling a domain will turn off public access to your bucket through that domain. Access through other domains or the managed `r2.dev` subdomain are unaffected.
The specified domain will also remain connected to R2 until you remove it or delete the bucket.

To disable a domain:

1. In **R2**, select the bucket you want to modify.
2. On the bucket page, Select **Settings**, go to **Custom Domains**.
3. Next to the domain you want to disable, select **...** and **Disable domain**.
4. The badge under **Access to Bucket** will update to **Not allowed**.

## Remove domain

Removing a custom domain will disconnect it from your bucket and delete its configuration from the dashboard. Your bucket will remain publicly accessible through any other enabled access method, but the domain will no longer appear in the connected domains list.

To remove a domain:

1. In **R2**, select the bucket you want to modify.
2. On the bucket page, Select **Settings**, go to **Custom Domains**.
3. Next to the domain you want to disable, select **...** and **Remove domain**.
4. Select **Remove domain** in the confirmation window. This step also removes the CNAME record pointing to the domain. You can always add the domain again.

## Public development URL

Expose the contents of this R2 bucket to the internet through a Cloudflare-managed r2.dev subdomain. This endpoint is intended for non-production traffic.

:::note

Public access through `r2.dev` subdomains is rate-limited and should only be used for development purposes.

To enable access management, cache, and bot management features, you must set up a custom domain when enabling public access to your bucket.

Avoid creating a CNAME record pointing to the `r2.dev` subdomain. This is an **unsupported access path**, and we cannot guarantee consistent reliability or performance. For production use, [add your domain to Cloudflare](#add-your-domain-to-cloudflare) instead.
:::

### Enable public development URL

When you enable public development URL access for your bucket, its contents become available on the internet through a Cloudflare-managed `r2.dev` subdomain.

To enable access through `r2.dev` for your buckets:

1. In **R2**, select the bucket you want to modify.
2. On the bucket page, select **Settings**.
3. Under **Public Development URL**, select **Enable**.
4. In **Allow Public Access?**, confirm your choice by typing `allow` to confirm and select **Allow**.
5. You can now access the bucket and its objects using the Public Bucket URL.

To verify that your bucket is publicly accessible, check that **Public URL Access** shows **Allowed** in your bucket settings.

### Disable public development URL

Disabling public development URL access removes your bucket's exposure through the `r2.dev` subdomain. The bucket and its objects will no longer be accessible via the Public Bucket URL.

If you have connected other domains, the bucket will remain accessible for those domains.

To disable public access for your bucket:

1. In **R2**, select the bucket you want to modify.
2. On the bucket page, select **Settings**.
3. Under **Public Development URL**, select **Disable**.
4. In **Disallow Public Access?**, type `disallow` to confirm and select **Disallow**.
