Versioning lets your platform give customers control over code deployments without immediately replacing the version that serves production traffic. Customers can test a new deployment, gradually roll it out, keep related requests on a consistent version, and roll back if something goes wrong.

**This allows you to:**

- Let customers test a new code deployment before it reaches production.
- Roll out a new version gradually, such as 90% stable version and 10% new version.
- Keep a user, session, account, project, or asset on a consistent version during a rollout.
- Roll back to a known-good version if a release causes errors.

## Expose versioning in your platform

As a platform, you can give customers control over code deployments by letting them create versions, test deployments before release, choose rollout percentages, keep related requests on a consistent version, and roll back changes from your product.

Your platform turns those customer actions into Workers for Platforms API calls, deployment settings, and request headers.

| Customer action                 | What your customer does                                               | What your platform does                                                                                                  |
| ------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Create a version                | Upload a change.                                                      | Create a new Worker version with the uploaded code and version-specific configuration.                                   |
| Test a version                  | Preview a deployment before release.                                  | Include that version in the active deployment, then send test traffic with `Cloudflare-Workers-Version-Overrides`.       |
| Start a rollout                 | Choose an initial traffic percentage, such as `10%`.                  | Create a deployment that splits traffic between the stable version and the new version.                                  |
| Increase a rollout              | Change the rollout percentage, such as from `10%` to `50%`.           | Create a new deployment with updated version percentages.                                                                |
| Keep rollout traffic consistent | Continue to send related requests to the same version during rollout. | Set `Cloudflare-Workers-Version-Key` from a stable identifier such as session ID, account ID, project ID, or asset path. |
| Roll back                       | Select a previous stable version.                                     | Create a deployment that sends `100%` of traffic back to that version.                                                   |

## How it works

Each Worker in a dispatch namespace has its own versions and deployments. Your platform manages those settings on the Worker itself: upload a new version, include it in a deployment, test it before production, move traffic gradually, or roll back to a previous version.

<WorkersForPlatformsVersioningDiagram />

This is separate from your dispatcher. The dispatcher still only decides which Worker should receive a request:

```js
export default {
	async fetch(request, env) {
		const workerName = new URL(request.url).hostname.split(".")[0];
		const worker = env.DISPATCHER.get(workerName);

		return worker.fetch(request);
	},
};
```

After `.get()` selects the Worker, Cloudflare checks the selected Worker's active deployment. The deployment decides which version handles the request.

```txt
HTTP request
  -> Dispatcher selects a Worker with env.DISPATCHER.get()
  -> Cloudflare checks the selected Worker's active deployment
  -> Cloudflare selects a version from the deployment
  -> Selected version handles fetch()
```

Creating a version does not change production traffic. Traffic changes only when your platform creates a deployment for that Worker. A deployment can send all traffic to one version, split traffic between two versions, or include a new version at `0%` so your platform can test it before production traffic reaches it.

## What your platform needs to manage

Your platform tracks the association between each user Worker and its version IDs. When a customer creates, tests, or rolls out a version, your platform uses those stored IDs to make deployment API calls and configure version routing in the dispatcher.

Your dispatcher is the trusted gateway for version routing headers:

- **For testing**, your dispatcher injects `Cloudflare-Workers-Version-Overrides` with the target version ID so test requests reach a specific version. Refer to [Versions](/cloudflare-for-platforms/workers-for-platforms/versioning/versions/#send-test-requests-to-the-new-version).
- **For version affinity during rollouts**, your dispatcher injects `Cloudflare-Workers-Version-Key` with a stable identifier so related requests stay on the same version. Refer to [Version affinity](/cloudflare-for-platforms/workers-for-platforms/versioning/version-affinity/).

External clients must not set these headers directly. Your dispatcher strips incoming version routing headers before forwarding requests to the user Worker.
