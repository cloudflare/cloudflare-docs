## Architecture

If you are familiar with [Workers](/workers/), Workers for Platforms introduces dispatch namespaces, dynamic dispatch Workers, user Workers, and optional platform controls for inbound and outbound traffic.

![Workers for Platforms architecture](~/assets/images/reference-architecture/programmable-platforms/programmable-platforms-1.svg)

### Dispatch namespace

A dispatch namespace is a container that holds all of your customers' Workers. Your platform takes the code your customers write, and then makes an API request to deploy that code as a user Worker to a namespace — for example `staging` or `production`. Compared to [Workers](/workers/), this provides:

- **Unlimited number of Workers** - No per-account script limits apply to Workers in a namespace
- **Isolation by default** - Each user Worker in a namespace runs in [untrusted mode](/cloudflare-for-platforms/workers-for-platforms/reference/worker-isolation/) — user Workers never share a cache even when running on the same Cloudflare zone, and cannot access the `request.cf` object
- **Dynamic invocation** - Your dynamic dispatch Worker can call any Worker in the namespace using `env.DISPATCHER.get("worker-name")`

:::note[Best practice]

All your customers' Workers should live in a single namespace (for example, `production`). Do not create a namespace per customer.

If you need to test changes safely, create a separate `staging` namespace.

:::

### Dynamic dispatch Worker

A dynamic dispatch Worker is the entry point for all requests to your platform. Your dynamic dispatch Worker:

- **Routes HTTP requests** - Determines which user Worker should handle each request based on hostname, path, headers, or any other criteria
- **Sets per-customer limits** - Enforces [custom limits](/cloudflare-for-platforms/workers-for-platforms/configuration/custom-limits/) on CPU time and subrequests based on plan type
- **Sanitizes responses** - Modifies or filters responses from user Workers

The dynamic dispatch Worker uses a dispatch namespace binding to invoke user Workers:

```js
export default {
	async fetch(request, env) {
		// Determine which user Worker to call
		const customerName = new URL(request.url).hostname.split(".")[0];

		// Get and invoke the user Worker
		const userWorker = env.DISPATCHER.get(customerName);
		return userWorker.fetch(request);
	},
};
```

### Inbound control (optional)

[Inbound control](/cloudflare-for-platforms/workers-for-platforms/inbound-control/) runs platform policy before a selected user Worker receives an invocation. It does not replace the dynamic dispatch Worker. The dynamic dispatch Worker routes HTTP requests; inbound control wraps the selected user Worker.

Use inbound control to require authentication, audit invocations, attach customer context, or block unsupported handlers before user Worker code runs. For cron triggers, queue consumers, previews, email handlers, and RPC calls, the target user Worker is already known, so the invocation can pass through inbound control without going through the dispatcher.

### User Workers

User Workers contain code written by your customers. Your customer sends their code to your platform, and then you make an API request to deploy a user Worker on their behalf. User Workers are deployed to a dispatch namespace and invoked by your dynamic dispatch Worker, cron triggers, queue consumers, previews, or direct calls. You can provide user Workers with [bindings](/cloudflare-for-platforms/workers-for-platforms/configuration/bindings/) to access KV, D1, R2, and other Cloudflare resources.

![Deployment and management flow](~/assets/images/reference-architecture/programmable-platforms/programmable-platforms-6.svg)

### Outbound control (optional)

[Outbound control](/cloudflare-for-platforms/workers-for-platforms/outbound-control/) intercepts [`fetch()`](/workers/runtime-apis/fetch/) requests made by user Workers. Use it to:

- **Control egress** - Block or allow external API calls from customer code
- **Log requests** - Track what external services customers are calling
- **Modify requests** - Add authentication headers or transform requests before they leave your platform

![Outbound Worker egress control pattern](~/assets/images/reference-architecture/programmable-platforms/programmable-platforms-3.svg)

### Request lifecycle

1. A request arrives at your dynamic dispatch Worker (for example, `customer-a.example.com/api`)
2. Your dynamic dispatch Worker determines which user Worker should handle the request
3. The dynamic dispatch Worker calls `env.DISPATCHER.get("customer-a")` to get the user Worker
4. If inbound control is configured, inbound control runs before the selected user Worker handles the request.
5. The user Worker executes. If it makes external `fetch()` calls and outbound control is configured, those requests pass through outbound control first.
6. The user Worker returns a response.
7. Your dynamic dispatch Worker can optionally modify the response before returning it.

## Workers for Platforms versus Service bindings

Both Workers for Platforms and [Service bindings](/workers/runtime-apis/bindings/service-bindings/) enable Worker-to-Worker communication. Use Service bindings when you know exactly which Workers need to communicate. Use Workers for Platforms when user Workers are uploaded dynamically by your customers.

You can use both simultaneously - your dynamic dispatch Worker can use Service bindings to call internal services while also dispatching to user Workers in a namespace.
