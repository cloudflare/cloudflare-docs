Custom bindings are a [Workers for Platforms](/cloudflare-for-platforms/workers-for-platforms/) feature that routes resource ([R2](/r2/) or [D1](/d1/)) operations through a platform-owned Worker before they reach the resource itself. Use this pattern when you deploy [User Workers](/cloudflare-for-platforms/workers-for-platforms/) and need to enforce query policy, log operations, or limit usage per tenant.

Only D1 custom bindings are supported today. R2 support is planned, and other `$binding` or `binding_interface` types return a `400`.

## How it works

The User Worker keeps using the standard [D1 API](/d1/worker-api/). Instead of binding `env.DB` directly to D1, you bind it to a Platform Worker and mark the binding with `binding_interface: "d1"`.

That flag tells the runtime to wrap the service binding so it presents the full, synchronous D1 API (`prepare()`, `bind()`, `all()`, and so on) to the User Worker, even though your Platform Worker backs it.

The Platform Worker receives each query through a single `query()` method over [JSRPC](/workers/runtime-apis/bindings/service-bindings/rpc/). It can inspect or reject the query, then forward allowed queries to the real D1 database that you pass in through [props](/workers/runtime-apis/context/#props).

1. **User Worker** — calls `env.DB.prepare().bind().all()` like a normal D1 binding.
2. **`query()` over JSRPC** — the wrapped binding turns the D1 call into a single `query()` RPC.
3. **Platform Worker** — the `query()` hook inspects each operation and can **log**, **rate-limit**, **reject**, or **forward** it.
   - **reject** — return a failed `QueryResponse`. The User Worker sees a `D1_ERROR`.
   - **forward** — call `this.ctx.props.D1.query(params)`.
4. **D1 database** — the real database, passed to the Platform Worker through `props`.

The `props` passed through the binding configuration are trusted, platform-owned values. The User Worker cannot read or change them.

## Get started

The commands below use placeholders like `<YOUR_ACCOUNT_ID>` and `<YOUR_DATABASE_ID>`. Replace them with your own values as you go.

Set the shell variables used by the upload command:

```bash
export NAMESPACE="custom-binding-ns"
export ACCOUNT_ID="<YOUR_ACCOUNT_ID>"
export API_TOKEN="<YOUR_API_TOKEN>"
export DATABASE_ID="<YOUR_DATABASE_ID>"
```

### 1. Create and deploy the Platform Worker

Export a `WorkerEntrypoint` with a `query()` method. The wrapped D1 binding calls this method for every database operation the User Worker runs.

Inside `query()`, inspect the incoming SQL and decide what to do. To forward a query to the real database, call `query()` on the D1 database passed through `props`.

:::caution[Important]
The `query()` parameter uses `params.queries`. This is an array of statements, and each statement has a `.sql` field. Do not use `params.statements`.

A single `env.DB.prepare(...).all()` call arrives as one entry in `params.queries`.
:::

Create the Platform Worker. If you use the JavaScript tab, save it as `src/index.js`.

<TypeScriptExample filename="platform-worker/src/index.ts">

```ts
import { WorkerEntrypoint } from "cloudflare:workers";

export class D1CustomBinding extends WorkerEntrypoint {
	async query(params) {
		// Inspect every statement in the batch.
		for (const stmt of params.queries) {
			console.log("Intercepted D1 query:", stmt.sql);

			const sql = stmt.sql.trim().toUpperCase();
			if (
				sql.startsWith("DELETE") ||
				sql.startsWith("INSERT") ||
				sql.startsWith("UPDATE")
			) {
				// A rejected query. The User Worker sees this as a D1_ERROR.
				return { success: false, error: new Error("Writes are not allowed") };
			}
		}

		// Forward the allowed query to the real D1 database passed through props.
		return this.ctx.props.D1.query(params);
	}
}

// A default export is required so Wrangler builds this as an ES module Worker.
// It is never invoked over HTTP. The binding uses the query() RPC method above.
export default {
	fetch() {
		throw new Error("unimplemented");
	},
};
```

</TypeScriptExample>

Add a minimal Wrangler configuration:

<WranglerConfig>

```jsonc
{
	"name": "custom-binding-platform-worker",
	"main": "src/index.js",
	"compatibility_date": "$today"
}
```

</WranglerConfig>

Deploy the Platform Worker:

```sh
wrangler deploy
```

### 2. Keep the User Worker on the standard D1 API

The User Worker calls `env.DB.prepare().bind().all()` as usual. It does not need to know that `env.DB` routes through the Platform Worker.

The upload in step 4 uses `main_module: "worker.js"`. Save the JavaScript output as `worker.js`, or change both the field name and `main_module` to match your file.

<TypeScriptExample filename="worker.ts">

```ts
interface Env {
	DB: D1Database;
}

export default {
	async fetch(request, env): Promise<Response> {
		if (request.method === "DELETE") {
			await env.DB.prepare("DELETE FROM Customers WHERE CustomerID = ?")
				.bind("BSBEV")
				.run();

			return new Response("Deleted customer");
		}

		const result = await env.DB.prepare(
			"SELECT ContactName FROM Customers WHERE CompanyName = ?",
		)
			.bind("Bs Beverages")
			.all();

		return Response.json(result.results);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

### 3. Create a dispatch namespace

User Workers are uploaded into a [dispatch namespace](/cloudflare-for-platforms/workers-for-platforms/configuration/dispatch-namespaces/) and are invoked through a dispatcher Worker. They are not routable directly.

Create the namespace that receives the User Worker upload:

```sh
wrangler dispatch-namespace create "$NAMESPACE"
```

### 4. Upload the User Worker with the custom binding

Configure `env.DB` as a service binding to the Platform Worker. Then add two fields that turn it into a custom D1 binding:

- **`binding_interface: "d1"`** — wraps the service binding so the User Worker sees the full, synchronous D1 API. This must be a string. Only `"d1"` is supported today, and `"r2"` is planned.
- **`props.D1`** with the `$binding` syntax — hands a real D1 database to the Platform Worker, so it can forward queries with `this.ctx.props.D1.query()`.

The `compatibility_flags` array must include `d1_binding_jsrpc`. Upload with the [Workers for Platforms script upload API](/api/resources/workers_for_platforms/subresources/dispatch/subresources/namespaces/subresources/scripts/methods/update/):

```bash
curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/dispatch/namespaces/$NAMESPACE/scripts/user-worker" \
  -H "Authorization: Bearer $API_TOKEN" \
  -F 'metadata={
    "main_module": "worker.js",
    "compatibility_date": "2026-08-15",
    "compatibility_flags": ["d1_binding_jsrpc"],
    "bindings": [
      {
        "type": "service",
        "name": "DB",
        "service": "custom-binding-platform-worker",
        "entrypoint": "D1CustomBinding",
        "binding_interface": "d1",
        "props": {
          "D1": {
            "$binding": {
              "type": "d1",
              "database_id": "'$DATABASE_ID'"
            }
          }
        }
      }
    ]
  }' \
  -F 'worker.js=@worker.js;type=application/javascript+module'
```

:::note
The multipart field name, `worker.js`, becomes the module name and must match `main_module`. If your file on disk has a different name, rename it to `worker.js` or change both the field name and `main_module` to match.

`binding_interface` and the `$binding` props syntax are not available in `wrangler.jsonc` yet. That is why this step uses the raw upload API.

Only `type: "d1"` is accepted inside `$binding` today, and R2 is planned. Any other binding type returns a `400`.
:::

You can pass trusted policy values through `props` alongside the database. These values are visible to the Platform Worker but not to the User Worker. For example:

- The D1 database for a specific tenant.
- The tenant or customer ID.
- The maximum queries allowed per minute.
- The plan tier.

### 5. Deploy a dispatcher Worker to invoke the User Worker

Create a small dispatcher Worker that forwards requests into the namespace. If you use the JavaScript tab, save it as `src/index.js`.

<TypeScriptExample filename="dispatcher/src/index.ts">

```ts
interface Env {
	DISPATCHER: DispatchNamespace;
}

export default {
	async fetch(request, env): Promise<Response> {
		const userWorker = env.DISPATCHER.get("user-worker");
		return userWorker.fetch(request);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

Add a Wrangler configuration for the dispatcher Worker:

<WranglerConfig>

```jsonc
{
	"name": "custom-binding-dispatcher",
	"main": "src/index.js",
	"compatibility_date": "$today",
	"dispatch_namespaces": [
		{
			"binding": "DISPATCHER",
			"namespace": "custom-binding-ns"
		}
	]
}
```

</WranglerConfig>

Deploy the dispatcher Worker:

```sh
wrangler deploy
```

### 6. Test it

Send a read and a write to the dispatcher's URL:

```bash
# Allowed: the SELECT is forwarded to D1.
curl "https://custom-binding-dispatcher.<your-subdomain>.workers.dev"

# Rejected: a write returns a D1_ERROR to the User Worker.
curl -X DELETE "https://custom-binding-dispatcher.<your-subdomain>.workers.dev"
```

To watch the interception live, tail the Platform Worker in another terminal:

```sh
wrangler tail custom-binding-platform-worker
```

You will see the intercepted query logged. Rejected writes surface to the User Worker as a `D1_ERROR`.

## Full example

This example shows a Platform Worker that blocks writes, a User Worker that queries D1, and the binding configuration that connects them.

**Platform Worker** (`src/index.js`)

**User Worker binding configuration**

Send this object in the `metadata` field of the upload API request:

```jsonc
{
	"main_module": "worker.js",
	"compatibility_date": "2026-08-15",
	"compatibility_flags": ["d1_binding_jsrpc"],
	"bindings": [
		{
			"type": "service",
			"name": "DB",
			"service": "custom-binding-platform-worker",
			"entrypoint": "D1CustomBinding",
			"binding_interface": "d1",
			"props": {
				"D1": {
					"$binding": {
						"type": "d1",
						"database_id": "<YOUR_DATABASE_ID>"
					}
				}
			}
		}
	]
}
```

**What this shows:**

- The User Worker keeps the normal D1 API.
- `binding_interface: "d1"` makes the service binding present as a D1 database.
- The Platform Worker inspects every query and can block writes.
- The binding routes `env.DB` through the Platform Worker first, then to the real D1 database passed in through `props`.
