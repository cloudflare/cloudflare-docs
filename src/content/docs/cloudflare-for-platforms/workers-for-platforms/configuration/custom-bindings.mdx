## Overview

A custom binding places a platform-owned Worker in front of a resource. The [User Worker](/cloudflare-for-platforms/workers-for-platforms/) calls the binding through `env` like any other binding, but the call routes to your Platform Worker instead of the resource directly.

This lets you enforce quota, rate limits, permissions, validation, and logging before an operation reaches the underlying resource. The User Worker's code stays the same.

Custom bindings are a [Workers for Platforms](/cloudflare-for-platforms/workers-for-platforms/) feature. This page covers custom bindings for [D1](/d1/).

## How it works

A custom D1 binding has three parts:

- **Platform Worker** — Your Worker that exports a [`WorkerEntrypoint`](/workers/runtime-apis/bindings/service-bindings/rpc/) class with a `query()` method. This is where you inspect, log, limit, or reject each database operation.
- **User Worker** — Your customer's Worker. It uses the standard [D1 API](/d1/worker-api/) and does not need to know that a Platform Worker sits in between.
- **Binding configuration** — A [service binding](/workers/runtime-apis/bindings/service-bindings/) in the User Worker that routes the `DB` binding to your Platform Worker. You pass the real database and any policy values through [`props`](/workers/runtime-apis/context/#props).

When the User Worker runs a query, the D1 binding serializes it and calls your Platform Worker's `query()` method over [RPC](/workers/runtime-apis/rpc/). Your Platform Worker inspects the query, then either rejects it or forwards it to the real database.

<CustomBindingsDiagram />

The `props` passed through the binding configuration are trusted, platform-owned values. The User Worker cannot read or change them.

The steps below walk through each part in order. The [full code example](#full-code-example) at the end of this page combines them into a project you can deploy and run.

## Get started

### Prerequisites

- A [Cloudflare account](/fundamentals/account/create-account/).
- [Wrangler](/workers/wrangler/install-and-update/) installed.
- A D1 database. If you do not have one, follow the [D1 getting started guide](/d1/get-started/) to create and populate a database. The examples below query the `Customers` table from that guide.

### 1. Create the Platform Worker

Create a Worker that exports a `WorkerEntrypoint` class with a `query()` method. The D1 binding calls this method for every database operation the User Worker runs.

Inside `query()`, you can read your trusted `props`, inspect the incoming SQL, and decide what to do. To forward a query to the real database, call `query()` on the D1 binding you passed through `props`.

This example logs each query, checks a rate limit, and rejects `DELETE` statements before forwarding the rest to D1.

<TypeScriptExample filename="platform-worker/src/index.ts">

```ts
import { WorkerEntrypoint } from "cloudflare:workers";
import type { QueryRequest, QueryResponse, D1BindingService } from "./binding-types";

// The D1 binding you pass through props is a real D1Database that also
// exposes the query() method used to forward operations.
interface D1Binding extends D1Database, D1BindingService {}

interface Props {
	TENANT_ID: string;
	D1: D1Binding;
}

export class D1CustomBinding extends WorkerEntrypoint<Env, Props> {
	async query(params: QueryRequest): Promise<QueryResponse> {
		const tenantId = this.ctx.props.TENANT_ID;

		// Pre-query: log the operation.
		console.log("D1 query intercepted", {
			tenantId,
			statementCount: params.queries.length,
			queries: params.queries.map((q) => q.sql),
		});

		// Enforce a rate limit.
		const allowed = await this.checkRateLimit(tenantId);
		if (!allowed) {
			return {
				success: false,
				error: new Error("D1 query rate limit exceeded"),
			};
		}

		// Reject destructive statements.
		for (const stmt of params.queries) {
			if (stmt.sql.trim().toUpperCase().startsWith("DELETE")) {
				return {
					success: false,
					error: new Error("DELETE statements are not permitted"),
				};
			}
		}

		// Forward the query to the real database.
		return this.ctx.props.D1.query(params);
	}

	private async checkRateLimit(tenantId: string): Promise<boolean> {
		// Implement with Durable Objects, KV, or an external service.
		return true;
	}
}

export default {
	fetch() {
		throw new Error("unimplemented");
	},
};
```

</TypeScriptExample>

The `query()` method receives a `QueryRequest` and returns a `QueryResponse`. These types define the contract between the D1 binding and your Platform Worker. Add them to your project as `binding-types.ts`.

<TypeScriptExample filename="platform-worker/src/binding-types.ts">

```ts
// The service the D1 binding calls on your Platform Worker.
export interface D1BindingService {
	query(params: QueryRequest): Promise<QueryResponse>;
}

// A bookmark identifying a point in the database session timeline.
export type D1Bookmark = "first-primary" | "first-unconstrained" | (string & {});

// The request sent by the D1 binding to execute a batch of queries.
export type QueryRequest = {
	queries: QuerySql[];
	bookmark?: D1Bookmark;
};

// The response returned for a batch of queries.
export type QueryResponse = RpcResponse<{
	queryResults: QuerySqlResult[];
	bookmark?: D1Bookmark;
}>;

export type QuerySql = {
	sql: string;
	params?: unknown[];
};

export type QuerySqlResult = {
	meta: D1Meta;
	data: QuerySqlResultData;
};

export type QuerySqlResultData = {
	kind: "raw";
	columns: string[];
	rows: unknown[][];
};

// A success or failure envelope for binding RPC methods.
export type RpcResponse<T = unknown> =
	| { success: true; results: T }
	| { success: false; error: Error };

export type D1Meta = {
	duration: number;
	rows_read: number;
	rows_written: number;
	changes: number;
	last_row_id: number;
	changed_db: boolean;
	size_after: number;
};
```

</TypeScriptExample>

:::note
Copy these types into your project for now. They will move to an official package once the D1 JSRPC migration is complete.
:::

To keep query latency low, use `console.log()` for structured output and attach a [Tail Worker](/workers/observability/logs/tail-workers/) to forward logs to [Analytics Engine](/analytics/analytics-engine/) or another pipeline asynchronously.

Configure the Platform Worker with the `d1_binding_jsrpc` compatibility flag.

}
```

</WranglerConfig>

Deploy the Platform Worker.

```

### 2. Keep the User Worker unchanged

The User Worker uses the standard D1 API. It does not need to know that `DB` routes through your Platform Worker. This includes [`batch()`](/d1/worker-api/d1-database/#batch) operations, which work like any other query.

<TypeScriptExample filename="user-worker/src/index.ts">

```ts
interface Env {
	DB: D1Database;
}

export default {
	async fetch(request, env): Promise<Response> {
		const customers = await env.DB.prepare(
			"SELECT CompanyName, ContactName FROM Customers WHERE CompanyName = ?",
		)
			.bind("Bs Beverages")
			.all();

		return Response.json(customers.results);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

### 3. Wire the binding

When you upload the User Worker, attach the Platform Worker as a [service binding](/workers/runtime-apis/bindings/service-bindings/) named `DB`. Use `props` to pass the real D1 database and any policy values, such as the tenant ID.

Two fields make this a custom binding:

- `binding_interface: "d1"` tells the runtime to expose the service binding to the User Worker as a `D1Database`. This is why `env.DB.prepare()` works with no code changes.
- The `$binding` object inside `props` passes a real D1 database to your Platform Worker, so it can forward queries with `ctx.props.D1.query()`.

The User Worker also needs the `d1_binding_jsrpc` compatibility flag. This tells the runtime to route D1 calls through your Platform Worker instead of directly to D1.

You can wire the binding with Wrangler or through the Workers for Platforms upload API. Both configure the same binding.

The `$binding` syntax inside `props` supports D1 bindings. Attach any other bindings your Platform Worker needs, such as [KV](/kv/) or [Analytics Engine](/analytics/analytics-engine/), directly to the Platform Worker in its own Wrangler configuration.

You can pass any trusted policy values through `props`, for example:

- The D1 database for a specific tenant
- The tenant or customer ID
- The maximum queries allowed per minute
- The plan tier

Once both Workers are deployed, requests to the User Worker route their D1 queries through your Platform Worker. A `DELETE` query returns a `D1_ERROR` to the User Worker, while a `SELECT` query is forwarded and returns results.

### User Worker

<TypeScriptExample filename="user-worker/src/index.ts">

```ts
interface Env {
	DB: D1Database;
}

export default {
	async fetch(request, env): Promise<Response> {
		if (request.method === "GET") {
			const customers = await env.DB.prepare(
				"SELECT CompanyName, ContactName FROM Customers WHERE CompanyName = ?",
			)
				.bind("Bs Beverages")
				.all();

			return Response.json(customers.results);
		}

		if (request.method === "DELETE") {
			// Rejected by the Platform Worker.
			await env.DB.prepare("DELETE FROM Customers WHERE CompanyName = ?")
				.bind("Bs Beverages")
				.run();

			return new Response("Deleted");
		}

		return new Response("Not found", { status: 404 });
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

```sh
curl https://custom-binding-user-worker.<YOUR_SUBDOMAIN>.workers.dev
```

The `SELECT` query is forwarded to D1 and returns results. A `DELETE` request is rejected by the Platform Worker and returns a `D1_ERROR` to the User Worker.
