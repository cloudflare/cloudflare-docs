Email authentication is critical for successful email delivery. This guide helps you troubleshoot common authentication, delivery, and inbox placement issues with Email Service.

## SPF (Sender Policy Framework) issues

### Multiple SPF records

Having multiple SPF records on your domain is not allowed and will prevent Email Service from working properly. If your domain has multiple SPF records:

1. Log in to the Cloudflare dashboard, select your account and domain, then go to **DNS** > **Records**.

   <DashButton url="/?to=/:account/:zone/dns/records" />

2. Look for multiple TXT records starting with `v=spf1`.
3. Delete the incorrect SPF record.
4. Ensure you have the correct SPF records:
   - For **Email Routing** (root domain): `v=spf1 include:_spf.mx.cloudflare.net ~all`
   - For **Email Sending** (`cf-bounce` subdomain): `v=spf1 include:_spf.mx.cloudflare.net ~all`

If you are unsure which SPF record is the correct one to keep, you can remove all of them and let Cloudflare regenerate the required records:

1. In **DNS** > **Records**, delete every TXT record starting with `v=spf1` on the affected name.
2. Go to **Compute** > **Email Service** and re-onboard or re-enable the affected service. Cloudflare adds the correct SPF record back automatically.

### Missing SPF record

If emails are being rejected due to SPF failures:

1. Log in to the Cloudflare dashboard, select your account and domain, then go to **DNS** > **Records**.

   <DashButton url="/?to=/:account/:zone/dns/records" />

2. Add TXT records for the appropriate service:
   - For **Email Routing**: **Name**: `@` (root domain), **Content**: `v=spf1 include:_spf.mx.cloudflare.net ~all`
   - For **Email Sending**: **Name**: `cf-bounce`, **Content**: `v=spf1 include:_spf.mx.cloudflare.net ~all`
3. If you already have an SPF record on the root domain, modify it to include `include:_spf.mx.cloudflare.net`

### SPF record syntax errors

Common SPF record syntax issues:

- **Missing version**: SPF records must start with `v=spf1`
- **Multiple includes**: Combine multiple services using separate `include:` statements
- **Too many DNS lookups**: SPF records are limited to 10 DNS lookups total
- **Incorrect all mechanism**: Use `~all` (SoftFail) or `-all` (Fail), not `+all`

**Correct format:**

```txt
v=spf1 include:_spf.mx.cloudflare.net include:other-service.com ~all
```

### Checking SPF records

Verify your SPF record is configured correctly:

```sh
dig TXT example.com +short | grep spf
```

Expected result should include:

```txt
"v=spf1 include:_spf.mx.cloudflare.net ~all"
```

## DKIM (DomainKeys Identified Mail) issues

### Missing DKIM records

Email Service automatically generates DKIM keys for your domain, but the DNS records must be properly configured. Email Sending and Email Routing use separate DKIM selectors:

1. In the [Cloudflare dashboard](https://dash.cloudflare.com/), go to **Compute** > **Email Service**.
2. Select your domain.
3. Check the **Settings** page for the appropriate service:
   - **Email Sending**: Go to **Email Sending** > **Settings** to find the sending DKIM record (`cf-bounce._domainkey`).
   - **Email Routing**: Go to **Email Routing** > **Settings** to find the routing DKIM record (`cf2024-1._domainkey`).
4. Copy the DKIM record details.
5. Go to **DNS** > **Records** and add the DKIM TXT record with the correct selector name and public key.

### DKIM key rotation

If you need to rotate DKIM keys:

1. Contact Cloudflare support to request key rotation.
2. Update your DNS records with the new DKIM key when provided.
3. Monitor email delivery during the transition period.

### Checking DKIM records

Verify your DKIM records are configured correctly:

```sh
# Check Email Sending DKIM
dig TXT cf-bounce._domainkey.example.com +short

# Check Email Routing DKIM
dig TXT cf2024-1._domainkey.example.com +short
```

Expected result for either:

```txt
"v=DKIM1; h=sha256; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA..."
```

### DKIM signature validation failures

If DKIM validation is failing:

1. Verify the DKIM record exists in DNS
2. Check that the record name matches the correct selector:
   - Email Sending: `cf-bounce._domainkey.yourdomain.com`
   - Email Routing: `cf2024-1._domainkey.yourdomain.com`
3. Ensure there are no extra spaces or characters in the DNS record
4. Wait for DNS propagation (up to 48 hours)
5. Use online DKIM validators to test your configuration

## DMARC (Domain-based Message Authentication, Reporting & Conformance) issues

### Missing DMARC policy

While not required, DMARC significantly improves email deliverability:

1. Go to **DNS** > **Records** in the Cloudflare dashboard.

   <DashButton url="/?to=/:account/:zone/dns/records" />

2. Add a TXT record:
   - **Name**: `_dmarc`
   - **Content**: `v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com`

### DMARC policy too strict

If a strict DMARC policy is causing delivery issues:

1. Start with a lenient policy: `p=none` (monitor only)
2. Monitor DMARC reports for several weeks
3. Gradually increase strictness: `p=quarantine` then `p=reject`
4. Ensure both SPF and DKIM are properly aligned

### DMARC alignment issues

DMARC requires either SPF or DKIM alignment:

**SPF alignment**: The domain in the `Mail From` header must align with the domain in the `From` header
**DKIM alignment**: The DKIM signature domain must align with the domain in the `From` header

Email Service ensures proper alignment automatically.

### Checking DMARC records

Verify your DMARC record:

```sh
dig TXT _dmarc.example.com +short
```

Example result:

```txt
"v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com; ruf=mailto:dmarc@example.com; sp=quarantine"
```

## Local development issues

### "Cannot serialize value: [object ArrayBuffer]"

This error occurs when passing `ArrayBuffer` content in attachment fields during local development with `wrangler dev`. The local email binding simulator cannot serialize `ArrayBuffer` values.

**Solution:** Deploy your Worker with `npx wrangler deploy` and test binary attachments (images, PDFs) against the deployed version. String content for text-based attachments works normally in local development. Refer to [local development for email sending](/email-service/observability/local-development/sending/#known-limitations) for more details.

## Common delivery issues

### Transactional email going to spam or junk

Use this checklist to diagnose inbox placement problems before opening a support case. Work through each step in order — most issues are identified at steps 1 through 4.

#### Delivery status versus inbox placement

A **Delivered** status in the Activity log means the recipient's mail server accepted the message with a successful SMTP response. What happens after acceptance — inbox, spam, or junk — is determined entirely by the receiving provider. Cloudflare does not receive that placement signal.

This means:

- A message can show as **Delivered** in your logs and still land in the recipient's spam or junk folder.
- A spam or junk classification after acceptance is a receiver-side decision. It can occur even when SPF, DKIM, and DMARC all pass.
- The receiving provider's reputation databases, spam filters, and user feedback signals (recipients marking messages as spam or moving them to their inbox) all influence placement independently of authentication.

#### Step 1: Verify authentication records

Go to **Compute** > **Email Service** > **Email Sending** > **Settings** and confirm that all DNS records show a healthy status. Every record must be present and valid.

You can also verify from the command line:

```sh
# SPF for the bounce domain
dig TXT cf-bounce.yourdomain.com +short

# DKIM for Email Sending
dig TXT cf-bounce._domainkey.yourdomain.com +short

# DMARC on the organizational domain
dig TXT _dmarc.yourdomain.com +short
```

Expected results:

- SPF: `"v=spf1 include:_spf.mx.cloudflare.net ~all"`
- DKIM: `"v=DKIM1; h=sha256; k=rsa; p=..."`
- DMARC: `"v=DMARC1; p=none;"` or stricter

If DMARC is missing, add a record with `p=none` and a `rua` reporting address to begin receiving aggregate data:

```txt
v=DMARC1; p=none; rua=mailto:dmarc@yourdomain.com
```

#### Step 2: Check the Activity log

1. Go to **Compute** > **Email Service** > **Email Sending** > **Activity log**.
2. Locate the affected message and confirm its status is **Delivered** — not **Failed** or **Rejected**.
3. Expand the message row to review the authentication results (SPF, DKIM, DMARC) and the receiving server's SMTP response.
4. Note the **Message-ID** — you will need this value if you open a support case.

A **Delivered** status with passing authentication and no bounce means the message reached the provider's server successfully. Any junk classification happened after acceptance and is outside Cloudflare's control.

#### Step 3: Read the received headers

Ask a recipient to share the full message source, not just the body. Most email clients expose this under **Show original**, **View source**, or **Message source**.

Look for these headers:

| Header | What it tells you |
|---|---|
| `X-Spam-Flag: yes` / `X-Suspected-Spam: true` | The provider flagged the message as spam after delivery |
| `X-Apple-Action: JUNK` / `X-Icl-Score` | iCloud classified the message as junk and its internal spam score |
| `X-MS-Exchange-Organization-SCL` | Outlook spam confidence level — 5 or higher causes junk placement |
| `X-Microsoft-Antispam: BCL` | Outlook bulk confidence level |
| `Authentication-Results` | The provider's own SPF, DKIM, and DMARC evaluation |

If all authentication results show `pass` and the spam flag is still set, the classification is based on domain reputation or message content — not a Cloudflare configuration problem.

#### Step 4: Assess domain age and sending history

Inbox providers weight domain sending history heavily. A domain that has sent fewer than a few hundred messages, or has been active for less than a few weeks, has no positive reputation signal for providers to draw on. Providers treat new senders cautiously regardless of whether authentication passes.

If your domain is fewer than four weeks old, or you have sent fewer than a few hundred messages, inbox placement problems are expected during this warm-up period. To build domain reputation:

1. Send at a low, steady volume — a few dozen messages per day — and increase gradually over two to four weeks.
2. Send only to recipients who expect the message. High engagement (opens, replies, inbox moves) improves your reputation.
3. Keep a consistent `From` address and sender name for each sending domain throughout warm-up.
4. Include both HTML and plain text versions in every message.
5. Link only to your own domain in message bodies. Third-party redirect services and URL shorteners can lower your reputation score.
6. Ask early recipients to move messages from junk to their inbox or mark them **Not Junk** or **Not Spam**. User actions are the strongest positive signal for most providers.

Cloudflare manages the shared sending IP pool and maintains good IP-level reputation with inbox providers. Domain reputation, message content, and engagement signals are under your control.

#### Step 5: Review message content

Check the message that was classified as junk:

- Does the `From` address use your own sending domain?
- Is the sender name consistent across messages?
- Does the message include both plain text and HTML versions?
- Do all links point to your own domain?
- Does the subject line or body contain words commonly associated with unsolicited mail, such as FREE, URGENT, or GUARANTEED?
- Is the HTML well-formed? Providers penalise messages with broken markup.

#### Step 6: Use provider postmaster tools

Register your sending domain with provider postmaster tools to see your reputation from each provider's perspective:

- **Gmail**: [postmaster.google.com](https://postmaster.google.com) shows your domain reputation (Low, Medium, High, Bad) and spam rate in Google's systems. Your domain must have a DMARC record with a `rua` reporting address to receive data.
- **Outlook**: [postmaster.live.com](https://postmaster.live.com) provides access to Microsoft's Smart Network Data Services (SNDS) and Junk Mail Reporting Program (JMRP).
- **iCloud**: Apple does not publish sender dashboards or allowlists. The only signal available to you is user action — having recipients mark your messages **Not Junk**.

### High bounce rates

To reduce bounce rates:

1. Validate email addresses: Use real-time validation
2. Maintain clean lists: Remove hard bounces immediately
3. Monitor feedback loops: Subscribe to ISP feedback loops
4. Gradual warm-up: For new domains, start with small volumes

### Suppressed recipient

Each sending domain has a [**Drop suppressed recipients** setting](/email-service/configuration/domains/#drop-suppressed-recipients). The setting is off by default.

When the setting is off, the REST API returns `400`, the Workers binding throws `E_RECIPIENT_SUPPRESSED`, and SMTP rejects the message. Any suppressed recipient causes the send to fail.

When the setting is on, Email Service removes suppressed recipients and processes the remaining recipients. If none remain, SMTP may return `250 2.0.0 Ok` without a Message-ID and deliver nothing.

To investigate a suppressed recipient:

<Steps>
1. Query the exact recipient:

   <APIRequest path="/accounts/{account_id}/email/sending/suppressions" method="GET" parameters={{ email: "recipient@example.com" }} />

2. Use the `reason`, `expires_at`, and `read_only` fields to choose an action. For the complete decision table, refer to [Suppression rules](/email-service/concepts/suppressions/#suppression-rules).
3. If `result` is empty, confirm that you queried the correct account. Then check the sending logs.
4. If the logs still report a suppression, [contact Cloudflare Support](/support/contacting-cloudflare-support/).
</Steps>

### Recipient blocked after expiration or deletion

Expired entries stop appearing in the public list after their `expires_at` timestamp passes. Delivery enforcement can take additional time to stop.

Updates and deletions also propagate asynchronously. The management list and delivery enforcement can briefly differ.

To investigate delayed enforcement:

<Steps>
1. Confirm that the entry no longer appears in the account list.
2. Retry later because suppression updates propagate asynchronously.
3. If the recipient remains blocked, [contact Cloudflare Support](/support/contacting-cloudflare-support/).
</Steps>

### Bounces before suppression enforcement

Bounce suppressions are created through background delivery processing. Messages already in progress can bounce before a new suppression takes effect.

### Complaint suppression does not appear

Complaint suppressions appear after Cloudflare receives and validates the provider report. The provider determines when that report arrives.

### Missing suppression after a bounce

Not every failure results in a suppression. Email Service creates automatic entries only for eligible recipient-side failures. Sender authentication, sender reputation, and unrelated infrastructure failures do not suppress the recipient. Check [Email sending logs](/email-service/observability/logs/) for the specific failure.

## Getting help

Before opening a support case for email going to spam or junk, complete the [transactional email troubleshooting checklist](#transactional-email-going-to-spam-or-junk). Many inbox placement problems are caused by domain warm-up and resolve without engineering involvement.

Cloudflare cannot force inbox placement. Inbox providers classify messages after accepting them, and that decision is entirely within the provider's own systems. New domains (fewer than four weeks old) being filtered to junk are experiencing expected new-sender treatment. Apple iCloud does not offer a feedback loop or allowlist path for senders on shared infrastructure.

If you have completed the checklist and still need support, include these details in your support case:

| Detail | Where to find it |
|---|---|
| **Message-ID** | Activity log — expand the message row |
| **UTC send time** | Activity log — timestamp column |
| **Recipient address** | Activity log or your application logs |
| **Sending domain** | **Email Sending** > **Settings** |
| **Zone ID** | Cloudflare dashboard **Overview** page, sidebar |
| **Full received headers** | Full message source from the recipient's mail client, including `Authentication-Results` and any `X-Spam-*` headers |
| **Provider and folder** | Where the message landed, for example `iCloud Mail — Junk` |
| **Reputation status** | **Email Sending** > **Settings** — reputation indicator |
| **Messages sent in the last 7 days** | Email Sending dashboard or Analytics |

If you subscribe to [Email Sending event subscriptions](/email-service/reference/event-subscriptions/), also include the raw event payload for the affected message.

For other authentication and delivery issues:

1. Check [Email Service Analytics](/email-service/observability/metrics-analytics/) for delivery metrics.
2. Review bounce messages for specific SMTP error codes.
3. Contact [Cloudflare Support](https://dash.cloudflare.com/?to=/:account/support).
