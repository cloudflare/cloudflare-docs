Use this guide to onboard your own IP prefixes to Cloudflare. Before you begin, you must contact your account team to confirm that your contract includes BYOIP and that your account has the required service configuration.

Review the [BYOIP Service-Specific Terms](https://www.cloudflare.com/service-specific-terms-network-services/#bring-your-own-ip-terms) before you onboard a prefix.

:::note[Magic Transit]
This guide does not apply to prefixes used with [Cloudflare Magic Transit](/magic-transit/). To onboard a Magic Transit prefix, refer to [Get started with Magic Transit](/magic-transit/get-started/).
:::

## Before you begin

You must meet all of the following requirements. Cloudflare cannot onboard your prefix if any registration, IRR, RPKI, or ownership validation check fails.

- You must register your prefix with one of the following Regional Internet Registries (RIRs):
  - [AFRINIC](https://afrinic.net/)
  - [APNIC](https://www.apnic.net/)
  - [ARIN](https://www.arin.net/)
  - [LACNIC](https://lacnic.net/)
  - [RIPE](https://www.ripe.net/)
- Minimum IPv4 prefix size of /24 and/or minimum IPv6 prefix of a /48 with a maximum prefix size of a /32.
- Your [Internet Routing Registry (IRR)](/byoip/concepts/irr-entries/) records must contain:
  - A `route` or `route6` object that exactly matches each prefix you want to onboard.
  - An `origin` that matches the ASN Cloudflare will use to advertise the prefix.
  - An editable `aut-num` object for your ASN, if you use your own ASN.
- Your [Route Origin Authorizations (ROAs)](/byoip/concepts/route-filtering-rpki/) must be accurate. You must verify them with [Cloudflare's RPKI Portal](https://rpki.cloudflare.com/?view=validator) and a second source such as [Routinator](https://rpki-validator.ripe.net/ui/).
- If your ASN has a published [Autonomous System Provider Authorization (ASPA)](/byoip/concepts/route-filtering-rpki/), its provider list must include AS13335. You do not need to publish an ASPA to onboard a prefix.
- You must have your Cloudflare account ID and an API token with the permissions required by each operation in this guide. If you are unfamiliar with the Cloudflare API, refer to [Cloudflare API fundamentals](/fundamentals/api/).

Self-service onboarding with your own ASN supports ASNs registered with AFRINIC, APNIC, ARIN, or RIPE. For a LACNIC-registered ASN, contact your account team. This ASN requirement is separate from the supported prefix registries.

## 1. Add and validate your prefix

### Add your prefix

<Steps>

1. Use the [Add Prefix endpoint](/api/resources/addressing/subresources/prefixes/methods/create/) to add the prefix to the Cloudflare account that will own it.

   Set `asn` to `13335` to use Cloudflare's ASN. To use your own ASN, enter its number without the `AS` prefix. Your IRR route and ROA must authorize the selected ASN.

   ```bash
   curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/addressing/prefixes" --request POST --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" --json '{"cidr":"203.0.113.0/24","asn":13335,"delegate_loa_creation":true}'
   ```

   ```json title="Response" {4,16-20}
   {
     "result": {
       "id": "72823e95d6c64d48a8111fec81179816",
       "created_at": "2025-02-25T00:34:11.423722Z",
       "modified_at": "2025-02-25T00:34:11.423722Z",
       "cidr": "203.0.113.0/24",
       "account_id": "654c5f71c324478cc9f68d60065d4620",
       "description": "",
       "approved": "P",
       "on_demand_enabled": false,
       "on_demand_locked": false,
       "advertised": null,
       "advertised_modified_at": null,
       "loa_document_id": "b9ff4afe312246a8b2e7324d98f40b23",
       "asn": 13335,
       "ownership_validation_token": "<OWNERSHIP_VALIDATION_TOKEN>",
       "delegate_loa_creation": true,
       "irr_validation_state": "pending",
       "rpki_validation_state": "pending",
       "ownership_validation_state": "pending"
     }
   }
   ```

2. Save the prefix `id` and `ownership_validation_token` from the response. You will use them in later steps.

</Steps>

When you use your own ASN, the same response's `result` object can also include the following fields:

```json title="Additional fields in result"
{
  "asn_ownership_validation_state": "pending",
  "aspa_validation_state": "pending"
}
```

`asn_ownership_validation_state` is omitted when ASN ownership validation does not apply, such as when you use AS13335. Its initial state can be `valid` if the same account previously verified the ASN.

When `aspa_validation_state` is present, its value is `pending`, `valid`, or `invalid`. If the field is omitted, no ASPA validation result is available. Omission does not indicate successful validation or confirm that no ASPA exists. For more information, refer to [Prefix validation checks](/byoip/troubleshooting/prefix-validation/).

:::note[Letter of Agency]
This guide uses automated <GlossaryTooltip term="letter of agency" link="/byoip/concepts/loa/">Letter of Agency (LOA)</GlossaryTooltip> generation. If you set `delegate_loa_creation` to `false`, you must upload the LOA manually, [update the prefix](/api/resources/addressing/subresources/prefixes/methods/edit/) after it is approved, and contact your account team. Manual LOA processing can increase onboarding time.
:::

### Validate prefix ownership

Prove ownership by adding the validation token to either your IRR record or reverse DNS. You only need to use one of these methods.

<Tabs>
<TabItem label="IRR record">

<Steps>

1. Copy the `ownership_validation_token` returned when you added the prefix.
2. Add the following value to a `description` or `remarks` field in the matching IRR `route` or `route6` object. Replace `<OWNERSHIP_VALIDATION_TOKEN>` with your token.

   ```text
   cf-validation: <OWNERSHIP_VALIDATION_TOKEN>
   ```

   The process for updating an IRR object depends on the registry. Refer to [IRR best practices](/byoip/concepts/irr-entries/best-practices/) for more information.

</Steps>

</TabItem>
<TabItem label="Reverse DNS">

<Steps>

1. Determine which reverse DNS zones are required for your prefix. IPv4 reverse DNS delegations commonly align on octet boundaries, and IPv6 delegations align on nibble boundaries. A prefix that does not align with the next boundary must be divided into smaller reverse zones.

   <Details header="Examples">

   Use the following formula to determine the number of zones at the next delegation boundary:

   ```text
   2^(next boundary - current prefix length)
   ```

   The IPv4 prefix `192.0.2.0/23` requires two `/24` reverse zones: one for `192.0.2.0/24` and one for `192.0.3.0/24`.

   The IPv6 prefix `2001:db8::/34` requires four `/36` reverse zones: `2001:db8::/36`, `2001:db8:1000::/36`, `2001:db8:2000::/36`, and `2001:db8:3000::/36`.

   </Details>

2. Create the required reverse DNS zones. If you use Cloudflare for authoritative DNS, refer to [Set up a reverse DNS zone](/dns/additional-options/reverse-zones/#set-up-a-reverse-zone). Otherwise, follow your DNS provider's instructions.
3. In each reverse zone, create a TXT record named `cf-validation` whose value is the ownership validation token.

   ```text
   cf-validation.<REVERSE_ZONE> IN TXT "<OWNERSHIP_VALIDATION_TOKEN>"
   ```

4. At your RIR, delegate the reverse zones to the authoritative nameservers that host them.

</Steps>

</TabItem>
</Tabs>

### Validate ASN ownership

If `asn_ownership_validation_state` is present and is not `valid`, add `cf-validation: <OWNERSHIP_VALIDATION_TOKEN>` to an editable field in your ASN's `aut-num` object. Use the same `ownership_validation_token` returned when you added the prefix. Reverse DNS can prove prefix ownership, but it does not replace the `aut-num` check for ASN ownership.

Cloudflare verifies ASN ownership once per Cloudflare account and ASN. If `asn_ownership_validation_state` is already `valid`, you do not need to update the `aut-num` object.

### Check ASPA authorization

If you publish an ASPA for your ASN, use your RIR's RPKI tooling to confirm its provider list includes AS13335. You can keep other authorized providers. Publishing an ASPA is optional.

### Queue validation

After publishing the required ownership tokens and updating any ASPA, use the [Validate Prefix endpoint](/api/resources/addressing/subresources/prefixes/methods/validate/) to queue validation:

```bash
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/addressing/prefixes/$PREFIX_ID/validate" --request POST --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN"
```

Checks run asynchronously. Use the [Prefix Details endpoint](/api/resources/addressing/subresources/prefixes/methods/get/) to monitor the results. You do not need to submit repeated validation requests while checks are pending.

When all applicable checks pass, the `approved` field returns `"V"`. Checks include IRR, RPKI, prefix ownership, and, when applicable, ASN ownership and ASPA authorization.

After prefix ownership and any required ASN ownership checks return `valid`, you can remove the token from the IRR, reverse DNS, and `aut-num` records where you added it. Approval allows you to create service bindings. It does not advertise the prefix or activate traffic.

If validation fails, refer to [Troubleshoot prefix validation](/byoip/troubleshooting/prefix-validation/), correct the reported issues, and queue validation again.

### Optional: Delegate the prefix

You can allow another Cloudflare account to use all or part of the prefix. Refer to [Prefix delegations](/byoip/concepts/prefix-delegations/) for details.

```bash
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/addressing/prefixes/$PREFIX_ID/delegations" --request POST --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" --json '{"cidr":"<IP_PREFIX_TO_DELEGATE>","delegated_account_id":"<DELEGATED_ACCOUNT_ID>"}'
```

:::note
Service bindings for a delegated prefix are created and managed in the parent account that owns the prefix.
:::

## 2. Create service bindings

Service bindings determine which Cloudflare service receives traffic destined for an IP address in your prefix. Configure service bindings while the prefix is withdrawn.

### Create the default service binding

Each prefix requires a default service binding that covers the entire prefix. Cloudflare uses this binding for any IP address that does not have a more-specific binding.

<Steps>

1. Use the [List Services endpoint](/api/resources/addressing/subresources/services/methods/list/) to find the `id` of the service that will receive traffic by default.
2. If necessary, use the [List Prefixes endpoint](/api/resources/addressing/subresources/prefixes/methods/list/) to find the prefix `id`.
3. Use the [Create Service Binding endpoint](/api/resources/addressing/subresources/prefixes/subresources/service_bindings/methods/create/) to bind the entire prefix to the default service.

   ```bash
   curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/addressing/prefixes/$PREFIX_ID/bindings" --request POST --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" --json '{"cidr":"203.0.113.0/24","service_id":"<DEFAULT_SERVICE_ID>"}'
   ```

</Steps>

:::note[BGP prefix provisioning]
Cloudflare automatically creates a corresponding BGP prefix in a withdrawn state. Allow at least five hours for provisioning before you advertise the BGP prefix.
:::

### Optional: Create more-specific service bindings

Create more-specific bindings to send selected addresses in the prefix to a different service, such as CDN or Spectrum. Refer to [Service bindings](/byoip/service-bindings/) for service-specific configuration requirements.

Cloudflare recommends grouping contiguous IP addresses into the largest appropriate CIDR instead of creating a separate binding for each address.

<Details header="Example">

Suppose `203.0.113.0/24` uses Spectrum by default, but addresses `203.0.113.16` through `203.0.113.23` must use CDN. These eight contiguous addresses form `203.0.113.16/29`, so you can create one CDN binding for that CIDR.

</Details>

Use the [Create Service Binding endpoint](/api/resources/addressing/subresources/prefixes/subresources/service_bindings/methods/create/) to create the more-specific binding.

```bash
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/addressing/prefixes/$PREFIX_ID/bindings" --request POST --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" --json '{"cidr":"203.0.113.16/29","service_id":"<SERVICE_ID>"}'
```

The initial provisioning state in the response is `provisioning`:

```json title="Response" {9}
{
	"errors": [],
	"messages": [],
	"success": true,
	"result": {
		"cidr": "203.0.113.16/29",
		"id": "<SERVICE_BINDING_ID>",
		"provisioning": {
			"state": "provisioning"
		},
		"service_id": "<SERVICE_ID>",
		"service_name": "<SERVICE_NAME>"
	}
}
```

Creating or deleting a service binding takes four to six hours to propagate across Cloudflare's network. Use the [Get Service Binding endpoint](/api/resources/addressing/subresources/prefixes/subresources/service_bindings/methods/get/) to monitor its status. Wait until all bindings are active before you advertise the BGP prefix.

:::note
Magic Transit can only be the default binding for an entire prefix. For more information, refer to [Service binding scope](/byoip/service-bindings/#scope).
:::

## 3. Advertise the BGP prefix

Cloudflare creates the BGP prefix in a withdrawn state. While it is withdrawn, you can configure service bindings, but you cannot create an address map that uses its IP addresses.

After the default binding and any more-specific bindings are active, advertise the prefix:

<Steps>

1. Use the [List BGP Prefixes endpoint](/api/resources/addressing/subresources/prefixes/subresources/bgp_prefixes/methods/list/) to get the BGP prefix `id`.

2. Use the [Update BGP Prefix endpoint](/api/resources/addressing/subresources/prefixes/subresources/bgp_prefixes/methods/edit/) to advertise the prefix.

   ```bash
   curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/addressing/prefixes/$PREFIX_ID/bgp/prefixes/$BGP_PREFIX_ID" --request PATCH --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" --json '{"on_demand":{"advertised":true}}'
   ```

</Steps>

Confirm that the prefix is advertised before proceeding. Route propagation across the global Internet can take several minutes.

:::caution
Before Cloudflare advertises a production prefix, make sure that its service bindings and service-specific configuration are complete. Advertising an incomplete configuration can disrupt traffic to the prefix.
:::

## 4. Configure address maps for CDN

If the prefix will be used for CDN ingress, create an address map after the BGP prefix is advertised. An address map determines which BYOIP addresses Cloudflare returns for proxied DNS records in an account or zone.

<Steps>

1. Confirm that the BGP prefix is advertised and that the CDN service binding is active.

2. Create an [address map](/byoip/address-maps/setup/) containing the BYOIP addresses that Cloudflare should return.

3. Associate the address map with the appropriate account or zones.

4. Verify that DNS queries for proxied hostnames return the expected BYOIP addresses before moving production traffic.

</Steps>

Address maps are not required for prefixes used only with services that do not use Cloudflare's proxied DNS responses. For more information, refer to [About address maps](/byoip/address-maps/).
