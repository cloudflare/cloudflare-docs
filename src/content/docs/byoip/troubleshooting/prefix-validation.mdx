Use this page if you cannot add your prefix during [BYOIP onboarding](/byoip/get-started/). Also use it if your prefix does not pass validation.

## Add Prefix request fails

The Add Prefix endpoint checks your IRR object before it adds the prefix. For IRR errors such as `irr_entry_not_found` or `irr_mismatch_asn`, refer to [IRR check fails](#irr-check-fails).

The Add Prefix endpoint can also return the following error:

| Error code                          | Cause                                                                                   | Solution                                                                                                         |
| ----------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `prefix_entitlement_limit_exceeded` | Your account has reached the maximum number of prefixes. Existing prefixes count toward this limit. | To add the same prefix again, delete the existing prefix first. To add more prefixes, contact your account team. |

After you fix the issue, send the Add Prefix request again.

## Check the validation result

Use the [Prefix Details endpoint](/api/resources/addressing/subresources/prefixes/methods/get/) to get the current validation states.

<APIRequest
	path="/accounts/{account_id}/addressing/prefixes/{prefix_id}"
	method="GET"
/>

```json title="Response" {9,14-19}
{
	"result": {
		"id": "72823e95d6c64d48a8111fec81179816",
		"created_at": "2025-02-25T00:34:11.423722Z",
		"modified_at": "2025-02-25T00:34:11.423722Z",
		"cidr": "203.0.113.0/24",
		"account_id": "<ACCOUNT_ID>",
		"description": "",
		"approved": "P",
		"on_demand_enabled": false,
		"on_demand_locked": false,
		"advertised": null,
		"advertised_modified_at": null,
		"loa_document_id": null,
		"asn": 13335,
		"ownership_validation_token": "<OWNERSHIP_VALIDATION_TOKEN>",
		"delegate_loa_creation": true,
		"irr_validation_state": "valid",
		"rpki_validation_state": "valid",
		"ownership_validation_state": "missing"
	}
}
```

Review these fields:

| Field                        | What it checks                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| `approved`                   | `V` means that all checks passed. `P` means that the prefix is not approved yet.                     |
| `irr_validation_state`       | Your IRR `route` or `route6` object matches the prefix and the ASN.                                  |
| `rpki_validation_state`      | Your <GlossaryTooltip term="Route Origin Authorization (ROA)">ROA</GlossaryTooltip> authorizes the ASN to originate the prefix. |
| `ownership_validation_state` | Cloudflare found your validation token, or Cloudflare verified your LOA.                             |
| `ownership_validation_token` | The token to publish. This field is not present if you added the prefix with an LOA.                 |
| `loa_document_id`            | The LOA linked to the prefix. If you use `delegate_loa_creation`, this field is `null` until the prefix is approved. |

Your IRR record and ROA must meet the [onboarding prerequisites](/byoip/get-started/#before-you-begin).

## Validation states

Each check returns one of the following states:

| State                    | Meaning                                                                                  | What to do                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `valid`                  | The check passed.                                                                        | No action is necessary.                                                                                      |
| `pending`                | Cloudflare has not finished the check.                                                   | Wait, and then check again. If you have not started validation, use the Validate Prefix endpoint.             |
| `missing`                | Cloudflare did not find the required record.                                             | Refer to the section for that check, for example [IRR check fails](#irr-check-fails).                                                                    |
| `mismatch_asn`           | Cloudflare found a record for the prefix, but the ASN does not match.                    | Update the record so that it uses the ASN from the prefix. If the prefix has the wrong ASN, delete the prefix, and then add it again with the correct ASN. |
| `mismatch_more_specific` | The record is for a smaller prefix than the prefix you added.                            | Create a record that matches the prefix exactly.                                                             |
| `mismatch_less_specific` | The IRR record is for a larger prefix that covers the prefix you added.                  | The IRR check accepts this state. No action is necessary.                                                    |
| `invalid`                | The record exists, but it does not meet the requirements.                                | Refer to the section for that check, for example [IRR check fails](#irr-check-fails).                                                                    |
| `error`                  | Cloudflare could not complete the check.                                                 | Run validation again. If the state does not change, contact your account team.                               |

## IRR check fails

- Make sure that a `route` (IPv4) or `route6` (IPv6) object exists for the exact prefix.
- Make sure that the `origin` of the object is the ASN of the prefix.
- For more information, refer to [IRR entries](/byoip/concepts/irr-entries/) and [IRR best practices](/byoip/concepts/irr-entries/best-practices/).

If the Add Prefix request fails, fix the IRR object, and then send the request again. The Add Prefix endpoint can return the following IRR errors:

| Error code                      | Cause                                                                | Solution                                                            |
| ------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `irr_entry_not_found`           | Cloudflare did not find a `route` or `route6` object for the prefix. | Create the object.                                                  |
| `irr_mismatch_asn`              | The `origin` of the object does not match the ASN in the request.    | Update the `origin`, or use the ASN from the object in the request. |
| `irr_cidr_too_specific`         | The object is for a smaller prefix than the prefix in the request.   | Create an object that matches the prefix exactly.                   |
| `prefix_validation_irr_invalid` | The object does not meet the requirements in this section.                     | Review the object against the requirements in this section.                   |

## RPKI check fails

- Make sure that a ROA exists for the prefix and authorizes the ASN that you used.
- Make sure that the maximum length of the ROA covers the prefix.
- Verify the ROA with [Cloudflare's RPKI Portal](https://rpki.cloudflare.com/?view=validator) and a second source such as [Routinator](https://rpki-validator.ripe.net/ui/).
- For more information, refer to [Route filtering and RPKI](/byoip/concepts/route-filtering-rpki/).

## Ownership check fails

Ownership validation passes only when the RPKI check is `valid` and Cloudflare finds your token. Fix the RPKI check first.

If you use the IRR method:

- Add `cf-validation: <OWNERSHIP_VALIDATION_TOKEN>` to a `descr` or `remarks` field of the `route` or `route6` object.
- The object must be in the database of your RIR: AFRINIC, APNIC, ARIN, LACNIC, or RIPE. Cloudflare does not check RADB or other IRR databases for the token.
- The object must match the prefix and the ASN exactly.

If you use the reverse DNS method:

- Create a TXT record named `cf-validation` in every reverse zone that the prefix requires. Refer to [Validate prefix ownership](/byoip/get-started/#validate-prefix-ownership).
- The TXT value must be the token only, without a `cf-validation:` prefix.
- At your RIR, delegate each reverse zone to the nameservers that host it.

## No ownership validation token

If the response has a `loa_document_id` value but no `ownership_validation_token` field, you added the prefix with an LOA. Cloudflare does not create a token for these prefixes. Ownership validation passes only after Cloudflare verifies the LOA. Until then, `ownership_validation_state` is `invalid` and `approved` is `P`.

To continue, contact your account team to verify the LOA.

To use the self-serve token flow instead, delete the prefix with the [Delete Prefix endpoint](/api/resources/addressing/subresources/prefixes/methods/delete/). Then add it again without `loa_document_id`. Refer to [Add your prefix](/byoip/get-started/#add-your-prefix).

If you added the prefix without `loa_document_id` and lost the token, use the Prefix Details endpoint. The response includes `ownership_validation_token`.
