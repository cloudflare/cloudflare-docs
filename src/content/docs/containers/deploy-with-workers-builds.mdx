This guide shows how to deploy a Worker that uses [Containers](/containers/) with [Workers Builds](/workers/ci-cd/builds/).

Workers Builds does not run a separate Containers pipeline. It runs the **build command** and **deploy command** you configure. Those commands decide whether images build and instances roll out.

For the deploy model (order of operations, version skew, and how to confirm readiness), see [Container deployments](/containers/deployments/). For connecting a repo only, see [Workers Builds](/workers/ci-cd/builds/).

## Before you start

- A Worker with a [`containers`](/workers/wrangler/configuration/#containers) entry in Wrangler config
- The Worker [connected to a Git repository](/workers/ci-cd/builds/) in the Cloudflare dashboard
- Either a Dockerfile path (or directory) in config, or a registry image reference you already publish another way

## How Builds maps onto Containers

| Branch type              | Default deploy command         | What updates                                                                                                                  |
| ------------------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Production               | `npx wrangler deploy`          | Worker becomes active; image builds or resolves when config needs it; instances roll out (gradual by default)                 |
| Non-production (preview) | `npx wrangler versions upload` | Worker version only. No image build or push. No instance rollout. Running containers keep the image from the last full deploy |

Implications:

- A green production build that runs `wrangler deploy` follows the same container path as a local full deploy.
- A green preview build that runs `wrangler versions upload` can ship new Worker code against an **older container image**.
- Build success means the configured commands finished. It does not mean every container instance already runs a new image.

Which Wrangler commands change which artifacts: [Container deployments](/containers/deployments/#which-commands-change-which-artifacts).

The Workers Builds environment provides Docker, so Dockerfile-based `wrangler deploy` can build and push images during the deploy command.

## Configure production for a full container deploy

<Steps>

1. In the Cloudflare dashboard, go to **Workers & Pages**, open your Worker, then go to **Settings** > **Builds**.

   <DashButton url="/?to=/:account/workers-and-pages" />

2. Set **Deploy command** to a full deploy, for example:

   ```sh
   npx wrangler deploy
   ```

   Customize only if you already use Wrangler environments or a package script (for example `npm run deploy` or `npx wrangler deploy --env production`). See [Deploy command](/workers/ci-cd/builds/configuration/#deploy-command).

3. Keep the Dockerfile (or image reference) and `containers` config in the repo path that Builds uses as the [root directory](/workers/ci-cd/builds/configuration/).

4. Push to your [production branch](/workers/ci-cd/builds/build-branches/).

5. Open the build in the dashboard and confirm it succeeds. Then verify containers using the checks in [Confirm a deploy](/containers/deployments/#confirm-a-deploy).

</Steps>

### Optional production deploy flags

Put rollout flags on the production deploy command when you need them:

```sh
# Worker and image must cut over together
npx wrangler deploy --containers-rollout=immediate

# Worker only; leave images and instances unchanged
npx wrangler deploy --containers-rollout=none
```

[`rollout_active_grace_period`](/workers/wrangler/configuration/#containers) still applies on immediate rollouts. Flag reference: [Rollouts](/containers/platform-details/rollouts/#rollout-modes).

Use `--containers-rollout=none` only when you intend to leave the running container image unchanged.

## Configure non-production preview builds

Non-production builds default to `npx wrangler versions upload`. For Container Workers, keep that default unless you have a dedicated non-production target.

| Goal                                                                     | What to configure                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Preview **Worker** code only; leave the production container image alone | Keep `npx wrangler versions upload` (default). Design Worker changes to stay compatible with the image from the last full production deploy.                                                                                                                                                                                                                                                                                                            |
| Exercise a **new image** before production                               | Do **not** point the production Worker's non-production deploy command at `npx wrangler deploy`. That command performs a full container deploy for whatever Worker and Wrangler environment the build uses, and can roll instances that serve real traffic. Instead, run image-changing deploys against a **separate Worker or Wrangler environment** that has its own container config, or land image changes only through the production deploy path. |

When non-production branch builds are enabled, set the command under **Non-production branch deploy command**. See [Configuration](/workers/ci-cd/builds/configuration/#non-production-branch-deploy-command) and [Build branches](/workers/ci-cd/builds/build-branches/#configure-non-production-branch-builds).

If preview Worker code must talk to containers before the matching image is in production, keep the Worker/image protocol backward compatible until the production deploy, or validate the pair on a non-production Worker/environment first.

## Dockerfile and build environment

When the production deploy command runs `wrangler deploy` and `image` points at a Dockerfile:

1. Builds starts a managed build environment for your job.
2. Your **build command** runs (if set).
3. Your **deploy command** runs Wrangler.
4. Wrangler builds the image with Docker in that environment, pushes to the account registry when needed, then configures containers and starts a rollout.

You do not need to install Docker in your repository for that path. You still need a valid Dockerfile and a Wrangler version that supports your Containers config (from your project dependencies when you invoke `npx wrangler`).

If you use only pre-built registry images (no Dockerfile on deploy), Docker is not required for the image step; Wrangler resolves the image reference instead. See [Image management](/containers/platform-details/image-management/).

## Verify after a Builds deploy

1. Build history shows success for the commit you expect.
2. For production `wrangler deploy`, Worker **Deployments** shows a new active deployment.
3. Apply the [minimum or strict confirm checks](/containers/deployments/#confirm-a-deploy) that match how careful this release needs to be.
4. Hit a route that must reach the container and confirm behavior matches the Worker and image you intended.
5. If you used a gradual rollout, allow time for steps to finish before requiring every instance to show the new image.

## Common failure modes

| Symptom                                            | Likely cause                                                              | What to do                                                                                                                                 |
| -------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Preview Worker breaks talking to containers        | Preview used `versions upload`; image still old                           | Keep APIs compatible until production deploy, or validate image changes on a separate Worker/environment                                   |
| Production build green but instances look old      | Gradual rollout still in progress, or grace period holding busy instances | Wait for rollout steps; check [Rollouts](/containers/platform-details/rollouts/); confirm you did not pass `--containers-rollout=none`     |
| Deploy fails needing Docker                        | Dockerfile image but deploy cannot use Docker                             | Use Workers Builds (Docker available), run Docker locally, switch to a pre-built image ref, or `--containers-rollout=none` for Worker-only |
| First Containers deploy errors on container routes | Image still provisioning                                                  | Wait several minutes; check logs; see [First deploy](/containers/deployments/#first-deploy)                                                |
