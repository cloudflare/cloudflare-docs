This page is the reference for how **container instances** update after a deploy: defaults, replace sequence, and `--containers-rollout` modes.

For what a full deploy changes (Worker, image, and instances) and why they can temporarily disagree, see [Container deployments](/containers/deployments/).

## Defaults

When you run [`wrangler deploy`](/workers/wrangler/commands/workers/#deploy) with Containers configured:

| Subject               | Default behavior                                                                      |
| --------------------- | ------------------------------------------------------------------------------------- |
| Worker code           | Updates when the new Worker version becomes active (immediately on a standard deploy) |
| Container instances   | Update with a gradual rollout                                                         |
| Default rollout steps | Two steps: 10% of instances, then the remaining 90% (`[10, 100]`)                     |
| Active grace period   | `0` seconds (instances become eligible to replace without an extra delay)             |
| Stop signal           | `SIGTERM`, then `SIGKILL` after 15 minutes if the process is still running            |

Configure step percentages with [`rollout_step_percentage`](/workers/wrangler/configuration/#containers). Configure the active grace period with [`rollout_active_grace_period`](/workers/wrangler/configuration/#containers).

## Instance replace sequence

When an instance is selected to update during a rollout:

1. The instance must be past `rollout_active_grace_period` (minimum seconds after it became active before it is eligible).
2. The platform sends `SIGTERM` to the container process.
3. The process has 15 minutes to exit. Perform cleanup in that window if you need a graceful stop.
4. If the process is still running after 15 minutes, the platform sends `SIGKILL`.
5. A new instance starts with the target image. Requests may hang while the new instance starts.

Disk remains [ephemeral](/containers/faq/#is-disk-persistent-what-happens-to-my-disk-when-my-container-sleeps) across replace and sleep cycles unless you persist data outside the container filesystem.

## Rollout modes

The `--containers-rollout` flag applies to [`wrangler deploy`](/workers/wrangler/commands/workers/#deploy) only. It does not apply to [`wrangler versions upload`](/workers/wrangler/commands/workers/#versions), which does not build images or roll out instances. Command comparison: [Container deployments](/containers/deployments/#which-commands-change-which-artifacts).

| Mode              | Flag                                     | Instance behavior                                                    |
| ----------------- | ---------------------------------------- | -------------------------------------------------------------------- |
| Gradual (default) | omit flag, or behavior from config steps | Replaces instances in steps defined by `rollout_step_percentage`     |
| Immediate         | `--containers-rollout=immediate`         | Rolls out to 100% of eligible instances in one step                  |
| None              | `--containers-rollout=none`              | Skips image build/push and instance rollout; deploys the Worker only |

`rollout_active_grace_period` still applies in immediate mode. Instances that are not yet eligible remain on the previous image until they pass the grace period and drain.

### Immediate rollouts

Use an immediate rollout when Worker code and the container image must cut over together:

<PackageManagers
	pkg="wrangler"
	type="exec"
	args="deploy --containers-rollout=immediate"
/>

### None

Use `--containers-rollout=none` when you need to ship Worker-only changes and leave container images and instances unchanged. If your config points at a Dockerfile and Docker is unavailable, Wrangler may require this flag (or a working Docker setup) so the deploy can skip container build steps.

## Example configuration

Five-minute grace period and two steps (10%, then 100%):

<WranglerConfig>

```jsonc
{
	"containers": [
		{
			"max_instances": 10,
			"class_name": "MyContainer",
			"image": "./Dockerfile",
			"rollout_active_grace_period": 300,
			"rollout_step_percentage": [10, 100],
		},
	],
	"durable_objects": {
		"bindings": [
			{
				"name": "MY_CONTAINER",
				"class_name": "MyContainer",
			},
		],
	},
	"migrations": [
		{
			"tag": "v1",
			"new_sqlite_classes": ["MyContainer"],
		},
	],
}
```

</WranglerConfig>

## Compatibility during a rollout

Worker code updates on deploy while container instances follow the rollout mode above. Until the rollout finishes, new Worker code may run against previous images. Keep changes backward compatible across that window, or use an immediate rollout for breaking cutovers. Background: [Version skew](/containers/deployments/#version-skew).
