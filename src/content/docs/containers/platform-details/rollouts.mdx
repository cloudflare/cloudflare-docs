After you [deploy](/containers/deploy/), Worker code goes live with the new Worker version. Container instances update with a rolling strategy.

## Defaults

| Setting             | Default                                                                    |
| ------------------- | -------------------------------------------------------------------------- |
| Rollout steps       | Two steps: 10% of instances, then the remaining 90% (`[10, 100]`)          |
| Active grace period | `0` seconds                                                                |
| Stop signal         | `SIGTERM`, then `SIGKILL` after 15 minutes if the process is still running |

Set step percentages with [`rollout_step_percentage`](/workers/wrangler/configuration/#containers). Set the grace period with [`rollout_active_grace_period`](/workers/wrangler/configuration/#containers).

## How an instance updates

When an instance is selected during a rollout:

1. It must be past `rollout_active_grace_period` (seconds after it became active before it is eligible).
2. The platform sends `SIGTERM` to the container process.
3. The process has 15 minutes to exit. Run cleanup in that window if you need a graceful stop.
4. If it is still running after 15 minutes, the platform sends `SIGKILL`.
5. A new instance starts with the new image. Requests may hang while it starts.

Disk is [ephemeral](/containers/faq/#is-disk-persistent-what-happens-to-my-disk-when-my-container-sleeps) across replace and sleep unless you store data outside the container filesystem.

Until the rollout finishes, new Worker code may still talk to instances on the previous image. Prefer backward-compatible changes with the default gradual rollout, or use an immediate rollout for a hard cutover.

## Rollout modes

`--containers-rollout` applies to [`wrangler deploy`](/workers/wrangler/commands/workers/#deploy) only. It does not apply to [`wrangler versions upload`](/workers/wrangler/commands/workers/#versions), which does not build images or roll out instances.

| Mode              | Flag                             | Behavior                                                             |
| ----------------- | -------------------------------- | -------------------------------------------------------------------- |
| Gradual (default) | omit flag                        | Replaces instances in steps from `rollout_step_percentage`           |
| Immediate         | `--containers-rollout=immediate` | Rolls out to 100% of eligible instances in one step                  |
| None              | `--containers-rollout=none`      | Skips image build/push and instance rollout; deploys the Worker only |

`rollout_active_grace_period` still applies in immediate mode.

### Immediate

Use when Worker code and the container image must switch together:

<PackageManagers
	pkg="wrangler"
	type="exec"
	args="deploy --containers-rollout=immediate"
/>

### None

Use when you want Worker-only changes and must leave images and instances unchanged. If your config points at a Dockerfile and Docker is unavailable, Wrangler may require this flag (or a working Docker setup) so the deploy can skip container build steps.

## Example configuration

Five-minute grace period and two steps (10%, then 100%):

<WranglerConfig>

```jsonc
{
	"containers": [
		{
			"max_instances": 10,
			"class_name": "MyContainer",
			"image": "./Dockerfile",
			"rollout_active_grace_period": 300,
			"rollout_step_percentage": [10, 100],
		},
	],
	"durable_objects": {
		"bindings": [
			{
				"name": "MY_CONTAINER",
				"class_name": "MyContainer",
			},
		],
	},
	"migrations": [
		{
			"tag": "v1",
			"new_sqlite_classes": ["MyContainer"],
		},
	],
}
```

</WranglerConfig>
