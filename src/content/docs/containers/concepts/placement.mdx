By default, containers run in the location nearest to the incoming request with a pre-fetched image. Use placement constraints to restrict where your containers run for data residency, compliance, or latency requirements.

## Regional constraints

Use the `regions` constraint to limit container placement to specific geographic areas:

| Region | Description           | Notes            |
| ------ | --------------------- | ---------------- |
| `ENAM` | Eastern North America |                  |
| `WNAM` | Western North America |                  |
| `EEUR` | Eastern Europe        |                  |
| `WEUR` | Western Europe        |                  |
| `APAC` | Asia Pacific          |                  |
| `SAM`  | South America         |                  |
| `ME`   | Middle East           | Limited capacity |
| `OC`   | Oceania               | Limited capacity |
| `AFR`  | Africa                | Limited capacity |

Limited capacity regions (ME, OC, AFR) cannot be used exclusively. Include at least one other region, or contact support for dedicated access.

## Jurisdictional constraints

Use the `jurisdiction` constraint to restrict containers to compliance boundaries:

| Jurisdiction | Regions    | Use case          |
| ------------ | ---------- | ----------------- |
| `eu`         | EEUR, WEUR | EU data residency |
| `us`         | ENAM, WNAM | US data residency |
| `fedramp`    | ENAM, WNAM | FedRAMP regions   |

When you specify both `jurisdiction` and `regions`, the regions must be valid for that jurisdiction. For example, specifying `jurisdiction: "eu"` with `regions: ["ENAM"]` is invalid.

:::caution[Jurisdiction controls where containers run, not where images are stored]
The `jurisdiction` constraint controls where Container instances run. It does not determine where Container images or [snapshots](/containers/guides/snapshots/) are stored. If storage location is part of your requirement, confirm the supported image workflow with your account team before you deploy.

The `jurisdiction` constraint in Wrangler configuration applies to applications that use the [`default` scheduling policy](/containers/configuration/scheduling-policy/). With the [`durable_object` scheduling policy](/containers/configuration/scheduling-policy/#use-the-durable-object-scheduling-policy), a Container runs where its Durable Object runs. To restrict that location, create the Durable Object in a [jurisdiction](/durable-objects/reference/data-location/#restrict-durable-objects-to-a-jurisdiction).

For Data Localization Suite support, refer to [Product compatibility](/data-localization/compatibility/#developer-platform).
:::

## Configure placement

Set placement constraints in your Wrangler configuration:

<WranglerConfig>

```toml
[[containers]]
name = "my-container"
image = "docker.io/my-org/my-image:latest"

[containers.constraints]
regions = ["ENAM", "WNAM"]
jurisdiction = "fedramp"
```

</WranglerConfig>

Refer to [Lifecycle of a Container](/containers/concepts/architecture/) for more details on how placement affects container startup and routing.
