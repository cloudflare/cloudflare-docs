When you deploy a Worker that uses [Containers](/containers/), more happens than a Worker script upload. This page explains which artifacts change, in what order, why Worker code and container instances can temporarily disagree, and how to tell that a deploy succeeded.

For a first hands-on deploy, use [Get started](/containers/get-started/). For rollout flags and step configuration, see [Rollouts](/containers/platform-details/rollouts/). For Dockerfile and registry behavior, see [Image management](/containers/platform-details/image-management/). For git-connected deploys, see [Deploy Containers with Workers Builds](/containers/deploy-with-workers-builds/).

## Worker, image, and instances

A Containers app updates three related artifacts on different schedules:

| Artifact            | What it is                                                                     | When it changes on a full `wrangler deploy`                                                            |
| ------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| Worker              | Your Worker script, bindings, and Durable Object classes that drive containers | As soon as the new Worker [version](/workers/versions-and-deployments/) becomes active                 |
| Container image     | The image built from your Dockerfile or resolved from a registry               | After the Worker upload, when Wrangler builds or resolves the image                                    |
| Container instances | Running instances of that image on the network                                 | After the image is ready, according to your [rollout](/containers/platform-details/rollouts/) settings |

The Worker decides when to start instances, how to route requests, and which Durable Object ID maps to which workload. The image defines the process that runs inside each instance.

These artifacts are related, but they are not one atomic unit. A successful deploy does not mean every instance already runs the new image.

## What `wrangler deploy` does

For a Worker with a [`containers`](/workers/wrangler/configuration/#containers) configuration, [`wrangler deploy`](/workers/wrangler/commands/workers/#deploy) roughly follows this sequence:

1. **Upload the Worker.** Cloudflare creates a new Worker version. On a standard deploy, that version becomes active and starts serving traffic.
2. **Build or resolve the container image.** If `image` points at a Dockerfile (or a directory that contains one), Wrangler builds with Docker and pushes to the [Cloudflare container registry](/containers/platform-details/image-management/). If `image` is already a registry reference, Wrangler resolves that reference instead.
3. **Update container configuration for each configured class.** Wrangler applies image and instance settings for the Durable Object classes listed under `containers`.
4. **Roll out container instances.** Existing instances move to the new image according to your [rollout](/containers/platform-details/rollouts/) settings. The default is a gradual rollout, not an instant replace of every instance.

Wrangler runs the container steps only when container rollout is enabled for the deploy. The default is a gradual instance rollout. Pass [`--containers-rollout`](/containers/platform-details/rollouts/#rollout-modes) to change that behavior for one command.

## Version skew

Because the Worker can become active before every container instance has the new image, the two sides can disagree for a while. During that window you may see:

- New Worker code talking to instances that still run the previous image
- A mix of old and new images across instances while a gradual rollout is in progress
- Requests that wait while an instance stops, starts, or pulls a new image

Design deploys so that overlap is safe:

- Prefer backward-compatible changes when you use the default gradual rollout (for example additive APIs, tolerant readers, and feature flags).
- Use an [immediate rollout](/containers/platform-details/rollouts/#immediate-rollouts) when Worker code and the image must switch together (breaking protocol changes, mismatched entrypoints, or a hard dependency on a new binary).
- Remember that [`rollout_active_grace_period`](/workers/wrangler/configuration/#containers) still delays replacing busy instances, even on an immediate rollout.

Rollout steps, stop signals, and grace periods are documented in [Rollouts](/containers/platform-details/rollouts/).

## First deploy versus later deploys

### First deploy

The first time you deploy a Containers Worker, Cloudflare still has to make the image available and ready instances across the network. That provisioning often takes several minutes. During that period the Worker may already be reachable, while calls into the container fail or wait until an instance can start.

Cached image layers and later deploys are usually faster than the first push. See [Image management](/containers/platform-details/image-management/) for build and push behavior, and [Lifecycle of a Container](/containers/platform-details/architecture/) for how instances start after the image exists.

### Later deploys

On later deploys, Wrangler uploads a new Worker version, publishes image changes when needed, and rolls instances. Only some instances move at each rollout step unless you override the default. Idle or newly started instances pick up the target image according to rollout rules. Long-lived busy instances may wait until they pass the active grace period and drain.

## Confirm a deploy

There is no single global containers-ready indicator in the dashboard. Choose a bar that matches the risk of the change.

### Minimum bar (safe to treat the deploy command as successful)

1. **Wrangler (or your CI deploy command) finished without errors.** The Worker upload and the container configure or rollout requests for that command completed.
2. **Worker Deployments** (for a standard `wrangler deploy`) shows the new active deployment, or your preview version exists if you only ran `versions upload`.
3. **A request that must hit the container** returns the behavior you expect for the Worker code you just shipped (knowing instances may still be on a mixed image set during a gradual rollout).

### Strict bar (every instance should be on the new image)

1. Meet the minimum bar.
2. Inspect apps and images with `npx wrangler containers list` and `npx wrangler containers images list`, or use the [Containers dashboard](https://dash.cloudflare.com/?to=/:account/workers/containers).
3. Allow gradual rollout steps to finish before you require a uniform image. After `--containers-rollout=immediate`, expect a shorter cutover that is still subject to grace period and instance startup time.
4. Re-check application behavior on paths that exercise long-lived instances, not only a single cold start.

A successful command never means every instance worldwide has already finished replacing. If the Worker answers but the container path errors right after a first deploy, wait for provisioning and check logs before assuming the configuration is wrong.

## CI and git-connected deploys

[Workers Builds](/workers/ci-cd/builds/) runs your configured build and deploy commands in a managed environment. It does not use a separate Containers pipeline. The command you configure is what performs the deploy:

- Production defaults to `npx wrangler deploy`, which runs the full path above, including Dockerfile builds when configured. The Builds environment provides Docker for that path.
- Non-production defaults to `npx wrangler versions upload`, which uploads a Worker version only and does not build or roll out container images.

Treat a green build as "the configured commands finished," not as "every container instance runs the new image."

Step-by-step setup, preview configuration, and failure modes: [Deploy Containers with Workers Builds](/containers/deploy-with-workers-builds/).
