In addition to the predefined finding types that detect security issues in your SaaS and cloud applications, Cloudflare CASB lets you define custom finding types from scratch. Custom finding types give you control over the security conditions CASB detects. For example, you can detect administrators without two-factor authentication, or users with a specific license.

## Prerequisites

- You have added a [Cloud or SaaS integration](/cloudflare-one/integrations/cloud-and-saas/).
- You are familiar with [Rego](https://www.openpolicyagent.org/docs/policy-language).

## Standard and custom finding types

CASB evaluates your assets against two kinds of finding types. They differ in who manages the definition. In [Cloudflare One](https://one.dash.cloudflare.com), go to **Cloud & SaaS findings** > **Findings library** to see the **Origin** of each finding type.

- **Standard** (Origin: _Standard_): A predefined finding type that Cloudflare CASB creates and manages. You can inspect and duplicate it, but not change it.
- **Custom** (Origin: _Custom_): A finding type that you create and manage in your account with Rego expressions.

The following table shows what you can do with each kind of finding type:

| Capability                                                        | Standard | Custom |
| ----------------------------------------------------------------- | -------- | ------ |
| Inspect detection logic                                           | ✅       | ✅     |
| Create posture finding types                                      | ❌       | ✅     |
| Duplicate posture finding types                                   | ✅       | ✅     |
| Edit posture finding types                                        | ❌       | ✅     |
| Delete posture finding types                                      | ❌       | ✅     |
| Disable posture finding types                                     | ❌       | ❌     |
| Create, duplicate, edit, delete, or disable content finding types | ❌       | ❌     |

A custom finding type created by duplicating a standard finding type shares the same logic at the time of duplication. You can edit and delete the copy.

## How custom finding types work

### Example scenario

A security team that uses Google Workspace wants to know whenever an administrator account does not have two-factor authentication (2FA) turned on. CASB does not include a standard finding type for this policy, so the team creates a custom finding type.

1. **Define the finding type.** In the Findings library, the team creates a custom finding type named "Admin without 2FA". They set the severity to _High_, choose Google Workspace as the provider, and write a Rego expression that returns `"fail"` when an account is an administrator and 2FA is off.
2. **See the results.** As CASB receives updates for the company's Google Workspace accounts, it evaluates each one. Accounts that match appear as finding instances under **Posture Findings**.
3. **Take action.** The team creates a CASB policy for this finding type that sends a webhook to their ticketing system. Each new finding instance opens a ticket for the account owner.

The following sections describe each part of this flow.

### Finding type fields

A custom finding type has the following fields:

| Field             | Description                                                                                                                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding Name**  | The display name of the finding type.                                                                                                                                                               |
| **Description**   | What the finding type detects.                                                                                                                                                                      |
| **Severity**      | The impact of the finding type: _Low_, _Medium_, _High_, or _Critical_. For more information, refer to [Severity levels](/cloudflare-one/cloud-and-saas-findings/manage-findings/#severity-levels). |
| **Provider**      | The [integration vendor](/cloudflare-one/integrations/cloud-and-saas/) the finding type detects against.                                                                                            |
| **Asset Class**   | The set of asset fields available to the detection logic. These fields appear under **Available asset fields** in the finding type builder.                                                         |
| **Category Type** | The classification of the finding it generates.                                                                                                                                                     |
| **Integrations**  | The integrations CASB evaluates the finding type against. Select **Apply to all integrations** to evaluate every integration your account owns for the provider.                                    |
| **Rego Package**  | The detection logic CASB uses to generate finding instances.                                                                                                                                        |

CASB evaluates a custom finding type against an asset when the asset is created or updated in the selected integrations. CASB does not run a new finding type retroactively against existing assets.

Continuing the [example scenario](#example-scenario), two Google Workspace administrators, Alice and Bob, both have 2FA turned off:

| Day       | Event                                                  | Finding instance created?                                                          |
| --------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Sunday    | Alice's account is updated.                            | No. The "Admin without 2FA" finding type does not exist yet.                       |
| Monday    | The team creates the "Admin without 2FA" finding type. | No. Alice's account has not changed since the finding type was created.            |
| Tuesday   | Bob's account is created or updated.                   | Yes. CASB evaluates Bob's account.                                                 |
| Wednesday | Alice's account is updated again.                      | Yes. CASB evaluates Alice's account. No ticket exists for Alice until this update. |

### Detection logic

Write the detection logic as a Rego v1 expression that uses a restricted subset of built-ins and operations.

```txt
default result := "pass"

result := "fail" if {
	input.asset.isAdmin == true
	input.asset.is2faEnabled == false
}
```

The expression works as follows:

- `default result := "pass"` sets the result to `"pass"` for every asset unless a rule changes it.
- `result := "fail" if { ... }` changes the result to `"fail"` when every line inside the braces is true. A `"fail"` result creates a finding instance.
- `input.asset.isAdmin == true` checks that the account is an administrator.
- `input.asset.is2faEnabled == false` checks that 2FA is off.

Both conditions must be true, so a non-administrator without 2FA, or an administrator with 2FA, stays at `"pass"`.

Follow these rules:

- Define a `result` that returns either `"pass"` or `"fail"`. A `"fail"` result means the asset matches the definition and creates a finding instance.
- Add a `default` rule so the expression returns `"pass"` when no fail condition matches.
- Use `input.asset` for fields on the selected asset class. Use `input.associated` for related assets, when available.
- Do not add a package declaration or `import rego.v1`. CASB adds them for you.

### Validation

**Validate** compiles the expression and checks it against the asset schema. It reports syntax errors and unsupported built-ins. Validation does not run the expression against your data. To confirm the expression detects the intended conditions, [verify detection](#verify-detection) after you create the finding type.

## Create a custom finding type

<Steps>
1. In [Cloudflare One](https://one.dash.cloudflare.com), go to **Cloud & SaaS findings** > **Findings library**.
2. Select **Create finding**.
3. Under **General Information**, enter a finding type name and description, then select a severity.
4. Under **Scope Definition**, select a provider and asset class.
5. Choose whether the finding type applies to all integrations for the provider or to selected integrations.
6. Under **Detection Logic**, enter the Rego expression. Use **Available asset fields** to identify supported fields.
7. Select **Validate**, and resolve each validation error.
8. Select **Create finding**.
</Steps>

CASB applies the custom finding type when it receives future asset updates within the selected scope. Matching assets appear as posture finding instances.

## Verify detection

<Steps>
1. Create or update an asset within the finding type's integration scope. The asset must receive an update after you create or change the custom finding type.
2. In [Cloudflare One](https://one.dash.cloudflare.com), go to **Cloud & SaaS findings** > **Posture Findings**.
3. Find the custom finding type. The **Finding Instances** column shows how many assets currently match.
4. Select **Manage** to view the matching assets.
</Steps>

If the asset does not appear, check the provider, asset class, integration scope, field names, field types, and Rego result.

## Use custom finding types in policies

You can select a custom finding type in a [CASB policy](/cloudflare-one/cloud-and-saas-findings/policies/) the same way you select a standard finding type. When you [create a policy](/cloudflare-one/cloud-and-saas-findings/policies/#create-a-policy), select the custom finding type from the **Finding type** list.

- Policies with custom finding types can send webhooks. Remediation actions are not supported.
- A policy acts on findings from the integrations it selects, or from all integrations if **Apply to all integrations** is set. It can only act on integrations within the custom finding type's integration scope. If you [edit](#edit-a-custom-finding-type) the scope to remove an integration, CASB no longer creates finding instances for that integration, so the policy has nothing to act on there.
- If the custom finding type is [quarantined](#quarantined-custom-finding-types), CASB creates no new finding instances, so the policy does not trigger.
- You cannot delete a custom finding type while a policy uses it. [Delete the policy](/cloudflare-one/cloud-and-saas-findings/policies/#edit-turn-off-or-delete-a-policy) first, then [delete the custom finding type](#delete-a-custom-finding-type).

### Example scenario

Continuing the [example scenario](#example-scenario), the team wants a ticket opened each time CASB finds an administrator without 2FA.

1. **Create the policy.** The team creates a CASB policy and selects "Admin without 2FA" from the **Finding type** list.
2. **Set the scope.** They select **Apply to all integrations**, so the policy covers every Google Workspace integration the finding type is evaluated against.
3. **Choose the action.** The policy sends a webhook to the team's ticketing system.
4. **See it work.** When CASB evaluates an updated administrator account as `"fail"`, it creates a finding instance. The policy fires the webhook, and a ticket opens for the account owner.

## Manage custom finding types

### Duplicate a finding type

Open a standard finding type to inspect its detection logic. If the logic is a useful starting point, duplicate it to create an editable copy. You can duplicate standard and custom posture finding types. Content finding types are not supported.

<Steps>
1. In [Cloudflare One](https://one.dash.cloudflare.com), go to **Cloud & SaaS findings** > **Findings library**.
2. In the finding type menu, select **Duplicate**.
3. Review the copied name, description, severity, provider, asset class, integration scope, and Rego expression, and change them as needed.
4. Select **Validate**, and resolve each validation error.
5. Select **Create finding**.
</Steps>

The duplicate is a separate custom finding type. Changes to the duplicate do not affect the original.

#### Example scenario

Continuing the [example scenario](#example-scenario), the "Admin without 2FA" finding type applies to every Google Workspace integration. The team now wants a stricter version for their production integration only, with a severity of _Critical_. You cannot edit severity after creation, so they duplicate the finding type.

1. They select **Duplicate** on "Admin without 2FA". CASB copies the fields and Rego expression into the builder.
2. They rename the copy "Admin without 2FA (production)", set the severity to _Critical_, and limit the integration scope to the production integration. The expression stays the same.
3. They select **Validate**, then **Create finding**.

The original finding type keeps running unchanged. Administrators in the production integration now also receive findings for the copy.

### Edit a custom finding type

You can only edit the name, description, and integration scope. To change the provider, asset class, severity, or Rego expression, [duplicate the finding type](#duplicate-a-finding-type).

<Steps>
1. In [Cloudflare One](https://one.dash.cloudflare.com), go to **Cloud & SaaS findings** > **Findings library**.
2. In the custom finding type menu, select **Edit**.
3. Update the name, description, or integration scope.
4. Select **Save**.
</Steps>

### Delete a custom finding type

:::caution
Deleting a custom finding type cannot be undone. CASB also deletes the finding type's existing finding instances. You cannot delete a custom finding type while a [CASB policy](/cloudflare-one/cloud-and-saas-findings/policies/) uses it. Delete the policy first.
:::

<Steps>
1. In [Cloudflare One](https://one.dash.cloudflare.com), go to **Cloud & SaaS findings** > **Findings library**.
2. In the custom finding type menu, select **Delete**.
3. Confirm the deletion.
</Steps>

CASB stops evaluating the deleted finding type against future asset updates.

### Disable a custom finding type

You cannot disable a custom finding type. To stop CASB from evaluating it, delete it.

To stop a policy that uses a custom finding type from triggering, turn off the policy instead. For more information, refer to [Edit, turn off, or delete a policy](/cloudflare-one/cloud-and-saas-findings/policies/#edit-turn-off-or-delete-a-policy).

## Quarantined custom finding types

Quarantined is a system-assigned status. CASB applies it when it cannot safely evaluate a custom finding type's expression because evaluation is consistently long-running or allocates excessive memory. A warning icon appears next to the entry in **Cloud & SaaS findings** > **Findings library**.

While a custom finding type is quarantined:

- Existing finding instances remain visible.
- CASB does not evaluate the expression on asset updates, so it creates no new finding instances.
- Other custom and standard finding types on the same integrations continue to run normally.

The **Policies** list does not show when a policy uses a quarantined custom finding type. To check, look for the warning icon in **Findings library**.

You cannot quarantine a custom finding type or remove the status. Editing the name, description, or integration scope does not remove it.

### Causes

Common causes of quarantine include:

- Nested iteration over large arrays, such as comparing every item in a list to every other item.
- Timeouts caused by evaluation against large or deeply nested asset fields.
- Running regular expressions against every element of a large collection when a simpler check, such as `startswith` or `endswith`, is sufficient.

An expression can pass validation and still be quarantined later, because validation does not run the expression against asset data.

### Resolve a quarantined custom finding type

Because you cannot edit an expression, duplicate the quarantined finding type and correct the expression in the copy.

<Steps>
1. In [Cloudflare One](https://one.dash.cloudflare.com), go to **Cloud & SaaS findings** > **Findings library**.
2. In the quarantined custom finding type menu, select **Duplicate**.
3. Rewrite the expression to reduce its runtime and memory use. Refer to [Causes](#causes).
4. Select **Validate**, and resolve each validation error.
5. Select **Create finding**. The duplicate is a new custom finding type and is not quarantined.
6. If a policy uses the quarantined finding type, update the policy to use the new one.
7. [Delete the quarantined custom finding type](#delete-a-custom-finding-type).
</Steps>

:::note
A quarantined custom finding type still counts toward the [limits](#limits). If you are at a limit, copy the expression and delete the quarantined finding type before you create the replacement.
:::

If you cannot identify why CASB quarantined the expression, contact [Cloudflare Support](/support/contacting-cloudflare-support/) and provide the custom finding type ID and as much detail as possible.

## Limits

- An account can have up to 250 custom finding types.
- Up to 25 custom finding types can apply to one integration.
- Custom finding types support posture findings only. They do not support Data Loss Prevention (DLP) content findings.
- The complete Rego policy, including declarations CASB adds, can be up to 4 KiB.
- Network access is not available.
- The editor does not accept package or import declarations.
- New and updated custom finding types do not apply retroactively.

## Rego reference

Custom finding types use Rego v1 syntax and the built-ins listed in this section.

- [Rego policy language](https://www.openpolicyagent.org/docs/policy-language)
- [OPA built-ins](https://www.openpolicyagent.org/docs/policy-reference/builtins)
- [OPA style guide](https://www.openpolicyagent.org/docs/style-guide)
- [OPA Playground](https://play.openpolicyagent.org/)

:::note
The OPA documentation and Playground include built-ins that custom finding types do not support. An expression that works in the Playground may fail validation in Cloudflare One. Use only the built-ins listed on this page.
:::

### Example expressions

#### Iterate over an array

For the Anthropic `AnthropicComplianceRole` asset class, the following expression detects a role with the Cowork permission:

```txt
default result := "pass"

result := "fail" if {
	some permission in input.asset.permissions
	permission.action == "cowork"
}
```

#### Handle a nullable value

For the Anthropic `AnthropicComplianceUser` asset class, the following expression detects a non-null email in the `example.com` domain:

```txt
default result := "pass"

result := "fail" if {
	input.asset.email != null
	regex.match(`(?i)@example\.com$`, input.asset.email)
}
```

#### Use an associated asset

For the Google Workspace `GoogleWorkspaceLicenseAssignment` asset class, the following expression detects a non-suspended, non-administrator user with an AI Ultra license:

```txt
ai_ultra_sku_id := "1010470008"

default result := "pass"

result := "fail" if {
	input.asset.skuId == ai_ultra_sku_id
	input.associated.user.isAdmin == false
	input.associated.user.isSuspended == false
}
```
