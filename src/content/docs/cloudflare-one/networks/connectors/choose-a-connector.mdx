You connect once, and Cloudflare does the rest. Every connector brings traffic into the same global network, where the same policies, identity controls, and logs apply. What changes from one connector to the next is **what you are connecting**.

> **Mesh is the default connector for Cloudflare One and private networks. Tunnel is the best way to publish an HTTP application on the public Internet.**
> Code running on Cloudflare uses Workers VPC, and whole sites use Cloudflare WAN.

## Start with what you are connecting

_Each connector is a door into Cloudflare One, sized for a different kind of traffic._

<ConnectorMapDiagram variant="connectors" />

People and their devices arrive through the [Cloudflare One Client](/cloudflare-one/team-and-resources/devices/cloudflare-one-client/). Infrastructure arrives through one of four connectors:

| Connector | You are connecting | What it does | Usually run by |
| --- | --- | --- | --- |
| [Cloudflare Mesh](/mesh/) | **Anything private: networks, servers, devices, and private applications** | The default connector for Cloudflare One (SASE) and private networks. Gives every participant a private Mesh IP, and carries TCP, UDP, and ICMP in both directions. | Platform, DevOps, and cloud infrastructure teams |
| [Cloudflare Tunnel](/tunnel/) | **A web application on the public Internet** | Publishes HTTP applications on public hostnames, with or without [Access](/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/) in front. `cloudflared` connects out, so the origin needs no inbound port. | Application and web teams |
| [Workers VPC](/workers-vpc/) | **Code on Cloudflare** | Lets Workers and agents call private APIs and databases, wherever and however they connect. | Developers building on Workers |
| [Cloudflare WAN](/cloudflare-one/networks/connectors/cloudflare-wan/) | **A whole site** | Brings branch offices and data centers online with the [Cloudflare One Appliance](/cloudflare-one/networks/connectors/cloudflare-wan/configuration/appliance/), or IPsec and GRE from your existing routers. | Network engineering teams |

The quickest way to tell them apart is the boundary you are connecting: a public web application, anything private, your own code, or the edge of a whole network.

## Public applications or private networks: Tunnel and Mesh

_Public HTTP goes through Tunnel. Everything private goes through Mesh._

Cloudflare Tunnel and Cloudflare Mesh both run as software beside your infrastructure, and both connect out to Cloudflare without opening inbound ports. They differ in direction and layer.

**Mesh is the default for private access.** It is the connector for Cloudflare One (SASE): users on the Cloudflare One Client reach private applications, servers, and networks through it. Every participant, whether a laptop, phone, server, VM, or container, gets a private [Mesh IP](/mesh/concepts/#mesh-ips), and any participant can start a connection to any other. Mesh forwards packets at layer 3, so any TCP, UDP, or ICMP traffic works. Routes extend Mesh to whole subnets and to private hostnames behind a node.

**Tunnel publishes a web application on the public Internet.** `cloudflared` proxies HTTP requests that arrive from Cloudflare to a service it can reach. Put [Access](/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/) in front to require sign-in, or leave the hostname open. Either way, the full edge stack, including DDoS protection, WAF, and bot and API rules, applies to the traffic. Tunnel is built for HTTP: it proxies UDP flow by flow, which does not suit heavy or long-lived UDP traffic. For UDP, even a private application is better on Mesh.

<ConnectorDirection client:visible>

A laptop, Cloudflare, a connector, and a private server sit on one vertical path. With Cloudflare Tunnel selected, a connection the laptop starts reaches the server and returns, but a connection the server starts is refused at `cloudflared`, because Tunnel only carries connections clients start. With Cloudflare Mesh selected, both directions work: the laptop has a Mesh IP the server can reach, and the source IP is preserved.

</ConnectorDirection>

|  | Cloudflare Tunnel | Cloudflare Mesh |
| --- | --- | --- |
| **Best for** | Publishing HTTP applications on the public Internet, with or without Access | Cloudflare One private access, private networks, servers, devices, and agents |
| **Direction** | Client to application | Bidirectional |
| **Layer** | L7 HTTP proxy (HTTP/2, QUIC). TCP services such as SSH and RDP also work. | L3: any TCP, UDP, or ICMP traffic, over MASQUE |
| **UDP** | Proxied flow by flow. Fine for light traffic, not for DNS at scale, VoIP, or video. | Forwarded packet by packet |
| **Connector** | `cloudflared` | Cloudflare One Client (`warp-cli`) as a Mesh node, or the [`cloudflare/mesh`](/mesh/guides/run-mesh-in-containers/) container image |
| **Addressing** | Public hostnames, or private routes to resources | A Mesh IP for every participant, plus CIDR and hostname routes |
| **Source IP** | The origin sees `cloudflared`. HTTP origins can read `CF-Connecting-IP`. | Preserved end to end |
| **Runs on** | Linux, macOS, Windows, Docker, and Kubernetes | Linux hosts and containers (amd64 and arm64) for nodes. Client devices on desktop and mobile. |

Quick checks settle most cases:

- **Is it an HTTP application on a public hostname?** Use Tunnel, with or without Access in front.
- **Is it private, reached from the Cloudflare One Client?** Use Mesh.
- **Does it use UDP?** Use Mesh, even for a private application.
- **Does the server need to start connections, or need the original source IP?** Use Mesh.
- **Is an AI agent connecting?** Use Mesh.
- **Is it a whole LAN, or does it need 1 Gbps or more?** Use Cloudflare WAN.

<Details header="I already route private networks through Cloudflare Tunnel. Do I need to move?">

No. Tunnel [private network routes](/cloudflare-one/networks/connectors/cloudflare-tunnel/private-net/) keep working for client-to-server traffic, such as users reaching internal web applications from the Cloudflare One Client. For new private access, we recommend Mesh. Move workloads to Mesh when they use UDP, such as DNS, VoIP, or video, or when they need server-initiated traffic, source IP preservation, or long-lived connections such as database replication or Active Directory and SCCM traffic. Both can run in the same account.

</Details>

## Code on Cloudflare: Workers VPC

_Your code becomes part of the private network._

[Workers VPC](/workers-vpc/) lets a Worker call private services with `fetch()` for HTTP and `connect()` for raw TCP. One [VPC Network](/workers-vpc/configuration/vpc-networks/) binding with `network_id: "cf1:network"` reaches services behind Cloudflare Tunnel, Mesh nodes and their routes, and Cloudflare WAN on-ramps. The address you pass at runtime picks the destination. For the narrowest scope, a [VPC Service](/workers-vpc/configuration/vpc-services/) binds to one host and port.

Workers VPC does not replace Tunnel or Mesh. It uses them. Connect the private network with Tunnel, Mesh, or Cloudflare WAN, then bind your Worker to it.

## Whole sites: Cloudflare WAN

_When you need a managed box, not a software agent._

[Cloudflare WAN](/cloudflare-one/networks/connectors/cloudflare-wan/) connects branch offices and data centers, with all their users, phones, printers, and devices, at the network layer. The [Cloudflare One Appliance](/cloudflare-one/networks/connectors/cloudflare-wan/configuration/appliance/) is a hardware or virtual appliance that you ship and plug in: connectivity and configuration come down automatically, and traffic steering and shaping handle busy sites. If you already run a capable router or firewall, connect it with [IPsec or GRE](/cloudflare-one/networks/connectors/cloudflare-wan/configuration/third-party/) instead. To keep traffic off the public Internet, use [Cloudflare Network Interconnect](/network-interconnect/).

Cloudflare WAN requires an Enterprise plan.

## Connect AI agents

_Agents need network access, not application access._

Human access depends on things an agent cannot do: open a browser, sign in to an identity provider, approve an MFA prompt, and hold a session. The usual workarounds each leave a credential in the open. A public endpoint protected by a shared secret is reachable by anyone who finds it. A VPN credential handed to an agent scopes access to the whole network, and its logs only record that a device connected.

Mesh makes the agent a participant instead. Put a node beside the private resource, then let the agent dial its Mesh IP or hostname. Agents on a server or in a container get a service identity, and agents on a laptop use the signed-in user's identity, so you can write one policy for people and another for workloads.

<ConnectorMapDiagram variant="agents" />

| Pattern | Connector | How it works |
| --- | --- | --- |
| A coding agent on a laptop reaches a private database | Cloudflare Mesh | Run a Mesh node beside the database. The agent connects to the node's Mesh IP, with no bastion, port forward, or network credential in the agent's runtime. |
| An agent in one cloud reaches services in another | Cloudflare Mesh | Run a node in each VPC and advertise each subnet as a [route](/mesh/features/routes/). Both nodes dial out, so neither cloud opens a port, and there is no VPC peering to manage. |
| A Worker or agent on Cloudflare calls an internal API | Workers VPC | Bind the Worker with `cf1:network`, then `fetch()` the private hostname or IP. |
| An agent calls a private MCP server | Workers VPC or Cloudflare Mesh | Keep the MCP server private behind a node, and give it a [hostname route](/mesh/features/routes/#hostname-routes). Every call passes through Gateway and appears in your logs. |

Every pattern is the same three steps: put a node beside the resource, give it a route or a name, then dial it from the agent.

## Combine connectors

_Most deployments use two or three connectors together._

Connectors share one routing table and one policy plane, so they combine without extra infrastructure. Common combinations:

| Scenario | Connectors |
| --- | --- |
| Remote workforce reaching internal apps and servers | Cloudflare One Client for users, Mesh for private applications and networks, and Tunnel for public web applications |
| SaaS or developer platform with private customer environments | Tunnel, with [Tunnels for Platforms](/tunnel/features/tunnels-for-platforms/) as tunnel count grows with customer count |
| Cloud-native team with private APIs and agents | Mesh nodes in each VPC or cluster, and Workers VPC for code on Cloudflare |
| Enterprise with branch offices and data centers | Cloudflare One Appliance or IPsec at each site, the Cloudflare One Client for remote users, and Tunnel for public web applications |

A typical hybrid design uses Cloudflare WAN for managed branches and data centers, Mesh for private access, cloud workloads, and small sites, and Tunnel for public web applications. Keep one route inventory, and record which connector owns each prefix, so overlapping routes do not send traffic to the wrong place.

:::caution[Cloudflare Mesh and Cloudflare WAN]
To use Cloudflare Mesh and Cloudflare WAN in the same account, the account must use [Cloudflare One Unified Routing](/cloudflare-one/networks/connectors/cloudflare-wan/reference/traffic-steering/#unified-routing).
:::

For routing priority, MTU planning, and a compatibility matrix across all connectivity options, refer to [Connectivity options](/cloudflare-one/networks/connectivity-options/#combine-cloudflare-one-connectivity-options).

## Avoid these mistakes

_Each one tends to surface as "Cloudflare does not work."_

| Mistake | What happens | Do this instead |
| --- | --- | --- |
| Using Tunnel as a site gateway | A private application behind `cloudflared` still sends its own outbound traffic over its local route, and the network cannot start connections through the tunnel. | When the network needs to start traffic, use Mesh or Cloudflare WAN. |
| Forgetting the reply path | A private host receives a packet from `100.96.x.x`, has no route back, and drops the reply. The connection opens and then hangs. | Keep [source NAT](/mesh/guides/run-mesh-in-containers/#source-nat) on, or add a return route to the Mesh IP range. |
| Confusing routes with replicas | Two nodes that advertise overlapping routes do not fail over. The longest prefix wins, with no health check first. | For failover, add [replicas](/mesh/features/high-availability/) to one node instead of adding routes. |
| Excluding Mesh in split tunnels | Nodes and devices cannot reach each other. | Send `100.96.0.0/12` through Cloudflare, and use MASQUE in the device profile. On Windows, allow inbound `100.96.0.0/12` in Windows Firewall. |
| Sending heavy UDP through Tunnel | `cloudflared` keeps state for every UDP flow. High-volume DNS, VoIP, or video can drop packets or exhaust the connector. | Carry UDP over Mesh, which forwards packets without per-flow state on the node. |
| Treating Tunnel private routes as site-to-site | A private route lets clients reach destinations behind `cloudflared`. It does not make `cloudflared` a router for traffic that starts inside the network. | Use Mesh for software-defined sites, or Cloudflare WAN for managed sites. |
| Expecting one connector to be highly available | One `cloudflared` instance, one Mesh node, or one IPsec tunnel is still a single point of failure. | Run [Tunnel replicas](/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-availability/), Mesh [replicas](/mesh/features/high-availability/), or redundant WAN tunnels, and test failover. |
| Binding a Worker too broadly | `cf1:network` reaches everything Mesh and Cloudflare WAN reach. | Advertise only the routes the Worker needs, or bind a single VPC Service. |
