Use this guide to troubleshoot common issues with Data Loss Prevention (DLP).

## DLP policy is not triggering or blocking content

DLP not inspecting or blocking content is the most common issue reported. If you have configured a [DLP policy](/cloudflare-one/data-loss-prevention/dlp-policies/) but it fails to inspect or block traffic, the cause is almost always that the traffic is not being decrypted. To use DLP to scan the content of HTTPS requests, you must turn on TLS decryption.

### Incorrect configuration

A policy that does not explicitly enable decryption will not inspect or block traffic.

| Selector    | Operator | Value          | Logic | Action |
| ----------- | -------- | -------------- | ----- | ------ |
| Domain      | in       | _box.com_      | And   | Block  |
| DLP Profile | in       | _Credit Cards_ |       |        |

### Correct configuration

Create a Gateway HTTP policy that enables TLS Decryption for the traffic you intend to inspect. Ensure this decryption policy has a higher precedence (is ordered before) your DLP policy.

Step 1: Create a decryption policy.

| Selector | Operator | Value     | Action  |
| -------- | -------- | --------- | ------- |
| Domain   | in       | `box.com` | Decrypt |

Step 2: Create your DLP block policy.

| Selector    | Operator | Value          | Logic | Action |
| ----------- | -------- | -------------- | ----- | ------ |
| Domain      | in       | `box.com`      | And   | Block  |
| DLP Profile | in       | `Credit Cards` |       |        |

:::note
For a detailed guide, refer to the documentation on [configuring TLS
decryption](/cloudflare-one/policies/gateway/http-policies/tls-decryption/).
:::

## DLP scans are triggering false positives or blocking legitimate sites

If your DLP policy is blocking access to business-critical applications (like Zoho, Google, internal domains) or generating a high number of false positives, your policy is likely too broad. Profiles like **Credentials and Secrets** are powerful but can be overly aggressive if not scoped correctly.

### Problematic configuration

Applying a sensitive profile to all traffic causes unnecessary blocks.

| Selector    | Operator | Value                     | Action |
| ----------- | -------- | ------------------------- | ------ |
| DLP Profile | in       | _Credentials and Secrets_ | Block  |

### Recommended solution

Make your policies more specific. Instead of a blanket block, create granular policies that target high-risk destinations or user groups.

Example: A more specific policy.

This policy only blocks uploads of financial data to file-sharing websites for a specific user group, reducing the risk of false positives on other sites.

| Selector           | Operator | Value                           | Logic | Action |
| ------------------ | -------- | ------------------------------- | ----- | ------ |
| User Group         | in       | `Finance Team`                  | And   | Block  |
| Destination Domain | in       | `dropbox.com`, `wetransfer.com` | And   |        |
| DLP Profile        | in       | `Financial Information`         |       |        |

You can also use the **Do Not Scan** action for trusted applications that are known to cause false positives.

## Inconsistent detection

(for example, works for text but not images)

If you find that DLP detects sensitive data in plain text but not within images or certain applications, check the following:

- **OCR Is Enabled:** For DLP to scan text within images (like a picture of a credit card), you must enable **Optical Character Recognition (OCR)** in your DLP Profile. This feature is available on the Enterprise plan.
- **Application-Specific Behavior:** Some applications, like WhatsApp Web, use protocols or encryption methods (such as WebSockets) that may not be fully inspected by standard HTTP policies.
- **Supported File Types:** Ensure the content is in a [supported file type](/cloudflare-one/policies/data-loss-prevention/dlp-profiles/#supported-file-types) for DLP inspection.

**Example: Enabling OCR in a DLP Profile**

When editing a custom DLP profile, ensure the **"Scan with OCR"** option is checked.

## Enable DLP inspection option is missing or you cannot create custom profiles

If you cannot find the **Enable DLP inspection** option when creating an HTTP policy or are blocked from creating a custom DLP Profile, it typically means one of two things:

1. Incorrect plan. These features require a Zero Trust Enterprise plan. If you believe your account should have this entitlement, contact your account team to confirm your subscription details.
2. Permissions issue. You may not have the required administrative privileges to configure DLP settings. Check with your Cloudflare account administrator.
