## What are CDS and CDNSKEY records?

**CDS** (Child Delegation Signer) and **CDNSKEY** (Child DNSKEY) records are used to automate the management of the chain of trust between your domain and the Top-Level Domain registry.

Historically, enabling DNSSEC required manually copying a DS record from your DNS provider to your domain registrar. Cloudflare publishes CDS and CDNSKEY records to eliminate this manual step for registrars that support [RFC 8078](https://datatracker.ietf.org/doc/html/rfc8078).

### How Cloudflare uses these records

1. **Generation**: When you enable DNSSEC in the Cloudflare dashboard, Cloudflare automatically generates and publishes these records in your zone.
2. **Signaling**: The CDS and CDNSKEY records signal to the registry what your DS record should look like.
3. **Automatic update**: Modern registries and registrars that support RFC 8078 periodically scan your domain for these records and automatically update the DS record at the registry level.

### The difference between CDS and CDNSKEY

| Record | Purpose | What it contains |
| --- | --- | --- |
| **CDS** | High-level instruction | A hashed version of the public key (the same data found in a DS record) |
| **CDNSKEY** | Public key instruction | The full public Key Signing Key (KSK) that the parent can use to generate its own DS record |

Cloudflare publishes both to ensure compatibility with different registry requirements.

### Key rollover automation

One of the biggest benefits of CDS/CDNSKEY records is handling key rollovers. When Cloudflare rotates DNSSEC keys, the CDS records signal the change to the parent registry. If your registrar supports automatic scanning, the DS record updates before the old key expires, ensuring zero downtime.

## How often does Cloudflare rotate DNSSEC keys?

Cloudflare's Key Signing Key (KSK) is rarely rotated and remains extremely stable. When a KSK rotation does occur:

- The DS record changes
- CDS and CDNSKEY records automatically signal the change to registrars that support RFC 8078
- Zone Signing Key (ZSK) rotation is handled automatically by Cloudflare

You do not need to take any action when Cloudflare rotates keys. If your registrar supports CDS scanning, the DS record updates automatically. Otherwise, you may need to manually update the DS record at your registrar if notified.

## Can I use my own DNSSEC keys with Cloudflare?

No, Cloudflare does not support uploading private keys to the platform. Cloudflare generates and manages DNSSEC keys for your zone.

If you are migrating to Cloudflare from another DNS provider with DNSSEC enabled, you have two options:

1. **Disable DNSSEC** (recommended for most migrations):
   - Disable DNSSEC at your registrar
   - Migrate nameservers to Cloudflare
   - Re-enable DNSSEC on Cloudflare

2. **Multi-signer DNSSEC**:
   - Requires both providers to support multi-signer setup
   - Both providers must exchange ZSK DNSKEYs
   - More complex but avoids DNSSEC downtime
   - Refer to [Multi-signer DNSSEC](/dns/dnssec/multi-signer-dnssec/)

## Why can't I keep my existing DS record when migrating to Cloudflare?

DNSSEC validation follows a chain of trust from the root DNS servers down to your zone:

1. A resolver queries your parent registry (for example, `.com`) for your DS record
2. The DS record contains a hash of your Key Signing Key (KSK)
3. The resolver expects all Zone Signing Keys (ZSK) to be signed by that specific KSK
4. If Cloudflare uses a different KSK, validation fails when resolvers query Cloudflare nameservers

This is why you must either:
- Disable DNSSEC before migration and re-enable it on Cloudflare
- Use multi-signer DNSSEC to coordinate keys between both providers

Simply adding your existing DS record to Cloudflare will not work because the cryptographic chain of trust is broken.

## Does Cloudflare support EDNS0 (extension mechanisms for DNS)?

Yes, Cloudflare DNS supports EDNS0. EDNS0 is enabled for all Cloudflare customers. It is a building block for modern DNS implementations that adds support for signaling if the DNS Resolver (recursive DNS provider) supports larger message sizes and DNSSEC.

EDNS0 is the first approved set of mechanisms for [DNS extensions](http://en.wikipedia.org/wiki/Extension_mechanisms_for_DNS), originally published as [RFC 2671](https://datatracker.ietf.org/doc/html/rfc2671).
