Private network routing allows you to proxy HTTP/HTTPS traffic from public hostnames to origins in your private network. When you enable this setting on a DNS record, Cloudflare reaches the origin over your private network connectivity instead of the public Internet.

For end-to-end setup, refer to the guide for your connectivity type: [Cloudflare WAN](/dns/private-origins/set-up-via-cloudflare-wan/), [Cloudflare Tunnel](/dns/private-origins/set-up-via-cloudflare-tunnel/), or [Cloudflare Mesh](/dns/private-origins/set-up-via-cloudflare-mesh/).

:::note[Closed beta]
This feature is in closed beta. Contact your account team to request access.
:::

## Aspects to consider

Before you enable private network routing, consider the following:

- You need the Private Origins entitlement and a working connection to your private network through Cloudflare WAN (IPsec, GRE, or CNI), Cloudflare Tunnel, or Cloudflare Mesh. The route to the origin must be in your default virtual network.
- If you connect over Cloudflare WAN or Cloudflare Mesh, your account must be on [Unified Routing](/cloudflare-wan/reference/traffic-steering/#unified-routing). Contact your account team to enable it. This applies to new and existing accounts. Cloudflare Tunnel does not need Unified Routing.
- Private network routing is available for `A` (IPv4) and `AAAA` (IPv6) records only. Records must be [proxied](/dns/proxy-status/).
- If you have multiple `A` or `AAAA` records on the same name, and at least one of them has private network routing enabled, all records on that name will use private network routing. This is consistent with the [proxy status behavior](/dns/proxy-status/#mix-proxied-and-unproxied) in these cases.

## Automatically detected ranges

The following private address ranges are automatically detected:

| Range            | Description                                                       |
| ---------------- | ----------------------------------------------------------------- |
| `10.0.0.0/8`     | Private ([RFC 1918](https://www.rfc-editor.org/rfc/rfc1918.html)) |
| `172.16.0.0/12`  | Private ([RFC 1918](https://www.rfc-editor.org/rfc/rfc1918.html)) |
| `192.168.0.0/16` | Private ([RFC 1918](https://www.rfc-editor.org/rfc/rfc1918.html)) |
| `fc00::/7`       | Private ([RFC 4193](https://www.rfc-editor.org/rfc/rfc4193.html)) |
| `100.64.0.0/10`  | CGNAT ([RFC 6598](https://www.rfc-editor.org/rfc/rfc6598.html))   |

:::caution[CGNAT origins and the Cloudflare source range]
`100.64.0.0/10` is detected as private, but the default Cloudflare source range `100.64.0.0/12` sits inside it. If your origins use addresses in `100.64.0.0/12`, [change the Cloudflare source IP range](/cloudflare-wan/configuration/how-to/configure-cloudflare-source-ips/) to a different private `/12` before you enable private network routing.
:::

When you use an IP address from one of these ranges, the **Use private network routing** toggle turns on automatically. You can also turn it on manually for public IP addresses that are only reachable through your tunnel.

## Cloudflare source IP ranges

When Cloudflare reaches an origin over Cloudflare WAN or Cloudflare Mesh, traffic comes from the Cloudflare source IP ranges:

| IP version | Range | Configurable |
| --- | --- | --- |
| IPv4 | `100.64.0.0/12` (default) | Yes, to another private `/12` |
| IPv6 | `2606:4700:cf1:5000::/64` | No |

Add return routes in your private network that send these ranges back to Cloudflare, and allow them in your origin's firewall. Refer to [Configure Cloudflare source IPs](/cloudflare-wan/configuration/how-to/configure-cloudflare-source-ips/).

Behind Cloudflare Tunnel, your origin sees the host running `cloudflared` as the source instead.

## Enable private network routing

:::note[Virtual networks]
Traffic routes through your default virtual network. Selecting a specific virtual network is not supported.
:::

<Tabs syncKey="dashPlusAPI"> <TabItem label="Dashboard">

1. In the Cloudflare dashboard, go to the **DNS Records** page.

   <DashButton url="/?to=/:account/:zone/dns/records" />

2. Select **Add record** or select **Edit** on an existing `A` or `AAAA` record.
3. Enter the origin IP address.
4. Verify that **Proxy status** is enabled (orange cloud).
5. Turn on **Use private network routing**.

   For [private IP addresses](#automatically-detected-ranges) (for example, `10.0.0.50`), the toggle turns on automatically. For public IP addresses used with private infrastructure, turn on the toggle manually.

6. Select **Save**.

</TabItem>

<TabItem label="API">

To create a record with private routing enabled, use a [POST request](/api/resources/dns/subresources/records/methods/create/) and set `private_routing` to `true`:

<APIRequest
	path="/zones/{zone_id}/dns_records"
	method="POST"
	json={{
		type: "A",
		name: "app.example.com",
		content: "10.0.0.50",
		proxied: true,
		private_routing: true,
	}}
/>

To enable private routing on an existing record, use a [PATCH request](/api/resources/dns/subresources/records/methods/edit/):

<APIRequest
	path="/zones/{zone_id}/dns_records/{dns_record_id}"
	method="PATCH"
	json={{
		private_routing: true,
	}}
/>

</TabItem> </Tabs>

### API field behavior

If you use the API to create or edit DNS records with private network routing, consider the following:

| Scenario                                  | `private_routing` value |
| ----------------------------------------- | ----------------------- |
| Proxied `A`/`AAAA` record with private IP | Auto-set to `true`      |
| Proxied `A`/`AAAA` record with public IP  | Defaults to `false`     |
| Non-`A`/`AAAA` record types               | Field not supported     |

Also, if you manually set `private_routing: false` on a proxied `A`/`AAAA` record with private IP, the API will return an error.
