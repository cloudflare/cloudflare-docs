You can trigger Workflows both programmatically and via the Workflows APIs, including:

1. With [Workers](/workers/) via HTTP requests in a `fetch` handler, or from a `queue` or `scheduled` handler
2. On a recurring interval by defining `schedules` on a Workflow in your configuration file
3. Using the [Workflows REST API](/api/resources/workflows/methods/list/)
4. Via the [Wrangler CLI or Cloudflare CLI (`cf`)](/workflows/reference/cli-commands/) in your terminal

## Workers API (Bindings)

You can interact with Workflows programmatically from any Worker script — either directly through [`ctx.exports`](/workflows/build/workers-api/#call-a-workflow-through-ctxexports) in the same Worker, or by creating a binding to a Workflow. A Worker can bind to multiple Workflows, including Workflows defined in other Workers projects (scripts) within your account.

You can trigger a Workflow:

- Directly over HTTP via the [`fetch`](/workers/runtime-apis/handlers/fetch/) handler
- From a [Queue consumer](/queues/configuration/javascript-apis/#consumer) inside a `queue` handler
- On a recurring schedule by defining `schedules` on the Workflow in your configuration file
- From a [Cron Trigger](/workers/configuration/cron-triggers/) inside a `scheduled` handler
- Within a [Durable Object](/durable-objects/)

:::note

New to Workflows? Start with the [Workflows tutorial](/workflows/get-started/guide/) to deploy your first Workflow and familiarize yourself with Workflows concepts.

:::

To call a Workflow from your Workers code, configure it in your configuration file. For example, for the Workflow defined in the [get started guide](/workflows/get-started/guide/), add the following configuration:

<WranglerConfig
	cfConfig={`import { defineConfig, exports } from "cf/config";
import * as entrypoint from "./src/index.ts" with { type: "cf-worker" };

export default defineConfig({
	worker: {
		name: "workflows-tutorial",
		entrypoint,
		compatibilityDate: "$today",
		exports: {
			// Must match the class defined in your code that extends WorkflowEntrypoint
			MyWorkflow: exports.workflow({
				// The name of the Workflow
				name: "workflows-tutorial",
			}),
		},
	},
});`}
>

```jsonc
{
	"$schema": "./node_modules/wrangler/config-schema.json",
	"name": "workflows-tutorial",
	"main": "src/index.ts",
	"upload_source_maps": true,
	"compatibility_date": "$today",
	"workflows": [
		{
			// The name of the Workflow
			"name": "workflows-tutorial",
			// The binding name, which must be a valid JavaScript variable name.  This will
			// be how you call (run) your Workflow from your other Workers handlers or
			// scripts.
			"binding": "MY_WORKFLOW",
			// Must match the class defined in your code that extends the Workflow class
			"class_name": "MyWorkflow"
		}
	]
}
```

</WranglerConfig>

<CliVariants>
<CliVariant cli="wrangler">

The `binding = "MY_WORKFLOW"` line defines the JavaScript variable (`env.MY_WORKFLOW`) that your Workflow methods are accessible on, including `create` (which triggers a new instance) or `get` (which returns the status of an existing instance).

</CliVariant>
<CliVariant cli="cf">

Because `MyWorkflow` is declared under `worker.exports`, your Worker accesses it directly on `ctx.exports.MyWorkflow` without a separate `env` binding. It exposes the same `Workflow` methods — including `create` (which triggers a new instance) and `get` (which returns the status of an existing instance). To call this Workflow from a different Worker, add a [`bindings.workflow()`](/workflows/build/workers-api/#cross-script-calls) entry under `worker.env` in the calling Worker.

</CliVariant>

### Schedule a Workflow directly

If you want to create Workflow instances on a recurring interval, add `schedules` (up to 100 cron expressions per account) to your Workflow configuration:

<WranglerConfig
	cfConfig={`import { defineConfig, exports } from "cf/config";
import * as entrypoint from "./src/index.ts" with { type: "cf-worker" };

export default defineConfig({
	worker: {
		name: "workflows-tutorial",
		entrypoint,
		compatibilityDate: "$today",
		exports: {
			MyWorkflow: exports.workflow({
				name: "workflows-tutorial",
				schedules: ["0 * * * *"],
			}),
		},
	},
});`}
>

```jsonc
{
	"$schema": "./node_modules/wrangler/config-schema.json",
	"name": "workflows-tutorial",
	"main": "src/index.ts",
	"upload_source_maps": true,
	"compatibility_date": "$today",
	"workflows": [
		{
			"name": "workflows-tutorial",
			"binding": "MY_WORKFLOW",
			"class_name": "MyWorkflow",
			"schedules": ["0 * * * *"]
		}
	]
}
```

</WranglerConfig>

<CliVariants>
<CliVariant cli="wrangler">

Each matching cron expression creates a new Workflow instance automatically. Use this when you want to run a Workflow on a schedule without defining top-level `triggers.crons` and a separate `scheduled` handler.

</CliVariant>
<CliVariant cli="cf">

Each matching cron expression creates a new Workflow instance automatically. Use this when you want to run a Workflow on a schedule without defining `triggers.scheduled()` and a separate `scheduled` handler.

</CliVariant>
</CliVariants>

Scheduled instances include the matching cron expression and scheduled trigger time on `event.schedule`:

```ts
export class MyWorkflow extends WorkflowEntrypoint<Env> {
	async run(event: WorkflowEvent<unknown>, step: WorkflowStep) {
		if (event.schedule) {
			console.log(event.schedule.cron);
			console.log(new Date(event.schedule.scheduledTime));
		}
	}
}
```

On [Workers Paid](/workers/platform/pricing/#workers), Workflow instances created by `schedules` can run for up to one hour per cron firing without consuming a Workflow concurrency slot. If the instance pauses or sleeps after that window, the instance yields and enters the normal concurrency queue upon resume. It resumes when a concurrency slot is available.

This also applies to a Workflow with a [concurrency limit](/workflows/build/concurrency-limits/#per-workflow-concurrency-limits): instances created by `schedules` are not held back by the limit during the one-hour window. After the window, the instance yields and is queued until both your account and the Workflow have a free slot.

<CliVariants>
<CliVariant cli="wrangler">

Use the latest Wrangler release when configuring Workflow schedules. If your local Wrangler schema does not recognize `schedules` yet, update Wrangler before deploying.

The following example shows how you can manage Workflows from within a Worker, including:

- Retrieving the status of an existing Workflow instance by its ID
- Creating (triggering) a new Workflow instance
- Returning the status of a given instance ID

<TypeScriptExample filename="src/index.ts">

```ts
interface Env {
	MY_WORKFLOW: Workflow;
}

export default {
	async fetch(req: Request, env: Env) {
		// Get instanceId from query parameters
		const instanceId = new URL(req.url).searchParams.get("instanceId");

		// If an ?instanceId=<id> query parameter is provided, fetch the status
		// of an existing Workflow by its ID.
		if (instanceId) {
			let instance = await env.MY_WORKFLOW.get(instanceId);
			return Response.json({
				status: await instance.status(),
			});
		}

		// Else, create a new instance of our Workflow, passing in any (optional)
		// params and return the ID.
		const newId = crypto.randomUUID();
		let instance = await env.MY_WORKFLOW.create({ id: newId });
		return Response.json({
			id: instance.id,
			details: await instance.status(),
		});
	},
};
```

</TypeScriptExample>

</CliVariant>

### Inspect a Workflow's status

You can inspect the status of any running Workflow instance by calling `status` against a specific instance ID. This allows you to programmatically inspect whether an instance is queued (waiting to be scheduled), actively running, paused, or errored.

```ts
let instance = await env.MY_WORKFLOW.get("abc-123");
let status = await instance.status(); // Returns an InstanceStatus
```

The possible values of status are as follows:

```ts
  status:
    | "queued" // means that instance is waiting to be started (see concurrency limits)
    | "running"
    | "paused"
    | "errored"
    | "terminated" // user terminated the instance while it was running
    | "complete"
    | "waiting" // instance is hibernating and waiting for sleep or event to finish
    | "waitingForPause" // instance is finishing the current work to pause
    | "unknown";
  error?: {
    name: string,
    message: string
  };
	output?: unknown;
	rollback:
		| {
				outcome: "complete" | "failed";
				error: {
					name: string,
					message: string,
				} | null,
		  }
		| null;
```

If your Workflow registers rollback handlers on `step.do()`, inspect `rollback` after the instance finishes to see whether the compensating steps completed successfully. While rollback is actively running, the Workers API continues to return `status: "running"`.

To receive historical and live execution updates without polling, refer to [Subscribe to events](/workflows/build/subscribe-to-instance-events/).

### Explicitly pause a Workflow

You can explicitly pause a Workflow instance (and later resume it) by calling `pause` against a specific instance ID.

```ts
let instance = await env.MY_WORKFLOW.get("abc-123");
await instance.pause(); // Returns Promise<void>
```

### Resume a Workflow

You can resume a paused Workflow instance by calling `resume` against a specific instance ID.

```ts
let instance = await env.MY_WORKFLOW.get("abc-123");
await instance.resume(); // Returns Promise<void>
```

Calling `resume` on an instance that is not currently paused will have no effect.

:::caution
If you have reached the maximum concurrent instances for your account, or the [concurrency limit](/workflows/build/concurrency-limits/#per-workflow-concurrency-limits) set on your Workflow, resuming an instance may not restart it immediately. The instance will be queued until a concurrency slot becomes available.
:::

### Stop a Workflow

You can stop/terminate a Workflow instance by calling `terminate` against a specific instance ID.

```ts
let instance = await env.MY_WORKFLOW.get("abc-123");
await instance.terminate(); // Returns Promise<void>
```

To run registered rollback handlers before terminating, pass `rollback: true`:

```ts
let instance = await env.MY_WORKFLOW.get("abc-123");
await instance.terminate({ rollback: true }); // Returns Promise<void>
```

<CliVariants>
<CliVariant cli="wrangler">

You can also run rollback handlers from Wrangler:

```sh
npx wrangler workflows instances terminate <WORKFLOW_NAME> <INSTANCE_ID> --rollback
# For a local Workflows instance during wrangler dev:
npx wrangler workflows instances terminate <WORKFLOW_NAME> <INSTANCE_ID> --local --rollback
```

</CliVariant>
<CliVariant cli="cf">

You can also run rollback handlers from the [Cloudflare CLI (`cf`)](/cf/):

```sh
cf workflows instances terminate <INSTANCE_ID> --workflow-name <WORKFLOW_NAME> --status terminate --rollback
```

During `cf dev`, terminate local Workflow instances in [Local Explorer](/workflows/build/local-development/#local-explorer).

:::note

`cf workflows instances terminate` currently requires `--status terminate` alongside the command.

:::

</CliVariant>
</CliVariants>

Once stopped/terminated, the Workflow instance _cannot_ be resumed.

### Restart a Workflow

```ts
let instance = await env.MY_WORKFLOW.get("abc-123");
await instance.restart(); // Returns Promise<void>
```

Restarting an instance will immediately cancel any in-progress steps, erase any intermediate state, and treat the Workflow as if it was run for the first time. However, the restarted instance maintains the concurrency slot of the previous instance instead of returning to the queued state.

:::caution
Exercise caution when using the `restart()` method to avoid concurrency slot deprivation. If you call the `restart()` method recursively without a conditional, that instance will run indefinitely, effectively eliminating a concurrency slot.
:::

To restart an instance from a specific step instead of the beginning, refer to [`restart`](/workflows/build/workers-api/#restart) in the Workers API reference.

Because a restart erases all intermediate state, keep any state that must survive a restart outside of the instance itself. The following example uses the `restart` method to maintain a document processing pipeline:

- Chunks of a document are stored in, and retrieved from, R2 with an identifiable object [prefix](/r2/api/workers/workers-api-reference/#r2listoptions).
- Each [R2 object key](/r2/api/workers/workers-api-reference/#r2object-definition) is used as the `instanceId` for processing that chunk.
- The workflow retrieves 100 chunks at a time, processes the chunks, and updates their prefix.
- Then, if there are remaining objects with the original prefix, the Workflow instance restarts.

<TypeScriptExample filename="index.ts">

```ts
export class MyWorkflow extends WorkflowEntrypoint<Env, Params> {
	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
		const listResult = await step.do("list files from R2", async () => {
			// Restarts delete all state with the exception of search params.
			// So we will need a cursor to keep track of progress.
			const maybeCursor = await this.env.CHUNKS_BUCKET.get(
				`cursor/${event.instanceId}`,
			);

			const cursor = maybeCursor
				? (await maybeCursor.json<{ cursor: string }>()).cursor
				: undefined;

			// List first 100 files from R2 with prefix "chunked/"
			const listed = await this.env.CHUNKS_BUCKET.list({
				prefix: "chunked/",
				limit: 100,
				cursor,
			});

			if (listed.truncated) {
				const cursor = listed.cursor;
				await this.env.CHUNKS_BUCKET.put(
					`cursor/${event.instanceId}`,
					JSON.stringify({ cursor }),
					{
						httpMetadata: {
							contentType: "application/json",
						},
					},
				);
			}

			return {
				keys: listed.objects.map((obj) => obj.key),
				truncated: listed.truncated,
			};
		});

		for (const key of listResult.keys) {
			await step.do(`process file: ${key}`, async () => {
				return await doSomething(key, this.env.CHUNKS_BUCKET, event.instanceId);
			});
		}

		await step.do("restart workflow", async () => {
			if (listResult.truncated) {
				// There are still chunks to process, restarting the workflow to continue processing.
				const instance = await this.env.CHUNK_PROCESSOR.get(event.instanceId);
				await instance.restart();
			} else {
				// If the workflow has ended we reset the cursor, so that we can preserve determinism.
				// If/when we re-run this workflow we will still process all the files.
				await this.env.CHUNKS_BUCKET.delete(`cursor/${event.instanceId}`);

				return "was not truncated, done";
			}
		});
	}
}
```

</TypeScriptExample>

### Delete Workflow instances

Deleting an instance removes its stored state. Deleting a running instance stops its current execution without running rollback handlers.

Delete one instance by calling `delete()` on its handle:

<TypeScriptExample>

```ts
const instance = await env.MY_WORKFLOW.get("instance-abc");
await instance.delete();
```

</TypeScriptExample>

If a Workflow deletes its own instance, execution stops during `await instance.delete()`. Code after the call does not run.

Delete up to 100 instances in one call with `deleteBatch()`:

<TypeScriptExample>

```ts
const result = await env.MY_WORKFLOW.deleteBatch([
	"instance-abc",
	"instance-def",
]);

console.log(result.deleted); // [{ id: "instance-abc" }, { id: "instance-def" }]
console.log(result.errors); // Per-instance failures, if any
```

</TypeScriptExample>

`deleteBatch()` accepts between 1 and 100 IDs. Missing IDs are returned as per-instance errors. Duplicate IDs count toward the limit and are deleted once, with the result repeated for each input position. If any ID is invalid, the call fails before deleting any instances.

<CliVariants>
<CliVariant cli="wrangler">

Wrangler accepts one or more instance IDs or a file containing a top-level JSON array of strings. You can combine positional IDs with `--filename`, up to 100 IDs total. Use `latest` to delete the most recently created instance.

```json title="instance-ids.json"
["instance-abc", "instance-def"]
```

```sh
npx wrangler workflows instances delete <WORKFLOW_NAME> <INSTANCE_ID>
npx wrangler workflows instances delete <WORKFLOW_NAME> <INSTANCE_ID> <INSTANCE_ID>
npx wrangler workflows instances delete <WORKFLOW_NAME> latest
npx wrangler workflows instances delete <WORKFLOW_NAME> --filename ./instance-ids.json
# For local Workflow instances during wrangler dev:
npx wrangler workflows instances delete <WORKFLOW_NAME> <INSTANCE_ID> --local
```

</CliVariant>
<CliVariant cli="cf">

Use `cf workflows instances delete` to delete a single instance, or `cf workflows instances batch delete` to delete up to 100 instances at once with repeated `--instances` flags or a JSON file via `--body`:

```json title="instance-ids.json"
{
	"instances": ["instance-abc", "instance-def"]
}
```

```sh
cf workflows instances delete <INSTANCE_ID> --workflow-name <WORKFLOW_NAME>
cf workflows instances batch delete <WORKFLOW_NAME> --instances <INSTANCE_ID> --instances <INSTANCE_ID>
cf workflows instances batch delete <WORKFLOW_NAME> --body @./instance-ids.json
```

Pass an explicit instance ID from `cf workflows instances list --workflow-name <WORKFLOW_NAME>`. During `cf dev`, delete local Workflow instances in [Local Explorer](/workflows/build/local-development/#local-explorer).

</CliVariant>
</CliVariants>

For the full APIs, refer to [`delete`](/workflows/build/workers-api/#delete) and [`deleteBatch`](/workflows/build/workers-api/#deletebatch).

### Trigger a Workflow from another Workflow

You can create a new Workflow instance from within a step of another Workflow. The parent Workflow will not block waiting for the child Workflow to complete — it continues execution immediately after the child instance is successfully created.

<TypeScriptExample>

```ts
export class ParentWorkflow extends WorkflowEntrypoint<Env, Params> {
	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
		// Perform initial work
		const result = await step.do("initial processing", async () => {
			// ... processing logic
			return { fileKey: "output.pdf" };
		});

		// Trigger a child workflow for additional processing
		const childInstance = await step.do("trigger child workflow", async () => {
			return await this.env.CHILD_WORKFLOW.create({
				id: `child-${event.instanceId}`,
				params: { fileKey: result.fileKey },
			});
		});

		// Parent continues immediately - not blocked by child workflow
		await step.do("continue with other work", async () => {
			console.log(`Started child workflow: ${childInstance.id}`);
			// This runs right away, regardless of child workflow status
		});
	}
}
```

</TypeScriptExample>

If the child Workflow fails to start, the step will fail and be retried according to your retry configuration. Once the child instance is successfully created, it runs independently from the parent.
