If your certificate is stuck in **Pending Validation** or failing to issue, the <GlossaryTooltip term="Certificate Authority (CA)">certificate authority (CA)</GlossaryTooltip> may be unable to complete [domain control validation (DCV)](/ssl/edge-certificates/changing-dcv-method/dcv-flow/). This page helps you identify and resolve common DCV issues.

:::note
If you are using the Cloudflare API, error messages are presented under the `validation_errors` parameter.
:::

## Quick checklist

Use this checklist to identify common DCV issues:

- [ ] [No rules blocking the validation URL](#blocked-validation-url) - WAF rules, IP access rules, or Under Attack mode can block the CA
- [ ] [No redirects on the validation path](#redirection) - The `/.well-known/*` path must not redirect (especially HTTP to HTTPS in partial setups)
- [ ] [DNS records are resolvable](#dns-settings-and-records) - DNSSEC must be valid, and records must resolve from all locations
- [ ] [CAA records allow the CA](#caa-records) - CAA records must permit Cloudflare's partner CAs to issue certificates
- [ ] [No CA-side errors](#ca-errors) - Rate limits, policy blocks, or temporary CA issues

## Blocked validation URL

If you have issues while HTTP DCV is in place, review the following settings:

- **Anything affecting `/.well-known/*`**: Review [WAF custom rules](/waf/custom-rules/), [IP Access Rules](/waf/tools/ip-access-rules/), and other [configuration rules](/rules/configuration-rules/) to make sure that your rules _do not_ enable interactive challenge on the validation URL.

- **Workers routes**: If you have [Workers routes](/workers/configuration/routing/routes/) matching `*/*` or paths that include `/.well-known/pki-validation/*` or `/.well-known/acme-challenge/*`, your Worker may intercept DCV requests from the certificate authority. Make sure your Worker either passes through requests to these paths or does not match them. This is especially relevant for [Cloudflare for SaaS](/cloudflare-for-platforms/cloudflare-for-saas/) zones that use a [Worker as the fallback origin](/cloudflare-for-platforms/cloudflare-for-saas/start/advanced-settings/worker-as-origin/).

- **Cloudflare Account Settings** and **Page Rules**: Review your [account settings](/fundamentals/reference/under-attack-mode/), [Configuration Rules](/rules/configuration-rules/), and [Page Rules](/rules/page-rules/) to ensure you have not enabled Under Attack mode on the validation URL.

## Redirection

Enabling [Always Use HTTPS](/ssl/edge-certificates/additional-options/always-use-https/) does not impact the validation process.

In a [Partial (CNAME) setup](/ssl/edge-certificates/changing-dcv-method/#partial-dns-setup---action-sometimes-required) where you are managing the token on the origin side, please ensure that no redirection from HTTP to HTTPS occurs on the `/.well-known/*` path.

When using [Redirect Rules](/rules/url-forwarding/single-redirects/), exclude the `/.well-known/*` path from redirections by adding a condition to your rule:

```txt
not starts_with(http.request.uri.path, "/.well-known/")
```

For example, if you have a rule that redirects all HTTP traffic to HTTPS, modify the rule expression to:

```txt
(http.request.scheme eq "http") and not starts_with(http.request.uri.path, "/.well-known/")
```

## DNS settings and records

The errors below refer to situations that have to be addressed at the authoritative DNS provider:

- `the Certificate Authority had trouble performing a DNS lookup: dns problem: looking up caa for <hostname>: dnssec: bogus`
- `Certificate authority encountered a SERVFAIL during DNS lookup, please check your DNS reachability.`

Consider the following when troubleshooting:

- [DNSSEC](https://www.cloudflare.com/learning/dns/dns-security/) must be configured correctly. You can use [DNSViz](https://dnsviz.net/) to understand and troubleshoot the deployment of DNSSEC.
- The HTTP verification process is done preferably over **IPv6**, so if any AAAA record exists and does not point to the same dual-stack location as the A record, the validation will fail.
- If an [NS record](/dns/manage-dns-records/reference/dns-record-types/#ns) is present for the hostname or its parent, DNS resolution will be managed externally by the DNS provider defined in the NS target. In this case, you must either add the DCV TXT record at the external DNS provider, or remove the NS record at Cloudflare.

### CAA records

- Your [CAA records](/ssl/edge-certificates/caa-records/) must be resolvable from all locations.
- Your [CAA records](/ssl/edge-certificates/caa-records/) should allow Cloudflare's partner [certificate authorities (CAs)](/ssl/reference/certificate-authorities/) to issue certificates on your behalf.
- If you are using a [subdomain setup](/dns/zone-setups/subdomain-setup/) (`subdomain.example.com`) and Cloudflare is not the authoritative DNS provider for the parent domain (`example.com`), you should make sure that the parent domain (`example.com`) either has CAA records that allow [Cloudflare's partner CAs](/ssl/reference/certificate-authorities/), or has no CAA records at all.

You can check the CAA records by running the following command:

<Tabs>
<TabItem label="macOS and Linux">

```bash
dig example.com CAA +short
```
</TabItem>

<TabItem label="Windows">

```powershell
Resolve-DnsName -Name example.com -Type CAA
```
</TabItem>
</Tabs>

## Certificate authority (CA) errors

A [certificate authority (CA)](/ssl/reference/certificate-authorities/) is the organization that issues your SSL/TLS certificate. Cloudflare partners with multiple CAs to provide certificates for your domain.

:::note
Selecting a different CA is only available with [Advanced Certificate Manager](/ssl/edge-certificates/advanced-certificate-manager/) or [SSL for SaaS](/cloudflare-for-platforms/cloudflare-for-saas/security/certificate-management/). [Universal SSL](/ssl/edge-certificates/universal-ssl/) customers cannot change the CA.
:::

### Rate limiting

<Render file="error-rate-limiting" product="ssl" />

When you see `The authority has rate limited these domains. Please wait for the rate limit to expire or try another authority`, the certificate authority has temporarily blocked certificate issuance for your domain due to too many recent requests.

Rate limit windows vary by CA:
- **Let's Encrypt**: 7 days for most rate limits (refer to [Let's Encrypt rate limits](https://letsencrypt.org/docs/rate-limits/))
- **Google Trust Services**: Varies by limit type (refer to [Google Trust Services documentation](https://pki.goog/faq/))

**Resolution**: Wait for the rate limit window to expire, or select a different CA.

### CAA records block issuance

The error `CAA records block issuance. Please remove all CAA records or add records for this authority` indicates that your domain's [CAA records](/ssl/edge-certificates/caa-records/) do not allow the selected certificate authority to issue certificates.

**Resolution**: Either remove all CAA records from your domain, or add CAA records that explicitly allow [Cloudflare's partner certificate authorities](/ssl/reference/certificate-authorities/).

## DCV token values changed

DCV tokens are generated by the certificate authority (CA), not by Cloudflare. If the token value you previously retrieved is no longer accepted, it may have changed for one of these reasons:

| Reason | Details |
| --- | --- |
| **Token expiry** | CA tokens have a fixed validity period defined by the [CA/B Baseline Requirements](https://cabforum.org/baseline-requirements-documents/). After this period, Cloudflare generates new tokens automatically. |
| **Validation failure** | If a DCV check fails, the current token may become invalid and Cloudflare generates a replacement. Refer to [DCV tokens](/ssl/edge-certificates/changing-dcv-method/dcv-flow/#dcv-tokens) for details on when this occurs. |

Token validity periods by CA:

| Certificate authority | Token validity |
| --- | --- |
| Google Trust Services | 14 days |
| Let's Encrypt | 7 days |
| SSL.com | 14 days |

In both cases — expiry and failure — the token value changes. If you are managing DCV manually, always retrieve the current token value via the [SSL Verification API](/api/resources/ssl/subresources/verification/methods/list/) immediately before placing or updating your DNS record. Do not reuse a previously noted token value.

To trigger an immediate DCV recheck after placing your record — rather than waiting for Cloudflare's next scheduled attempt — use the [Edit SSL Certificate Pack Validation Method](/api/resources/ssl/subresources/verification/methods/edit/) endpoint, specifying the same `validation_method` you are currently using.

Refer to [Validation backoff schedule](/ssl/edge-certificates/changing-dcv-method/validation-backoff-schedule/) for the full retry schedule and token validity details.

:::tip
To avoid managing DCV tokens manually, consider using [Delegated DCV](/ssl/edge-certificates/changing-dcv-method/methods/delegated-dcv/). With Delegated DCV, Cloudflare handles token rotation automatically on your behalf, so token expiry and validation failures no longer require manual intervention.
:::

## HTTP DCV falling back to TXT

This section applies only when you are using HTTP DCV in a [partial DNS setup](/dns/zone-setups/partial-setup/) and managing DCV tokens manually.

If you configured [HTTP DCV](/ssl/edge-certificates/changing-dcv-method/methods/http/) but the verification response now shows a TXT token, your validation method has automatically fallen back to TXT.

This fallback occurs after HTTP DCV fails continuously for a period that depends on the certificate validity period:

<Render file="http-to-txt-schedule" product="ssl" />

Once the fallback occurs, Cloudflare generates TXT tokens that you must place manually at your authoritative DNS provider. To understand why HTTP DCV is failing, refer to [Blocked validation URL](#blocked-validation-url) and [Redirection](#redirection).

### Certificate renewal behaviour

At certificate renewal, Cloudflare always attempts HTTP DCV first, regardless of the method used at initial issuance. Renewal completes automatically via HTTP only if all of the following conditions are met:

- All hostnames on the certificate are proxied through Cloudflare.
- All hostnames resolve to the Cloudflare IP addresses assigned to the zone.
- The certificate contains no wildcard hostnames.

If any condition is not met, renewal falls back to your configured method and you must manually place new DCV records. Renewal tokens are generated 30 days before certificate expiry.

To avoid manual renewal steps in a partial setup, consider using [Delegated DCV](/ssl/edge-certificates/changing-dcv-method/methods/delegated-dcv/), which lets Cloudflare manage DCV on your behalf even when you control the authoritative DNS.
