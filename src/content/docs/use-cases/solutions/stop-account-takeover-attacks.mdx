When your site has login pages, you need to decide how to verify that visitors are human, how aggressively to limit failed attempts, and which request patterns to block. This guide covers five stages: enforce HTTPS, turn on bot protection, add [Turnstile](/turnstile/) to your login form, create Application Security [rate limiting rules](/waf/rate-limiting-rules/) and [custom rules](/waf/custom-rules/) for suspicious patterns, and monitor for ongoing attacks using [SSL/TLS](/ssl/) transport security and [Cloudflare bot solutions](/bots/). The core workflow covers features available on Free, Pro, and Business plans. Enterprise features such as leaked credentials custom detection locations and Bot Management custom rules are included as callouts.

:::note
Most procedures in this guide are configured per domain. Select your domain in the Cloudflare dashboard before starting. Turnstile is the exception. It is configured at the account level.
:::

## Enforce HTTPS to protect credentials in transit

Credentials sent over plain HTTP are visible to anyone on the network path between the visitor and your origin server. Cloudflare [SSL/TLS](/ssl/) provides two settings that enforce HTTPS connections: [Always Use HTTPS](/ssl/edge-certificates/additional-options/always-use-https/) and [HTTP Strict Transport Security (HSTS)](/ssl/edge-certificates/additional-options/http-strict-transport-security/).

### Turn on Always Use HTTPS

Always Use HTTPS redirects all visitor requests from `http` to `https` for all subdomains and hosts.

<Render file="enable-always-use-https" product="ssl" />

:::note
Cloudflare recommends not performing redirects at your origin web server, as this can cause [redirect loop errors](/ssl/troubleshooting/too-many-redirects/).
:::

:::note[Optional: HTTP Strict Transport Security (HSTS)]
For additional transport hardening, consider enabling HTTP Strict Transport Security (HSTS). HSTS tells browsers to only connect over HTTPS, preventing downgrade attacks on the initial request. HSTS is irreversible for the configured Max Age duration. If you later disable HTTPS, your site becomes inaccessible until the Max Age expires. Review the [HSTS requirements](/ssl/edge-certificates/additional-options/http-strict-transport-security/#requirements) before turning it on.
:::

### Free plan: Bot Fight Mode

{/* Source: /bots/get-started/bot-fight-mode/ — Bot Fight Mode enable procedure */}

Bot Fight Mode challenges requests that match known bot patterns. It applies to all traffic on your domain and cannot be customized with exceptions or path-specific rules.

For login protection, the following are recommended starting values. Adjust based on your traffic patterns.

- **Definitely automated**: _Managed Challenge_. After reviewing Security Events to confirm the setting does not affect legitimate traffic, switch to _Block_.
- **Likely automated**: _Managed Challenge_.
- **Verified bots**: _Allow_.

:::caution
If your organization also uses [Cloudflare Tunnel](/cloudflare-one/networks/connectors/cloudflare-tunnel/), keep **Definitely Automated** set to **Allow**. Otherwise, tunnels might fail with a `websocket: bad handshake` error.
:::

[Custom rules](/waf/custom-rules/) are executed before Super Bot Fight Mode. To create exceptions for specific paths or traffic, create a custom rule with the [Skip action](/waf/custom-rules/skip/). The Skip action allows the request to bypass the Super Bot Fight Mode phase without terminating the request, enabling it to continue through the rest of the security stack.

## Protect your login form with Turnstile and rate limiting

Two tools protect login endpoints from automated abuse, and they cover different attack vectors:

- **[Turnstile](/turnstile/)** verifies that visitors are human without showing a CAPTCHA. It can be embedded into any website without sending traffic through Cloudflare. Use Turnstile to challenge automated form submissions.
- **Application Security [rate limiting rules](/waf/rate-limiting-rules/)** define rate limits for requests matching an expression and the action to perform when those limits are reached. Use rate limiting to protect login endpoints from abuse, such as brute-force attacks.

Both together provide the strongest coverage. Turnstile challenges automated submissions at the form level. Rate limiting catches high-volume attacks that bypass or do not encounter the form, such as direct `POST` requests to the endpoint.

### Add Turnstile to your login form

Implementing Turnstile involves three steps: create a widget, add the client-side snippet to your login form, and validate the token on your server.

#### 1. Create a Turnstile widget

Turnstile is configured at the account level.

<Render file="create-widget-dashboard" product="turnstile" />

You need both the sitekey and secret key in the following steps.

#### 2. Add the client-side snippet

Add the Turnstile script and widget container to your login form. Replace `<YOUR-SITE-KEY>` with the sitekey from the previous step.

{/* Source: /turnstile/tutorials/integrating-turnstile-waf-and-bot-management/ — client-side integration */}

```html
<form id="login-form">
	<input type="text" id="username" placeholder="Username" required />
	<input type="password" id="password" placeholder="Password" autocomplete="off" required />
	<div class="cf-turnstile" data-sitekey="<YOUR-SITE-KEY>"></div>
	<button type="submit">Log in</button>
</form>

<script
	src="https://challenges.cloudflare.com/turnstile/v0/api.js"
	async
	defer
></script>
```

The widget renders inside the `div` and produces a token when the visitor passes the challenge. When the form is submitted, a `cf-turnstile-response` token is included in the form data.

#### 3. Validate the token on your server

Before processing the form submission, send the token to the Turnstile siteverify endpoint to confirm the visitor passed the challenge.

{/* Source: /turnstile/get-started/server-side-validation/ — server-side validation (JS JSON example) */}

```js title="server.js"
const SECRET_KEY = "your-secret-key";

async function validateTurnstile(token, remoteip) {
	try {
		const response = await fetch(
			"https://challenges.cloudflare.com/turnstile/v0/siteverify",
			{
				method: "POST",
				headers: {
					"Content-Type": "application/json",
				},
				body: JSON.stringify({
					secret: SECRET_KEY,
					response: token,
					remoteip: remoteip,
				}),
			},
		);

		const result = await response.json();
		return result;
	} catch (error) {
		console.error("Turnstile validation error:", error);
		return { success: false, "error-codes": ["internal-error"] };
	}
}
```

Replace `"your-secret-key"` with your Turnstile secret key. The endpoint returns a JSON object with a `success` field. Only process the form submission if `success` is `true`.

For the complete response format, error codes, and examples in other languages, refer to [Validate the token](/turnstile/get-started/server-side-validation/).

#### Test your implementation

Turnstile provides test site keys that return predictable results without contacting the Siteverify API.

{/* Source: /turnstile/troubleshooting/testing/ — testing procedures */}

- **Always passes**: Use site key `1x00000000000000000000AA` and secret key `1x0000000000000000000000000000000AA` to simulate a successful challenge.
- **Always blocks**: Use site key `2x00000000000000000000AB` and secret key `2x0000000000000000000000000000000AA` to simulate a failed challenge.
- **Forces interactive challenge**: Use site key `3x00000000000000000000FF` to test the interactive challenge flow.

For the full list of test keys and expected behaviors, refer to [Test your Turnstile implementation](/turnstile/troubleshooting/testing/).

### Rate limit your login endpoint

{/* Source: /waf/rate-limiting-rules/ — rate limiting rules overview */}

#### Create a rate limiting rule for your login endpoint

The following example creates a rate limiting rule that issues a Managed Challenge after more than five POST requests to your login path from the same IP within one minute. Start with Managed Challenge rather than Block. Managed Challenge allows legitimate users who trigger the limit to pass by completing a challenge, while blocking automated traffic that cannot solve it. After monitoring [Security Events](/waf/analytics/security-events/) to confirm the rule is not producing false positives, switch to Block. Adjust the path (`/login`), threshold, and period for your site.

{/* Source: /waf/rate-limiting-rules/best-practices/ — credential stuffing protection pattern. Navigation from /waf/custom-rules/create-dashboard/. Expression from source. Threshold (5 req/min) is guide-specific example. */}
{/* UNTESTED: custom workflow combining sourced expression with guide-specific threshold. Validate syntax in dashboard. */}

<Tabs syncKey="dashNewNav">
<TabItem label="New dashboard" icon="rocket">

<Steps>

1. In the Cloudflare dashboard, go to the **Security rules** page.

   <DashButton url="/?to=/:account/:zone/security/security-rules" />

2. Select **Create rule** and choose **Rate limiting rule**.

3. Enter a name for the rule (for example, "Rate limit login endpoint").

4. In the expression editor, enter:

   ```txt
   http.host eq "example.com" and http.request.uri.path eq "/login" and http.request.method eq "POST"
   ```

   Replace `example.com` with your domain and `/login` with your login endpoint path.

5. Under **Counting characteristics**, select _IP_.

6. (Optional) Under **Increment counter when**, enter a counting expression to count only failed login attempts:

   ```txt
   http.request.uri.path eq "/login" and http.request.method eq "POST" and http.response.code in {401 403}
   ```

   This counts requests based on the response status code. Successful logins (200) do not increment the counter.

   :::note
   Using a counting expression separate from the matching expression requires a Business plan or above.

   {/* Confirmed: /waf/rate-limiting-rules/best-practices/ says "These example rules require a Business plan or above." */}
   :::

7. Set **Rate** to _5 requests_ per _1 minute_.

8. For **Action**, select _Managed Challenge_.

9. Select **Deploy**.

</Steps>

#### Escalating rate limits for persistent attackers

For sites that experience sustained credential stuffing campaigns, consider deploying multiple rate limiting rules with increasing severity. The following pattern from the Application Security documentation uses three rules with separate counting expressions that track failed login responses (401/403 status codes):

{/* Source: /waf/rate-limiting-rules/best-practices/ — escalating penalty pattern */}

| Rule   | Rate                                    | Action            | Scope           |
| ------ | --------------------------------------- | ----------------- | --------------- |
| Rule 1 | 4 failed login requests per 1 minute    | Managed Challenge | Login path only |
| Rule 2 | 10 failed login requests per 10 minutes | Managed Challenge | Login path only |
| Rule 3 | 20 failed login requests per 1 hour     | Block for 1 day   | Entire domain   |

Rule 1 handles short bursts. Rule 2 catches slower distributed attacks. Rule 3 blocks persistent attackers from the entire domain. The counting expressions use response status codes, so successful logins do not count against the limit. To create these rules, follow the same procedure as the rate limiting rule above but adjust the expression, rate, and action for each row. For the full configuration details, including expression syntax for response code counting, refer to [Rate limiting best practices](/waf/rate-limiting-rules/best-practices/).

:::note
These example rules require a Business plan or above because they use counting expressions that reference HTTP response codes.
:::

## Add Application Security rules for suspicious login patterns

Application Security [custom rules](/waf/custom-rules/) and [traffic detections](/waf/detections/) give you additional signals beyond request rate to identify and act on suspicious login traffic. Detections populate request fields (such as leaked credential status and bot score) that your custom rules can then reference.

### Turn on leaked credentials detection

{/* Source: /waf/detections/leaked-credentials/ — leaked credentials detection overview */}

Leaked credentials detection scans incoming login requests for usernames and passwords that appear in known data breach databases. Cloudflare hashes credentials before comparison and does not store plaintext passwords. When a match is found, the detection populates fields you can use in custom rules and rate limiting rules.

The `cf.waf.credential_check.password_leaked` field is available on all plans.

:::note
The `cf.waf.credential_check.username_and_password_leaked` field requires a Pro plan or above.
:::

{/* Confirmed: /waf/detections/leaked-credentials/ says "Available on all plans" for password_leaked and "Requires a Pro plan or above" for username_and_password_leaked */}

<Render file="leaked-credentials-detection-enable" product="waf" />

After turning on the detection, your origin server can receive leaked credential status via the `Exposed-Credential-Check` request header. To forward this header, turn on the [Add leaked credentials checks header](/rules/transform/managed-transforms/reference/#add-leaked-credentials-checks-header) managed transform. Your origin can then trigger a password reset for affected users.

:::note[Enterprise: Custom detection locations]
If your application uses non-standard credential field names, Enterprise customers can configure [custom detection locations](/waf/detections/leaked-credentials/#custom-detection-locations) to tell Cloudflare where to find usernames and passwords in HTTP requests.
:::

### Create a skip rule for legitimate automated traffic

Before deploying rules that challenge or block login traffic, create a skip rule that exempts known legitimate automated traffic. This prevents your monitoring tools, health checks, and partner integrations from being blocked by the rules that follow.

## Monitor for ongoing compromise attempts

After deploying the rules and configurations from the previous sections, monitor your login endpoint to verify the rules are working and to detect new attack patterns.

### Review Security Events

{/* Source: /waf/analytics/security-analytics/ — Security Analytics overview. Navigation (steps 1-2) validated against source. Steps 3-4 are guide-specific. */}

[Security Events](/waf/analytics/security-events/) shows requests that Cloudflare security products acted on or flagged. Filter by your login path to see the volume of blocked and challenged attempts.

<Steps>

1. In the Cloudflare dashboard, go to the **Analytics** page.

   <DashButton url="/?to=/:account/:zone/security/analytics" />

2. Select the **Events** tab.

3. Add a filter: set **URI Path** to your login endpoint path (for example, `/login`).

4. Review the events to identify patterns:
   - Are attacks concentrated from specific countries or Autonomous System Numbers (ASNs)?
   - Are Application Security rate limiting rules triggering as expected?
   - Are legitimate users being challenged or blocked?

</Steps>

If you see legitimate users being affected, adjust your rate limiting thresholds or add exceptions for specific IP ranges.

### Set up notifications for security event spikes

Set up a **Security Events Alert** notification to receive alerts when security event volume spikes, giving you early warning of a new attack campaign. This notification is in the **WAF** category of the [Notifications](/notifications/) page. For setup instructions, refer to [Create a notification](/notifications/get-started/).

:::note
Security Events Alert notifications are available on Business and Enterprise plans. Enterprise customers can use Advanced Security Events Alert for more granular filtering.
:::

### Review bot traffic patterns

{/* Source: /bots/concepts/bot-score/ — bot score groupings */}

:::note
Bot traffic analytics require a Pro plan or above.
:::

Bot traffic analytics show bot score distribution on your login endpoint over time. A sudden spike in low-score traffic (scores 1-29) on your login path is an early signal of a credential stuffing campaign.

<Render file="bot-score-categories" product="bots" />

<Steps>

1. In the Cloudflare dashboard, go to **Security** > **Bots**.

2. Review the **Bot Report** for traffic distribution across the bot score groupings above.

3. Apply a filter for your login path to isolate login-specific bot traffic.

</Steps>

If you see sustained automated traffic reaching your login endpoint despite the rules deployed in this guide, review the [Security features interoperability](/waf/feature-interoperability/) page to verify your rules are executing in the expected order, and consider adjusting thresholds.
