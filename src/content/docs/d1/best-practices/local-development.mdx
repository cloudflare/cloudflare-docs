<TabItem label="Cloudflare CLI (cf)">

D1 supports local development with the [Cloudflare CLI (`cf`)](/cf/), running an emulated local D1 database powered by the same SQLite engine that D1 runs in production.

## Start a local development session

:::note
If you are new to D1 or Cloudflare Workers, refer to the [D1 Getting started guide](/d1/get-started/) to install `cf` and deploy your first database.
:::

Local development sessions create a standalone, local-only environment so you can test your Worker and D1 queries before deploying to production.

Declare your D1 binding in [`cloudflare.config.ts`](/cf/projects/cloudflare-config/) using `bindings.d1()`:

```ts title="cloudflare.config.ts"
import { bindings, defineConfig } from "cf/config";
import * as entrypoint from "./src/index.ts" with { type: "cf-worker" };

export default defineConfig({
	worker: {
		name: "my-worker",
		entrypoint,
		compatibilityDate: "<COMPATIBILITY_DATE>",
		env: {
			DB: bindings.d1({
				id: "<DATABASE_ID>",
				name: "test-db",
			}),
		},
	},
});
```

Start a local development session:

```sh
cf dev
```

`cf dev` starts your project's local development server and prints its local URL (by default `http://localhost:5173/` in Vite projects).

`cf dev` separates local and remote (production) data by default. To connect a local development session to your remote D1 database instead, set `dev: { remote: true }` on the binding. Because `cloudflare.config.ts` is TypeScript, you can also enable remote access conditionally based on an environment variable (such as `NODE_ENV`) or [config mode](/cf/projects/cloudflare-config/#evaluate-configuration):

```ts title="cloudflare.config.ts"
DB: bindings.d1({
	id: "<DATABASE_ID>",
	name: "test-db",
	// Set to `true` directly, or toggle conditionally by environment:
	dev: { remote: process.env.NODE_ENV === "staging" },
}),
```

Changes made against a remote database cannot be undone. For more information, refer to [Remote bindings](/workers/local-development/#remote-bindings) and [Start development](/cf/projects/#start-development).

## Run local queries and migrations

`cf d1` commands operate on your remote Cloudflare database by default. Pass `--local` to run queries or migrations against your local development state instead.

To run SQL statements or a `.sql` file locally, use `cf d1 raw --local` (`cf d1 query` targets the remote Cloudflare API only):

```sh
cf d1 raw <DATABASE_ID> --sql "CREATE TABLE IF NOT EXISTS users (user_id INTEGER PRIMARY KEY, email_address TEXT);" --local
```

```sh
cf d1 raw <DATABASE_ID> --sql @schema.sql --local
```

To apply [D1 migrations](/d1/reference/migrations/) to your local database:

```sh
cf d1 migrations apply <DATABASE_ID> --local
```

## Persist data

Local D1 data persists across runs of `cf dev` in `.cloudflare/state` next to `cloudflare.config.ts` by default. If your local development or tests expect an empty database, include `DROP TABLE IF EXISTS <table_name>` before `CREATE TABLE`.

To target a different local state directory from `cf d1` commands, pass `--persist-to <DIR>`:

```sh
cf d1 migrations apply <DATABASE_ID> --local --persist-to ./tmp-state
```

## Full-stack apps and static assets

With `cf`, build full-stack and static-asset applications on [Cloudflare Workers with Static Assets](/workers/static-assets/) rather than Cloudflare Pages. Everything you can build on Cloudflare Pages is supported on Workers, with full local development support for D1 via `bindings.d1()` in `cloudflare.config.ts` and `cf dev`. To move an existing Pages project to Workers, refer to [Migrate from Pages to Workers](/workers/static-assets/migration-guides/migrate-from-pages/).

<TabItem label="Wrangler">

D1 has fully-featured support for local development, running the same version of D1 as Cloudflare runs globally. Local development uses [Wrangler](/workers/wrangler/install-and-update/), the command-line interface for Workers, to manage local development sessions and state.

## Start a local development session

:::note

This guide assumes you are using [Wrangler v3.0](https://blog.cloudflare.com/wrangler3/) or later.

Users new to D1 and/or Cloudflare Workers should visit the [D1 tutorial](/d1/get-started/) to install `wrangler` and deploy their first database.

:::

Local development sessions create a standalone, local-only environment that mirrors the production environment D1 runs in so that you can test your Worker and D1 _before_ you deploy to production.

An existing [D1 binding](/workers/wrangler/configuration/#d1-databases) of `DB` would be available to your Worker when running locally.

To start a local development session:

1. Confirm you are using wrangler v3.0+.

   ```sh
   wrangler --version
   ```

   ```sh output
   ⛅️ wrangler 3.0.0
   ```

2. Start a local development session

   ```sh
   wrangler dev
   ```

   ```sh output
   ------------------
   wrangler dev now uses local mode by default, powered by 🔥 Miniflare and 👷 workerd.
   To run an edge preview session for your Worker, use wrangler dev --remote
   Your worker has access to the following bindings:
   - D1 Databases:
   	- DB: test-db (c020574a-5623-407b-be0c-cd192bab9545)
   ⎔ Starting local server...

   [mf:inf] Ready on http://127.0.0.1:8787/
   [b] open a browser, [d] open Devtools, [l] turn off local mode, [c] clear console, [x] to exit
   ```

In this example, the Worker has access to local-only D1 database. The corresponding D1 binding in your [Wrangler configuration file](/workers/wrangler/configuration/) would resemble the following:

<WranglerConfig>

```jsonc
{
	"d1_databases": [
		{
			"binding": "DB",
			"database_name": "test-db",
			"database_id": "c020574a-5623-407b-be0c-cd192bab9545"
		}
	]
}
```

</WranglerConfig>

Note that `wrangler dev` separates local and production (remote) data. A local session does not have access to your production data by default. To access your production (remote) database, set `"remote" : true` in the D1 binding configuration. For more information, refer to [Remote bindings](/workers/local-development/#remote-bindings). Any changes you make when running against a remote database cannot be undone.

For more information on configuring a local development session, refer to [`wrangler dev`](/workers/wrangler/commands/general/#dev).

## Persist data

:::note

By default, in Wrangler v3 and above, data is persisted across each run of `wrangler dev`. If your local development and testing requires or assumes an empty database, you should start with a `DROP TABLE <tablename>` statement to delete existing tables before using `CREATE TABLE` to re-create them.

:::

Use `wrangler dev --persist-to=/path/to/file` to persist data to a specific location. This can be useful when working in a team (allowing you to share) the same copy, when deploying via CI/CD (to ensure the same starting state), or as a way to keep data when migrating across machines.

Users of wrangler `2.x` must use the `--persist` flag: previous versions of wrangler did not persist data by default.

## Develop locally with Pages

You can only develop against a _local_ D1 database when using [Cloudflare Pages](/pages/) by creating a minimal [Wrangler configuration file](/workers/wrangler/configuration/) in the root of your Pages project. This can be useful when creating schemas, seeding data, or otherwise managing a D1 database directly, without adding to your application logic.

:::caution[Local development for remote databases]

It is currently not possible to develop against a _remote_ D1 database when using [Cloudflare Pages](/pages/).
:::

Your [Wrangler configuration file](/workers/wrangler/configuration/) should resemble the following:

<WranglerConfig>

```jsonc
{
	// If you are only using Pages + D1, you only need the below in your Wrangler config file to interact with D1 locally.
	"d1_databases": [
		{
			"binding": "DB", // Should match preview_database_id
			"database_name": "YOUR_DATABASE_NAME",
			"database_id": "the-id-of-your-D1-database-goes-here", // wrangler d1 info YOUR_DATABASE_NAME
			"preview_database_id": "DB" // Required for Pages local development
		}
	]
}
```

</WranglerConfig>

You can then execute queries and/or run migrations against a local database as part of your local development process by passing the `--local` flag to Wrangler:

```bash
wrangler d1 execute YOUR_DATABASE_NAME \
  --local --command "CREATE TABLE IF NOT EXISTS users ( user_id INTEGER PRIMARY KEY, email_address TEXT, created_at INTEGER, deleted INTEGER, settings TEXT);"
```

The preceding command executes queries against the **local-only** version of your D1 database.

## Test programmatically

### Miniflare

[Miniflare](https://miniflare.dev/) allows you to simulate Workers and resources like D1 using the same underlying runtime and code used in production.

You can use Miniflare's [support for D1](https://miniflare.dev/storage/d1) to create D1 databases you can use for testing:

<WranglerConfig
	cfConfig={`import { bindings, defineConfig } from "cf/config";
import * as entrypoint from "./src/index.ts" with { type: "cf-worker" };

export default defineConfig({
	worker: {
		name: "my-worker",
		entrypoint,
		compatibilityDate: "$today",
		env: {
			DB: bindings.d1({
				id: "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
				name: "test-db",
			}),
		},
	},
});`}
>

```jsonc
{
	"compatibility_date": "$today",
	"d1_databases": [
		{
			"binding": "DB",
			"database_name": "test-db",
			"database_id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
		}
	]
}
```

</WranglerConfig>

```js
const mf = new Miniflare({
	d1Databases: {
		DB: "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
	},
});
```

You can then use the `getD1Database()` method to retrieve the simulated database and run queries against it as if it were your real production D1 database:

```js
const db = await mf.getD1Database("DB");

const stmt = db.prepare("SELECT name, age FROM users LIMIT 3");
const { results } = await stmt.run();

console.log(results);
```

### Integration test harness

<CliVariants>
<CliVariant cli="wrangler">

Use Wrangler's [Integration test harness](/workers/testing/test-harness/) (`createTestHarness()`) to run integration tests against your Worker and a local D1 database from any Node.js test runner such as Vitest.

Call `worker.applyD1Migrations("DB")` after starting or resetting storage to apply [D1 migrations](/d1/reference/migrations/) automatically from your configured `migrations_dir` (or `./migrations` by default), then seed test rows through `worker.getEnv()` and send requests with `server.fetch()`:

<TypeScriptExample filename="test/index.test.ts">

```ts
import {
	afterAll,
	afterEach,
	beforeAll,
	beforeEach,
	describe,
	expect,
	test,
} from "vitest";
import { createTestHarness } from "wrangler";

const server = createTestHarness({
	workers: [{ configPath: "./wrangler.jsonc" }],
});

const worker = server.getWorker<Env>();

describe("Test D1 Worker endpoint", () => {
	beforeAll(async () => {
		await server.listen();
	});

	beforeEach(async () => {
		await worker.applyD1Migrations("DB");
		const env = await worker.getEnv();
		await env.DB.prepare(
			"INSERT INTO users (user_id, email) VALUES (?, ?), (?, ?)",
		)
			.bind(1234, "foo@example.com", 6789, "bar@example.com")
			.run();
	});

	afterEach(async () => {
		await server.reset();
	});

	afterAll(async () => {
		await server.close();
	});

	test("returns an array of users", async () => {
		const resp = await server.fetch("/api/users/?limit=2");
		expect(resp.status).toBe(200);
		expect(await resp.json()).toEqual({
			results: [
				{ user_id: 1234, email: "foo@example.com" },
				{ user_id: 6789, email: "bar@example.com" },
			],
		});
	});
});
```

</TypeScriptExample>

For more information on configuring the harness, applying migrations, and preparing test state, refer to the [Integration test harness documentation](/workers/testing/test-harness/) and [Prepare test state](/workers/testing/test-harness/prepare-test-state/#apply-d1-migrations).

</CliVariant>
