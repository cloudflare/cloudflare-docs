This guide shows how to build a multi-tenant SaaS platform using D1 and Workers for Platforms. You will learn how to provision an isolated D1 database for each tenant, bind databases dynamically to user Workers, and implement platform-level controls that protect your business from runaway usage.

D1 is designed to scale without a practical ceiling. Standard Workers Paid plans include 50,000 databases per account, and Enterprise plans support millions to tens-of-millions of databases (or more) per account. This lets your platform adopt a true database-per-tenant model: every end-user receives their own isolated SQLite database, provisioned and bound on demand through the Cloudflare API.

## Architecture overview

A SaaS platform built on Workers for Platforms can provision a unique D1 database for every end-user tenant. This database-per-tenant pattern provides strong data isolation: each tenant's tables, indexes, and rows exist in a separate SQLite file that no other tenant can access.

D1 supports 50,000 databases per account on standard Workers Paid plans. On Enterprise plans, that limit is raised to millions to tens-of-millions of databases (or more) per account — effectively unbounded for most platform workloads. There is no operational overhead for managing database servers, connection pools, or schema migrations across tenants.

The architecture consists of three layers:

1. **Platform control plane**: A dynamic dispatch Worker that authenticates requests, looks up tenant mappings, and routes traffic to the correct user Worker.
2. **User Worker**: A sandboxed Worker that contains the tenant's custom code and is bound to exactly one D1 database.
3. **D1 database**: A serverless SQL database created and bound dynamically through the Cloudflare API.

### Why database-per-tenant

| Requirement          | Single shared database        | Database-per-tenant                |
| -------------------- | ----------------------------- | ---------------------------------- |
| Data isolation       | Row-level security only       | Complete logical separation        |
| Schema customization | Shared schema for all tenants | Per-tenant schema evolution        |
| Query performance    | Noisy neighbor risk           | Single-threaded per tenant         |
| Compliance scope     | Entire database in scope      | Individual database in scope       |
| Migration risk       | One failure affects all       | Blast radius limited to one tenant |

### Consistency model

D1 uses asynchronous replication. A write in one region reaches read replicas globally within milliseconds. For most SaaS workloads this is imperceptible, but if a tenant requires read-after-write guarantees across requests, use the [Sessions API](/d1/best-practices/read-replication/) and pass bookmarks between requests.

## Provision a tenant database and user worker

Provisioning a new tenant requires three operations: create a D1 database, upload a user Worker, and attach the database binding dynamically.

<Steps>
1. Create a D1 database for the tenant via the REST API:

    ```bash
    curl -X POST "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/d1/database" \
      -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{
        "name": "tenant-acme-corp",
        "location": "weur"
      }'
    ```

    Store the returned `uuid` in your platform's tenant registry. This value is the `database_id` required for binding.

2. Upload a user Worker to your dispatch namespace with the D1 binding attached in the multipart metadata:

    ```bash
    curl -X PUT \
      "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/workers/dispatch/namespaces/$NAMESPACE/scripts/tenant-acme-corp" \
      -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
      -H "Content-Type: multipart/form-data" \
      -F 'metadata={
        "main_module": "index.js",
        "bindings": [
          {
            "type": "d1",
            "name": "TENANT_DB",
            "id": "<database-uuid-from-step-1>"
          }
        ]
      }' \
      -F 'index.js=@/path/to/user-worker.js'
    ```

    The user Worker accesses the database through `env.TENANT_DB`. No connection strings, TLS certificates, or connection pools are required.

3. Record the tenant-to-Worker mapping in your platform's routing store (for example, Workers KV or a platform-wide D1 catalog):

    ```bash
    curl -X PUT "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/storage/kv/namespaces/$KV_NAMESPACE/values/tenant-acme-corp.example.com" \
      -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
      -H "Content-Type: text/plain" \
      -d "tenant-acme-corp"
    ```
</Steps>

:::note
Bindings are defined in the `metadata` object of the multipart upload request. You cannot upload a Wrangler configuration file as a module to configure bindings for user Workers. For more details, refer to [Multipart upload metadata](/workers/configuration/multipart-upload-metadata/).

If you add new bindings to an existing user Worker later, include `keep_bindings` in the metadata to preserve existing bindings. For an example, refer to [Bindings](/cloudflare-for-platforms/workers-for-platforms/configuration/bindings/).
:::

### Location hints and jurisdictions

When you create a tenant database, set a `location` hint that matches the tenant's primary geography. This reduces round-trip latency for every query.

Available location hints:

| Hint   | Region                |
| ------ | --------------------- |
| `wnam` | Western North America |
| `enam` | Eastern North America |
| `weur` | Western Europe        |
| `eeur` | Eastern Europe        |
| `apac` | Asia-Pacific          |
| `oc`   | Oceania               |

If a tenant requires data residency for compliance, use a jurisdiction constraint instead of a location hint. Supported values are `eu` and `fedramp`. Jurisdictions can only be set on creation and cannot be changed later.

## Dynamic dispatch routing

The dynamic dispatch Worker is the entry point for all tenant traffic. It looks up the target user Worker, optionally enforces custom limits, and forwards the request.

### Configure the dispatch namespace binding

Add a dispatch namespace binding to your platform Worker's Wrangler configuration:

<WranglerConfig>

```jsonc
{
  "dispatch_namespaces": [
    {
      "binding": "DISPATCHER",
      "namespace": "my-saas-namespace"
    }
  ]
}
```

</WranglerConfig>

### Route requests and enforce custom limits

The dispatch Worker below performs three tasks on every request: authenticate the tenant, look up the user Worker name from KV, and enforce CPU limits based on the tenant's plan.

<TypeScriptExample filename="src/dispatch.ts">
```ts
export interface Env {
  DISPATCHER: DispatchNamespace;
  TENANT_ROUTING: KVNamespace;
  PLANS: KVNamespace;
}

export default {
  async fetch(request: Request, env: Env) {
    const url = new URL(request.url);
    const hostname = url.hostname;

    // 1. Look up user Worker name from KV
    const userWorkerName = await env.TENANT_ROUTING.get(hostname);
    if (!userWorkerName) {
      return new Response("Tenant not found", { status: 404 });
    }

    // 2. Look up tenant plan for limit enforcement
    const plan = await env.PLANS.get(userWorkerName);
    const limits = plan === "enterprise"
      ? { cpuMs: 50, subRequests: 50 }
      : { cpuMs: 10, subRequests: 10 };

    // 3. Dispatch with custom limits
    const userWorker = env.DISPATCHER.get(userWorkerName, {}, { limits });
    return await userWorker.fetch(request);

},
};

````
</TypeScriptExample>

For more routing patterns (subdomain-based, path-based, or custom metadata), refer to [Dynamic dispatch Worker](/cloudflare-for-platforms/workers-for-platforms/configuration/dynamic-dispatch/).

## Billing and limits at platform scale

Operating a platform with thousands of tenant databases requires understanding how D1 limits and billing aggregate across your account.

### Database and storage limits

| Feature | Workers Free | Workers Paid | Enterprise |
| --- | --- | --- | --- |
| Databases per account | 10 | 50,000 [^1] | Unbounded [^1] |
| Maximum database size | 500 MB | 10 GB | 10 GB |
| Maximum storage per account | 5 GB | 1 TB [^2] | 1 TB [^2] |

[^1]: The maximum number of databases per account can be increased by request on Workers Paid and Enterprise plans, with support for millions to tens-of-millions of databases (or more) per account. On Enterprise, this is effectively unbounded — there is no hard ceiling on database count. Refer to [Limits increases](/workers/platform/limits/#limit-increases) to request an increase.

[^2]: The maximum storage per account can be increased by request on Workers Paid and Enterprise plans. Refer to [Limits increases](/workers/platform/limits/#limit-increases) to request an increase.

### Usage-based billing

D1 bills on three metrics aggregated across all databases in your account. There are no charges for compute hours, connection pools, or data transfer.

| Metric | Workers Paid inclusion | Overage rate |
| --- | --- | --- |
| Rows read | First 25 billion per month | $0.001 per million rows |
| Rows written | First 50 million per month | $1.00 per million rows |
| Storage | First 5 GB per month | $0.75 per GB-month |

Because billing is aggregate, a single runaway tenant can inflate your platform's bill even if 99% of tenants use negligible resources. Every query returns a `meta` object containing `rows_read` and `rows_written`. Use this object to attribute cost to individual tenants and to detect anomalies.

<TypeScriptExample filename="src/user-worker.ts">
```ts
const result = await env.TENANT_DB.prepare(
  "SELECT * FROM orders WHERE tenant_id = ?"
).bind(tenantId).all();

console.log({
  tenant: tenantId,
  rowsRead: result.meta.rows_read,
  rowsWritten: result.meta.rows_written,
});
````

</TypeScriptExample>

### Example cost projection

A platform with 10,000 active tenants might see the following monthly aggregates:

| Metric       | Per-tenant average | Platform total | Billable                 |
| ------------ | ------------------ | -------------- | ------------------------ |
| Rows read    | 2,000,000          | 20 billion     | 0 (within 25B inclusion) |
| Rows written | 5,000              | 50 million     | 0 (within 50M inclusion) |
| Storage      | 40 MB              | 400 GB         | 395 GB ($296.25)         |

If one tenant executes an unindexed analytical query that scans 10 billion rows, your platform incurs an additional $10.00 in read overages ($0.001 per million rows × 10,000 million rows). Without controls, a small number of tenants can generate disproportionate cost.

## Platform safeguards

Implement the following controls to protect your platform from unexpected usage and billing overages.

### 1. Inspect query cost before executing expensive operations

For analytical or administrative endpoints, check the `meta` object after the query and reject requests that exceed a per-query threshold.

<TypeScriptExample filename="src/user-worker.ts">
```ts
const MAX_ROWS_PER_QUERY = 1_000_000;

const result = await env.TENANT_DB.prepare(sql).bind(...params).all();

if (result.meta.rows_read > MAX_ROWS_PER_QUERY) {
// Log to analytics, return error, or queue for async processing
return new Response("Query exceeded platform row limit", { status: 429 });
}

````
</TypeScriptExample>

### 2. Enforce custom CPU and subrequest limits

Set [custom limits](/cloudflare-for-platforms/workers-for-platforms/configuration/custom-limits/) in your dispatch Worker based on tenant tier. A free-tier tenant might receive 10 milliseconds of CPU time per request, while an enterprise tenant receives 50 milliseconds.

If a user Worker exceeds its CPU limit, the platform receives an exception that you can catch and convert into a `429 Too Many Requests` response.

### 3. Index every column used in predicates and joins

D1 is single-threaded per database. A full table scan on a million-row table can consume millions of billed rows and block subsequent queries for that tenant. Enforce indexing discipline in your platform's schema requirements:

```sql
CREATE INDEX idx_orders_tenant_date ON orders(tenant_id, created_at);
````

After creating or dropping an index, run `PRAGMA optimize` to update query planner statistics.

### 4. Batch writes to reduce overhead

Tenant code that inserts rows in a loop issues one round-trip per insert. Use `db.batch()` to group writes into a single transaction:

<TypeScriptExample filename="src/user-worker.ts">
```ts
const statements = records.map((r) =>
  env.TENANT_DB.prepare(
    "INSERT INTO events (type, payload) VALUES (?, ?)"
  ).bind(r.type, r.payload)
);
await env.TENANT_DB.batch(statements);
```
</TypeScriptExample>

### 5. Implement per-tenant rate limiting

Use Workers KV or Durable Objects to track request rates per tenant. If a tenant exceeds their allotted queries per minute, return `429` from the dispatch Worker before the request reaches the user Worker or D1.

### 6. Monitor aggregate platform usage

Track platform-wide metrics using the [GraphQL Analytics API](/d1/observability/metrics-analytics/#query-via-the-graphql-api/) or the Cloudflare dashboard. Set up billing alerts so you are notified when aggregate rows read or rows written approach your inclusion thresholds.

## Best practices for tenant isolation

### Use parameterized queries

Never interpolate user input into SQL strings. Parameterized queries prevent SQL injection and keep query metrics clean for analytics aggregation.

<TypeScriptExample filename="src/user-worker.ts">
```ts
// Never do this
const stmt = env.TENANT_DB.prepare(`SELECT * FROM users WHERE email = '${email}'`);

// Always do this
const stmt = env.TENANT_DB.prepare("SELECT \* FROM users WHERE email = ?").bind(email);

````
</TypeScriptExample>

### Design for read replication

If tenant workloads are read-heavy and globally distributed, enable [read replication](/d1/best-practices/read-replication/) and use the Sessions API. Even if you do not enable replication today, design user Worker code to use `withSession()` from the start.

<TypeScriptExample filename="src/user-worker.ts">
```ts
const session = env.TENANT_DB.withSession("first-unconstrained");
const result = await session.prepare("SELECT * FROM products WHERE id = ?").bind(id).all();

// Pass bookmark to the client for sequential consistency on next request
const bookmark = session.getBookmark();
````

</TypeScriptExample>

### Chunk large mutations

Never update or delete hundreds of thousands of rows in a single query. A single large mutation can exceed CPU or memory limits and trigger a Durable Object reset.

<TypeScriptExample filename="src/user-worker.ts">
```ts
const CHUNK_SIZE = 10_000;
while (true) {
  const result = await env.TENANT_DB.prepare(
    `DELETE FROM old_logs WHERE id IN (
      SELECT id FROM old_logs WHERE created_at < ? LIMIT ?
    )`
  ).bind(cutoffDate, CHUNK_SIZE).run();

if (result.meta.changes < CHUNK_SIZE) break;
}

````
</TypeScriptExample>

### Capture Time Travel bookmarks before migrations

[Time Travel](/d1/reference/time-travel/) is always on and costs nothing. Before any destructive schema migration, capture a bookmark so you can restore the tenant database in seconds if the migration fails.

```bash
npx wrangler d1 time-travel info tenant-acme-corp
````

### Respect per-database resource ceilings

A single D1 database has fixed CPU and memory resources. Warn tenants when their database approaches the 10 GB size limit, and guide them to archive old data or split large tables.

| Limit                         | Value        |
| ----------------------------- | ------------ |
| Max database size             | 10 GB (Paid) |
| Max query duration            | 30 seconds   |
| Max SQL statement length      | 100 KB       |
| Max bound parameters          | 100          |
| Max string, BLOB, or row size | 2 MB         |

## Troubleshooting

### Tenant reports slow queries

**Diagnosis:**

- Run `EXPLAIN QUERY PLAN` on the tenant's slow query to check for table scans.
- Inspect the query `meta` object for unexpectedly high `rows_read`.
- Verify the database location hint matches the tenant's user geography.

**Fix:**

- Add indexes on columns in `WHERE`, `JOIN`, and `ORDER BY` clauses.
- Run `PRAGMA optimize` after adding indexes.
- Enable read replication and use the Sessions API for global traffic.

### Tenant hits `D1 DB is overloaded`

**Diagnosis:** The tenant database is receiving more concurrent requests than it can process, or individual queries are too slow.

**Fix:**

- Optimize query performance (add indexes, reduce rows scanned).
- Batch writes to reduce round-trips.
- Implement client-side rate limiting for that tenant.
- If the tenant has outgrown one database, migrate them to a sharded architecture or upgrade their plan.

### Unexpected billing overages

**Diagnosis:** One or more tenants are executing queries with high row counts.

**Fix:**

- Identify the top databases by `rows_read` in the Cloudflare dashboard.
- Contact the affected tenants and require indexes on heavily scanned columns.
- Implement per-query row limits in your platform's user Worker template.
- Enforce stricter custom CPU limits for the affected tenant tier.

### Migration fails with `FOREIGN KEY constraint failed`

**Diagnosis:** D1 enforces foreign keys by default. A migration may temporarily create orphan rows.

**Fix:**

- Use `PRAGMA defer_foreign_keys = on` at the start of the migration transaction.
- Do not use `PRAGMA foreign_keys = off`; it is silently ignored in D1.
- Resolve all violations before the transaction commits.

## Quick reference checklist

Before onboarding a new tenant or shipping a platform update, verify the following:

- [ ] Database created with a location hint matching tenant geography
- [ ] User Worker uploaded with D1 binding via multipart metadata
- [ ] Tenant-to-Worker mapping stored in the routing layer
- [ ] Custom limits configured in the dispatch Worker based on tenant plan
- [ ] Indexes exist for all `WHERE`, `JOIN`, and `ORDER BY` columns
- [ ] Parameterized queries with `.bind()` used in all user Worker templates
- [ ] `db.batch()` used for bulk insert and update operations
- [ ] Per-query row cost inspection implemented for analytical endpoints
- [ ] Application-level retry with exponential backoff for idempotent writes
- [ ] Time Travel bookmark captured before destructive migrations
- [ ] `withSession()` used if read replication is or will be enabled
- [ ] Chunk size for bulk mutations capped at roughly 10,000 rows
- [ ] Aggregate platform usage monitored via dashboard or GraphQL API
