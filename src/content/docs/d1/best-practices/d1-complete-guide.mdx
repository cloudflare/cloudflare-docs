This guide covers everything you need to build production applications on [D1](/d1/), Cloudflare's serverless SQL database. It is self-contained: you can read it end-to-end without jumping between pages. Each section links to the dedicated reference page for deeper detail.

The guide is organized around two themes:

1. **Fundamentals** — what D1 is, when to use it, and how to get started.
2. **Production patterns** — optimization, replication, schema management, per-tenant architecture, and troubleshooting.

## Decide if D1 fits your workload

Before you write a query, answer two questions:

1. Is the workload read-heavy or write-heavy?
2. Do you need strict global consistency on every read?

D1 is built on [SQLite](https://www.sqlite.org/) and runs on Cloudflare's global network. It excels at read-heavy workloads with simple schemas. It is not designed for write-heavy analytics or workloads that require strict global serializability.

### Use-case fit

| Use case                                    | Fit     | Reason                                                      |
| ------------------------------------------- | ------- | ----------------------------------------------------------- |
| User profiles and configuration             | Good    | Small rows, frequent reads, infrequent writes               |
| Blog posts, CMS content                     | Good    | Read-heavy, globally distributed readers                    |
| URL shorteners                              | Good    | Fast lookups, simple schema                                 |
| E-commerce product catalogs                 | Good    | Read-heavy catalog with occasional inventory updates        |
| IoT device state                            | Good    | Edge-local writes, periodic sync                            |
| Multiplayer game leaderboards               | Depends | Acceptable if write volume is moderate                      |
| High-frequency trading or real-time bidding | Poor    | Too write-heavy, needs strict serializability               |
| Write-heavy analytics pipelines             | Poor    | D1 is single-threaded per database                          |
| Multi-GB datasets with complex joins        | Poor    | 10 GB limit per database, memory constraints on large scans |
| Data warehouse or OLAP                      | Poor    | Not designed for analytical workloads                       |

If you need a SQL database for a [Worker](/workers/) or [Pages](/pages/) project and do not need PostgreSQL-specific features such as `JSONB` operators, `SERIAL` types, or stored procedures, D1 is the simplest option.

## Understand how D1 works

### SQLite at the core

D1 is built on SQLite, the most widely deployed database engine. Unlike PostgreSQL or MySQL, SQLite is not a client-server database. It is a library that reads and writes a single file. D1 takes that file and makes it serverless and globally distributed.

### Serverless billing

You do not provision servers or pick instance sizes. Cloudflare runs your query and bills for the rows read and written. When nobody uses your application, the database costs nothing. Refer to [D1 pricing](/d1/platform/pricing/) for details.

### Storage and replication

Your data lives in a single SQLite file backed by a [Durable Object](/durable-objects/) pinned to a geographic region. Cloudflare replicates this file across its network when you enable [read replication](/d1/best-practices/read-replication/).

![D1 read replication concept](/images/d1/d1-read-replication-concept.png)

### Consistency model

D1 uses **asynchronous replication**. This is the most important concept in this guide.

- **Read your own writes** — A user in London writes data, then reads it back in London. The data is usually available immediately.
- **Global consistency** — A user in London writes data, and a user in Sydney reads 10 milliseconds later. The data might not be there yet.

That delay is called **replica lag**. For most web applications it is imperceptible. For financial ledgers it may be a dealbreaker. The [Sessions API](/d1/best-practices/read-replication/#use-sessions-api) lets you guarantee sequential consistency within a session.

### Single-database throughput

Each D1 database is single-threaded. It processes queries one at a time.

| Average query duration | Approximate max throughput |
| ---------------------- | -------------------------- |
| 1 ms                   | ~1,000 queries per second  |
| 10 ms                  | ~100 queries per second    |
| 100 ms                 | ~10 queries per second     |

If a database receives more concurrent requests than it can process, it queues them. If the queue fills, D1 returns an `overloaded` error.

D1 is designed for horizontal scale-out across many smaller databases (for example, one per tenant), not for vertical scale-up of one massive database. Refer to [Scale with database-per-tenant](#scale-with-database-per-tenant) for details.

## Get started in five minutes

This section gives a minimal end-to-end example. For the full walkthrough with dashboard and CLI tabs, refer to [Getting started](/d1/get-started/).

### Prerequisites

You need [Node.js](https://nodejs.org/) installed. Then install Wrangler:

```sh
npm install -g wrangler
```

Log in to your Cloudflare account:

```sh
npx wrangler login
```

### Create a database and Worker

<Steps>

1. Create a database:

    ```sh
    npx wrangler d1 create my-first-db
    ```

    Wrangler returns a configuration block. Copy it.

2. Create a schema file named `schema.sql`:

    ```sql
    DROP TABLE IF EXISTS links;
    CREATE TABLE links (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      slug TEXT UNIQUE NOT NULL,
      url TEXT NOT NULL,
      created_at DATETIME DEFAULT CURRENT_TIMESTAMP
    );
    ```

3. Apply the schema:

    ```sh
    npx wrangler d1 execute my-first-db --file=./schema.sql
    ```

4. Bind the database to a Worker. Add the D1 binding to your Wrangler configuration file:

    <WranglerConfig>

    ```toml
    name = "my-d1-app"
    main = "src/index.ts"
    compatibility_date = "$today"

    [[d1_databases]]
    binding = "DB"
    database_name = "my-first-db"
    database_id = "<unique-ID-for-your-database>"
    ```

    </WranglerConfig>

5. Write your Worker code:

    <TypeScriptExample filename="src/index.ts">

    ```ts
    export interface Env {
      DB: D1Database;
    }

    export default {
      async fetch(request: Request, env: Env): Promise<Response> {
        const url = new URL(request.url);
        const slug = url.pathname.slice(1);

        if (request.method === "POST" && slug === "create") {
          const body = await request.json<{ slug: string; url: string }>();
          await env.DB.prepare(
            "INSERT INTO links (slug, url) VALUES (?, ?)"
          ).bind(body.slug, body.url).run();
          return new Response("Created", { status: 201 });
        }

        const result = await env.DB.prepare(
          "SELECT url FROM links WHERE slug = ?"
        ).bind(slug).first<{ url: string }>();

        if (result) {
          return Response.redirect(result.url, 302);
        }

        return new Response("Not found", { status: 404 });
      },
    } satisfies ExportedHandler<Env>;
    ```

    </TypeScriptExample>

    `env.DB` is available directly. No connection strings, TLS certificates, or connection pools are required.

6. Deploy:

    ```sh
    npx wrangler deploy
    ```

</Steps>

You now have a globally distributed, database-backed application.

## Optimization and best practices

The following practices are the difference between a D1 application that performs well and one that does not.

### Index every queried column

D1 is single-threaded per database. A table scan that takes 100 milliseconds limits throughput to roughly 10 queries per second. A point lookup on an indexed column takes less than 1 millisecond.

```sql
CREATE INDEX IF NOT EXISTS idx_users_email ON users(email);
```

After creating or dropping an index, run `PRAGMA optimize` to update query planner statistics:

```sql
PRAGMA optimize;
```

Use `EXPLAIN QUERY PLAN` to verify that a query uses the index:

```sql
EXPLAIN QUERY PLAN SELECT * FROM users WHERE email = ?;
```

For full details on multi-column indexes, partial indexes, and naming conventions, refer to [Use indexes](/d1/best-practices/use-indexes/).

:::note
Every indexed column adds at least one extra row written per `INSERT` or `UPDATE`. This tradeoff is almost always worth it for read-heavy workloads, but be aware of write amplification on write-heavy tables.
:::

### Batch related queries

All queries in a `batch()` call share a single transaction and a single round-trip. Calling `.run()` in a loop issues one round-trip per query.

<TypeScriptExample filename="src/index.ts">

```ts
// One round-trip for all inserts
const statements = users.map((u: { name: string }) =>
	env.DB.prepare("INSERT INTO users (name) VALUES (?)").bind(u.name),
);
await env.DB.batch(statements);
```

</TypeScriptExample>

For more on the `batch()` method, refer to [D1Database](/d1/worker-api/d1-database/#batch).

### Retry write queries

D1 automatically retries read-only queries up to two times on transient errors. Write queries are never auto-retried. Your application must implement retry logic for idempotent writes.

Use exponential backoff with jitter. Only retry on errors marked as retryable:

<TypeScriptExample filename="src/retry.ts">

```ts
function shouldRetry(err: unknown, nextAttempt: number): boolean {
	const errMsg = String(err);
	const isRetryable =
		errMsg.includes("Network connection lost") ||
		errMsg.includes("storage caused object to be reset") ||
		errMsg.includes("reset because its code was updated");
	return nextAttempt <= 3 && isRetryable;
}

async function queryWithRetry(
	db: D1Database,
	sql: string,
	params: unknown[],
): Promise<D1Result> {
	let attempt = 0;
	while (true) {
		try {
			return await db
				.prepare(sql)
				.bind(...params)
				.run();
		} catch (err) {
			attempt++;
			if (!shouldRetry(err, attempt)) throw err;
			const delay = Math.min(50 * Math.pow(2, attempt), 2000);
			const jitter = Math.random() * delay;
			await new Promise((r) => setTimeout(r, jitter));
		}
	}
}
```

</TypeScriptExample>

Refer to [Retry queries](/d1/best-practices/retry-queries/) and the [error list](/d1/observability/debug-d1/#error-list) for which errors are retryable.

### Chunk bulk mutations

Never modify hundreds of thousands of rows in a single query. A large `UPDATE` or `DELETE` can exceed CPU or memory limits and trigger a Durable Object reset. The in-flight operation is lost.

Process in chunks of roughly 10,000 rows:

<TypeScriptExample filename="src/cleanup.ts">

```ts
const CHUNK_SIZE = 10_000;
let hasMore = true;

while (hasMore) {
	const result = await env.DB.prepare(
		`DELETE FROM old_logs WHERE id IN (
      SELECT id FROM old_logs WHERE created_at < ? LIMIT ?
    )`,
	)
		.bind(cutoffDate, CHUNK_SIZE)
		.run();

	hasMore = (result.meta.changes ?? 0) >= CHUNK_SIZE;
}
```

</TypeScriptExample>

### Use parameterized queries

Never interpolate user data into SQL strings.

<TypeScriptExample filename="src/index.ts">

```ts
// Never do this — SQL injection risk
const bad = env.DB.prepare(`SELECT * FROM users WHERE email = '${email}'`);

// Always do this
const good = env.DB.prepare("SELECT * FROM users WHERE email = ?").bind(email);
```

</TypeScriptExample>

Beyond SQL injection protection, bound parameters are stripped from [D1 query insights](/d1/observability/metrics-analytics/). This lets you aggregate analytics across all executions of the same query template.

### Set a location hint

D1 databases are backed by Durable Objects pinned to a region. Without a location hint, Cloudflare picks a region close to the request that created the database. If your CI pipeline runs in Oregon but your users are in Europe, your database ends up in Oregon.

Set a location hint at creation time:

```sh
npx wrangler d1 create my-db --location=weur
```

Available hints:

| Hint   | Region                |
| ------ | --------------------- |
| `wnam` | Western North America |
| `enam` | Eastern North America |
| `weur` | Western Europe        |
| `eeur` | Eastern Europe        |
| `apac` | Asia-Pacific          |
| `oc`   | Oceania               |

For compliance requirements, use a jurisdiction constraint instead. Supported values are `eu` and `fedramp`. Jurisdictions can only be set at creation and cannot be changed. Refer to [Data location](/d1/configuration/data-location/) for full details.

:::caution
Location hints are not supported for South America (`sam`), Africa (`afr`), or the Middle East (`me`). The hint falls back to the nearest available region.
:::

### Use the Sessions API for read replication

[Read replicas](/d1/best-practices/read-replication/) reduce latency for read-heavy applications with global users. Even if you do not enable read replication today, design your code to use `withSession()` from the start. This lets you toggle replication on later without changing Worker code.

<TypeScriptExample filename="src/index.ts">

```ts
// Start a session
const session = env.DB.withSession("first-unconstrained");

const result = await session
	.prepare("SELECT * FROM products WHERE id = ?")
	.bind(id)
	.all();

// Pass the bookmark to the next request for sequential consistency
const bookmark = session.getBookmark();
```

</TypeScriptExample>

Session constraint options:

| Parameter                       | Behavior                                                            |
| ------------------------------- | ------------------------------------------------------------------- |
| `first-unconstrained` (default) | First query routes to any replica for minimum latency               |
| `first-primary`                 | First query routes to the primary for the latest data               |
| A bookmark string               | Starts from a specific previous state, guaranteeing monotonic reads |

![Sequential consistency with Sessions API](/images/d1/consistency-with-sessions-api.png)

Return the bookmark to your client (for example, in an HTTP header) so subsequent requests from the same user session maintain consistency.

### Capture Time Travel bookmarks before migrations

[Time Travel](/d1/reference/time-travel/) is always on and costs nothing. It lets you restore a database to any minute within the last 30 days (7 days on the Free plan).

Before any destructive migration, capture a bookmark:

```sh
npx wrangler d1 time-travel info my-db
```

If the migration fails, restore in seconds:

```sh
npx wrangler d1 time-travel restore my-db --bookmark=<YOUR_BOOKMARK>
```

:::caution
Restoring is a destructive, in-place overwrite. In-flight queries are cancelled. Bookmarks older than 30 days expire and cannot be used.
:::

### Handle foreign keys in migrations

Unlike vanilla SQLite, D1 enforces foreign keys in every transaction. If you migrate a schema designed with `PRAGMA foreign_keys = off`, existing violations surface immediately.

To temporarily defer enforcement during a migration:

```sql
PRAGMA defer_foreign_keys = on;

-- Run ALTER TABLE, DROP COLUMN, and similar statements here

PRAGMA defer_foreign_keys = off;
```

Do **not** use `PRAGMA foreign_keys = off`. D1 silently ignores it because every query runs inside an implicit transaction. If outstanding violations remain when the transaction ends, you receive a `FOREIGN KEY constraint failed` error.

Refer to [Define foreign keys](/d1/sql-api/foreign-keys/) for full details on defining relationships and available actions (`CASCADE`, `RESTRICT`, `SET DEFAULT`, `SET NULL`, `NO ACTION`).

### Respect resource limits

A single D1 database has fixed resources. Large aggregation queries scanning an entire table often fail due to CPU or memory limits.

| Limit                         | Value                        |
| ----------------------------- | ---------------------------- |
| Max database size             | 10 GB (Paid) / 500 MB (Free) |
| Max query duration            | 30 seconds                   |
| Max SQL statement length      | 100 KB                       |
| Max bound parameters          | 100                          |
| Max string, BLOB, or row size | 2 MB                         |

If you outgrow one database, shard your data horizontally across multiple databases. D1 supports 50,000 databases per account on Workers Paid plans, and millions or more on Enterprise plans. Refer to [Limits](/d1/platform/limits/) for the full table.

## Scale with database-per-tenant

D1 is designed for horizontal scale-out across many smaller databases. The database-per-tenant pattern gives each tenant (user, organization, or project) their own isolated SQLite database. This is the recommended architecture when you need to serve many independent datasets.

### Why database-per-tenant

| Requirement          | Single shared database        | Database per tenant                |
| -------------------- | ----------------------------- | ---------------------------------- |
| Data isolation       | Row-level filtering only      | Complete logical separation        |
| Schema customization | Shared schema for all tenants | Per-tenant schema evolution        |
| Query performance    | Noisy neighbor risk           | Single-threaded per tenant         |
| Compliance scope     | Entire database in scope      | Individual database in scope       |
| Migration risk       | One failure affects all       | Blast radius limited to one tenant |

### Provision a database per tenant

Use the Cloudflare REST API to create databases programmatically. Set a location hint that matches the tenant's primary geography.

```bash
curl -X POST "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/d1/database" \
  -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "tenant-acme-corp",
    "location": "weur"
  }'
```

Store the returned `uuid` as the `database_id` for binding.

### Bind databases dynamically with Workers for Platforms

If you run a SaaS platform using [Workers for Platforms](/cloudflare-for-platforms/workers-for-platforms/), you can provision isolated D1 databases and bind them to user Workers dynamically.

The architecture has three layers:

1. **Platform dispatch Worker** — authenticates requests, looks up tenant mappings, and routes traffic to the correct user Worker.
2. **User Worker** — a sandboxed Worker bound to exactly one D1 database.
3. **D1 database** — created and bound through the REST API.

Upload a user Worker with its D1 binding in the multipart metadata:

```bash
curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/workers/dispatch/namespaces/$NAMESPACE/scripts/tenant-acme-corp" \
  -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  -H "Content-Type: multipart/form-data" \
  -F 'metadata={
    "main_module": "index.js",
    "bindings": [
      {
        "type": "d1",
        "name": "TENANT_DB",
        "id": "<database-uuid>"
      }
    ]
  }' \
  -F 'index.js=@/path/to/user-worker.js'
```

The user Worker accesses the database through `env.TENANT_DB`.

:::note
Bindings are defined in the `metadata` object of the multipart upload request. You cannot upload a Wrangler configuration file to configure bindings for user Workers. For more details, refer to [Multipart upload metadata](/workers/configuration/multipart-upload-metadata/).
:::

### Route requests with a dispatch Worker

The dispatch Worker looks up the target user Worker, enforces custom limits based on tenant plan, and forwards the request.

<WranglerConfig>

```toml
[[dispatch_namespaces]]
binding = "DISPATCHER"
namespace = "my-saas-namespace"
```

</WranglerConfig>

<TypeScriptExample filename="src/dispatch.ts">

```ts
export interface Env {
	DISPATCHER: DispatchNamespace;
	TENANT_ROUTING: KVNamespace;
	PLANS: KVNamespace;
}

export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const url = new URL(request.url);
		const hostname = url.hostname;

		const userWorkerName = await env.TENANT_ROUTING.get(hostname);
		if (!userWorkerName) {
			return new Response("Tenant not found", { status: 404 });
		}

		const plan = await env.PLANS.get(userWorkerName);
		const limits =
			plan === "enterprise"
				? { cpuMs: 50, subRequests: 50 }
				: { cpuMs: 10, subRequests: 10 };

		const userWorker = env.DISPATCHER.get(userWorkerName, {}, { limits });
		return await userWorker.fetch(request);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

For more routing patterns, refer to [Dynamic dispatch Worker](/cloudflare-for-platforms/workers-for-platforms/configuration/dynamic-dispatch/).

### Monitor per-tenant cost

D1 bills on three metrics aggregated across all databases in your account. Every query returns a `meta` object with `rows_read` and `rows_written`. Use these values to attribute cost to individual tenants.

<TypeScriptExample filename="src/user-worker.ts">

```ts
const result = await env.TENANT_DB.prepare(
	"SELECT * FROM orders WHERE status = ?",
)
	.bind(status)
	.all();

console.log({
	rowsRead: result.meta.rows_read,
	rowsWritten: result.meta.rows_written,
});
```

</TypeScriptExample>

| Metric       | Workers Paid inclusion     | Overage rate            |
| ------------ | -------------------------- | ----------------------- |
| Rows read    | First 25 billion per month | $0.001 per million rows |
| Rows written | First 50 million per month | $1.00 per million rows  |
| Storage      | First 5 GB per month       | $0.75 per GB-month      |

A single runaway tenant can inflate your account bill. Implement per-query row limits and tenant-tier rate limiting to prevent this.

## Troubleshooting

### Queries are slow

**Diagnosis:**

- Run `EXPLAIN QUERY PLAN` on the slow query to check for table scans.
- Inspect `wrangler d1 insights` for slow queries in production.
- Check if you are querying from a region far from your database's primary location.

**Fix:**

- Add indexes on columns in `WHERE`, `JOIN`, and `ORDER BY` clauses.
- Run `PRAGMA optimize` after adding indexes.
- Set a [location hint](/d1/configuration/data-location/) closer to your users.
- Enable [read replication](/d1/best-practices/read-replication/) and use the Sessions API.

### `D1 DB is overloaded`

**Diagnosis:** The database is receiving more concurrent requests than it can process, or individual queries are too slow.

**Fix:**

- Optimize query performance (add indexes, reduce rows scanned).
- Use `batch()` to reduce round-trips.
- Shard data across multiple databases if you have many concurrent users.
- Implement client-side rate limiting or backpressure.

### `D1 DB exceeded its CPU time limit`

**Diagnosis:** A query scanned too many rows or joined too many tables.

**Fix:**

- Break large `UPDATE` or `DELETE` statements into chunks of roughly 10,000 rows.
- Add indexes so the query planner avoids full table scans.
- Avoid `SELECT *` on large tables without `LIMIT` clauses.

### Write fails with a transient error

**Diagnosis:** Errors such as `Network connection lost` or `Internal error in D1 DB storage caused object to be reset`.

**Fix:**

- Implement [application-level retry](#retry-write-queries) with exponential backoff and jitter.
- Only retry idempotent operations.
- Refer to the [error list](/d1/observability/debug-d1/#error-list) for which errors are retryable.

### Migration fails with `FOREIGN KEY constraint failed`

**Diagnosis:** D1 enforces foreign keys by default. A migration may temporarily create orphan rows.

**Fix:**

- Use `PRAGMA defer_foreign_keys = on` at the start of the migration.
- Do not use `PRAGMA foreign_keys = off` — D1 silently ignores it.
- Resolve all violations before the transaction commits.

### Cannot connect from a desktop database client

**Diagnosis:** D1 does not expose a TCP socket or standard connection string.

**Fix:**

- Use Wrangler for ad-hoc queries: `npx wrangler d1 execute my-db --command="SELECT ..."`.
- Use the Worker [binding API](/d1/worker-api/) for application queries.
- For local development, `wrangler dev` creates a local SQLite file you can inspect. Refer to [Local development](/d1/best-practices/local-development/).

### Read replica data is stale

**Diagnosis:** A user submits a form, reloads the page, and does not see their update. Without the Sessions API, read replicas may serve data from before the write replicated.

**Fix:**

- Use `db.withSession()` and pass bookmarks between requests.
- Start sessions with `first-primary` if the latest data is required immediately.
- Refer to [Global read replication](/d1/best-practices/read-replication/) for the full guide.

## Quick reference checklist

Before shipping a D1-backed application, verify the following:

- [ ] Indexes exist for all `WHERE`, `JOIN`, and `ORDER BY` columns
- [ ] `PRAGMA optimize` run after schema changes
- [ ] Parameterized queries with `.bind()` used everywhere
- [ ] `db.batch()` used for bulk operations
- [ ] Application-level retry implemented for idempotent writes
- [ ] Location hint set at database creation
- [ ] Time Travel bookmark captured before destructive migrations
- [ ] `withSession()` used if read replication is or will be enabled
- [ ] Chunk size for bulk mutations capped at roughly 10,000 rows
- [ ] Query duration verified under 100 ms for hot paths
