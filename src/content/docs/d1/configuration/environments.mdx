<TabItem label="Cloudflare CLI (cf)">

In [`cloudflare.config.ts`](/cf/projects/cloudflare-config/), environments are modeled as [modes](/cf/projects/cloudflare-config/#evaluate-configuration). This is useful when your Worker code refers to a single D1 binding like `DB`, and you want that binding to point to different D1 databases for staging and production.

Store your staging and production database IDs in a separate module (for example, `d1-databases.ts`):

```ts title="d1-databases.ts"
export const prodDatabaseId = "<PROD_DATABASE_ID>";
export const stagingDatabaseId = "<STAGING_DATABASE_ID>";
```

Then pass a function to `defineConfig(({ mode }) => ...)` and return a complete configuration for each mode, binding `DB` to the database for that mode:

```ts title="cloudflare.config.ts"
import { bindings, defineConfig } from "cf/config";
import * as entrypoint from "./src/index.ts" with { type: "cf-worker" };
import { prodDatabaseId, stagingDatabaseId } from "./d1-databases.ts";

export default defineConfig(({ mode }) => {
	const isProduction = mode === "production";

	return {
		worker: {
			name: isProduction ? "my-worker" : "my-worker-staging",
			entrypoint,
			compatibilityDate: "<COMPATIBILITY_DATE>",
			env: {
				DB: bindings.d1({
					id: isProduction ? prodDatabaseId : stagingDatabaseId,
					name: isProduction ? "my-db-production" : "my-db-staging",
				}),
			},
		},
	};
});
```

Using the same binding name (`DB`) for both databases keeps your Worker code identical across environments.

Run `cf dev --mode staging` or `cf deploy --mode staging` so `env.DB` targets your staging database. Run `cf deploy --mode production` so `env.DB` targets your production database.

To run queries or apply migrations from the terminal with `cf d1`, pass the database ID directly. Because each database ID is unique, `cf d1` targets the exact staging or production database without a `--mode` lookup:

```sh
cf d1 query <STAGING_DATABASE_ID> --sql "SELECT name FROM sqlite_schema WHERE type = 'table';"
```

```sh
cf d1 migrations apply <PROD_DATABASE_ID>
```

`cf d1` commands act on your remote D1 database by default. Pass `--local` to `cf d1 raw` or `cf d1 migrations` commands to target local development state instead.

To supply a separate D1 database for [Worker Previews](/cf/projects/#deploy-a-preview), inspect `isPreview` alongside `mode` in `defineConfig(({ mode, isPreview }) => ...)`.

<TabItem label="Wrangler">

[Environments](/workers/wrangler/environments/) are different contexts that your code runs in. Cloudflare Developer Platform allows you to create and manage different environments. Through environments, you can deploy the same project to multiple places under multiple names.

To specify different D1 databases for different environments, use the following syntax in your Wrangler file:

<WranglerConfig>

```jsonc
{
	"env": {
		// This is a staging environment
		"staging": {
			"d1_databases": [
				{
					"binding": "<BINDING_NAME_1>",
					"database_name": "<DATABASE_NAME_1>",
					"database_id": "<UUID1>"
				}
			]
		},
		// This is a production environment
		"production": {
			"d1_databases": [
				{
					"binding": "<BINDING_NAME_2>",
					"database_name": "<DATABASE_NAME_2>",
					"database_id": "<UUID2>"
				}
			]
		}
	}
}
```

</WranglerConfig>

In the code above, the `staging` environment is using a different database (`DATABASE_NAME_1`) than the `production` environment (`DATABASE_NAME_2`).

## Anatomy of Wrangler file

If you need to specify different D1 databases for different environments, your [Wrangler configuration file](/workers/wrangler/configuration/) may contain bindings that resemble the following:

<WranglerConfig>

```jsonc
{
	"env": {
		"production": {
			"d1_databases": [
				{
					"binding": "DB",
					"database_name": "DATABASE_NAME",
					"database_id": "DATABASE_ID"
				}
			]
		}
	}
}
```

</WranglerConfig>

In the above configuration:

- `[[env.production.d1_databases]]` creates an object `production` under `env` with a property `d1_databases`, where `d1_databases` is an array of objects, since you can create multiple D1 bindings in case you have more than one database.
- Any property below the line in the form `<key> = <value>` is a property of an object within the `d1_databases` array.

Therefore, the above binding is equivalent to:

```json
{
  "env": {
    "production": {
      "d1_databases": [
        {
          "binding": "DB",
          "database_name": "DATABASE_NAME",
          "database_id": "DATABASE_ID"
        }
      ]
    }
  }
}
```
