A custom [D1](/d1/) binding lets a platform-owned Worker inspect each database operation before it reaches D1.

Use this pattern when you deploy User Workers and need tenant-level logging, limits, auditing, or inline query policy.

## Overview

The User Worker keeps using the standard [D1 Workers API](/d1/worker-api/). Calls such as `env.DB.prepare().bind().all()` do not need code changes.

Instead of binding `env.DB` directly to a D1 database, you bind it to a Platform Worker. The Platform Worker exports a `WorkerEntrypoint` class with a `query()` method that receives each D1 operation.

You can use the `query()` method to:

- Track and limit usage per tenant.
- Rate-limit in-flight queries per tenant.
- Reject queries that break your policy.
- Log live query metadata for debugging and audits.
- Forward allowed operations to the real D1 database.

## How it works

A custom D1 binding has three parts:

- **Platform Worker**: Your Worker that implements the custom D1 binding logic.
- **User Worker**: Your customer's Worker that uses the standard D1 API.
- **Binding configuration**: A service binding that routes `env.DB` through your Platform Worker.

The request flow looks like this:

```mermaid
flowchart LR
  A[User Worker code] -->|env.DB.prepare().all()| B[D1 binding]
  B -->|query(params)| C[Platform Worker entrypoint]
  C -->|inspect, log, limit, or reject| C
  C -->|ctx.props.D1.query(params)| D[D1 database]
  D -->|QueryResult| C
  C -->|QueryResult| A
```

Only User Workers uploaded with the custom D1 binding service binding and compatibility flag route through your Platform Worker.

:::caution[Existing User Workers]
Previously deployed User Workers keep their existing D1 binding behavior. Redeploy them with the service binding and compatibility flag to route D1 calls through the Platform Worker.
:::

## Prerequisites

Before you start, make sure you have:

- A Platform Worker that you control.
- A D1 database for each tenant, or a routing model for tenant databases.
- A deployment flow that can upload User Workers with multipart metadata.
- A compatibility flag of `d1_custom_binding` on each User Worker.
- A way to store policy state, such as [Durable Objects](/durable-objects/), [Workers KV](/kv/), or an external service.

## Define the interface

The Platform Worker entrypoint must expose a `query()` method. The D1 binding calls this method for D1 operations.

If your generated Workers runtime types do not include these declarations, define them locally in your Platform Worker.

<TypeScriptExample>

```ts
export interface QueryParamStatement {
	sql: string;
	params?: unknown[];
}

export interface QueryParams {
	statements: QueryParamStatement[];
}

export interface StatementMeta {
	rows_read: number;
	rows_written: number;
	duration: number;
}

export interface StatementResult {
	meta: StatementMeta;
}

export interface QueryResult {
	success: boolean;
	error?: Error;
	results?: {
		statementResults: StatementResult[];
	};
}
```

</TypeScriptExample>

## Create the Platform Worker

In the Platform Worker, export a `WorkerEntrypoint` class. Its `query()` method runs before each D1 operation reaches the database.

This example logs query metadata, checks a rate limit, calls a policy placeholder, and records basic query metrics.

<TypeScriptExample filename="platform-worker.ts">

```ts
import { WorkerEntrypoint } from "cloudflare:workers";

interface QueryParamStatement {
	sql: string;
	params?: unknown[];
}

interface QueryParams {
	statements: QueryParamStatement[];
}

interface StatementMeta {
	rows_read: number;
	rows_written: number;
	duration: number;
}

interface StatementResult {
	meta: StatementMeta;
}

interface QueryResult {
	success: boolean;
	error?: Error;
	results?: {
		statementResults: StatementResult[];
	};
}

interface D1BindingProxy {
	query(params: QueryParams): Promise<QueryResult>;
}

interface D1CustomBindingProps {
	D1: D1BindingProxy;
	TENANT_ID: string;
	MAX_QUERIES_PER_MIN?: number;
}

export class D1CustomBinding extends WorkerEntrypoint<
	Cloudflare.Env,
	D1CustomBindingProps
> {
	async query(params: QueryParams): Promise<QueryResult> {
		const tenantId = this.ctx.props.TENANT_ID;

		console.log("D1 query intercepted", {
			tenantId,
			statementCount: params.statements.length,
		});

		const allowed = await this.checkRateLimit(tenantId);

		if (!allowed) {
			return {
				success: false,
				error: new Error("D1 query rate limit exceeded"),
			};
		}

		for (const statement of params.statements) {
			if (!this.isStatementAllowed(statement.sql)) {
				return {
					success: false,
					error: new Error("D1 query rejected by platform policy"),
				};
			}
		}

		const result = await this.ctx.props.D1.query(params);

		if (result.success && result.results) {
			const totalRowsRead = result.results.statementResults.reduce(
				(sum, statementResult) => sum + statementResult.meta.rows_read,
				0,
			);
			const totalRowsWritten = result.results.statementResults.reduce(
				(sum, statementResult) => sum + statementResult.meta.rows_written,
				0,
			);

			console.log("D1 query completed", {
				tenantId,
				rowsRead: totalRowsRead,
				rowsWritten: totalRowsWritten,
				duration: result.results.statementResults[0]?.meta.duration,
			});
		}

		return result;
	}

	private async checkRateLimit(tenantId: string): Promise<boolean> {
		// Implement with Durable Objects, KV, or an external service.
		return true;
	}

	private isStatementAllowed(_sql: string): boolean {
		// Use a SQL parser or a statement allowlist for production policy.
		return true;
	}
}
```

</TypeScriptExample>

Use [`console.log()`](/workers/observability/logs/workers-logs/) for structured logs. To avoid adding work to the request path, attach a [Tail Worker](/workers/observability/logs/tail-workers/) that forwards logs to [Analytics Engine](/analytics/analytics-engine/) or another analytics pipeline.

If you log SQL text or bound parameters, redact tenant data before you forward logs.

## Keep User Worker code unchanged

The User Worker uses the standard D1 API. It does not need to know that `DB` routes through your Platform Worker.

This example reads users for one organization. The same binding path also applies to `batch()` calls.

<TypeScriptExample filename="user-worker.ts">

```ts
interface Env {
	DB: D1Database;
}

export default {
	async fetch(request, env): Promise<Response> {
		const users = await env.DB.prepare(
			"SELECT name, email FROM users WHERE org_id = ?",
		)
			.bind(42)
			.all();

		return Response.json(users.results);
	},
} satisfies ExportedHandler<Env>;
```

</TypeScriptExample>

## Wire the binding

When you upload the User Worker, attach the Platform Worker as a service binding named `DB`. The service binding entrypoint must match the class exported by your Platform Worker.

Use `props` to pass tenant-specific resources and policy values. This example passes the tenant's real D1 database and tenant ID.

```json
{
	"bindings": [
		{
			"type": "service",
			"name": "DB",
			"service": "d1-platform-worker",
			"entrypoint": "D1CustomBinding",
			"props": {
				"D1": {
					"$binding": {
						"type": "d1_database",
						"id": "<DATABASE_ID>"
					}
				},
				"TENANT_ID": "tenant-abc-123"
			}
		}
	]
}
```

This `curl` command uploads a User Worker through the Workers for Platforms dispatch API. It includes the compatibility flag and service binding metadata.

```bash
curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/<ACCOUNT_ID>/workers/dispatch/namespaces/<NAMESPACE>/scripts/<SCRIPT_NAME>" \
  -H "Content-Type: multipart/form-data" \
  -H "Authorization: Bearer $API_TOKEN" \
  -F 'metadata={
    "main_module": "worker.js",
    "compatibility_date": "<COMPATIBILITY_DATE>",
    "compatibility_flags": ["d1_custom_binding"],
    "bindings": [
      {
        "type": "service",
        "name": "DB",
        "service": "d1-platform-worker",
        "entrypoint": "D1CustomBinding",
        "props": {
          "D1": {
            "$binding": {
              "type": "d1_database",
              "id": "<DATABASE_ID>"
            }
          },
          "TENANT_ID": "tenant-abc-123"
        }
      }
    ]
  }' \
  -F 'worker.js=@worker.js'
```

For more information about multipart uploads, refer to [multipart upload metadata](/workers/configuration/multipart-upload-metadata/).

## Pass policy values

You can pass more resources and policy values through `props`. Use this for tenant IDs, query budgets, plan tiers, or analytics resources.

This example passes a D1 database, a tenant ID, a per-minute query limit, a plan tier, and an Analytics Engine dataset.

```json
{
	"props": {
		"D1": {
			"$binding": {
				"type": "d1_database",
				"id": "<DATABASE_ID>"
			}
		},
		"TENANT_ID": "tenant-abc-123",
		"MAX_QUERIES_PER_MIN": 1000,
		"PLAN_TIER": "enterprise",
		"ANALYTICS": {
			"$binding": {
				"type": "analytics_engine",
				"dataset": "<DATASET_NAME>"
			}
		}
	}
}
```

## Deploy the pattern

Use this sequence when you add custom D1 bindings to your platform.

<Steps>

1. Deploy the Platform Worker that exports the `D1CustomBinding` entrypoint.
2. Update your User Worker upload flow to add the `d1_custom_binding` compatibility flag.
3. Replace each direct D1 binding with a service binding named `DB`.
4. Pass the tenant's D1 database and policy values through `props`.
5. Redeploy existing User Workers that need platform-level D1 controls.
6. Verify that your Platform Worker logs each query before forwarding it.

</Steps>
