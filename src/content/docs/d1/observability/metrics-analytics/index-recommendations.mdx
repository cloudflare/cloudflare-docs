D1 Insights can recommend indexes for active [D1](/d1/) databases. Each recommendation includes validated `CREATE INDEX` SQL, the impacted queries, and the measured workload behind the recommendation.

An [index](/d1/best-practices/use-indexes/) helps D1 find rows without scanning an entire table. Fewer scanned rows can improve performance and reduce rows-read charges.

Indexes also use storage and add work to database writes. Review each recommendation before you change your schema.

## Availability

Index recommendations are available on the [Workers Paid plan](/workers/platform/pricing/) and are turned on by default. Recommendation generation uses [Workers AI](/workers-ai/).

Enterprise customers can opt in from the dashboard. No account team request is required.

## Opt in or out

Insights controls whether D1 sends your account's query data to Workers AI to generate recommendations.

When Insights is on, D1 generates and stores recommendations for active databases in your account. When Insights is off, D1 stops generating recommendations and hides existing recommendations in the dashboard and API.

Stored recommendations are kept and show again if you turn Insights back on. Opting out does not affect D1 query metrics, billing, or other D1 features.

<Tabs syncKey="d1InsightsOptIn">

2. Select the **Metrics** tab.

3. In the **Recommendations** card, open the settings menu and turn index recommendations on or off.

The setting applies to every database in your account and requires an account-level admin. Enterprise customers use the same toggle to opt in. When Insights is off, the card shows a disabled state.

</TabItem>

	--header "Content-Type: application/json" \

## Generate recommendations

When Insights is on, D1 evaluates active databases in the background. It stores recommendations for the dashboard, Cloudflare CLI (`cf`), Wrangler, and REST API.

D1 uses Workers AI to precompute recommendations where indexes provide measurable impact. On-demand recommendation generation is not supported.

Some databases may not have recommendations. This can happen when D1 does not have enough recent query activity, or when D1 does not find an index that should improve the measured workload.

```sh
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/d1/insights/recommendations?limit=20" \
	--header "Authorization: Bearer $CLOUDFLARE_API_TOKEN"
```

Fetch recommendations for one database with the `database_id` filter:

```sh
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/d1/insights/recommendations?database_id=$DATABASE_ID" \
	--header "Authorization: Bearer $CLOUDFLARE_API_TOKEN"
```

</TabItem>
</Tabs>

The `database_id` filter accepts one or more database IDs. Pass a comma-separated list or repeat the parameter, for example `?database_id=$DATABASE_ID_1,$DATABASE_ID_2`. You can pass up to 50 IDs. Results are paginated, and each page includes a `result_info.next_cursor` value.

If a database ID does not exist or belongs to another account, the response is an empty list.

If you use an API token, the token must have permission to read D1 databases and account analytics.

## View in the dashboard

Recommendations appear in the **Recommendations** card at the top of the **Metrics** tab for a database. The card shows up to 10 recommendations.

The D1 database list marks databases that have recommendations. Their actions menu also includes **View recommendations**, which links to the Metrics tab.

To find databases with recommendations from the API, add `recommendation_count` to the `fields` list on the database list request:

```sh
curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/d1/database?fields=uuid,name,recommendation_count" \
	--header "Authorization: Bearer $CLOUDFLARE_API_TOKEN"
```

`recommendation_count` is returned only when you request it and Insights is available for the account. A missing value means the count is unknown, not zero.

## Interpret a recommendation

Each recommendation includes a validated `CREATE INDEX` statement. The summary and reasoning identify the target table, columns, and query patterns.

Recommendation payloads contain these fields:

| Field | Description |
| --- | --- |
| `recommendations.items[].database_id` | Database identifier. |
| `recommendations.items[].database_name` | Database name. |
| `recommendations.items[].query_window.from` | Inclusive start of the query metrics window. |
| `recommendations.items[].query_window.to` | Exclusive end of the query metrics window. |
| `recommendations.items[].id` | Stable recommendation identifier. |
| `recommendations.items[].generated_at` | RFC 3339 timestamp for the completed evaluation. |
| `recommendations.items[].type` | Recommendation type, which is `index_suggestion`. |
| `recommendations.items[].priority` | Suggested review priority, either `high` or `low`. |
| `recommendations.items[].summary` | Short description of the recommended change. |
| `recommendations.items[].reasoning` | Performance bottleneck that produced the recommendation. |
| `recommendations.items[].suggestions[].kind` | Suggestion type, which is `index_creation`. |
| `recommendations.items[].suggestions[].sql` | Validated `CREATE INDEX` statement. |
| `recommendations.items[].impacted_queries` | Query patterns affected by the suggested index. |
| `result_info.next_cursor` | Cursor for the next page of results. |

Impacted query metrics come from D1 query analytics. They are not Workers AI estimates.

The following response recommends an index for `OrderDetail.OrderId`:

```json
{
	"success": true,
	"result": {
		"recommendations": {
			"items": [
				{
					"id": "9f8a7b6c-5d4e-4a21-9234-6f7890abcdef",
					"database_id": "7c9e2b14-3f6a-4d8e-9b21-5a0c8f3e6d47",
					"database_name": "orders-prod",
					"generated_at": "<GENERATED_AT>",
					"query_window": {
						"from": "<WINDOW_START>",
						"to": "<WINDOW_END>"
					},
					"type": "index_suggestion",
					"priority": "high",
					"summary": "Create an index on OrderDetail.OrderId",
					"reasoning": "Two query patterns join OrderDetail by OrderId.",
					"suggestions": [
						{
							"kind": "index_creation",
							"sql": "CREATE INDEX idx_OrderDetail_OrderId ON OrderDetail(OrderId);"
						}
					],
					"impacted_queries": [
						{
							"query": "SELECT * FROM OrderDetail WHERE OrderId = ?",
							"metrics": {
								"execution_count": 320,
								"total_rows_read": 1250000,
								"total_rows_written": 0,
								"p95_query_duration_ms": 42.8
							}
						}
					]
				}
			]
		},
		"result_info": {
			"next_cursor": null
		}
	},
	"errors": [],
	"messages": []
}
```

## Apply a recommendation

Apply recommended SQL through a [D1 migration](/d1/reference/migrations/). This stores the schema change with your application code.

<Steps>
1. Review the suggested SQL, target table, columns, and impacted queries.

2. From your Worker project directory, create a migration file:

   <PackageManagers
    type="exec"
    pkg="wrangler"
    args={"d1 migrations create <DATABASE_NAME> add_query_insights_index"}
   />

3. Add the suggested `CREATE INDEX` statement to the generated file.

   The migration should contain the reviewed statement:

   ```sql title="migrations/0001_add_query_insights_index.sql"
   CREATE INDEX idx_OrderDetail_OrderId ON OrderDetail(OrderId);
   ```

4. Apply the migration to your local database:

   <PackageManagers
    type="exec"
    pkg="wrangler"
    args={"d1 migrations apply <DATABASE_NAME> --local"}
   />

5. Test the impacted queries against your local database.

6. Apply the migration to the corresponding remote environment:

   <PackageManagers
    type="exec"
    pkg="wrangler"
    args={"d1 migrations apply <DATABASE_NAME> --remote --env <ENVIRONMENT>"}
   />
</Steps>

Confirm that your Wrangler configuration maps the database name to the intended environment. Omit `--env` when the binding uses your top-level configuration.

Repeat the local review and test process for each environment. Apply the migration remotely only after testing it against representative queries.
