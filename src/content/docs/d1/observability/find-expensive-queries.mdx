import { Tabs, TabItem } from "~/components";

A small number of databases and queries usually cause most of the rows read and written in an account. These rows are what you pay for, and these queries make your databases slow. A query is usually slow when it reads many more rows than it returns. A read query that runs many times also puts load on a database.

To find these databases and queries, use `wrangler d1 insights` or the [`cf sql query`](/analytics/sql-api/get-started/#use-the-cloudflare-cli) command of the Cloudflare CLI. `wrangler d1 insights` returns the top queries from the GraphQL Analytics API. For all its options, refer to [Query `insights`](/d1/observability/metrics-analytics/#query-insights). `cf sql query` sends SQL to the [SQL API](/analytics/sql-api/). You can change the SQL in the examples to get different results.

If you use an API token, the token must have the **Account Analytics Read** permission. Both commands return JSON, so an AI agent can run them and read the results.

The SQL examples use the `events.d1Queries` dataset. This dataset has one row for each D1 query, with the columns `databaseId`, `query`, `queryDurationMs`, `rowsRead`, `rowsReturned`, `rowsWritten`, and `error`. The value of `error` is an empty string when the query is successful.

:::note
The `events.d1Queries` dataset is sampled. The SQL API applies the sample weights to `COUNT`, `SUM`, and `AVG` automatically. Do not multiply values by `sampleInterval`. Give `sampleInterval` as the weight only to functions that have a weight argument, such as `quantileWeighted`. For more information, refer to [Adaptive sampling](/analytics/sql-api/sql-reference/functions/#adaptive-sampling).
:::

## Find the most expensive databases

Find the databases that read the most rows in your account during the last 7 days:

<Tabs syncKey="d1Insights">
<TabItem label="Wrangler">

```sh
npx wrangler d1 insights --sort-by=reads --time-period=7d --limit=20 --json
```

`wrangler d1 insights` returns queries, not databases. Each result includes the `databaseId` of the database that ran the query. Add the `totalRowsRead` of the results that have the same `databaseId` to find the most expensive databases.

</TabItem>
<TabItem label="Cloudflare CLI">

```sh
npx cf sql query --scope-account <account_id> "
  SELECT
    databaseId,
    COUNT(*) AS numberOfTimesRun,
    SUM(rowsRead) AS totalRowsRead,
    SUM(rowsWritten) AS totalRowsWritten,
    AVG(queryDurationMs) AS avgDurationMs
  FROM events.d1Queries
  WHERE timestamp >= NOW() - INTERVAL '7' DAY
    AND error = ''
  GROUP BY databaseId
  ORDER BY totalRowsRead DESC
  LIMIT 10
"
```

To find the databases that write the most rows, change `ORDER BY` to `totalRowsWritten`. To find the slowest databases, change `ORDER BY` to `avgDurationMs`.

</TabItem>
</Tabs>

To get the name of a database, run `npx wrangler d1 info <database_id>`. To find out how rows read and rows written affect your bill, refer to [Pricing](/d1/platform/pricing/).

2. Get the top queries for the database that you want to fix. Use the `databaseId` from step 1, or from [Find the most expensive databases](#find-the-most-expensive-databases):

   <Tabs syncKey="d1Insights">
   <TabItem label="Wrangler">

   ```sh
   npx wrangler d1 insights <database_id> --sort-by=reads --time-period=7d --json
   ```

   </TabItem>
   <TabItem label="Cloudflare CLI">

   ```sh
   npx cf sql query --scope-account <account_id> "
     SELECT
       query,
       COUNT(*) AS numberOfTimesRun,
       SUM(rowsRead) AS totalRowsRead,
       AVG(rowsRead) AS avgRowsRead,
       AVG(queryDurationMs) AS avgDurationMs,
       quantileWeighted(0.95)(queryDurationMs, sampleInterval) AS p95DurationMs,
       if(SUM(rowsRead) = 0, 0.0,
          SUM(rowsReturned) / SUM(rowsRead)) AS queryEfficiency
     FROM events.d1Queries
     WHERE timestamp >= NOW() - INTERVAL '7' DAY
       AND databaseId = '<database_id>'
       AND error = ''
     GROUP BY query
     ORDER BY totalRowsRead DESC
     LIMIT 5
   "
   ```

   </TabItem>
   </Tabs>

3. Find the queries with a high `avgRowsRead` and a `queryEfficiency` much lower than `1`. These queries read many rows to return a small number of rows. Usually, a column in the `WHERE`, `JOIN`, or `ORDER BY` clause does not have an index.

   In the example output in step 1, the `JOIN` query reads 1,244,521 rows each time it runs, and its `queryEfficiency` is approximately `0.000016`. The `OrderDetail.OrderId` column in the `JOIN` clause does not have an index.

4. Find the index that fixes the query. To find the correct fix for each query pattern, refer to [Indexes and your bill](/d1/best-practices/use-indexes/#indexes-and-your-bill). For the example query, add an index on the `OrderId` column of the `OrderDetail` table.

5. Create a [migration](/d1/reference/migrations/) for the index. The database must be in your [Wrangler configuration file](/d1/get-started/#3-bind-your-worker-to-your-d1-database):

   ```sh
   npx wrangler d1 migrations create <database_name> add_orderdetail_orderid_index
   ```

   ```sh output
   ✅ Successfully created Migration '0001_add_orderdetail_orderid_index.sql'!
   ```

   The number at the start of the file name depends on the migrations that you already have.

6. Add the `CREATE INDEX` statement to the new migration file:

   ```sql title="migrations/0001_add_orderdetail_orderid_index.sql"
   -- Migration number: 0001 	 2026-10-29T15:42:06.092Z
   CREATE INDEX IF NOT EXISTS idx_orderdetail_orderid ON OrderDetail (OrderId);
   ```

7. Apply the migration to your remote database:

   ```sh
   npx wrangler d1 migrations apply <database_name> --remote
   ```

   ```sh output
   ┌────────────────────────────────────────┬────────┐
   │ name                                   │ status │
   ├────────────────────────────────────────┼────────┤
   │ 0001_add_orderdetail_orderid_index.sql │ ✅     │
   └────────────────────────────────────────┴────────┘
   ```

8. Make sure that D1 uses the new index. Put `EXPLAIN QUERY PLAN` in front of the query and run it:

   ```sh
   npx wrangler d1 execute <database_name> --remote --command="EXPLAIN QUERY PLAN <query>"
   ```

   The line for the table that you added the index to should show `SEARCH ... USING INDEX`, not `SCAN`. For the example query, `SCAN OrderDetail` changes to `SEARCH OrderDetail USING INDEX idx_orderdetail_orderid (OrderId=?)`. For more information, refer to [Test an index](/d1/best-practices/use-indexes/#test-an-index).

9. Make sure that the number of rows read decreases. Run the command from step 2 again with a shorter time period, such as `--time-period=1h` or `INTERVAL '1' HOUR`.

   The results include all the queries in the time period. Queries that ran before you added the index increase the totals of a long time period.

## Find queries to cache

A read query that runs many times often returns the same data each time. If you keep the result in a cache, your Worker does not send the query to D1 each time. This decreases the load on your database and the number of rows read.

1. Find the queries that run the most in your account during the last day:

   <Tabs syncKey="d1Insights">
   <TabItem label="Wrangler">

   ```sh
   npx wrangler d1 insights --sort-by=count --time-period=1d --json
   ```

   </TabItem>
   <TabItem label="Cloudflare CLI">

   ```sh
   npx cf sql query --scope-account <account_id> "
     SELECT
       databaseId,
       query,
       COUNT(*) AS numberOfTimesRun,
       SUM(rowsRead) AS totalRowsRead,
       AVG(queryDurationMs) AS avgDurationMs
     FROM events.d1Queries
     WHERE timestamp >= NOW() - INTERVAL '1' DAY
       AND rowsWritten = 0
       AND error = ''
     GROUP BY databaseId, query
     ORDER BY numberOfTimesRun DESC
     LIMIT 5
   "
   ```

   </TabItem>
   </Tabs>

   The SQL query returns only queries that do not write rows. The Wrangler output includes all queries. To find the read queries in the Wrangler output, look for a `totalRowsWritten` of `0`.

2. Find the queries with a high `numberOfTimesRun` that return the same data each time. Cache the result if the data does not change frequently, or if your application can show data that is a short time old.

3. Keep the result in [Workers KV](/kv/) or the [Cache API](/workers/runtime-apis/cache/). Set an expiration time that agrees with how frequently the data changes.

If a query must always return the newest data, do not cache it.
