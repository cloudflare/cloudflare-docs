D1 allows you to capture exceptions and log errors returned when querying a database. To debug D1, you will use the same tools available when [debugging Workers](/workers/observability/).

D1's [`stmt.`](/d1/worker-api/prepared-statements/) and [`db.`](/d1/worker-api/d1-database/) methods throw an [Error object](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Error) whenever an error occurs. To capture exceptions, log the `e.message` value.

For example, the code below has a query with an invalid keyword - `INSERTZ` instead of `INSERT`:

```js
try {
    // This is an intentional misspelling
    await db.exec("INSERTZ INTO my_table (name, employees) VALUES ()");
} catch (e: any) {
    console.error({
        message: e.message
    });
}
```

The code above throws the following error message:

```json
{
	"message": "D1_EXEC_ERROR: Error in line 1: INSERTZ INTO my_table (name, employees) VALUES (): sql error: near \"INSERTZ\": syntax error in INSERTZ INTO my_table (name, employees) VALUES () at offset 0"
}
```

:::note
Prior to [`wrangler` 3.1.1](https://github.com/cloudflare/workers-sdk/releases/tag/wrangler%403.1.1), D1 JavaScript errors used the [cause property](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Error/cause) for detailed error messages.

To inspect these errors when using older versions of `wrangler`, you should log `error?.cause?.message`.
:::

## Automatic retries

D1 detects read-only queries and automatically attempts up to two retries to execute those queries in the event of failures with retryable errors.

D1 ensures that any retry attempt does not cause database writes, making the automatic retries safe from side-effects, even if a query causing modifications slips through the read-only detection. D1 achieves this by checking for modifications after every query execution, and if any write occurred due to a retry attempt, the query is rolled back.

:::note
Only read-only queries (queries containing only the following SQLite keywords: `SELECT`, `EXPLAIN`, `WITH`) are retried. Queries containing any [SQLite keyword](https://sqlite.org/lang_keywords.html) that leads to database writes are not retried.
:::

## D1 binding timeout behavior

D1 binding methods — `run()`, `all()`, `first()`, and `batch()` — do not accept a timeout option or an `AbortSignal`. There is no per-call timeout built into the D1 binding client.

Workers have no wall-time limit on incoming HTTP requests while the client connection is open — see [Workers limits](/workers/platform/limits/). If the D1 database is temporarily unreachable, a D1 binding call blocks until the operation completes, an internal limit is reached, or the Worker is terminated by an external event such as the client disconnecting.

To limit how long your Worker waits on a D1 call, use `Promise.race` with a timer:

```js
const timeout = new Promise((_, reject) =>
  setTimeout(() => reject(new Error('D1 call timed out')), 5000)
);
const result = await Promise.race([
  db.prepare('SELECT 1').first(),
  timeout,
]);
```

:::caution[Write operations and Promise.race]
`Promise.race` bounds how long your Worker waits — it does not cancel the D1 query. A write that loses the race may still commit in the background. Always confirm the outcome of a write before retrying to avoid duplicate writes.
:::

## API error codes

In addition to the `D1_ERROR` constants above, D1 returns numeric error codes on certain failures. Use the following table to identify the cause and recommended action.

| Code  | Name                          | Common cause                                                                                     | Recommended action                                                                                                                                                                                                   |
| ----- | ----------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 7403  | Service authorization failure | The API token or Wrangler OAuth session does not have sufficient scope for the operation.        | Verify the token has the required permission for the endpoint. Run `wrangler login` to refresh the Wrangler OAuth session.                                                                                            |
| 7404  | Database not found            | The database UUID does not exist in the account, or the binding is misconfigured.                | Confirm the `database_id` in your `wrangler.toml` matches the database UUID shown in the Cloudflare dashboard.                                                                                                       |
| 7406  | Limit exceeded                | The account has reached the maximum number of D1 databases allowed on its plan.                  | Review your [current limits](/d1/platform/limits/). Enterprise accounts with a custom database limit should contact Cloudflare support if the limit is not reflected.                                                  |
| 7429  | DB overloaded                 | Too many concurrent requests are queued, or queued requests are taking too long to complete.     | Retry with exponential backoff and jitter. If the error recurs while SQL execution time (`queryBatchTimeMs`) is fast and your workload is low, check the [Cloudflare System Status](https://www.cloudflarestatus.com/) page. |
| 7500  | Internal error                | A platform-side storage event made the database temporarily unavailable.                         | Check the [Cloudflare System Status](https://www.cloudflarestatus.com/) page. Retry with exponential backoff. If the database remains unavailable after the incident resolves, [contact Cloudflare support](/support/contacting-cloudflare-support/). |
| 10000 | Authentication error          | The API token does not have the required scope for the endpoint.                                 | Check the required permission for the endpoint in the [API reference](/api/resources/d1/) and create a token with the correct scope. See [error 10000 and the export endpoint](#error-10000-and-the-export-endpoint). |

### Error 7429 and analytics

If you receive error 7429 while your analytics show fast SQL execution times, the error may originate from a server-side platform event rather than your application's workload. The `queryBatchTimeMs` metric measures only SQL execution time inside the database, not the total time a request spends waiting to reach SQL. Check the [Cloudflare System Status](https://www.cloudflarestatus.com/) page before reducing application concurrency.

### Error 10000 and the export endpoint

Error 10000 from the D1 export endpoint means the API token does not have the required permission for that endpoint.

To resolve this:

1. Go to **API Tokens** in your Cloudflare dashboard. <DashButton url="/profile/api-tokens" />
2. Create a new token with the permission required for D1 export — check [Import and export data](/d1/best-practices/import-export-data/) for the required permission.
3. Use that token for the export request.
