A sandbox runs code you do not trust. A model might generate the code, a user might write it, or a package might bring it in as a dependency. Cloudflare isolates the sandbox from your Worker and from other sandboxes. For more information about that isolation, refer to [Sandboxes on Cloudflare](/sandbox/).

Isolation does not limit what the code does inside its own sandbox. The safe assumption is that the code uses everything it can reach there, including the files, credentials, and network access your Worker provides.

## Everything in one sandbox is shared

Every process in a Container runs on the same Linux system. The processes can read the same files, see each other, and connect to the same `localhost` ports. Code loaded into one Dynamic Worker shares its memory in the same way.

A separate Linux user does not keep a command away from files. In a deployed sandbox, every process has the same Linux capabilities as `root`, so file permissions do not restrict it, and it can switch back to `root`. For more information, refer to the [`exec()` `user` option](/durable-objects/api/container/#exec).

The sandbox is therefore the smallest unit of trust. When two users share a sandbox, each user's code can read the other's work. A sandbox for each user, or for each job, keeps one user's code away from another user's files and credentials.

## Code can read what you put in its sandbox

Consider a coding agent that clones a private repository, installs its dependencies, and runs its tests. If your Worker puts a token in the clone URL, Git saves that URL in the repository's `.git/config` file. The tests, and every dependency they load, run with the same access as the agent. Any of that code can read the token.

<SandboxCredentials client:visible>

Inside a coding agent's sandbox, the agent runs `git pull`, and code from a test dependency reads `.git/config`. With the token in the clone URL, the dependency reads the token from that file. With the token in your Worker, the file holds no token, your Worker adds the token to requests for `github.com`, and `git pull` still works.

</SandboxCredentials>

Environment variables, command arguments, and files your Worker writes work the same way. Once a value is in the sandbox, all the code there can read it and send it anywhere the sandbox can reach.

Credentials are safer outside the sandbox. A Container can send its request without the credential, and an outbound handler in your Worker adds the credential after the request leaves the sandbox. A Dynamic Worker can receive a method that uses the credential in your Worker and returns only the result. The code uses the service without holding the key. The method or handler also decides which requests to make, so it limits what the code can do with the service. For both patterns, refer to [Call an authenticated API from a sandbox](/sandbox/network/call-an-authenticated-api/).

## The sandbox name decides what a request reaches

A sandbox keeps its files while its instance runs. A snapshot saves those files, including a token in `.git/config`, and restoring the snapshot brings them back. Your Worker reaches the same sandbox whenever it calls `getByName()` with the same name.

So the name decides which sandbox, and which saved files, a request reaches. The name does not show who sent the request. Your Worker authenticates the caller and derives the sandbox name from that identity. Reusing a name or a snapshot for someone else gives them the earlier user's files. The how-to guides read the name from the URL only to keep the examples short.

For more information about what a sandbox keeps between instances, refer to [Sandbox lifetime](/sandbox/concepts/lifetime/#snapshots-carry-files-to-the-next-instance).

## Every opening is also a way out

A Container starts with `enableInternet: false` by default, so it cannot make outbound requests. A Dynamic Worker has the network access of your Worker unless you load it with `globalOutbound: null`, which makes `fetch()` and `connect()` throw.

Each destination you allow gives the code a way to send out what it can read. Turning on Internet access so `npm install` can download packages also lets a dependency send the token to any server. An outbound handler in your Worker can allow the package registry alone, which narrows where the data can go. Keep Internet access off when you use one: handlers see HTTP on port `80` and HTTPS on port `443`, and with Internet access on, connections to other ports go out directly. To route requests through your Worker, refer to [`interceptOutboundHttps()`](/durable-objects/api/container/#interceptoutboundhttps) for Containers and [Egress control](/dynamic-workers/usage/egress-control/) for Dynamic Workers.

## Output carries the same risk

Results, files, and HTTP responses from a sandbox come from the code you do not trust. They need the same checks as user input before your application stores them, acts on them, or shows them to someone else.

A web preview goes further, because the browser runs it. When your Worker forwards a page from a sandbox, the page runs in the visitor's browser under the hostname that served it. On your application's hostname, the page can use your application's cookies and call its APIs. A separate hostname for previews keeps the page away from both. For an example, refer to [Serve previews on their own hostnames](/sandbox/previews/serve-previews-on-their-own-hostnames/).
