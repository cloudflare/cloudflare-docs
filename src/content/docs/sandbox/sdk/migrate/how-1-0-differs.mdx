In Sandbox SDK 0.12, the `Sandbox` class from the package was your Durable Object, and it talked to a server that ran inside the container. In 1.0, a Durable Object class that you write starts the container and calls it through `this.ctx.container`.

Most differences follow from that change. Work that the `Sandbox` class did moves into your class. Work that the SDK server did becomes commands that your class runs in the container.

<SandboxSdkVersions client:visible>

In 0.12, your Worker calls `getSandbox()`, and the `Sandbox` class from the package starts the container, keeps it running, and manages previews and backups. The container runs the `cloudflare/sandbox` image, with the SDK server and bash sessions. In 1.0, your Worker calls `getByName()`, and your own Durable Object does the same jobs. The container runs your image and your commands, plus the `sandbox-shim` helper when you use `Files`.

</SandboxSdkVersions>

## Your class starts the container

In 0.12, `getSandbox()` returned a stub of the `Sandbox` class. The first call to that stub started the container. The image and instance type came from your Wrangler configuration, so every sandbox of a class ran the same image.

In 1.0, your class calls [`start()`](/durable-objects/api/container/#start) when it needs a container. Each call passes the image, and it can also pass the instance type and the entrypoint. Two sandboxes of the same class can run different images.

For the steps, refer to [Move to your own Durable Object](/sandbox/sdk/migrate/your-own-durable-object/).

## Your class keeps the container running

In 0.12, `sleepAfter` and `keepAlive` decided how long a sandbox kept running, and the package renewed that time on every call.

In 1.0, [`setInactivityTimeout()`](/durable-objects/api/container/#setinactivitytimeout) sets how long the container keeps running after your Durable Object becomes inactive, up to 6 hours. The timeout does not survive a restart of the Durable Object, so your class sets it on every request. A command that runs in the container does not count as activity.

A deploy also works differently. In 0.12, a deploy that changed the image replaced running containers. In 1.0, a deploy restarts your Durable Objects, and running containers keep running. A new image applies from the next `start()`.

For more information, refer to [Sandbox lifetime](/sandbox/concepts/lifetime/).

## A container has no Internet access by default

In 0.12, containers reached the Internet unless the class set `enableInternet` to `false`. Outbound rules were properties of the class, such as `allowedHosts` and `Sandbox.outboundByHost`.

In 1.0, a container reaches the Internet only when `start()` passes `enableInternet: true`. To let a container reach one hostname, your class sends requests for that hostname to a Worker entrypoint with [`interceptOutboundHttps()`](/durable-objects/api/container/#interceptoutboundhttps). The entrypoint can add credentials that the container never sees. Each new container needs its rules registered again.

For the steps, refer to [Move outbound rules](/sandbox/sdk/migrate/outbound-traffic/).

## Commands run without a shell

In 0.12, `exec("npm test")` sent a line of text to a bash session in the container. The default session kept the working directory and exported variables from one call to the next.

In 1.0, [`exec()`](/durable-objects/api/container/#exec) takes an array of arguments and starts that process directly. No shell reads the arguments, so pipes, `&&`, and `$VAR` work only in a shell that you start, such as `["sh", "-c", "npm ci && npm test"]`. Each call sets its own `cwd` and `env`, and nothing carries over to the next call.

`exec()` returns a handle to the process. The process keeps running when your code drops the handle, and the package keeps no list of processes. To find a process later, your class stores its own record.

For the steps, refer to [Change commands and file calls](/sandbox/sdk/migrate/commands-and-files/) and [Move background processes](/sandbox/sdk/migrate/background-processes/).

## The image is yours

In 0.12, an image had to start from `docker.io/cloudflare/sandbox`, because the SDK server in that image answered every call. The image also provided the tools that commands used, such as Python and Git.

In 1.0, `exec()` runs commands in any Linux image. `cloudflare/debian-trixie` runs without a Dockerfile and includes Node.js 24 and npm, but no Python or Git. Your image needs every tool that your commands use.

The `Files` and `S3Mounts` classes from `@cloudflare/sandbox` 1.0 need one file from the package in the image: the `sandbox-shim` helper. For the `COPY` line, refer to [`@cloudflare/sandbox` requirements](/sandbox/reference/#requirements).

## Your class stores the state

In 0.12, the `Sandbox` class kept its own records in Durable Object storage, such as the sandbox name, the default session, exposed ports, and tunnels.

In 1.0, the package writes nothing to storage. A preview token, a process record, or a snapshot ID exists only if your class stores it.

The keys that 0.12 wrote stay in storage after the switch. Code for 1.0 never reads them, and they have no effect.

## Errors and time limits are yours

In 0.12, the package retried a container start for about two minutes, applied its own time limits while the container started, and threw its own error classes, such as `ContainerUnavailableError`.

In 1.0, the package sets no time limits and retries nothing. An error from `start()` or `exec()` comes from the platform. `Files` throws `SandboxFileError`, with the Linux error name in `code`.

To limit how long a command runs, pass an `AbortSignal` to `exec()`. A call that fails or is cancelled may already have changed files in the container, so your code decides whether to repeat it.

## Where each 0.x feature goes

To predict what a 0.x feature becomes, find the part that did its work in 0.12:

- Work that the `Sandbox` class did, such as lifetime, previews, tunnels, backups, and tracking processes, becomes code in your Durable Object class, often with records in its storage.
- Work that the SDK server did, such as commands, sessions, and file calls, becomes `exec()` calls, or `Files` calls through `sandbox-shim`.
- Settings in the class or the Wrangler configuration, such as the image, Internet access, and outbound rules, become options to `start()` and outbound handlers.

Some 0.x features have no equivalent in 1.0. For the list, refer to [What changes in your code](/sandbox/sdk/migrate/#what-changes-in-your-code).
