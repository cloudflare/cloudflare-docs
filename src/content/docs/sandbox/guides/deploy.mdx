This guide helps you deploy a Sandbox SDK Worker so both the **Worker package** and the **sandbox container image** update safely.

Sandbox runs on [Containers](/containers/). A deploy is the Containers deploy path, plus Sandbox rules for keeping the SDK package and image on the same release line.

This page is **not** custom-domain setup for preview URLs. If you use `exposePort()`, see [Configure preview URLs on a custom domain](/sandbox/guides/preview-urls-custom-domain/).

:::note[Coming soon: Sandbox SDK 1.0]
This guide targets today's stable `@cloudflare/sandbox` package.

On **`@cloudflare/sandbox@next`**, keep the Worker package and container image on the same preview line. Breaking protocol cutovers use an immediate container rollout — see [Migrate](/sandbox/1-0-preview/migrate/#deploy-the-cutover).
:::

## Before you start

- A working Sandbox app from [Get started](/sandbox/get-started/) (or an existing project)
- [Docker](https://www.docker.com/) running locally if your Wrangler `image` points at a Dockerfile
- Familiarity with your [Wrangler configuration](/sandbox/configuration/wrangler/)

## What deploy changes

On a full deploy:

1. Wrangler uploads the Worker. The new Worker version can become active immediately.
2. Wrangler builds and pushes the sandbox image (Dockerfile) or resolves a registry image.
3. Container instances roll out to the new image. The default is a **gradual** rollout.

Worker code and sandbox instances can temporarily disagree during a gradual rollout. Background: [Containers deployments](/containers/deployments/).

| Command                                          | Worker       | Sandbox image / instances                         |
| ------------------------------------------------ | ------------ | ------------------------------------------------- |
| `wrangler deploy` (default)                      | Active       | Build/push when needed; gradual instance rollout  |
| `wrangler deploy --containers-rollout=immediate` | Active       | Build/push when needed; one-step instance rollout |
| `wrangler deploy --containers-rollout=none`      | Active       | No image build; no instance rollout               |
| `wrangler versions upload`                       | Version only | No image build; no instance rollout               |

## Keep package and image aligned

The Worker depends on `@cloudflare/sandbox` (or `@cloudflare/sandbox@next`). The container image must come from the **same release line** as that package (for example the Dockerfile and base image tags your template or docs prescribe for that version).

After you bump the npm package:

1. Update the Dockerfile (or image reference) for the same line.
2. Deploy with a command that publishes the new image (`wrangler deploy`, not `versions upload` alone).
3. For breaking Worker↔image protocol changes, use an [immediate rollout](#when-to-use-an-immediate-rollout).

Do not mix a new Worker package with an old sandbox image, or the reverse.

## Deploy from your machine

1. Confirm Docker is running if you build from a Dockerfile.
2. From the project root:

   <PackageManagers type="exec" pkg="wrangler" args="deploy" />

3. Wait for Wrangler to finish. The first Containers deploy can take several minutes while the image provisions. See [First deploy](/containers/deployments/#first-deploy).
4. Confirm the Worker URL responds, then exercise a sandbox path (for example run a command or open a route that uses the sandbox).
5. Optionally list containers and images:

   <PackageManagers type="exec" pkg="wrangler" args="containers list" />

   <PackageManagers type="exec" pkg="wrangler" args="containers images list" />

More verification signals: [Confirm a deploy](/containers/deployments/#confirm-a-deploy).

## When to use an immediate rollout

Use gradual rollouts (the default) when Worker and image changes stay backward compatible.

Use an immediate container rollout when they must cut over together:

```sh
npx wrangler deploy --containers-rollout=immediate
```

Typical cases:

- Sandbox SDK major/preview line cutover (stable → `@next`, or other breaking protocol bumps) — detailed steps in [Migrate](/sandbox/1-0-preview/migrate/#deploy-the-cutover)
- Image entrypoint or control-plane changes the old Worker cannot drive
- Any change where mixed old/new pairs fail hard

[`rollout_active_grace_period`](/workers/wrangler/configuration/#containers) still applies. Leave it at `0` for hard cutovers unless you intentionally drain longer. See [Containers rollouts](/containers/platform-details/rollouts/).

## Deploy with Workers Builds

[Workers Builds](/workers/ci-cd/builds/) runs your configured deploy command. It does not add a separate Sandbox pipeline.

| Branch         | Default command                | Sandbox image updated?    |
| -------------- | ------------------------------ | ------------------------- |
| Production     | `npx wrangler deploy`          | Yes (full container path) |
| Non-production | `npx wrangler versions upload` | **No**                    |

Preview builds can therefore run new Worker code against the **image from the last full deploy**. Keep APIs compatible across that gap, or run image-changing deploys with `wrangler deploy` on the environment that should receive them.

Dockerfile builds work in the Builds environment during `wrangler deploy`. Full guide: [Deploy Containers with Workers Builds](/containers/deploy-with-workers-builds/).

## Preview URLs are a separate task

Deploying the Worker and image does **not** configure wildcard DNS for `exposePort()` preview URLs. `.workers.dev` is enough when you do not need those URLs.

To serve preview URLs on your domain: [Configure preview URLs on a custom domain](/sandbox/guides/preview-urls-custom-domain/).
