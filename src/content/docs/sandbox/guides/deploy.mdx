This guide covers what is specific to deploying a [Sandbox](/sandbox/) app: keeping the Worker package and sandbox container image aligned, choosing a rollout when they must cut over together, and avoiding preview CI skew.

Sandbox runs on [Containers](/containers/). Platform deploy behavior — what `wrangler deploy` changes, version skew, readiness checks, and Workers Builds — is documented once under Containers:

- [Container deployments](/containers/deployments/)
- [Rollouts](/containers/platform-details/rollouts/)
- [Deploy Containers with Workers Builds](/containers/deploy-with-workers-builds/)

This page is **not** custom-domain setup for `exposePort()` preview URLs. That is a separate task: [Configure preview URLs on a custom domain](/sandbox/guides/preview-urls-custom-domain/).

:::note[Coming soon: Sandbox SDK 1.0]
This guide targets today's stable `@cloudflare/sandbox` package.

On **`@cloudflare/sandbox@next`**, keep the Worker package and container image on the same preview line. Breaking protocol cutovers use an immediate container rollout — see [Migrate](/sandbox/1-0-preview/migrate/#deploy-the-cutover).
:::

## Before you start

- A working Sandbox app from [Get started](/sandbox/get-started/) (or an existing project)
- [Docker](https://www.docker.com/) running locally if your Wrangler `image` points at a Dockerfile
- Familiarity with your [Wrangler configuration](/sandbox/configuration/wrangler/)

## Keep package and image on the same release line

The Worker depends on `@cloudflare/sandbox` (or `@cloudflare/sandbox@next`). The container image must come from the **same release line** as that package — the Dockerfile and base image tags your template or docs prescribe for that version.

After you bump the npm package:

1. Update the Dockerfile (or image reference) for the same line.
2. Publish the new image with a full deploy (`wrangler deploy`), not `wrangler versions upload` alone.
3. For breaking Worker↔image protocol changes, use an [immediate rollout](#when-to-use-an-immediate-rollout).

Do not mix a new Worker package with an old sandbox image, or the reverse.

Which commands build images or roll instances is listed under [Container deployments](/containers/deployments/#which-commands-change-which-artifacts).

## Deploy from your machine

1. Confirm Docker is running if you build from a Dockerfile.
2. From the project root:

   <PackageManagers type="exec" pkg="wrangler" args="deploy" />

3. Wait for Wrangler to finish. The first Containers deploy can take several minutes while the image provisions. See [First deploy](/containers/deployments/#first-deploy).
4. Confirm the Worker URL responds, then exercise a sandbox path (for example run a command or open a route that uses the sandbox).
5. Optionally list containers and images:

   <PackageManagers type="exec" pkg="wrangler" args="containers list" />

   <PackageManagers type="exec" pkg="wrangler" args="containers images list" />

Readiness checks: [Confirm a deploy](/containers/deployments/#confirm-a-deploy).

## When to use an immediate rollout

Use the default gradual rollout when Worker and image changes stay backward compatible.

Use an immediate container rollout when they must cut over together:

```sh
npx wrangler deploy --containers-rollout=immediate
```

Typical Sandbox cases:

- SDK major or preview line cutover (stable → `@next`, or other breaking protocol bumps) — detailed steps in [Migrate](/sandbox/1-0-preview/migrate/#deploy-the-cutover)
- Image entrypoint or control-plane changes the old Worker cannot drive
- Any change where mixed old/new package and image pairs fail hard

[`rollout_active_grace_period`](/workers/wrangler/configuration/#containers) still applies. Leave it at `0` for hard cutovers unless you intentionally drain longer. See [Rollouts](/containers/platform-details/rollouts/).

## Workers Builds

[Workers Builds](/workers/ci-cd/builds/) runs your configured deploy command. It does not add a Sandbox-specific pipeline.

- Production defaults to `npx wrangler deploy` (full container path, including Dockerfile builds in the Builds environment).
- Non-production defaults to `npx wrangler versions upload` (Worker version only; **sandbox image does not update**).

Preview builds can therefore run new Worker code — and a newer `@cloudflare/sandbox` package — against the **image from the last full deploy**. Keep package and image compatible across that gap, or validate image-changing deploys on a non-production Worker or environment. Do not point the production Worker's preview deploy command at `wrangler deploy` to "get a new image" on a feature branch.

Full CI setup: [Deploy Containers with Workers Builds](/containers/deploy-with-workers-builds/).

## Preview URLs are a separate task

Deploying the Worker and image does **not** configure wildcard DNS for `exposePort()` preview URLs. `.workers.dev` is enough when you do not need those URLs.

To serve preview URLs on your domain: [Configure preview URLs on a custom domain](/sandbox/guides/preview-urls-custom-domain/).
