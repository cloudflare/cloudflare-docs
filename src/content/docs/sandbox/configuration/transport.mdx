Configure how the Sandbox SDK communicates with containers using transport modes.

## Overview

The Sandbox SDK supports two transport modes for SDK-container communication:

- **HTTP transport** (default) - Standard HTTP requests for each operation
- **WebSocket transport** - Persistent connection that multiplexes all operations over a single WebSocket

## When to use WebSocket transport

Use WebSocket transport when running sandboxes inside Workers or Durable Objects to avoid sub-request limits.

### Sub-request limits

Cloudflare Workers and Durable Objects have [sub-request limits](/workers/platform/limits/#subrequests):

- **Workers**: 50 sub-requests per invocation (1000 with higher limits)
- **Durable Objects**: 50 sub-requests per WebSocket message

With HTTP transport (default), each SDK operation (like `exec()`, `readFile()`, `writeFile()`) consumes one sub-request. Applications that make many sandbox operations can quickly hit these limits.

### How WebSocket transport helps

WebSocket transport establishes a single persistent connection to the container and multiplexes all SDK operations over it. This counts as only **one sub-request** regardless of how many sandbox operations you perform.

**Example without WebSocket transport:**

```typescript
// Each operation = 1 sub-request (4 total)
await sandbox.exec("python setup.py");
await sandbox.writeFile("/app/config.json", config);
await sandbox.exec("python process.py");
const result = await sandbox.readFile("/app/output.txt");
```

With HTTP transport, this uses **4 sub-requests**.

**Example with WebSocket transport:**

```typescript
// All operations multiplexed over single WebSocket (1 sub-request total)
await sandbox.exec("python setup.py");
await sandbox.writeFile("/app/config.json", config);
await sandbox.exec("python process.py");
const result = await sandbox.readFile("/app/output.txt");
```

With WebSocket transport, this uses **1 sub-request** total.

## Configuration

Set the `SANDBOX_TRANSPORT` environment variable to configure transport mode.

### HTTP transport (default)

HTTP transport is the default and requires no configuration:

<WranglerConfig>
```jsonc
{
	"name": "my-sandbox-worker",
	"main": "src/index.ts",
	"compatibility_date": "2025-10-13",
	"containers": [
		{
			"class_name": "Sandbox",
			"image": "./Dockerfile",
		},
	],
	"durable_objects": {
		"bindings": [
			{
				"class_name": "Sandbox",
				"name": "Sandbox",
			},
		],
	},
}
```
</WranglerConfig>

### WebSocket transport

Enable WebSocket transport by setting the `SANDBOX_TRANSPORT` environment variable:

<WranglerConfig>
```jsonc
{
	"name": "my-sandbox-worker",
	"main": "src/index.ts",
	"compatibility_date": "2025-10-13",
	"containers": [
		{
			"class_name": "Sandbox",
			"image": "./Dockerfile",
			"environment": {
				"SANDBOX_TRANSPORT": "websocket"
			}
		},
	],
	"durable_objects": {
		"bindings": [
			{
				"class_name": "Sandbox",
				"name": "Sandbox",
			},
		],
	},
}
```
</WranglerConfig>

## Transport behavior

### Connection lifecycle

**HTTP transport:**
- Creates a new HTTP request for each operation
- No persistent connection
- Stateless - each request is independent

**WebSocket transport:**
- Establishes connection on first sandbox operation
- Maintains persistent connection for all subsequent operations
- Connection closed when sandbox sleeps or is evicted
- Automatically reconnects if needed

### Streaming support

Both transports support streaming operations (like `exec()` with real-time output):

- **HTTP transport** - Uses Server-Sent Events (SSE)
- **WebSocket transport** - Uses WebSocket streaming messages

The SDK handles streaming differences automatically - your code remains identical regardless of transport mode.

### Error handling

Both transports provide identical error handling. Network errors are automatically retried with exponential backoff.

**WebSocket-specific errors:**

- Connection failures automatically fall back to reconnection
- The SDK transparently handles WebSocket disconnections
- Operations are never lost due to connection issues

## Performance considerations

### Latency

**HTTP transport:**
- Higher latency for many small operations (connection overhead per request)
- Better for single large operations
- Suitable for low-frequency sandbox usage

**WebSocket transport:**
- Lower latency for many operations (connection reuse)
- Small overhead for initial connection establishment
- Better for high-frequency sandbox usage

### Memory usage

**HTTP transport:**
- Minimal memory usage
- No persistent connection state

**WebSocket transport:**
- Small memory overhead for persistent connection
- Negligible impact on Worker/Durable Object memory limits

## Choosing a transport

Use this decision guide:

| Scenario | Recommended Transport |
|----------|----------------------|
| Making many sandbox operations per request | WebSocket |
| Running inside Workers/Durable Objects | WebSocket |
| Approaching sub-request limits | WebSocket |
| Simple, infrequent sandbox usage | HTTP (default) |
| Running outside Cloudflare (self-hosted) | HTTP (default) |

:::note[Default is fine for most cases]
HTTP transport works well for most applications. Only switch to WebSocket transport if you are hitting sub-request limits or making many rapid sandbox operations.
:::

## Migration guide

Switching between transports requires no code changes - only configuration.

### Switch from HTTP to WebSocket

1. Update your `wrangler.jsonc` to add `SANDBOX_TRANSPORT` environment variable:

<WranglerConfig>
```jsonc
{
	"containers": [
		{
			"class_name": "Sandbox",
			"image": "./Dockerfile",
			"environment": {
				"SANDBOX_TRANSPORT": "websocket"
			}
		},
	],
}
```
</WranglerConfig>

2. Deploy your Worker:

```bash
wrangler deploy
```

No application code changes needed.

### Switch from WebSocket to HTTP

Remove the `SANDBOX_TRANSPORT` environment variable from your container configuration:

<WranglerConfig>
```jsonc
{
	"containers": [
		{
			"class_name": "Sandbox",
			"image": "./Dockerfile",
			// Remove environment.SANDBOX_TRANSPORT
		},
	],
}
```
</WranglerConfig>
