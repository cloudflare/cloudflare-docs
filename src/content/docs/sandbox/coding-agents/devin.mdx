[Devin](https://docs.devin.ai/cloud/outposts/overview) runs its agent loop in its own service. A Devin Outpost moves the machine that each session works on, where Devin runs commands, edits files, and opens a browser, to infrastructure that you choose. The Devin Outpost template runs each session in its own Linux sandbox: a [Container](/containers/) that one Durable Object starts for that session.

## Prerequisites

You need:

- A Devin Enterprise organization with permission to manage outposts and service users
- A Cloudflare account on the Workers Paid plan with access to Containers and R2
- For manual deployment, [Node.js 24](https://nodejs.org/) and a running [Docker](https://www.docker.com/) daemon

### Get your Devin credentials

<Steps>
1. Open your Devin organization outpost settings. Replace both instances of `my-org` in this URL with your organization slug:

   ```txt
   https://my-org.devinenterprise.com/org/my-org/settings/enterprise-environment?tab=outposts
   ```

2. Create or select an outpost, and copy its outpost ID for `DEVIN_OUTPOST_ID`.

3. For `DEVIN_API_TOKEN`, use a Devin service-user token with the **Run outpost workers** permission.
</Steps>

For more information about outposts, refer to the [Devin Outposts overview](https://docs.devin.ai/cloud/outposts/overview).

## Deploy with one click

The **Deploy to Cloudflare** button creates the Worker, the cron trigger, the Durable Object namespace, the container application, and the R2 bucket for session checkpoints.

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/cloudflare/sandbox-sdk/tree/main/devin)

Enter these values when the deployment flow prompts for them:

| Variable           | Value                                                                  |
| ------------------ | ---------------------------------------------------------------------- |
| `DEVIN_OUTPOST_ID` | Your Devin Outpost ID                                                  |
| `DEVIN_API_TOKEN`  | A Devin service-user token with the **Run outpost workers** permission |

After the deployment finishes, select your outpost from the **Virtual environment** menu when you create a Devin session.

## Customize and deploy manually

Deploy manually when you need to add dependencies, tools, or environment variables to the container image.

<Steps>
1. Create a project from the Devin Outpost template:

   <PackageManagers
   	type="create"
   	pkg="cloudflare@latest"
   	args={
   		"cloudflare-devin-outpost --template=cloudflare/sandbox-sdk/devin"
   	}
   />

2. Go to the project directory and log in to your Cloudflare account:

   ```sh
   cd cloudflare-devin-outpost
   npx wrangler login
   ```

3. Create the R2 bucket for session checkpoints:

   ```sh
   npx wrangler r2 bucket create devin-outpost-state
   ```

   To use another bucket name, update `bucket_name` in `wrangler.jsonc`.

4. In `wrangler.jsonc`, replace the empty `DEVIN_OUTPOST_ID` value with your outpost ID.

   The default `DEVIN_API_URL` is `https://api.devin.ai/opbeta`. Change this value only if your Devin environment uses another API URL.

5. Store your Devin API token as a Worker secret:

   ```sh
   npx wrangler secret put DEVIN_API_TOKEN
   ```

   Enter your service-user token when Wrangler prompts you. Do not add the token to `wrangler.jsonc`.

6. Deploy the Worker and container:

   ```sh
   npm run deploy
   ```

   Wrangler builds the container image and deploys the Worker, the container application, and the cron trigger.

7. Check the deployment with the Worker URL from the Wrangler output:

   ```sh
   curl https://<YOUR_WORKER>.workers.dev/
   ```

   The Worker returns:

   ```json
   {
   	"service": "devin-outpost",
   	"status": "ok"
   }
   ```
</Steps>

## Run a Devin session

In Devin, create a session and select your outpost from the **Virtual environment** menu. The Worker checks for new sessions every 10 seconds by default, so the sandbox for the session starts shortly after you create it.

## How the template runs sessions

A cron trigger runs the Worker once a minute. During each run, the Worker asks Devin for the sessions of your outpost every 10 seconds, or every `DEVIN_RECONCILE_INTERVAL_MS` milliseconds if you set that variable. The Worker sends each session's status to the Durable Object for that session:

| Devin status         | What the template does                                        |
| -------------------- | ------------------------------------------------------------- |
| `pending`, `running` | Starts the sandbox for the session if it is not running.      |
| `suspended`          | Lets Devin exit, then saves the session's files as a checkpoint. |
| `terminated`         | Destroys the sandbox and deletes its checkpoint.              |

The Durable Object only starts and stops its container. Inside the sandbox, the Devin CLI (`devin worker start`) claims the session and runs it.

When a suspended session exits, the container archives `/root`, `/workspace`, and `/opt/devin-persistent`, and sends the archive to R2 through the Worker. The container never receives R2 credentials. When the session continues, the template restores the archive before Devin starts again.

:::note
The template saves a checkpoint only when Devin suspends a session. If a container stops unexpectedly, recent changes are lost. Each compressed checkpoint must fit within the R2 5 GiB single-upload limit.
:::

## Security

Each session runs in its own container, so sessions do not share files or processes. Inside that container, Devin runs as root, can reach the Internet, and holds the Devin API token, because the Devin CLI needs the token. Code that runs in a session can read that token. Deploy a separate outpost for each group of users that must not share access.

For more information, refer to [Sandbox security](/sandbox/security/).
