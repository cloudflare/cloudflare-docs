---
title: Spec-compliant dispatchEvent() exception handling
description: A new compatibility flag aligns event dispatch exception handling with the DOM specification.
products:
  - workers
date: 2026-08-19
---

A new compatibility flag, `spec_compliant_dispatch_exceptions`, changes what happens when an event listener throws an exception. The Workers runtime reports the exception but continues running the remaining listeners, as required by the [DOM specification](https://dom.spec.whatwg.org/#dispatching-events). This flag becomes the default for all Workers with a compatibility date of `2026-09-01` or later.

Previously, when an event listener threw an exception during `dispatchEvent()`, the runtime propagated it immediately and skipped the remaining listeners. With this flag, the runtime reports listener exceptions through the global `error` event and the console. It continues running the remaining listeners without throwing from `dispatchEvent()` or `AbortController.abort()`.

This change affects `dispatchEvent()` calls, `AbortSignal` abort events, and runtime-fired events on `WebSocket`, `EventSource`, and `MessagePort`. For runtime-fired events, existing failure reactions still apply after the remaining listeners run. A throwing listener then causes a `WebSocket` to error, an `EventSource` to close, or a `MessagePort` to emit `messageerror`.

Top-level Worker event delivery is not affected. This includes module-style `fetch()` and `scheduled()` handlers, and legacy Service Worker syntax entry points such as `addEventListener("fetch", ...)`.

To opt in before the default date, add `spec_compliant_dispatch_exceptions` to your `compatibility_flags`. To preserve the old behavior after the default date, use `no_spec_compliant_dispatch_exceptions`.

For more details, refer to the [compatibility flags documentation](/workers/configuration/compatibility-flags/).
