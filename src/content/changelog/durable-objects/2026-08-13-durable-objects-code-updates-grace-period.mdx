Durable Objects can stay active across requests, allowing you to run long-running [agents](/agents/), maintain [long-lived WebSocket connections](/durable-objects/best-practices/websockets/) and coordinate state across many clients. This is possible because each Durable Object is globally unique, and this means it must run only one version of your code at a time. Previously, when you deployed a change to your Durable Objects code, that change would be applied immediately, which could interrupt in-flight work and terminate open connections.

You can now set a deployment grace period, which tells Cloudflare to wait to update code until the Durable Object "hibernates" and becomes inactive. This lets you allow in-flight work to finish before code updates and allows open WebSocket connections that use the [Hibernation API](/durable-objects/examples/websocket-hibernation-server/) to remain connected.

Add `deployment_grace_period` to `durable_objects` in your Wrangler configuration, or pass it as a flag for a single deployment:

<PackageManagers type="exec" pkg="wrangler" args="versions deploy <VERSION_ID>@100% --durable-objects-deployment-grace-period 30" />

The value is in seconds. The default is 30, and the maximum is 300 (five minutes). Set it to `0` to reset active objects immediately — useful when you need to ship a fix during an incident or force a busy object off old code.

A grace period is best-effort, not a guarantee. Cloudflare can still reset an object early because of a crash, a resource limit, or an unrelated runtime update.

For more information, including how this interacts with gradual deployments, refer to [Delay code updates until hibernation](/durable-objects/reference/durable-objects-code-updates/).
